# 専門用語の対応の表

スキルの文は平易な語で書き、専門用語は目印として添える。この表は、スキルを書く側が呼び方をそろえるための道具と、検査（`scripts/check_terms.py`）の入力。スキルと一緒には配られないので、導入先で読まれるのは、各ファイルの中の括弧だけになる。

2026-11-19 から試行中。しばらく運用して、決まりと表を見直す。

## 決まり

- 平易な語を主にし、専門用語は「平易な語（専門用語）」の形で添える。逆（専門用語（平易な語））にはしない。
- 添えるのは、専門用語を使うファイルで、その専門用語が初めて出た所の1回だけ。平易な語がそれより前に出ていてもよい。専門用語が一度も出ないファイルには、添えなくてよい。
- 添えた後は、平易な語で書く。専門用語だけで書くのは避ける（検査はしない）。
- 「初めて出た所」は、ファイルごとに数える。SKILL.md の本文、description、`references/` と `templates/` の各 md ファイルは、それぞれ別に数える。見出し、表の中、山括弧の欄（`<…>` の形の書き込み欄）も数える。
- 数えないもの: コードブロック（フェンスで囲んだもの）、バッククォートで囲んだ部分、鉤括弧（「」）の中（起動の言い方や、引用した文、資料の題名）、リンク（`[…](…)` と素の URL）、HTML のコメント。資料の題名は、鉤括弧かリンクで書く。字下げだけのコードは数えてしまうので、コードはフェンスで書く。
- 括弧は全角にする。1つの括弧には、専門用語を1つだけ入れる。
- 固有の名前（製品、規格、団体。Storybook、WCAG、TLA+ など）は、名前のまま書いてよい。初めて出た所で、何のものかを一言添える（例: 部品のカタログ（Storybook））。この表には載せない。操作や概念の名前（rebase、worktree、squash など）は、道具の中のものでも表に載せる。
- 開発の群の規約の、道具の名前を本文の手順に入れない決まりと、入力と出力の表の1列目に型の名前だけを書く決まりは、こちらより優先する。添え書きは、説明の文の中に置く。
- description にも当てる。ただし、description を直すと起動の試験を流し直すことになるので、この決まりのためだけには直さない。ほかの理由で直すときに合わせる。
- 専門用語を新しく使ったら、この表に行を足す。同じ専門用語に、ファイルごとに別の平易な語を当てない。表記の揺れ（べき等、など）は、表の書き方にそろえる。
- 平易な語で足り、外で調べる場面も無い語には、専門用語を添えない。

## 試行の進め方

- 当てるのは、下の「対象」にあるスキルと、新しく作るスキル。ほかの群（Jev、LLM の選定など）は、専門家向けの調べものの群で、専門用語のほうが正確な所も多い。広げるかは、試行の後で決める。
- 今あるファイルは、まとめては直さない。新しく書くファイルと、直すファイルから当てる。
- 検査は、指摘を表示するだけで落とさない（`python3 -I scripts/check_terms.py`）。指摘の数の移り変わりを見て、落とす形にするか、決まりを直すかを決める。
- 検査が見るのは、表の専門用語の初出が「平易な語（専門用語）」の形かと、同じ添え書きが2回以上無いかだけ。表に無い形（冪等な、冪等にする、rebased、など）と、添えた後の書き方は見ない。参照の形のリンク（`[…][…]`）と、`references/` の md の先頭の front matter は数えてしまう。

## 対象

検査が見るスキルの名前。`*` は、何文字でも当たる。新しく作るスキルは、ここに足す。

- `dev-*`

## 例外

ファイルの欄の `*` は、何文字でも当たる。

| ファイル | 専門用語 | 理由 |
|---|---|---|
| skills/*/references/ddd.md | DDD | その専門用語で組む案件だけに読む資料で、専門用語そのものが主題 |

## 対応の表

| 平易な語 | 専門用語 | 一行の意味 |
|---|---|---|
| 画面をまたいで通しで確かめる試験 | E2E | 画面や外部とのやり取りをまたいで、利用者の操作の流れを始めから終わりまで確かめる試験の層 |
| テストを先に書く進め方 | TDD | 先に落ちる試験を書き、通る最小の実装を書き、整える、を繰り返す進め方 |
| 業務の言葉と決まりを中心に組む設計 | DDD | 業務の言葉と決まりを中心に、ソフトウェアの構造を組む設計の進め方 |
| 付け替え | rebase | 枝の変更を、指定したコミットの上へ載せ直す git の操作 |
| 切り離された状態 | detached HEAD | git で、今いる位置（HEAD）が枝を通さずに、コミットを直接指している状態 |
| git の別の作業場所 | worktree | 1つの git のリポジトリに、別のフォルダの作業ツリーを足して持つ仕組み。作業ツリーごとに別の枝を開くことが多い |
| やり直しても結果が変わらない性質 | 冪等性 | 同じ操作を2回以上しても、1回した時と結果が変わらない性質 |
| 二重の実行を防ぐ鍵 | 冪等キー | 同じ要求を2回以上受けても1回分だけ処理するために、要求に付けて送る識別子 |
| 押し出し | push | 手元の枝のコミットを、共有のリポジトリへ送る git の操作 |
| 1つのコミットにまとめる取り込み | squash | 枝の複数のコミットを、1つのコミットにまとめて取り込む git の操作 |
| 自動の検査 | CI | 変更を送るたびに、試験や検査を自動で流す仕組み |
