# LLM Skills

LLM の選定と裏取り、Jev の設計、時代考証、エージェント向けの契約の設計、開発作業の進め方、Cloudflare の基盤選定、会話の一区切りの振り返り、分野を問わない一次情報の裏取り、部品の 3D モデルの設計を支える、エージェントスキル集です。**Cursor, Claude Code, Antigravity, Codex** のマルチツールに対応しています。

スキルは目的ごとの「群」に分かれています。まず下の表で群を選び、入口のスキルから始めてください。

| 群 | 何に使うか | 入口のスキル |
| :--- | :--- | :--- |
| [1. LLM選定・裏取り](#1-llm選定裏取り) | 目的やシステム要件に応じて、外部ベンチマークやモデルカードを裏取りしたうえで、最適なLLM（主にローカルLLM）を提案する | `model-requirements-analyzer` |
| [2. Jev 設計](#2-jev-system-one-model-設計) | 要件定義書やドメインモデルから決定特化型モデル「Jev」の適用候補を抽出し、TCO試算、型付きのスキーマとフォールバック設計、評価セットの freeze、閾値較正（shadow 記録まで）、監視設計を支援する | `jev-candidate-detector` |
| [3. 歴史・文化背景の裏取り](#3-歴史文化背景の裏取り) | 人物や制度の判断を史料・研究と照合し、出来事の記録、当時や後世の評価、創作上の仮定を分ける | `historical-context-grounding` |
| [4. エージェント向けの契約（移転の案内）](#4-エージェント向けの契約移転の案内) | 既存のWebアプリにMCPサーバーを組み込み、HTTPでエージェントに公開する際の契約を、言語・SDKに依存せず設計する（開発作業の群の単位に移した） | `dev-agent-contract` |
| [5. 開発作業](#5-開発作業) | コードや文書の変更のレビューの一巡、新規開発、既存システムの改修・不具合の是正を、設計・試験・作業の分割まで含めて進める。単位を組み合わせるプロファイルで工程を選ぶ | `dev-profile-review-cycle`、`dev-profile-existing-system`、`dev-profile-new-feature`、`dev-profile-dependency-upkeep`、`dev-profile-exposure-sweep`、`dev-profile-inherited-system`、`dev-profile-version-control`、`dev-profile-interrupt-resume` |
| [6. Cloudflare の基盤選定](#6-cloudflare-の基盤選定) | 要件を Cloudflare 前提の制約に整理し、製品の仕様・制限・価格を毎回公式資料で裏取りして、構成案を出す | `cloudflare-requirements-framing`（一問一答は `cloudflare-product-survey`） |
| [7. 会話の一区切りの振り返り](#7-会話の一区切りの振り返り) | コーディングの会話の区切りで、摩擦を専門用語と情報処理技術者試験（基本情報から高度試験まで）の概念につなげ、利用者の個人用スキルを育てるかを判定する | `post-task-retrospective` |
| [8. 一次情報の裏取り](#8-一次情報の裏取り) | 競技のルール、規格、製品・素材のデータシートなど、設計を縛る外部の事実を原典の本文で確かめ、出典・版・引用・状態と縛る判断を項目ごとに記録する。分野を問わない汎用の手順で、専門の手順がある分野はそちらへ渡す | `primary-source-grounding` |
| [9. 部品の 3D モデルの設計](#9-部品の-3d-モデルの設計) | 3D プリントなどで作る部品を、CAD の道具のスクリプトを正本にしてパラメトリックに作り、検査し、試作の実測で直す。道具（FreeCAD など）は選べる | `cad-profile-part-design` |

## 1. LLM選定・裏取り

要件の整理 → 候補の探索と裏取り → ハードへの適合確認 → 比較と提案、の順に使います。

| スキル名 | 責務・役割 | 主な参照・裏取りリソース |
| :--- | :--- | :--- |
| **`model-requirements-analyzer`** | システム要件、タスク分類（コーディング/RAG/エージェント）、言語要件、ライセンス、レイテンシ、ハードウェア前提のヒアリングと定義 | システム要求仕様、コンプライアンス要件 |
| **`local-llm-researcher`** | 最新のモデル候補抽出、客観的ベンチマーク値（Leaderboard、実測値）の調査、既知の課題等の裏取り | Hugging Face (Model Cards), LMSYS Arena, BFCL, LiveCodeBench |
| **`hardware-compatibility-checker`** | パラメータ規模、コンテキスト長、KV Cache、量子化（GGUF, AWQ等）のメモリ計算と推論エンジン選定 | VRAM計算式、vLLM / Ollama / llama.cpp の仕様 |
| **`llm-selection-advisor`** | 上記を統合し、本命案・軽量案・拡張案の比較マトリクスと起動コマンドを含む提案レポートを作成 | 総合評価レポートテンプレート |

## 2. Jev (System One Model) 設計

候補の抽出 → ロジック設計 → 評価セット → 閾値較正 → 監視設計 → 監視基盤、の順に使います。共有の語彙と定形の結果レポートは `jev-shared` にあります。

| スキル名 | 責務・役割 | 主な参照・裏取りリソース |
| :--- | :--- | :--- |
| **`jev-candidate-detector`** | Kiro/cc-sddの`requirements.md`または同等の要件定義書を一次資料とし、`design.md` / `tasks.md`、ドメインモデル・ユースケース・画面/API/テーブル設計等で補完してJev適用候補を検出、期待TCOとレイテンシを試算 | 最新の公式価格、実測レイテンシ、業務・上位成果物への影響 |
| **`jev-logic-architect`** | 選定された候補を詳細設計（`design.md`）やタスク（`tasks.md`）に落とし込み、TypeScript型定義、Jevスキーマ、確信度（Confidence）別フォールバックコードを設計 | RLCD（校正済み確信度）アーキテクチャパターン |
| **`jev-eval-set`** | 承認済み設計に対し、正解定義・サンプリング/リーク防止・`datasetVersion`・freeze 記録を整え `datasetStatus: frozen` にする | 共有語彙 `jev-shared`、実験リポ上の評価成果物 |
| **`jev-calibration`** | frozen セット上で閾値を較正し、バッチ評価要約・推奨閾値・`validationStatus`・shadow 記録（本番非適用）を出す。区切り到達時は定形結果レポート必須 | ゲート基準はプロジェクト入力、定形レポートは `jev-shared/templates` |
| **`jev-observability`** | 判定イベント・時系列メトリクス・アラート意図・保持/プライバシー境界の観測契約を設計する（実装はしない） | 目標値はプロジェクト入力、実装は SRE/MLOps |
| **`jev-monitoring-platform`** | 観測契約を監視インフラ／監視アプリ要件に落とす。既定 Cloudflare、AWS/GCP/Azure 写像 | 制限値は出典付き裏取り／入力。実装は SRE/MLOps |

## 3. 歴史・文化背景の裏取り

| スキル名 | 責務・役割 | 主な参照・裏取りリソース |
| :--- | :--- | :--- |
| **`historical-context-grounding`** | 歴史上の人物・制度・道義に関わる判断の根拠を確認し、競合する規範、適用範囲、未確認点を整理する | 原史料の本文・注・評、信頼できる翻訳・校注、学術研究 |

時代考証はJevと独立して利用できる。史料の読み分けは `historical-context-grounding`、資料の取得・採用判定は利用者や案件が指定する手順（指定がなければ同スキルの[基本手順](skills/historical-context-grounding/references/source-workflows.md)）、Jevの入力・評価は[歴史的文脈を含む判断の設計と評価](skills/jev-shared/references/historical-judgment-evaluation.md)が担当する。

Jevの人物判断では `jev-logic-architect`、`jev-eval-set`、`jev-calibration` から必要な手順だけを参照する。個別案件の調査・実測はこのリポジトリに置かない。責務と保守範囲は[時代考証スキルの責務](docs/skill-responsibilities.md)を参照。

## 4. エージェント向けの契約（移転の案内）

この群にあった `app-mcp-server-integration` は、[5. 開発作業](#5-開発作業)の単位 **`dev-agent-contract`**（エージェント向けの契約を設計する）に移した。不変条件（INV-1〜15）の識別子と中身は変えておらず、道具の経路でも1件ごとに触ってよいかを確かめる INV-16 を末尾に足した。要件・実装・試験の段は、開発作業の群の単位（要件、テストケースの導出、テストを先に書く実装）が受け持ち、`dev-agent-contract` は契約の設計と、確かめる観点の対応表を渡す。

旧スキルを入れていた場合は、旧スキルのリンクやコピーを消し、`dev-agent-contract` と共有参照の `dev-shared`（型の一覧）を一緒に入れる。`dev-agent-contract` は完了条件の一覧を入力に取るので、要件から通すなら `dev-profile-new-feature` か `dev-profile-existing-system` から入る。

MCPクライアントの実装、既存のMCPサーバーを使うだけの作業、stdio のサーバーの認可は対象外。仕様の版ごとの仕組みの違いは[仕様の追従](skills/dev-agent-contract/references/mcp/spec-tracking.md)で確かめる。

## 5. 開発作業

`dev-` で始まるスキルは、一つの仕事を単独でこなす「単位」と、目的に合わせて単位を組み合わせる「プロファイル」に分かれる。単位どうしは互いを名指しせず、受け取る成果物と渡す成果物の型でつながる。単位だけを入れても使える（型の一覧を置いた共有参照の `dev-shared` は一緒に入れる）。

扱わないもの: 監視と警告の設計、障害の対応、退避と復旧（災害時の戻し）、ライセンスの確かめ。本番の作業は人が流し、エージェントは手順を作るまでを受け持つ。

| :--- | :--- | :--- |

| 単位 | **`dev-review-brief`** | 別の担当に渡すレビュー依頼文を書く。作った側の解釈を渡さず、原典への参照、事実、発見を求める観点だけを渡す |

- **使うモデルの強さ**: 一言の依頼からプロファイルを選ぶことと、自分で作った変更を自分でレビューしないことは、モデルの強さで差が出る。2026-11-13 の隔離した起動の試験（そのときの53件を各3回）では、Claude Sonnet 相当が 98%、Claude Haiku 相当が 91% で、Haiku 相当には、設計の観点を選ぶ一言の依頼でスキルを使わない回や、自分の変更を自分でレビューする回があった。その後に群が増えた今の定義（116件）は、Sonnet 相当で各1回流しただけで、Haiku 相当では流していない。Grok 4.7 は一部の依頼（7件）と作った本人の流れ、Gemini 3.8 Flash は作った本人の流れ（3回）だけを試し、その範囲では安定した。レビューの独立性が大事な場面では、Sonnet 相当以上のモデルで使うか、使うスキルを名前で指定する。

## 6. Cloudflare の基盤選定

要件を Cloudflare 前提の制約に整理し、製品の仕様を公式資料で裏取りして、構成案を出します。入口は `cloudflare-requirements-framing` です。仕様・制限・価格の一問一答だけなら `cloudflare-product-survey` を直接使います。Jev の監視基盤（`jev-monitoring-platform`）で Cloudflare の制限値を裏取りするときも、`cloudflare-product-survey` を使えます。

| スキル名 | 責務・役割 | 主な参照・裏取りリソース |
| :--- | :--- | :--- |
| **`cloudflare-requirements-framing`** | 機能要件・非機能要件やワークロードの説明を、製品を選ぶ前の制約シート（レイテンシ、リージョン、認証、コスト、状態性など）にまとめる。製品の選定はしない | 利用者の要件の文書 |
| **`cloudflare-product-survey`** | Cloudflare の製品・API の仕様、制限、価格、提供状態を、毎回公式資料で裏取りし、出典 URL と取得日を付けて答える | developers.cloudflare.com、GitHub の cloudflare/cloudflare-docs |
| **`cloudflare-architecture-advisor`** | 制約シートと裏取りの結果から、本命・軽量・拡張の三案を比べ、製品の役割と経路を示す構成案を出す | 制約シート、裏取りの結果、[適合の点検表](skills/cloudflare-architecture-advisor/references/fit-checklist.md) |

- 仕様・上限・料金の写しは持ちません。仕様は変わり続けるため、毎回公式資料で裏取りします。
- 確かめられなかった事項は、利用する案件の文書に残します。スキルのディレクトリには書き込みません。
- 一言の依頼でどのスキルが起動するかの試験は[起動の試験](docs/cloudflare-trigger-cases.md)にまとめています。

## 9. 部品の 3D モデルの設計

3D プリントなどで作る部品のモデルを、根拠を確かめてから作り、人が見て採り、試作の実測で直します。入口は `cad-profile-part-design` です。CAD の道具には依存せず、受付で道具を選び、組み立ての工程でその道具の資料と雛形を使います。

| 種類 | スキル名 | 責務・役割 |
| :--- | :--- | :--- |
| プロファイル | **`cad-profile-part-design`** | 受付と道具の選択、一次情報の裏取り（`primary-source-grounding`）、方針の確認、組み立てと検査、見た目の確認、試作と実測の反映の工程に振り分ける |
| 単位 | **`cad-parametric-modeling`** | 道具のスクリプトを正本にして、パラメータを一か所に集めて根拠と結び、作る前と作った後に検査し（閉じた一つのソリッド、非多様体と自己交差が無いこと）、STEP・STL とプレビューと確認の手順を残す |

- 道具ごとの書き方、落とし穴、雛形は[道具の資料の一覧](skills/cad-parametric-modeling/references/tools/README.md)にあります。今あるのは FreeCAD（1.0.0 で確かめた）だけです。ほかの道具は、一覧の確かめる観点に沿って公式の資料と手元の版で確かめてから使い、確かめた資料を足します。
- 規格・ルール・データシートの値は `primary-source-grounding` で確かめ、このスキルでは定め直しません。
- 案件に固有の制約（造形できる大きさ、プリンタ、素材の銘柄）と、作った設計・記録は、利用する案件の場所に置き、このリポジトリには置きません。
