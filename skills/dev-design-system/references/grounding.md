# 根拠と変えたところ

デザインシステムを定める手順が、どの先行の手法に基づき、どこを変え、どこが独自の判断かを書く。手順そのものは SKILL.md が正本で、ここは読む人が元の考え方をたどるための別紙。

- 確かめた水準: 「原典を読んだ」「書誌と二次資料で確かめた」「未確認」

## 先行の手法

| 手順の箇所 | 手法 | 出典 | 確かめた水準 | 同じところ | 変えた・足したところ |
|---|---|---|---|---|---|
| 2. トークンを決める | デザイントークンの形式 | Design Tokens Community Group「Design Tokens Format Module」の草案（Draft Community Group Report、頁の表示は 2026-09-08。https://www.designtokens.org/tr/drafts/format/ 。安定版 2025.10 があると頁に書かれている） | 原典を読んだ（2026-11-14 に草案の頁で、群、別名による参照、W3C の標準でも標準の道筋でもないという記述を確認。2025.10 の公開版の頁は開いていない） | トークンを群に分け、別のトークンを値として参照できる（別名）形で持つ | 形式そのものは案件で選ぶことにし、段（元の値 → 役目の名前 → 部品ごと）を要る分だけ作ることと、参照を一方向にすることを足した。段の分け方は独自の判断 |
| 3. 部品を決める | 素の HTML の要素を先に使う | W3C「Using ARIA」（https://www.w3.org/TR/using-aria/ 、2026-02-24 の打ち切りの草案） | 原典を読んだ（2026-11-14 に第一の決まりの節を確認。文書は打ち切りで、保守されず ARIA の手引きを指していることも確認） | 必要な意味を持つ素の HTML の要素があれば、ARIA で別の要素を作り直さずにそれを使う | 部品を作る前に、素の要素で足りないかを確かめる手順にした。文書が打ち切りなので、型の参照先は次の行の ARIA の手引きにした |
| 3. 部品を決める（フォーカスの管理、キーボードの操作） | ARIA の手引きの型 | W3C WAI「ARIA Authoring Practices Guide」の「Dialog (Modal)」（https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/ ） | 原典を読んだ（2026-11-14 に、開いた時にダイアログの中へフォーカスが移り、閉じた時に開いた要素へ戻ることを確認） | 型が定まった部品は、その型のキーボードの操作とフォーカスの決まりに従う | 部品の仕様の欄に、型を指して違う所だけを書く形にした |
| 5. アクセシビリティの基準を部品へ割り当てる | Web のアクセシビリティの基準 | W3C「Web Content Accessibility Guidelines (WCAG) 2.2」W3C 勧告（開いた頁の版の日付は 2024-12-12）（https://www.w3.org/TR/WCAG22/ ） | 原典を読んだ（2026-11-14 に 1.4.3、1.4.10、1.4.11、2.4.7、2.5.5、2.5.8、3.3.1、4.1.2、4.1.3 の本文を確認。2.4.11 と 2.4.13 は段だけを確認） | 文字のコントラスト（4.5:1、大きい文字は 3:1）、部品のコントラスト（3:1）、フォーカスの見え方、操作の的の大きさ（AA は 24×24 CSS px、44×44 は AAA）を基準にする | 目標の水準は画面の共通仕様が持ち、ここでは部品ごとに基準の番号を割り当てる形にした |
| 5. アクセシビリティの基準を部品へ割り当てる（自動の点検だけで足りるとしない） | 評価は道具だけでは決まらない | W3C WAI「Evaluating Web Accessibility Overview」（https://www.w3.org/WAI/test-evaluate/ 、2026-08-12 更新） | 原典を読んだ（2026-11-14 に、道具だけでは基準を満たすかを決められず、人の評価が要るという記述を確認） | 自動の点検に加えて、知識のある人の評価を求める | 人の手順を、キーボードでの一巡と読み上げでの確かめとして部品ごとに書く形にした |

## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| デザインシステムを新しい型にせず、設計の判断（観点「デザインシステム」）として出し、部品とトークンは名前を鍵にした一覧にする | 承認、規模の判定し直し、テストケースへの流れが設計の判断の上に既にあり、別の型にすると同じ流れを二重に持つため | 承認や規模の判定で、デザインシステムだけが別扱いになって抜けた件数を数え、型にするかを見直す |
| やり方を、既にあるものに従う、最小限を定める、広げる・変える、の3つに分け、最小限の既定を「既製の部品のライブラリを選び、上書きするトークンと足りない部品だけを定める」にする | 小さな案件でも一から全部を定めると、使われない部品とトークンが増えて保守できなくなるため | 定めた部品とトークンのうち、画面から一度も指されなかったものの割合を数え、既定を見直す |
| 版と廃止の予告と移行の手順は、広げる・変えるときだけ求める | 最初に定めるときに版の手続きを求めると、手続きだけが増えるため | 変えるときに、影響する画面の見落としや移行の抜けが起きた件数を数え、求める時点を見直す |
| トークンの名前は役目で付け、値の固定表を画面ごとに持たない | 値で名付けると、テーマや色の変更のたびに全部の参照を直すことになるため | テーマや色の変更で直した参照の数を数え、名前の付け方を見直す |
| 名前の照合（参照切れ、廃止した名前の使用、循環）を手で行い、結果を判断に書く。スクリプトにはしない | 部品とトークンの書き方が案件ごとに違い、機械の検査を群の側で決められないため | 照合で見つからずに後から見つかった参照切れの件数を数え、機械の検査を足すかを見直す |
| 使い分けの例（ボタンの3つの軸、状態の色）は規範にせず、案件が採ったものだけを決まりにする | 案件ごとにブランドと既にある決まりが違い、例を規範にすると既存の決まりとぶつかるため | 例をそのまま決まりにして、既存の決まりと食い違った件数を数え、例の置き方を見直す |
| 見た目の比較を外部のサービスで行うのは、人の承認が要る選択肢にする | 画面の写しが外へ送られるため | 承認の無いまま外へ送った件数を数え、決まりの置き場所を見直す |
