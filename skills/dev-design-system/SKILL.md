# デザインシステムを定める

画面がどう見えるかの共通の部品と決まりを、設計の判断（観点「デザインシステム」）として出す。何を、どの順で見せるか（画面の設計）とは分ける。部品とトークンは判断の中の一覧で、名前を行の鍵にする。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 原典の参照 | 任意 | 既にあるデザインシステム、選んだ部品のライブラリ、ブランドの決まり、部品のカタログ、画面の共通仕様 |
| 完了条件の一覧 | 任意 | 要件と受入条件の識別子（根拠の欄に書く） |
| 画面の設計 | 任意 | 使われる部品と状態の出どころ、アクセシビリティの目標の水準 |
| 設計の判断 | 任意 | 先に決めた判断（エラーの見せ方、認可による出し分け） |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

どれも無いときは、やり方 (b) の最小限として、何の画面のためかを依頼者に聞いてから始める。アクセシビリティの目標の水準は画面の共通仕様が持つ。決まっていなければ、既定（WCAG 2.2 の AA）を案として、画面の共通仕様の持ち主（画面の設計か、案件が続けて使う文書）へ返し、共通仕様に書かれるまでは、その案を前提として判断の未確認の欄に書く（判断の中で目標の水準を決めない）。

## 出力

| 型 | 中身の補足 |
|---|---|
| 設計の判断 | 観点は「デザインシステム」。やり方、トークンの一覧、部品の一覧、使い分けの決まり、部品へのアクセシビリティの基準の割り当て、名前の照合の結果、（やり方 (c) なら）版と廃止の予告と影響する画面と移行の手順 |

## 使わない場面

- 画面の一覧、流れ、見せる情報を決める。ワイヤーを作る。
- ロゴ、ブランドの世界観、宣伝の文を決める。
- 部品を実装する。story や試験のコードを書く。
- 実装した画面がアクセシビリティの基準を満たすかを点検する。

## 手順

### 1. やり方を選ぶ

| やり方 | 選ぶとき | 出すもの |
|---|---|---|
| (a) 既にあるものに従う | 案件にデザインシステムがあり、それで足りる | 画面で使う部品との対応と、足りない所の一覧 |
| (b) 最小限を定める | 案件に無い | 既定は、既製の部品のライブラリを選び、上書きするトークンと足りない部品だけを定める |
| (c) 広げる・変える | あるものに足す、変える、やめる | 変える所に加え、版、廃止の予告、影響する画面（検索の結果）、移行の手順 |

(a) で足りない所が見つかったら、(c) に切り替えるかを人に確かめる。

### 2. トークンを決める

- 名前は役目で付ける（「青」ではなく「主な操作の背景」）。値の固定表を画面ごとに持たない。
- 段（元の値 → 役目の名前 → 部品ごと）は、要る分だけ作る。役目の名前から元の値への参照は、一方向にする。
- テーマ（明るい、暗い、高いコントラスト）が要るかを決め、要るならテーマごとに役目の名前の値を持つ。
- 形式（ファイルの形、書き出し先）は案件で選ぶ。共同体の形式を使うときも、W3C の標準ではないことを踏まえる。

### 3. 部品を決める

- 素の HTML の要素で足りるなら、それを使い、部品を作らない。
- 部品ごとの欄は [部品の仕様の欄](references/component-spec.md) を見る（目的、使う場面と使わない場面、構成、種類、状態、入力・出力・イベント、選択と展開、フォーカスの管理、キーボードの操作、役割と名前と状態）。
- 新しい部品や種類を足す前に、既にある部品で足りないかを確かめる。意味で区別している見た目（状態の色など）を、見た目をそろえるために変えない。

### 4. 使い分けの決まりを書く

- 知らせ方（その場、帯、一時の知らせ）、開き方（ダイアログ、横のパネル、ページ）、押せなくするか隠すか、ボタンの軸（優先の語、塗りの段、大きさ）の使い分けを、案件の決まりとして書く。ここに書くのは選ぶ基準で、画面ごとにどれを選んだかは画面の設計が書く。
- 軸は混ぜない（優先の語の数と塗りの段の数を合わせる、など）。例は [使い分けの例](references/usage-patterns.md) にあるが、規範ではない。

### 5. アクセシビリティの基準を部品へ割り当てる

- 目標の水準は画面の共通仕様が持つ。ここでは、その水準の基準を部品ごとに割り当てる（文字と部品のコントラスト、フォーカスの見え方と隠れないこと、操作の的の大きさ、拡大と折り返し、入力の誤りと項目の結びつき、状態の知らせ）。基準の番号を書く。
- 自動の点検だけで満たしたとしない。キーボードでの一巡と、読み上げでの確かめは、人の手順として書く。

### 6. 名前を照合する

- 画面の設計とワイヤーが指す部品とトークンの名前が、一覧にあるか（参照切れ）、廃止した名前を使っていないか、トークンの参照が循環していないかを、手で照合し、結果を判断に書く。

### 7. カタログと照らす

- 部品のカタログは仕様の実演で、正本は仕様。照らすときは、仕様の状態ごとにカタログの表示があるか、仕様に無い状態がカタログにあるかを見る。
- 道具の資料（[Storybook](references/tools/storybook.md)）があれば読む。無ければ公式の資料で確かめる。カタログを動かすときは、隔離した環境で、本番のデータや資格情報を使わない。開いている間のブラウザの通信を記録し（許した宛先以外を止めて、止めた要求を残す）、許していない外部への送信が無いことを確かめる。見た目の比較を外部のサービスで行うのは、人の承認が要る選択肢にする（画面の写しが外へ送られるため）。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 設計の判断に、判断ごとの共通の欄（識別子、観点、承認の状態、確かめる観点、未確認）がそろい、トークンと部品の行に名前の鍵がある（[型の一覧](../dev-shared/references/artifact-types.md)の「設計の判断の書き方」）。
- 選んだやり方と、その理由が書かれている。
- 部品ごとに、状態、キーボードの操作、割り当てたアクセシビリティの基準がある。
- 名前の照合の結果（参照切れ、廃止、循環）が書かれている。
- やり方 (c) なら、版、廃止の予告、影響する画面、移行の手順がある。
