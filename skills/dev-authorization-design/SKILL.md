# 認可を設計する

誰が、どの対象に、どの操作をしてよいかを、判断の表にして決める。画面でボタンを隠すことは使い勝手の工夫で、守りではない。守りは、要求を受けたサーバーの側で、1件ごとに行う。方式の型（役割で決める、属性で決める、関係で決める）と分離の方式は [方式の選び方](references/models.md) に分ける。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 必須 | 操作と許可を、受入条件の識別子に結ぶ。否定を含む受入条件（「〜できない」）は、拒否の行の出どころになる |
| 原典の参照 | 任意 | 案件の既定の認可の方式、組織の構造、役割の定義、監査の要件 |
| ドメインモデル | 任意 | 主体（利用者の種類）、管理するもの、所有と所属の関係、状態（状態によって操作の可否が変わるとき） |
| 業務規則の一覧 | 任意 | 権限に関わる規則。規則の識別子は、許可の表の根拠と条件の列に書く。確かさが仮説・未確定の規則は根拠にせず、そのことを未確認の欄に書く |
| 設計の判断 | 任意 | 責務の配置（横断の関心事の一覧で、認可を守る場所と迂回の有無が決まっていれば従う） |
| 現状の振る舞いの記録 | 条件付き（既存の権限や分離を変えるとき必須） | 今の役割、判定の箇所、判定を通らない経路 |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

完了条件の一覧が無いときは、設計せずに止める。誰に何を許すかが原典に無いときは、推測で許可を決めず、人に確かめる（許可の範囲は業務の決定で、担当の裁量で決めない）。既存の権限や分離を変えるのに今の判定の箇所が分からないときは、判定を通らない経路を「未確認」として設計の判断に書き、人に確かめる。

## 出力

| 型 | 中身の補足 |
|---|---|
| 設計の判断 | 観点は「認可」。主体と役割の一覧、許可の表（行の鍵は操作と対象の組）、1件ごとの確かめ方、分離の強制点、権限の変化の扱い、判定の置き場所、拒否の見せ方、記録の要否、確かめる観点 |

## 使わない場面

- 本人であることの確かめ方（ログイン、多要素、トークンの発行と失効、セッションの寿命）を決める。
- 秘密や鍵の置き場所、通信の暗号化、応答のヘッダや Cookie の属性を決める。
- 契約の形（どの状態コードや終了コードで拒否を返すか）を決める。拒否をどの種類のエラーとして扱うかは、エラーの設計に渡す。
- 保存の構造、制約、移行（所属の列、行の権限の定義、保存先の分け方の作り）を決める。ここでは分離の方式を選び、保存の構造に及ぶ要求を波及と順序の欄に書いて渡す。
- コードの上で判定をどの層に置くか（横断の関心事の置き場所）を決める。
- 実装する。

## 手順

### 1. 主体と対象を挙げる

- 主体: 操作する者の種類（利用者、組織の管理者、運用者、ほかのシステム、AI エージェントなど）。人でない主体も、誰の権限で動くかを書く。
- 対象: 管理するものと、その所有者・所属（誰のものか、どの組織のものか）。
- 操作: 読む、一覧する、作る、変える、消す、外に出す（書き出し、送信）、権限を変える。一覧と1件の読みは分けて書く（一覧で漏れることが多い）。

### 2. 許可の表を作る

操作と対象の組を行の鍵にして、誰に許すかと条件を書く。

| 列 | 書くこと |
|---|---|
| 操作と対象 | 行の鍵（例: `請求書.確定`） |
| 許す主体 | 役割、または関係（所有者、同じ組織の者、担当に割り当てられた者） |
| 条件 | 主体によって変わる条件（自分が担当のものだけ、金額の上限が役割で違う、変えてよい欄・読める欄が役割で違う、など）。業務規則の識別子があれば書く。誰にでも当たる状態の条件（確定した請求書は変えられない、など）は書かず、業務規則の識別子で指す |
| 根拠 | 受入条件か業務規則の識別子、原典の参照 |

- 既定は拒否。表に無い組は許さない。
- 役割は、業務の言葉で名付ける。役割を増やす前に、関係（所有者か、同じ組織か）で表せないかを確かめる。
- 危険の大きい操作（権限を変える、代行する、まとめて書き出す、外へ送る、課金する、まとめて消す）は、別の行に分け、記録と再確認（もう一度の認証、二人目の承認）の要否を書く。

### 3. 1件ごとに確かめる

- 識別子で1件を読む・変える操作は、その1件を、この主体が触ってよいかを、要求を受けた側で確かめる。ログインしていることだけで許さない。
- 識別子は、推測しにくい値であっても、確かめの代わりにしない。
- 一覧と検索は、問い合わせの条件に所有や所属の絞り込みを入れる。取ってから捨てる形にしない（件数、並び、ページの境で漏れる）。
- 関連するものをたどる操作（請求書から明細へ、など）も、たどった先で確かめる。
- 入力に含まれる所属・所有者・参照先の識別子も確かめる。作るときにほかの組織の所属を指定する、更新で所属や所有者を動かす、ほかの組織のものを関連に付ける、を拒む（所属は入力から取らず、主体から決めるのを既定にする）。
- 件数、候補の表示（入力の補完）、一意の制約のエラーの文で、ほかの組織のものの存在が漏れないかを、7 の見せ方と合わせて確かめる。

### 4. 分離を強制する場所を決める

複数の利用者や組織のデータを同じ所に置くなら、分離をどこで強制するかを決める。

- 読み書きの全経路で、所属の条件を外せない形にする（共通の問い合わせの層で必ず付ける、データベースの行の権限で守る、組織ごとに保存先を分ける、など）。ここで決めるのは方式で、保存の構造（列、制約、移行）の作りは、波及と順序の欄に要求として書いて渡す。方式の比べ方は [方式の選び方](references/models.md)。
- 判定を通らない経路を挙げる。横断の関心事の一覧に守る場所と迂回の有無が書かれていれば、それを使い、足りない経路だけを足す。少なくとも次を見る: 一括の取り込みと書き出し、ジョブとバッチ、管理用の画面や道具、検索の索引、キャッシュ、ファイルの置き場、外部への送信、AI エージェントが呼ぶ道具。
- 組織をまたぐ操作（運用者の作業、集計）は、例外として別の行に書き、誰がどの記録を残して行うかを決める。

### 5. 権限の変化

- 役割の付け外し、組織の移動、退職、委任と代行で、いつから効くかを決める（すぐ効くか、次のログインからか）。長く続くセッションやトークン、キャッシュが古い権限を持ち続けないかを確かめる観点に書く。
- 対象の側の変化（所有者の移動、共有の取り消し、組織からの切り離し）も、いつから効くかを決める。
- 受け付けた後に動く処理（ジョブ、予約した処理）は、受付の時と実行の時のどちらの権限で判定するかを決める。既定は、実行の時にもう一度確かめる。
- 代行（ほかの人として操作する）は、元の主体を記録に残し、代行中にできないこと（権限を変える、など）を決める。
- 権限を変える操作そのものの許可（誰が誰に何を付けられるか。自分の権限を上げられないか）を、許可の表に入れる。

### 6. 判定を置く場所

- 「誰がこの操作をできるか」の判定は、業務の操作の手順を調整する所（入出力の境界ではなく）で、操作ごとに1か所に置く。1件ごとの確かめは、対象を読んだ所で行う。画面の表示の切り替えは、同じ判定の結果を使う写しとし、守りの役を持たせない。
- コードの上の置き場所は、責務の配置の横断の関心事の一覧に従う（ここでは決めない）。一覧が無ければ、判定の置き場所が決まっていないことを未確認の欄に書き、そこを通らない入口が無いことの確かめ方を確かめる観点に書く。
- 状態で可否が変わる操作（確定した請求書は変えられない、など）は、業務の判断と、許可の判定を分けて書く。前者は業務規則、後者は誰に許すか。

### 7. 拒否の見せ方と記録

- 他人のものの存在を知らせてよいかを決める。知らせないなら、「無い」と「触ってはいけない」を同じ見せ方にする。
- 拒否をどの種類のエラーとして扱うかを、エラーの設計に渡す形で書く。
- 拒否と、危険の大きい操作の許可を記録するかを決める。記録するなら、代行のときは元の主体も残す。記録の項目の詳しい設計は、ログと監査の決まり（無ければ原典の参照で人に確かめる）に任せる。
- AI エージェントを通す読み取りは、結果が外の提供元へ出ていく。外に出す操作として許可の表で別の行にするか、条件に経路を書くかを決める（道具の分類や見せ方はここでは決めない）。

### 8. 確かめる観点を渡す

行ごとに、許される主体で通るケースと、許されない主体で拒まれるケースを書く。さらに次を必ず入れる。

- 他人のもの・ほかの組織のものの識別子に差し替えた要求が拒まれる（読む、変える、消す、一覧、関連をたどる、入力の所属や参照先に入れる、のそれぞれ）。
- 判定を通らない経路（4 で挙げたもの）でも、分離が守られる。
- 権限を外した直後の要求が拒まれる（5 で決めた効く時点で）。

確かめる観点を動かして確かめるときは、隔離した環境で、本番のデータと本番の資格情報を使わない。代行や組織をまたぐ操作の確かめで外へ送る処理（通知など）が動くなら、送信を捕まえる設定にしてから動かす。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 設計の判断に、判断ごとの共通の欄（識別子、観点、承認の状態、確かめる観点、未確認）がそろい、許可の表の行に鍵がある（[型の一覧](../dev-shared/references/artifact-types.md)の「設計の判断の書き方」）。
- 完了条件の一覧のうち操作を含む受入条件のすべてに、許可の表の行がある。否定を含む受入条件には、拒否の行がある。
- 1件を読む・変える操作のすべてに、1件ごとの確かめ方がある。
- データを共有の所に置くなら、分離の強制点と、判定を通らない経路の一覧と、それぞれの扱いがある。
- 権限の変化（主体の側と対象の側）と、受け付けた後に動く処理について、効く時点が書かれている。
- 判定の置き場所が、横断の関心事の一覧を指すか、未確認として書かれている。
- 他人のものの存在を知らせるかが、決まっている。
- 確かめる観点に、8 の必ず入れる3つ（識別子の差し替え、判定を通らない経路、権限を外した直後）がある。
- 許可の範囲を人が決めていない行は、承認の状態が「人の決定待ち」になっている。
