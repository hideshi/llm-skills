## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 否定を含む受入条件（「〜できない」「〜は送られない」）をすべてエラーか無動作に対応づけ、原典に無い業務エラーを勝手に足さない（仮説規則は根拠にしない） | 受入条件の異常系が設計から抜け落ちることと、仕様に無いエラーを想像で作ってしまうのを防ぐため | 実装・受入で否定条件の異常系が抜けていた件数と、独断追加で不要になったエラー種別の件数を比べ、対応付け基準を見直す |
| 新しい種類を増やすのは「回復の動きが変わる・見せ方の構造が違う・監視で個別に数える」の3条件だけにし、操作ごとではなく規則ごとに種類を作る | 文言や画面が違うだけで種類が増殖し、呼び出し側の分岐や外側の変換表が肥大化するのを防ぐため | エラー一覧の種別数と文言差の重複・境界変換表の分岐肥大が起きた件数を記録し、3条件の区切り方を見直す |
| 規則に合わない入力を黙って補正して成功として扱わない | 不正な入力の隠蔽により後続のデータ不整合や意図しない業務挙動が起きるのを防ぐため | 厳格拒否で業務上の救済が止まった差し戻し件数と、曖昧処理によるデータ不整合件数を設計の判断・確認事項の記録・後続のレビュー結果（や案件の問題台帳）で比べ、禁止の例外条件を見直す |
| AI エージェントが呼ぶツール向けの面では、次の手が選べる短い案内と人の判断が要るエラーの区別を返し、会話記録に残るため秘密や内部情報を入れない | エージェントが誤った再試行や自己判断で権限越えを起こすことと、会話ログへの機密混入を防ぐため | ツール呼出での再試行ループ・無断変更の指摘件数とログへの機密露出件数を記録し、案内・非開示の基準を見直す |
| 例外を使う構成では、外側の境界に返し方へ変える変換表を1か所だけ持ち、表に無いエラーは技術の障害として扱う（具体的な状態コード等の確定は契約の設計に委ねる） | 未分類の例外がそのまま外部へ漏れて内部情報が露出する事故を防ぐため | 未分類例外の外部露出件数と境界変換表の差し戻し件数を記録し、変換の集約先とフォールバック規則を見直す |
| 一括処理で一部だけ失敗したとき、エラーの種類ごとに「1件の失敗で全体を止めるか、失敗した件を集めて続けるか」を決める | 処理やエラーの性質によって全件停止と失敗件一覧を残した継続の使い分けが必要なため | 一括処理での過剰停止や不整合継続による再実行・手戻り件数を記録し、停止／継続の分岐基準を見直す |
| エラーごとに「起きる」ケースと「境界の直前では起きない」ケースの双方を確かめる観点として渡す | 異常系の境界条件の取り違えや、正常系まで過剰に拒否する実装を防ぐため | 正常系の誤拒否や境界値の異常系漏れで後から見つかった不具合件数を記録し、対の観点の書式を見直す |
