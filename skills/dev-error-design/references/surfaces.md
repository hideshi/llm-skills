# 返す面ごとの例

同じエラーの一覧を、受け取る側ごとにどう見せるかの例。どの契約でどう返すか（状態コード、終了コード、応答の形）を最終的に決めるのは、その契約の設計。ここでは、エラーの設計の段階で考えておく観点を並べる。

## プログラムが呼ぶ API

- 回復の動きごとに、呼び出し側が分岐できる区分（HTTP なら状態コード）と、安定したコードを持たせる。
- 利用者向けの文言は、呼び出し側（画面など）がそのまま出せる形にするか、コードだけ返して呼び出し側が文言を持つかを決める。どちらかに統一する。

## CLI とバッチ

- 終了コードで回復の動き（流し直してよいか、入力を直すべきか）を分ける。
- 標準エラーに、運用者向けの文言（何が起きたか、次に何をするか）と相関の識別子を出す。
- 一部だけ失敗したバッチは、成功の件数、失敗の件数、失敗した件の一覧と理由を、終わりに出す（ファイルに残すなら、その場所を出力に書く）。

## ジョブとキュー

- 再試行してよいエラーと、再試行しても直らないエラーを分ける（再試行の回数と間隔は、非同期の実行の設計で決める）。
- 直らないエラーで止まったジョブは、人が見られる所に残す。黙って捨てない。

## 後から届く通知（メール、画面の通知など）

- 裏で動いた処理の失敗を知らせるときは、何の操作の結果か（いつ、何を依頼したか）が分かるようにする。
- 次にとる行動（流し直す、問い合わせる、何もしなくてよい）を書く。
- 同じ失敗を何度も知らせない。まとめ方は非同期の実行の設計で決める。

## 画面

- 入力の誤りは、項目の近くに、直し方が分かる文言で出す。
- 今の状態ではできない操作は、できる状態になるまで選べなくするか、理由を添えて出す。
- 技術の障害は、共通の文言と、問い合わせのときに伝える相関の識別子を出す。入力した内容を失わせない。

## AI エージェントが呼ぶツール

- エージェントが次の手を選べるように、何が足りないか、何を直せばよいかを、短い文で返す。
- 権限が無い、確認が要る、といった人の判断が要るエラーは、ほかのエラーと見分けられるようにする。
- 内部の情報や秘密の値を、エラーの文に入れない（エージェントの会話の記録に残る）。
