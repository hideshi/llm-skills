# 例外での組み立て

例外を使う言語で、本文の決まりを組み立てるときの例。

- 業務のエラーは、規則ごとの例外の型にし、名前を「概念＋破った規則」にする（例: `InvoiceAlreadyFinalized`）。業務の例外の共通の親を一つ持つと、外側の境界で「業務か技術か」を型で見分けられる。
- 例外の型に、安定したコード、記録向けの情報（規則の識別子、関係する識別子）を持たせる。利用者向けの文言は、例外の中に直接書かず、外側の境界でコードから引く（文言の規約を1か所で守るため）。
- 外側の境界（API の入口、CLI の main、ジョブの実行の枠）で、例外の型から返し方（状態コード、終了コード、応答の形）に変える表を1か所に持つ。表に無い例外は、技術の障害として扱う。
- 下の層の例外を包み直すときは、元の例外を原因として持たせる（言語の仕組みで連鎖させる）。
- 戻り値でエラーを返す言語（Go など）でも考え方は同じ。業務のエラーを値の型として定義し、呼び出し側が種類で見分けられるようにする（`errors.Is` や `errors.As` で判定できる形）。
