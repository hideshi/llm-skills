# ドメインモデルを作る

業務そのものの言葉と決まりを、システムの作りより先に固める。人は業務の言葉で答え、技術の言葉に置き換えるのはこちらの仕事。規則は業務規則の一覧に一つずつ識別子を付けて置き、モデルからは識別子で指す。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 原典の参照 | 必須 | 業務の説明、要望、範囲と範囲外、既存のモデル |
| 規模の判定 | 任意 | 範囲の広さと、通常の道か |
| 一次情報の記録 | 任意 | 外部の仕様や公的な規則から来る用語と規則 |
| 現状の振る舞いの記録 | 条件付き（既存のシステムを変えるとき必須） | 今の動き。実装で受け入れた動作の出どころ |
| 業務規則の一覧 | 任意 | 既にある規則（コードから抜き出したものを含む）。重複を除き、統合する |
| 確認事項の記録 | 任意 | 前の回の回答。続きの番号を振る |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

業務を説明できる人も資料も無いときは、たたき台だけを作り、全部の規則を仮説として返す。

## 出力

| 型 | 中身の補足 |
|---|---|
| ドメインモデル | 型の中身に従う。範囲がサービス群なら、[サービスをまたぐ概念の地図](references/cross-service-map.md)の形も使う |
| 業務規則の一覧 | 根拠と確かさを必ず付ける |
| 確認事項の記録 | 関係者に確かめる論点 |
| 問題台帳 | 指す先の無い参照、今の実装とモデルの食い違い |

## 使わない場面

- コードやデータから規則を機械的に抜き出す。既存のデータが規則を守っているかを調べる。
- 要件、受入条件、やらないことを書く。
- 設計（置き場所、データの構造、契約）や実装。

## 手順

### 1. 進め方を選ぶ

- 関係者と話せるなら、対話で進める（下の 2）。
- 関係者の時間が少ない、または業界の慣行が厚い領域なら、[たたき台を先に作る進め方](references/draft-first.md)で、慣行を調べてたたき台を作り、論点を先に全部並べてから確かめる。

### 2. 対話の段

輪郭 → 管理するもの → 状態と区分 → 規則 → ドラフトの確認、の順に聞く。技術の用語で答えを求めない。

- まとめるか分けるか: 寿命、変わる理由、使われる段階が一致するかで決める。同じ分類の語に属するだけで一つにまとめない。区分の値によって必須の項目が入れ替わる属性が複数あれば、二つのものが混ざっている兆し。
- 区分は、全部の場合を網羅しているかと、どの値にも入らない場合の扱いを確かめる。
- 識別子の付け方（連番か推測しにくい値か）のような、後で変えにくい事柄は、独断で決めず人に確かめる。
- 確かめるときは「はい」で終わらせず、具体例で言ってもらい、例外を必ず聞く。

### 3. 書く

- 用語は、日本語名（利用者に見える表示名が正）、英語名、1〜2行の定義をそろえる。同じ語が別の意味で使われていれば、修飾して分ける。
- 状態を持つ属性には、遷移ときっかけ・主体を書く。遷移が無ければ「遷移なし」と書く。
- 計算は、属性の表に式を書かず、計算の規則の節にだけ書く。端数処理を明示する。式はモデルに、結論（何をどう計算するかの決まり）と識別子は業務規則の一覧に置き、式から規則の識別子を指す。
- 操作は、状態遷移のきっかけとして名前だけ書く（ユースケースや画面の流れは、要件の側に書く）。
- ドメインイベントには、きっかけと、整合性の要件（すぐか、後でよいか）を書く。イベントで考えない案件では、イベントの欄に「使わない」と書く（書き忘れと分けるため）。
- 今有効な定義だけを書く。経緯は版の履歴か設計の判断に、なぜ要るかは要件の側に置く。

### 4. 業務規則を一覧にする

- 候補は、既存の規則の文、属性の表の制約、遷移ごとのガード、の3か所から全部挙げる。
- 識別子を振る目安は「テストやレビューで個別に識別したい制約か」。本文には結論だけを書く。
- 所有（違反を拒むガードを置く側）を一つに決める。所有が移っても識別子は変えない。
- 根拠の種類と出典を書く。出典の無い推測は「推測」と書く。規則が入ってくる起点ごとの確定の条件は [規則の起点](references/rule-sources.md) を見る。公的な規則と関係者の決定がぶつかったら、公的な規則が先で、その範囲で関係者の決定に従う。
- コードで確かめられない規則には、確かめる手段（レビュー、構造の検査）を書く。

### 5. 仮説と関門

- 確かめていない規則と論点は、確かさを「仮説」「未確定」にし、確認事項の記録に質問として並べる。
- お金・税・法令に関わるもの、後から変えると高いもの、顧客の外に見える約束は、担当の裁量で確定させない。関係者に確かめる。
- 回答を受けたら、どの結果でも（確定／変更／却下／一部／保留）、それに応じてモデルと一覧を直す（確定なら確かさを「確定」にし、根拠に確認事項の番号を書く）。直すのはこの単位の仕事で、回答を記録しただけでは確定にならない。保留は、関係者の了承と期限があるときだけ。
- 入力の業務規則の一覧に、コードから抜き出した候補や、一次情報から推定した規則（確かさが仮説）があり、今回の範囲で根拠にされるなら、ここで確かめる論点にする。
- 関門: 今回の範囲に、保留でない仮説・未確定が残っていたら、要件の根拠に使わせない（そのことを出力の先頭に書く）。

### 6. 文書の中の完全性

- 状態を持つ属性すべてに、遷移か「遷移なし」がある。指す先の無い参照が無い。
- イベントは、どれもきっかけに結ばれている。イベントを使わない案件では、イベントの欄に「使わない」とある。
- 既存のシステムを変えるときは、今の実装とモデルの食い違いを問題台帳に出す。実装で受け入れた動作は、根拠を「実装で受け入れた動作」として残す（誤った違反の診断を防ぐ）。

DDD で組む案件では、[DDD で組むとき](references/ddd.md)の言い換えと、集約・値オブジェクト・イベントの候補の見分け方を使う。

モデルの形の一例は [ドメインモデルの例](references/model-example.md)。形は任意で、欄がそろっていればよい。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 型の一覧の「モデルを終えるときの検査」を満たす。
- すべての業務規則に、種類、所有、根拠、確かさ、確かめる手段がある。
- 仮説・未確定が残るなら、確認事項の記録に質問として並び、関門の結果が出力の先頭にある。
