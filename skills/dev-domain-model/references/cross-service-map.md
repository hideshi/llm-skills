# サービスをまたぐ概念の地図

範囲が一つのシステムでなく、複数のサービスにまたがるとき、ドメインモデルを次の3点で書く。

1. 用語集: 用語、各サービスでの呼び方、定義。
2. 概念の関係: 概念どうしの関係と多重度（図にするなら、関係の図）。
3. 所有の表: どのサービスがどの概念の正本を持つか。

## 関係の種類

- 一種（AはBの一種）、含む（AはBを含む）、サービスをまたぐ対応・参照の3つを主に使う。ほかの関係は、関連の名前を付けて書く。
- 図にするときの記法は案件に任せる（例: Mermaid の classDiagram で、一種は `<|--`、含むは `*--`、対応・参照は `..>`）。分類が多いときは、補助の図に分ける。

## 用語集と所有の表の欄

- 用語集: 用語（表示名）、英語の呼び方（業務の呼び名。コードの綴りは書かない）、定義（1〜2行）、正本のサービス、サービス間の意味の違い（同一／部分一致／別物）。
- 所有の表: 概念ごと、サービスごとに、所有／参照／扱わない。所有のサービスは一つにする。
- 用語集にコードや表の列を足さない。各サービスでの名前を追いたいときは、そのサービスのドメインモデルを指す。

## 書く言葉

- 最初から、サービス群の正本として書く（一つのサービスの見方で書いて後から広げない）。
- 制約は、概念の関係として書く。
- 同じ名前で意味が違う概念は、サービス名で修飾して分ける。
- 日本語名は、利用者に見える表示名を正にする。
- 固定の規則と、既定の値（後から変えられるもの）を分ける。
- 概念が別のサービスへ引き継がれる関係は「〜しうる」で書く（必ず起きるとは限らない）。

## やらないこと

- 推論の仕組みや公理は扱わない。
- 実装の識別子、特定の機能への従属、画面、分類の軸を独立の概念にする、コードの列を写す、はしない。

## 作り方

- 第一の入力は、各サービスのドメインモデル。コードにしか無い知識は、先に各サービスのモデルへ返してから地図に載せる。
- 多重度、主体、条件は、各サービスのモデルで裏を取る。人の確かめは省かない。
- 1つの文書で、概念は50〜100を目安にする。超えるなら範囲を分ける。
- 地図と各サービスのモデルがずれていないかの判定は、人がする。

## 更新とずれ

- 範囲を広げるときは、新しい地図を作らず、今の地図に足す。地図の頭に、今の範囲を書いておく。
- 各サービスのドメインモデルが変わったら、作り方の手順で地図を導き直し、今の地図との差を見る。
- 差がどちらの誤りかは、人が決める。各サービスのモデルの側が正しければ、地図は概念が変わったときだけ直す。コードにしか無い知識が見つかったら、先に各サービスのモデルへ返す。
- 地図は続けて使う文書なので、今回の変更だけの置き場に置かない（型の一覧の「続けて使う文書」）。
