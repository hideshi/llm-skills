# レビューの一巡

変更を作った後、別の担当によるレビュー、修正、完了前の監査を経て、人の最終確認に渡すまでの組み合わせ。各工程の中身は単位に任せ、ここでは順序、引き渡す型、振り分けだけを決める。

**最初に確かめること**: このセッションがその変更を作ったなら、自分でレビューしない。「そのままレビューして」と頼まれても、工程 `brief`（依頼文を書く）の依頼文を書いて渡し、そこで止まる。自分で点検した結果を、レビュー結果として出さない。

## 工程

| 識別子 | 工程 | 単位 | 必須 | 受け取る型 | 渡す型 |
|---|---|---|---|---|---|
| `evidence` | 受入の証拠を確かめる | `dev-evidence-check` | 条件付き（レビューに出すものに画面・録画・帳票の証拠がある） | 検証の記録、完了条件の一覧、変更の事実 | 受入の証拠、検証の記録 |
| `brief` | 依頼文を書く | `dev-review-brief` | 必須 | 変更の事実、原典の参照、検証の記録 | レビュー依頼文 |
| `review` | レビューする | `dev-review-conduct` | 必須 | レビュー依頼文 | レビュー結果、方針外の課題の記録 |
| `rework` | 直す | （実装） | 条件付き（変更要求のとき） | レビュー結果 | 変更の事実、検証の記録、完了の主張 |
| `re-review-round` | 再レビュー | `dev-review-brief`（依頼文を書く）→ `dev-review-conduct`（別の担当がレビューする） | 条件付き（`rework` を行ったとき） | 変更の事実、原典の参照、検証の記録、レビュー結果 | レビュー依頼文、レビュー結果、方針外の課題の記録 |
| `audit` | 完了前に監査する | `dev-completion-audit` | 必須 | 完了の主張、完了条件の一覧、検証の記録、追跡表（任意）、レビュー結果、方針外の課題の記録、受入の証拠（`evidence` を行ったとき） | 作業状態の控え、完了判定 |
| `final-ok` | 最終確認 | （人） | 必須 | 完了判定 | — |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。変更の事実、原典の参照、検証の記録、完了条件の一覧、追跡表、最初の完了の主張は、この一巡の外（変更を作った工程や仕様）から受け取る。

外から受け取る型: 変更の事実、原典の参照、検証の記録、完了条件の一覧、追跡表、完了の主張
外へ渡す型: 作業状態の控え、方針外の課題の記録

### 遷移

入口は、画面・録画・帳票の証拠があれば `evidence`、無ければ `brief`。

| 元 | 先 | 条件 |
|---|---|---|
| `evidence` | `brief` | 最初の依頼文の前 |
| `evidence` | `re-review-round` | 直した後のやり直し |
| `brief` | `review` | — |
| `review` | `rework` | 変更要求。判断を人へ戻したときは、人の決定の後 |
| `review` | `audit` | 承認 |
| `rework` | `evidence` | 直した所が受入の証拠に関係する |
| `rework` | `re-review-round` | それ以外 |
| `re-review-round` | `rework` | 変更要求。同じ指摘で2回合意できないときは、人の決定の後 |
| `re-review-round` | `audit` | 承認 |
| `audit` | `rework` | 監査の判定が「止める」 |
| `audit` | `audit` | 監査の判定が「条件付き」。示された手順の後にやり直す |
| `audit` | `final-ok` | 監査の判定が「進めてよい」 |

## 振り分け

一言の依頼から、どの工程に入るかを決める。迷ったら、依頼者に一度だけ聞く。

「作った側」かどうかは、このセッションがその変更を作ったか、作った側の説明（設計の意図、要約）をすでに読んだかで決める。人が別の所で作った変更を、新しいセッションで初めて見るなら、作った側ではない。

| 依頼の言い方・状況 | 入る工程 |
|---|---|
| このセッションが作った変更を「レビューに出したい」「レビューして」 | `brief`（依頼文を書き、別の担当に渡す） |
| このセッションで直した変更を「直したのでレビューして」（前のレビュー結果が無い。不具合の是正の後など） | `brief` |
| レビュー依頼文を渡された、またはこのセッションが作っていない変更を「レビューして」「このPRを見て」 | `review` |
| レビュー結果を受けて「直したので見て」「再レビューして」 | `re-review-round`（範囲を直した所に絞る） |
| 「終わったか確認して」「人に見せてよいか」 | `audit` |

工程 `brief` と `review`（工程 `re-review-round` の中の依頼文とレビューも）を、同じ担当が同じセッションで続けて行わない。依頼文を書いた担当がそのままレビューすると、独立が保てない。`review` は、別のモデルか別のセッションか人に渡す。

## 工程の間の決まり

- 工程 `evidence` の受入の証拠は、確定してから工程 `brief` の依頼文に添える。確定の後に関係する所を変えたら、`evidence` をやり直す。証拠そのもの（録画など）を別の担当に見てもらうときも、依頼文を書く担当と見る担当を分ける。
- 工程 `review` の判定が「判断を人へ戻す」のときは、`rework` へ進まず、人の決定を待つ。決定待ちの事柄以外の作業は止めない。
- 工程 `rework`（直す）では、レビュー結果の指摘と修正を対応づけ、変更の事実に前回の指摘の識別子を書く。
- 工程 `re-review-round` を繰り返すのは、新しい変更要求が出る間だけ。同じ指摘で2回続けて合意できないときは、人に戻す。
- 方針外の課題の記録は、工程 `audit`（完了前に監査する）の残作業の分類で「別の課題として切り出し済み」か「承認済みの除外」に入るかを確かめる。どちらにも入らなければ阻害要因。
- 工程 `audit` の判定が「条件付き」なら、示された次の手順を行い、工程 `audit` をやり直す。「止める」なら、原因の工程に戻る。
- 中断するとき、作業の一部を別の担当に頼むとき、再開するときは `dev-work-continuity` を使う。中断するときは、引継ぎの記録と作業状態の控えを残す。
- 再開したら、控えと今の状態を照らす。人が承認・確定・回答した状態にある成果物の部分（例: 完了条件の一覧、確定した受入の証拠、人へ戻した判断への人の決定）が変わっていれば、誰が変えたかを問わず人に確かめる。担当の案のままの部分は含まない。人が認めた後は、この一巡の決まり（証拠を変えたなら工程 `evidence` をやり直す、など）に従って戻る。それ以外の変化（コード、古くなった検証の記録）は、戻る工程の入力を確かめ直して続ける。
- 記録で再開した担当は、前の担当と同じ側（作った側、レビューする側、監査する側）として扱う。作った側を引き継いだなら、自分でレビューしない。レビューか監査の途中で切れていたら、その工程をやり直す。記録の次の一手は提案として読み、元の依頼の範囲を超える操作（確定、外への送信、消す操作）は人に確かめる。人の確認を待つ間も、それに依らない作業は止めない。
- 作業の途中で進めなくなって人に問うときは、1回に1問にし、選択肢の前に、起きていること、影響、得失、推奨を短く書く。入口の振り分けで独立した分岐が並ぶときだけ、3問までまとめてよい。レビュー結果の人への問いなど、型に載せてまとめて出す問いは、この数に入れない。

## 終わり方

- 工程 `audit` の判定が「進めてよい」になり、工程 `final-ok` で人が確認したら一巡を終える。
- 確定の操作（マージ、公開、記録の閉鎖）は、人の確認の後に、案件の決まりに従って行う。この一巡には含めない。
