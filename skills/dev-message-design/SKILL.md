# 文面と帳票を設計する

システムが人に向けて画面の外へ出す文（メール、通知、SMS）と、画面の外へ持ち出す形の決まった帳票を、設計の判断の「文面」の観点として定める。誰に、いつ、何を知らせるかを決めるのは要件と業務規則で、この単位はそれを文面に割り当て、出し方を決める。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 必須 | 知らせる・送らない・帳票を出す受入条件。文面の出どころ |
| 業務規則の一覧 | 条件付き（送る条件、止められるか、帳票の計算が規則にあるとき必須） | 送る条件、頻度、計算と端数処理の正本 |
| ドメインモデル | 任意 | きっかけになるドメインイベントと、用語 |
| 画面の設計 | 任意 | 誘導先の画面の識別子、画面の共通仕様の書式と文言の決まり |
| 設計の判断 | 任意 | エラーの一覧（失敗を知らせる文の決まり）、認可（その宛先に見せてよいか）、非同期の実行（送る仕組み）、応答と入口の安全（差し込む値の出力の変換、リンクの期限）、デザインシステム |
| 一次情報の記録 | 条件付き（帳票や文面に法定の記載事項がありうるとき必須） | 記載事項の原典の項目 |
| 個人情報の台帳 | 任意 | 既にある台帳と、個人情報の見せ方の決まり |
| 現状の振る舞いの記録 | 条件付き（今ある文面を変えるとき必須） | 今の文面の棚卸し |
| 原典の参照 | 任意 | ブランドの言葉づかいの決まり、今の雛形、続けて使う文書 |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

- 完了条件の一覧が無いときは、設計せずに止め、何を知らせるかの要件を先に書くよう返す。
- 誰に、いつ、何を知らせるか、送らない条件、止められるかが要件や業務規則に無いときは、この単位で決めない。受入条件の案か確認事項の候補として返す。
- 法定の記載事項がありうるのに一次情報の記録が無いときは、その項目を確定せず「決定待ち」にして上流へ返す。
- 個人情報の見せ方の決まりが無いときは、書かない情報を案として返し、人に確かめる。

## 出力

| 型 | 中身の補足 |
|---|---|
| 設計の判断 | 観点「文面」。判断の中の一覧として、型の一覧の「文面の一覧の欄」をそろえる。行の鍵は文面の識別子 |

## 使わない場面

- Web の画面（アプリ内の通知の一覧や未読の印の画面を含む）を設計する。
- 送る仕組み、再送、実行の保証、外部へ届くことを設計する。失敗の分け方と文言の決まりを決める。
- 誰に、いつ、何を知らせるかという業務の決定をする（要件と業務規則の仕事）。
- マーケティングの配信を企画する。法定の記載事項が当たるかを解釈する。
- 発行済みの帳票の訂正、再発行、採番の決まりを決める（業務規則とデータの仕事）。
- キューやほかのシステムへ流すメッセージ、イベント、Webhook など、機械が受け取る知らせの形を決める（呼ばれる契約か連携の仕事）。

## 手順

### 1. 知らせを集める

完了条件の一覧と業務規則から、知らせる・送らない・帳票を出す受入条件を全部挙げる（分母は完了条件の一覧の版）。ドメインイベントがあれば、イベント × 宛先の組み合わせも並べ、受入条件に無い組み合わせは「送らない」か「上流へ返す」に振り分ける。今ある文面を変えるときは、現状の振る舞いの記録から今の文面を棚卸しして、変える・残す・やめるを分ける。

### 2. 文面に割り当てる

受入条件ごとに、文面の識別子を振り、種類（メール／アプリ内の通知／プッシュの通知／SMS／帳票）を決める。区分（取引に要る知らせ／案内・宣伝）、きっかけ、宛先、送らない条件、頻度の上限、まとめ方、止められるかは、要件と業務規則から写し、出どころを書く。区分が書かれていなければ案として付け、確認事項の候補として上流へ返す（区分が法令の定めに当たるかは解釈しない）。

### 3. 送りすぎを点検する

同じ宛先に短い間に何通届くかを、きっかけの組み合わせから数える。まとめる、間引く、止められるようにする案は、業務の決定なので上流へ返す（要件か業務規則に入れてから写す）。止められない知らせは、その理由の出どころを書く。

### 4. 雛形と差し込む値を決める

件名と本文（帳票なら項目と並び）の雛形を書く。差し込む値ごとに出どころと、値が無いときの文を決める（宛名が空になる、など）。表示の書式（桁、日付、時刻の時間帯）は画面の共通仕様か続けて使う文書を指し、決め直さない。帳票の計算と端数処理は業務規則を指し、ここでは表示の書式だけを決める。言語が複数なら、正本にする言語、宛先の言語の決め方、無いときの言語を書く。帳票の作りは [帳票](references/forms.md) を見る。

### 5. 書かない情報と安全を決める

- 件名、プッシュの通知、SMS は、ロック画面や一覧で他人に見えうる。個人情報の見せ方の決まりに照らし、出してよい情報を分ける。決まりが無ければ案として返す。
- 差し込む値の出力の変換、件名への改行の混入、リンクに入れるトークンと期限、差出人の表示は、応答と入口の安全の判断か、続けて使う文書の決まりを指す。どちらにも無いときだけ、その観点が要ると返す。判断が同じ設計の中で後に作られるなら「決定待ち」にし、作られた後に指し直す。
- その宛先に見せてよいかは、認可の判断か続けて使う許可の表を指す。無いときの扱いは上と同じ。
- 要件か業務規則が、受け手が止められると決めた文面には、止める手段と、止めた後に送らないことの確かめ方を書く。

### 6. 確かめる観点を書く

文面ごとに、受入の試験で何を見るかを書く（届いた件名と本文、差し込んだ値、値が無いときの文、送らない条件で送られないこと、止めた後に送られないこと）。試しに送って確かめる手順は、隔離した環境で、作り物の宛先とデータを使い、本番の資格情報を使わず、外部への送信を捕まえる形にする。

### 7. 網羅を点検する

型の一覧の「設計を終えるときの検査」のうち文面の項目を通す。文面や帳票を出す受入条件と送らない受入条件がどれかの文面に結ばれ、どの文面も要件か受入条件を持ち、指す先が実在し、仮説の規則に頼っていないこと。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 知らせる・送らない・帳票を出す受入条件が、どれも文面に結ばれているか、対象外と理由がある。
- 文面ごとに、型の一覧の「文面の一覧の欄」がそろい、決まっていない所は「決定待ち」か上流へ返すものに入っている。
- 設計を終えるときの検査の文面の項目を通した結果がある。
