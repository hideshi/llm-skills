# 既存のシステムから業務規則を抜き出す

文書に無く、コードやデータの定義に散らばっている規則を、候補として一覧にする。一番大事な発見は、守られていない経路（ある入口だけ検証が無い、など）。抜き出した候補は、関係者が確かめるまで確かさを「仮説」にする。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 改修の範囲 | 必須 | 調べる機能、項目、入口 |
| 業務規則の一覧 | 任意 | 既にある規則。重複を除き、同じ規則なら守っている箇所を足す |
| 原典の参照 | 任意 | 項目の辞書、データベースの定義の所在 |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

範囲が決まっていないときは、全体を調べずに止め、どの機能と項目を対象にするかを依頼者に聞く。

## 出力

| 型 | 中身の補足 |
|---|---|
| 業務規則の一覧 | 候補の行。確かさは「仮説」、根拠は「実装で受け入れた動作」か「不明」。守っている箇所（確認の水準つき）と守られていない経路。種類は分かる範囲で付け、所有と確かめる手段は「未記入」と明記する（決めるのはモデルを作る側） |
| 問題台帳 | 隣り合う入口の制約の差、意図が分からないもの |
| 検証の記録 | 実データで確かめたとき（任意の段） |

## 使わない場面

- 関係者と話して規則を決める、モデルを作る。
- 既存のデータが規則を守っているかを、全件で監査する。
- 規則や制約を直す。

## 手順

### 1. 項目の集合を決める

範囲の中の項目（入力の項目、保存の列、計算の値）を全部挙げる。これが分母になる。

### 2. 機械で絞る

- 検証の定義、データベースの制約、画面の入力の制限、計算の式を、検索で機械的に抜き出す。制約を含む行だけを残す。
- 検証が一つも無い項目も、それ自体が発見として残す。
- 道具ごとの抜き出し方は、道具の資料があれば読み、無ければ公式の資料で確かめる。

### 3. 項目と層の突き合わせ

項目ごとに、どの層（画面、入口の検証、業務の判断、データベースの制約）で、どの制約がかかっているかを表にする。

### 4. 分類する

- 観点: 値の範囲、形式、項目どうしの依存、構造、業務規則。観点は探すための分け方で、一覧の「種類」の欄には型の一覧の種類（不変条件、一意性など）を書く。
- 重要度: 高（データの不整合や計算の誤りに直結）、中（入力の品質）、低（画面の補助）。
- 隣り合う入口（同じ項目を受け取る別の API や画面）で制約が違えば、差の表を必ず出す。どちらが意図かは決めつけず、問題台帳に載せて人に確かめる。手がかりとして、変更や問い合わせが多く積み重なった側を意図の本命とみなしてよいが、評価の言葉で書かない。

### 5. 守られていない経路を書く

規則ごとに、期待値、守っている箇所（層ごと）、守られていない経路（その層を通らずに値が入る入口、一括の取り込み、管理用の操作など）の3点をそろえる。

### 6. 実データで当たりを付ける（任意）

人が許したときだけ、候補1件ごとに、隔離した複製のデータで違反する行があるかを数える（読み取りの問い合わせだけ）。0件なら確かさの手がかりに、違反があれば守られていない経路の証拠になる。違反の仕分け、違反のデータで何が壊れるかの再現、流し直せる形にすることはしない（それは既存のデータの監査の仕事）。本番のデータと本番の資格情報を使わない。システムは動かさない。結果に個人の具体値を出さない。

### 7. 一覧にまとめる

- 確かさは「仮説」にし、守っている箇所ごとに確認の水準（型の一覧の物差し: 実行／静的／公開情報／未確認。コードやデータベースの定義を読んで確かめたものは静的、実データで数えたものは実行）と出典（ファイルと行）を付ける。
- 落とし穴: 入れ子の配列の項目の取り違え、複数行にわたる定義の取りこぼし、表記の揺れ（同じ項目の別名）、設定ファイルにある制約の見落とし。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 範囲の全部の項目に、制約の有無と、ある場合の層ごとの箇所が書かれている。
- すべての候補に、期待値、守っている箇所、守られていない経路、確認の水準、出典がある。
- 隣り合う入口の制約の差が、問題台帳に人への問いとして載っている。
