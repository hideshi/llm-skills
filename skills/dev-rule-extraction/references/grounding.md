## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 範囲内の項目（入力・保存・計算）をすべて挙げて分母とし、画面・入口検証・業務判断・DB制約の層ごとに突き合わせ、制約が無い項目や守られていない経路を残す | 既存の検証コードだけを検索すると「どの層にも検証が欠けている項目」や「特定の経路だけ素通りする穴」を見落とすため | 抽出後に層抜けや別経路の素通りから不整合が発覚した件数を記録し、分母と層の分け方を見直す |
| 隣り合う入口（別 API や画面など）で制約が違えば差の表を必ず出し、どちらが意図かを決めつけず問題台帳で人に聞く | 入口ごとの制約差が意図的な仕様（管理画面だけの緩和など）か単なる実装漏れかはコードからは確定できず、勝手に揃えると業務を壊すため | 人への確認で仕様と確定した割合と不要な問い合わせによる確認待ち件数を問題台帳・確認事項の記録で比べ、差の表の登録基準を見直す |
| 抜き出した候補の確かさを「仮説」とし、所有と確かめる手段は「未記入」のまま返す | 規則の真偽や所有責任の決定は業務のモデルを決める段階の仕事であり、抽出の段階で勝手に確定させてはならないため | モデル側へ仮説・未記入で渡して合意変更になった割合と、未記入項目に関して確認事項の記録で追加確認になった件数を問題台帳で数え、返し方の制限を見直す |
| 実データで当たりを付けるときは人の許可・隔離した複製・読み取り専用問い合わせに限り、システムを動かさず個人の具体値を出力しない | 調査の段階で本番環境へ影響を与えたり、実データ由来の個人情報が調査記録へ漏出したりするのを防ぐため | 調査で個人情報や本番影響の懸念が出た件数と、隔離・秘匿の条件により読み取り対象を絞って未確認が残った割合を問題台帳で比べ、隔離と秘匿の基準を見直す |
