## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 点検は隔離した環境と点検用のデータに限り、外へ送る操作は送り先を疑似に差し替えた環境だけで踏む | キーボードでの一巡は、送信、削除、確定を踏みうる。共有の環境や本番では、利用者や外のサービスに影響するため | 点検の中で意図せず踏んだ操作と、踏まずに止めた操作の件数を記録し、範囲の決まりを見直す |
| 担当がブラウザを操作し、観察できるなら、キーボードでの一巡とアクセシビリティの木は担当が行う。できなければ人の手順に回す | 担当ができる操作まで人に回すと、待ちが増えて点検が回らない。できない環境で担当が判定すると、見ていないものを合格にするため | 担当が合格とした所見が、後で人の確かめで問題になった件数を記録し、線引きを見直す |
| 意味の判断（代わりの文、見出し、ラベル、リンクの目的）は、担当が案と根拠を書き、人が採るまで「未確認」とする | 内容を表すかは、業務と利用者を知る人でないと決められないため。全部を人に回すと待ちが増えるため | 人が担当の案を直した割合を記録し、案の書き方を見直す |
| 道具の指摘の仕分けと、基準の判定を分ける。ルールの結果を基準の判定に読み替えない | 自動の点検が通ったことが、基準の合格と読まれやすいため | 自動では通ったが操作か人の手順で問題が見つかった件数を記録し、確かめ方の割り当てを見直す |
| 基準の判定は所見から集め、未確認や確認不能の画面×状態が残れば「合格」にしない | 一部の状態だけを見て合格にすると、ダイアログや誤りの状態の問題が隠れるため | 合格とした基準で、後から見なかった状態の問題が見つかった件数を記録し、範囲の決め方を見直す |
| 所見に今回入ったか前からあるかを書き、前からある所見の判断の区分の既定を「別の計画で扱う」にする | 既存の画面では、今回の変更と関係ない問題が多く出て、範囲が広がりやすいため | 前からある所見を今回直した件数と、人が範囲を広げた件数を記録し、既定を見直す |
| 準拠や適合を書かない | 開発中の、範囲を絞った点検は、全体の適合の表明の根拠にならないため（評価の方法論も同じ立場） | 記録を読んだ人が適合と受け取った例を集め、書き方を見直す |

- 2026-11-17: 部品のカタログで流した自動の点検の結果を、読む単位が無かったので、この単位が受けるようにした（入力に検証の記録、手順4、終了条件、axe-core の資料）。部品×状態の行として道具の指摘の表に残し、画面×状態の行の代わりにしない。理由は、カタログの設定はデザインシステムの判断の道具の資料が持つが、結果の仕分けと判定の語彙はこの単位にしか無く、結果が読まれずに残るのを防ぐため。独立レビュー（2つ）を受けて、利用者の決定で次を足した: カタログだけで出た所見はそれ自体は基準に集めず、範囲の画面で確かめて決める（出たら数える、出なければ響かせない、まだなら未確認として合格にしない）、カタログの結果だけが届いたときの範囲は前回の範囲の表の画面、他人の記録を読んだだけの所見は確認の水準を「実行」にしない、結果の版が違えば今の版として扱わない、結果の種類が無ければ見ていない扱い、結果だけの依頼では仕分けて終えず点検する画面を求める、画面を変えていなくても新しく届いた結果は読む。
