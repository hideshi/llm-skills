# アクセシビリティを点検する

隔離した環境で動く Web の画面が、画面の設計と設計の判断で決めたアクセシビリティの基準を満たすかを、画面×状態の範囲で点検する。基準ごとに、確かめ方、判定、確かさを記録する。基準ごとの確かめ方は [基準と確かめ方](references/checks.md)、ルールで調べる道具の扱いは [axe-core の場合](references/tools/axe.md) に分ける。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 改修の範囲 | 条件付き（変更の事実が無いとき必須） | 点検する画面、環境、対象の版 |
| 変更の事実 | 条件付き（改修の範囲が無いとき必須） | 今回作ったか変えた画面と、その版 |
| 規模の判定 | 任意 | 道（軽い道なら範囲を変えた画面×状態に絞る）と、点検の作業に当てた理由 |
| 画面の設計 | 条件付き（あれば必須） | 共通仕様の目標の水準、画面一覧、画面ごとの状態とアクセシビリティの要件 |
| 設計の判断 | 任意 | デザインシステムの判断の、部品への基準の割り当て |
| 原典の参照 | 任意 | 案件の方針（目標の水準、読み上げソフトの実機での確かめを求めるか、対象の端末・ブラウザ・支援技術の組み合わせ、公的な基準が効くか）、点検に使ってよい環境の許し |
| アクセシビリティの点検の記録 | 任意 | 前回の点検（比べる元と、今回入った問題を分ける元）。無ければ初回として扱う |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

- 目標の水準が決まっていなければ、点検の中で決めない。既定（WCAG 2.2 の AA）を前提として点検し、記録の前提の欄に「未確認」と書いて、人の判断に回す行（問題台帳の仕様の質問）にする。
- 画面の設計が無い既存の画面では、今の画面から範囲の表（画面×状態）を作る。これは点検の記録の範囲の表に留め、画面の設計や今の振る舞いの記録として渡さない。
- 動かせる隔離した環境が無ければ、点検せずに止め、要る環境を書いて返す。

## 出力

| 型 | 中身の補足 |
|---|---|
| アクセシビリティの点検の記録 | 前提、対象の版と環境、範囲の表、基準の判定の表、所見の表、道具の指摘の表、前回との差 |
| 問題台帳 | 判定が「問題がある」の所見、判定の案を人に採ってもらう所見、未確認と確認不能の所見。行ごとに所見の識別子で点検の記録を指す（直す層、及ぶ画面、今回入ったか前からあるかの正本は点検の記録の所見の表）。確認の水準、判断の区分。人の決定の欄は書かずに渡す（人が決めたときに足す） |
| 検証の記録 | 流した自動の点検（道具、版、有効にしたルールと無効のルール、対象の画面×状態、実行の誤り）、担当が操作した手順、人に頼んだ手順と結果、行わなかった手順と理由 |

## 使わない場面

- 目標の水準や、画面ごとのアクセシビリティの要件を決める（画面の設計の仕事）。部品へ基準を割り当てる（デザインシステムの判断の仕事）。
- 部品カタログ（Storybook など）の点検の設定を決める（デザインシステムの判断の道具の資料）。
- 適合を宣言する。認証や第三者の試験の代わりにする。記録は「この範囲で、この確かめ方で、こう判定した」までにする。
- 見つけた問題を直す（実装か是正の仕事）。
- 帳票（PDF）、メールの文面、ネイティブアプリの画面を点検する。
- 本番の環境と、人の許しの無い共有の検証の環境を操作する。

## 手順

### 1. 操作してよい範囲を確かめる

- 点検は、隔離した手元か検証の環境と、点検用のデータで行う。共有の検証の環境は、原典の参照に人の許しがあるときだけ使う。
- キーボードでの一巡は、送信、削除、確定のボタンを踏みうる。外へ送る操作（メール、決済、外部のサービスの試験環境への書き込み）は、外への送り先を疑似に差し替えた環境だけで踏む。差し替えていなければ、その操作の手前で止め、踏まなかったと書く。
- 点検用の利用者の資格情報は人が用意する（ログイン済みのセッションか、環境の変数）。担当は値を読まず、記録に写さない。
- 記録に、点検用のデータ以外の個人の情報を写さない。画面の写しに写り込んだら、伏せてから残す。

### 2. 範囲を決める

- 画面の設計の画面一覧と状態から、範囲の表（画面×状態）を作る。状態は、通常、空、読み込み中、失敗、権限なし、入力の誤り、ダイアログやメニューを開いた状態を見る。
- 通常の範囲は、今回作ったか変えた画面×状態、それが使う共通の部品、利用者の主な仕事の流れのうちそれを通るもの（流れの途中の画面も含める）。依頼が範囲を絞るとき（規模の判定が軽い道のときを含む）は、変えた画面×状態に絞り、絞ったと書く。
- 前回の点検の記録があり、その後の変更を点検し直すときは、前の点検の後に変えた画面×状態（直した所見と、それが及ぶ画面×状態を含む）に絞る。前の点検の後に画面を変えていなければ（運用の文書だけの直しなど）、そう書いて終える。
- 標本の選び方は、変更の点検に要る所（構造化した標本と、完結した手続き）だけを使い、無作為の標本は使わないと書く。全体の適合の評価をするのではないと書く。
- 見なかった画面×状態と理由を書く。運営者や利用者が入れる内容（記事の画像の代替の文など）は、作り物のデータでは見られないので「見なかったもの」に入れる。

### 3. 基準の一覧を作る

- 目標の水準が AA なら、A と AA の全部の達成基準を並べる（AA は A を含む）。
- 公的な基準（日本の JIS X 8341-3 など）が効くと原典の参照にあれば、基準の名前、版、適用の範囲を原典で確かめ、目標の水準（WCAG 2.2 など）と版がずれていないかを書く。確かめられないか、ずれの扱いが決まっていなければ、点検の中で決めず、問題台帳の仕様の質問にして人に返す。
- 画面にその面が無い基準（動画、時間の制限、ドラッグなど）は「該当なし」とし、理由を書く。WCAG では、当てはまる内容が無い基準は満たした扱いになる。記録では「合格」と分けたまま、集計の読み方として書く。
- 画面の設計のアクセシビリティの要件と、部品へ割り当てた基準を、基準の行に結びつける。
- 案件が独自に決めた要件と、目標の水準より上の基準（例: 操作で起きる動きを止める 2.3.3 は AAA）は、別の水準の行として分ける。

### 4. 自動の点検を流す

- ルールで調べる道具を、範囲の表の画面×状態ごとに、その状態を開いてから流す。閉じたメニューや開いていないダイアログは調べられない道具がある。
- 道具の結果は、種類（通った、違反、要確認、当てはまらない、実行の誤り）をそのまま道具の指摘の表に残す。無効にしたルールと、道具の版も残す。
- WCAG の基準に結びつくルールと、それ以外（よい慣行のルールなど）を分ける。後者の違反は WCAG の違反として数えない（所見には残してよい）。
- 道具の指摘ごとに、本当の違反か、誤検知か、要確認かを仕分ける。誤検知とするなら理由を書く。
- ルールの結果を、そのまま基準の判定にしない。通ったことと、違反が無いことは、基準の合格ではない。「当てはまらない」は、基準の「該当なし」ではない。

### 5. 操作で確かめる

担当がブラウザを操作し、結果を観察できる環境なら、担当が行う。操作か観察ができない環境なら、その行は人の手順に回す。

- キーボードだけで一巡する: 順序、フォーカスの見え方、フォーカスが閉じ込められないか、フォーカスが他の内容に隠れないか、ダイアログを閉じた後のフォーカスの戻し先。
- アクセシビリティの木を見る: 名前、役割、状態、ラベルと入力欄の結びつき、誤りと状態の変化の知らせ。
- 拡大と折り返し: 文字を 200% にしても欠けないか、縦に読む内容は幅 320 CSS ピクセル相当、横に流れる内容は高さ 256 CSS ピクセル相当で二方向のスクロールが要らないか（二次元の配置が要る内容は例外）、文字の間隔を変えても欠けないか。
- そのほか: 色だけに頼らない、自動で始まり5秒を超えて動く・点滅する・流れるものを止められる、自動で更新される情報（件数、状況の表示など）を止めるか隠すか更新の頻度を変えられる（欠かせないものは例外）、的の大きさ（例外を含めて）。
- 見た目で決まる行（フォーカスの見え方、隠れない、欠け、色）は、根拠に測った値か画面の写しの所在を書く。
- 部品に期待するキーボードの操作は、WAI-ARIA の作り方の手引き（APG）を参考にする。手引きと違うだけでは「問題がある」にせず、どの根拠（WCAG の基準か、手引きの期待か）で問題としたかを書き分ける。

### 6. 人の手順を頼む

- 読み上げソフトの実機での確かめは、案件の方針か完了条件が求めたときに行う。WCAG は特定の支援技術での試験を手順として定めておらず、評価の方法論も利用者の関与を必須にしていない（利用者の関与と、評価者が支援技術で試すことは別のもの）。行うかはこの群の運用の方針として決める。
  - 求めるときは、対象の組み合わせ（端末、ブラウザ、支援技術）を案件の方針から取る。無ければ人に確かめる。手順、見る所、対象の版を書いて人に頼む。
  - 求めないときは、検証の記録の「行わなかった手順と理由」に書く。
- 意味の判断（代替の文が内容を表すか、見出しやラベルが内容を表すか、リンクの目的が分かるか）は、担当が判定の案と根拠を書き、人が採る。人が採るまで、その所見の判定は「未確認」とする。
- 人の結果を記録するときは、報告した人、実施した人、日、対象の版を書く。人の報告で確認の水準を上げない。

### 7. 判定する

- 所見ごとに、判定（語彙「アクセシビリティの判定」）、確かめ方（語彙「アクセシビリティの確かめ方」の当たるものを全部）、観察した事実と推定の別、確認の水準、証跡の所在を書く。判定の「確認不能」は、見たが判定できない（足りない証拠を書く）。「未確認」は、まだ見ていない（人の手順待ち、範囲外、操作できなかった）。
- 基準の判定は、所見から集める。
  - 範囲の中に「問題がある」所見が一つでもあれば「問題がある」。
  - 未確認か確認不能の画面×状態が残れば、「合格」にしない（残る中で一番弱い判定を基準の判定にする）。
  - 集めるときに、未確認の所見を消さない。
- 問題がある所見に、直す層（実装／画面の設計／デザインシステムの判断／目標の水準や受入条件）、及ぶ画面（部品の問題なら、同じ部品を使う画面）、今回入ったか前からあるかを書く。
  - 今回入ったか前からあるかは、前回の点検の記録か、変える前の版で流した自動の点検の結果と比べて決める。比べられなければ「不明」と書く。
  - 前からある所見の判断の区分は、既定を「別の計画で扱う」にする。
- 直すか、受け入れるか、保留するかは、この単位では決めない。人が決め、問題台帳の人の決定に書く。

### 8. 前回と比べる

- 前回の点検の記録があれば、閉じた所見、新しく出た所見、判定が変わった所見を先頭に置く。
- 見なかった所見を閉じたとしない。
- 点検し直しは、手順2で絞った範囲だけを見て、絞ったと書く。前に人が受け入れか保留を決めた所見は、その決定を引き継ぎ、人に決め直してもらう所見に数えない（範囲の中で内容が変わったときだけ、新しい所見として出す）。同じ所見が2回続けて直らなければ、その旨を書いて人に返す。

### 9. 書く

- 所見ごとに、まず起きることを専門の語を使わずに書く（誰が、何をしようとして、何ができないか）。その後に、基準の番号と根拠を添える。
- 記録は「この範囲で、この確かめ方で、こう判定した」までにする。準拠している、適合している、とは書かない。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 前提（目標の水準と確認の状態、対象の組み合わせ、読み上げソフトの実機の確かめを求めるか）と、範囲の表（見た画面×状態、見なかったものと理由）がある。
- 基準の判定の表に、目標の水準の全部の基準の行がある。どの行も、確かめ方、判定、問題のある所の識別子（あれば）を持つ。
- 自動の点検だけで「合格」にした行が無い。ルールの結果を基準の判定に読み替えていない。
- 問題がある所見、人に採ってもらう所見、未確認と確認不能の所見が、問題台帳の識別子で結ばれている。
- 本番と、許しの無い共有の環境を操作していない。外へ送る操作を、差し替えていない環境で踏んでいない。
