# HTTP での例

本文の決まりを HTTP の API で書くときの例。案件に既定の決まりがあれば、そちらを優先する。

## 操作の表し方

| 操作 | 例 | 冪等性 |
|---|---|---|
| 一覧を読む | `GET /invoices` | あり |
| 一件を読む | `GET /invoices/{id}` | あり |
| 新しく作る | `POST /invoices` | なし（冪等キーで補う） |
| 全体を置き換える | `PUT /invoices/{id}` | あり |
| 一部を変える | `PATCH /invoices/{id}` | 中身による |
| 消す | `DELETE /invoices/{id}` | あり |
| 出来事を起こす | `POST /invoices/{id}/finalize` | なし（冪等キーで補う） |

- 冪等キーは `Idempotency-Key` のようなヘッダで受け取ることが多い。
- 版は、URL に入れる（`/v2/...`）か、ヘッダで指定する。外部に公開するなら、URL に入れる方が呼び出し側に見えやすい。

## 一覧

- 上限の例: 1回に最大100件。続きは `cursor` のような値で指す。
- 応答の例: `{ "data": [...], "meta": { "next_cursor": "..." } }`

## 状態の区分の例

| 回復の動き | 状態コードの例 |
|---|---|
| 入力を直してもう一度送る | 400、422 |
| ログインし直す | 401 |
| 権限が無いことを伝える | 403 |
| 対象が無い | 404 |
| 今の状態では受け付けない（先に別の操作が要る） | 409 |
| 時間を置いて再試行してよい | 429、503 |
| 再試行しても直らない障害 | 500 |

## エラーの応答の形の例

```json
{
  "error": {
    "code": "invoice_already_finalized",
    "message": "この請求書は確定済みのため、変更できません。新しい請求書を作成してください。",
    "correlation_id": "c-7f3a",
    "fields": []
  }
}
```

入力の誤りでは、`fields` に項目ごとの理由を入れる。利用者向けの文言（`message`）の書き方は、エラーの設計で決める。
