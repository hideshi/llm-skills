# 画面を設計する

要件が決めた「誰が、何を見て、何を決めるか」を、画面に割り当てる。判断、入力情報、受入条件の正本は完了条件の一覧で、ここでは割り当てるだけにする。画面の側で聞き直して決めない。足りなければ上流へ返す。対象は Web の画面。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 必須 | 画面に関わる要件の利用者・目的・入力情報・判断と、受入条件 |
| 原典の参照 | 任意 | 案件が続けて使う画面の共通仕様、ブランドの決まり、今の画面、人が採った前の版の所在、画面への意見の原文の所在 |
| ドメインモデル | 任意 | 用語、状態と遷移、区分 |
| 業務規則の一覧 | 任意 | 画面の制御にする規則。確かさが仮説・未確定の規則は、制御の根拠にしない |
| 設計の判断 | 条件付き（認可・エラー・デザインシステムの判断があるとき必須） | 許可、エラー、部品とトークンの名前 |
| 現状の振る舞いの記録 | 条件付き（既存の画面を踏襲するとき必須） | 今の画面の構成と値 |
| 確認事項の記録 | 任意 | 戻し先が画面の意見と回答 |
| 画面の設計 | 条件付き（前の版を直すとき必須） | 直す元。識別子はそのまま使う |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

完了条件の一覧が無いときは、設計せずに止める。画面に関わる要件に入力情報か判断が無いときは、ここで補わず、欠けとして上流へ返す（手順 6）。

## 出力

| 型 | 中身の補足 |
|---|---|
| 画面の設計 | 共通仕様（か、その所在）、画面一覧、画面の流れ、画面ごとの仕様、踏襲する範囲（踏襲するとき）、上流へ返すもの、網羅の点検の結果 |

## 使わない場面

- 要件、受入条件、ユースケースを書く。業務規則を決める。
- ワイヤーを作る。
- 部品やトークン、色、部品のアクセシビリティの基準を決める。
- 許可やエラーの種類と文言を決める。
- 実装する。
- ネイティブアプリの画面、帳票、メールや通知の文面。

## 手順

### 1. 種別と共通仕様を決める

- 案件が続けて使う共通仕様があれば、原典の参照として読み、写さない。変える必要があれば、変える案を上流へ返す（今回の画面の中で黙って変えない）。
- 無ければ、画面の種別（管理面／公開面・訴求／公開面・道具／混在）を先に決める。決める問いは、認証の有無、主な目的、成功の目安、流入元、移動の形の順。種別で、画面の導き方と点検が変わる。
- 共通仕様に、利用者ごとの端末と優先する幅、言語と地域、日付と数値の書式、完了の知らせ方、文言の決まり、アクセシビリティの目標の水準を書く。目標の水準は案件の決定で、決まっていなければ既定（WCAG 2.2 の AA）を案として置き、人に確かめる。公的な基準が効く案件では、一次情報で確かめるよう上流へ返す。

### 2. 画面を導く

- 要件ごとに利用者、入力情報、判断を読み、画面に割り当てる。
- 管理面は「管理するもの × 操作」と「出来事 × 利用者」から、公開面は流れの段（訴求、入力、結果、問い合わせ、完了）から候補を出す。導き方は [画面の導き方](references/derivation.md) を見る。
- 導いた画面と、作らない画面（まとめた、省いた）を、理由と一緒に書く。要件に結びつかない画面は作らない。
- 1画面1タスクにする。目的を一文で言えない、保存の対象があいまい、主な操作がスクロールしないと見えない、は分けるしるし。操作の名前は業務の言葉にする（「登録」ではなく「申請する」）。

### 3. 流れを決める

- 遷移ごとに、元、操作、先、開き方（ページ／ダイアログ／横のパネル／その場で編集）、条件を書く。
- 要件の例外の流れから、失敗と権限の遷移を導く。行き止まり（戻れない、次が無い）を作らない。
- 権限が変わった・失効したときに開いている画面（詳細、ダイアログ、選んだデータ）がどうなるかを書く。

### 4. 画面ごとの仕様を書く

- 見せる情報は要件の入力情報から、操作は判断から写し、出どころの識別子を書く。
- データの範囲（本人／組織／横断）を決める。横断なら、行がどの組織のものかが分かるようにする。
- 業務規則を画面の制御（不可／警告／確認／非表示）に置き換える。置き換え方は [業務規則から画面の制御へ](references/rule-to-control.md) を見る。仮説・未確定の規則に頼る所は、制御を決めずに「決定待ち」と書き、確認事項の候補として返す。
- 画面で隠すこと、押せなくすることは、守りではない。守りはサーバー側にある。認可の判断に守りが無ければ、上流へ返す。
- エラーと許可は、設計の判断の識別子＋行の鍵で指し、文言や許可の表を写さない。ここで決めるのは、どこにどう出すかと、エラーの後に利用者がとる次の行動まで。
- 状態（通常、空、読み込み中、失敗、権限なし、権限の変化）、内容の極端（長い文字、0件、大量、一部の失敗、取り消せない操作）、未保存の変更・取り消し・再試行を書く。
- 個人情報は、画面の要素のほか、属性、ツールチップ、コピー、出力、件数や検索の候補による存在の露出、URL、ブラウザへの保存、画像や録画も見る。見せ方の決まりは設計の判断か続けて使う文書を指し、画面には表示への反映だけを書く。決まりが無ければ上流へ返す。公開面で入力を保持するなら、保存場所・期間・削除の決め事として返す。
- 文言は [文言の決まり](references/wording.md) に従う。内部の識別子、規則の番号、技術の語を画面に出さない。
- アクセシビリティは、共通仕様の目標の水準から、画面ごとに要る所（ラベルの結びつき、キーボードだけでの操作、エラーの読み上げ、色だけに頼らない）を書く。部品の基準はデザインシステムの判断に任せる。
- 開き方、知らせ方、押せなくするか隠すかを選ぶ基準がデザインシステムの判断にあれば、それを指し、ここには画面ごとに選んだものだけを書く。
- 公開面は、[公開面の画面](references/public-pages.md) で、最初の表示で見えるべきもの、計測点、同意と規約への導線を足す。
- 似た画面があれば、違い（列、データの範囲、見出し）を書く。

### 5. 既存の画面を踏襲するとき

- 画面ごとに、殻・配置・文言・操作を、踏襲／差分／未定に分けた表を作り、人と合意してから差分だけを設計する。合意の所在を書く。
- 値（文字の大きさ、色、列の幅）は今の実装から写し、推測しない。属性の中だけにある文言や、使われていない翻訳を、勝手に画面に出さない。
- 今の画面でできることを、要件の根拠にしない。決まった要件とずれた今の動きは、差分に載せる。

### 6. 上流へ返す

- 受入条件の案（論点になる見た目: 列の数、状態の色、重なりの順、最初の表示で見える範囲など）と、確認事項の候補を、画面の設計に書く。採るかどうかは、ここでは決めない。
- 入力情報か判断が欠けた要件は、欠けとして返す。
- 画面への意見のうち、規則か流れの疑いがあるもの（振り分けが済んでいないもの）は、直さずに返す。見せ方の意見のうち、部品やトークンの共通の定義に関わるものは、そう書いて返す。

### 7. 網羅を確かめる

- 型の一覧の「画面の設計を終えるときの検査」を通す。画面を持たない受入条件（バッチ、API、通知など）は、対象外と理由を書く。
- 逆に、どの要件にも結びつかない画面が残っていないかを見る。

### 8. 直すとき

- 画面の識別子は変えない。要らなくなった画面は、消さずに廃止の印を付ける。
- 人が採った後に直したら、直した所を書き、その所の承認の状態を「採り直し待ち」にする。直した所に結ばれた受入条件とテストケースを確かめ直す必要があることを書く。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 共通仕様があるか、その所在を指している。
- 画面一覧の画面ごとに、目的、利用者、データの範囲、支える要件・受入条件の識別子がある。作らない画面に理由がある。
- 流れに行き止まりが無く、失敗と権限の遷移がある。
- 画面ごとの仕様に、見せる情報と操作の出どころ、規則ごとの制御、状態、エラーと許可の指し先がある。
- 型の一覧の「画面の設計を終えるときの検査」を満たす。満たさない所は、上流へ返すものに入っている。
- 承認の状態が書かれている。
