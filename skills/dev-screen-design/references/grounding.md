## 先行の手法

| 手順の箇所 | 手法 | 出典 | 確かめた水準 | 同じところ | 変えた・足したところ |
|---|---|---|---|---|---|
| 1. 種別と共通仕様を決める / 4. 画面ごとの仕様を書く | Web のアクセシビリティの基準 | W3C「Web Content Accessibility Guidelines (WCAG) 2.2」W3C 勧告（開いた頁の版の日付は 2024-12-12）（https://www.w3.org/TR/WCAG22/ ） | 原典を読んだ（2026-11-14 に勧告の頁で、適合の段と 1.4.3、1.4.10、3.3.1、3.3.2、4.1.2、4.1.3 の本文を確認。本文の「キーボードだけでの操作」（2.1.1）と「色だけに頼らない」（1.4.1）の項は開いていない） | 適合の段（A、AA、AAA）を目標として決め、ラベル、エラーの文での知らせ、名前と役割、状態の知らせを画面の要件にする | 目標の水準を案件の決定として共通仕様に置き、決まっていなければ AA を案として人に確かめる形にした。部品ごとの基準の割り当ては、デザインシステムの判断に分けた |
| 2. 画面を導く | 1つのページに1つのこと | GOV.UK Service Manual「Structuring forms」（https://www.gov.uk/service-manual/design/form-structure 、2016 公開、2018 更新） | 原典を読んだ（2026-11-14 に「Start with one thing per page」の節を確認） | 入力を複数のページに分け、1ページに1つのことだけを置くところから始める | 入力の画面に限らず、管理面の画面全体に「1画面1タスク」として広げ、分けるしるし（目的を一文で言えない、保存の対象があいまい）を足した |
| 4. 画面ごとの仕様を書く（エラーの後の次の行動、取り消せない操作の確かめ） | ユーザビリティの10の原則 | Jakob Nielsen「10 Usability Heuristics for User Interface Design」Nielsen Norman Group、1994（2024 見直し。https://www.nngroup.com/articles/ten-usability-heuristics/ ） | 原典を読んだ（2026-11-14 に「Error Prevention」と「Help Users Recognize, Diagnose, and Recover from Errors」の項を確認） | 誤りを起こさない作り（確かめ、押せなくする）と、誤りの後に何が起きたかと直し方を伝えることを分けて扱う | 原則を、業務規則ごとの画面の制御（不可／警告／確認／非表示）と、エラーの文言を設計の判断で指す決まりに置き換えた |

## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 判断、入力情報、受入条件の正本は完了条件の一覧に置き、画面は割り当てるだけにする。欠けは画面の側で聞き直さず、上流へ返す | 画面の側で決めると、同じことが要件と画面の2か所に書かれ、片方だけが直されて食い違うため | 画面の設計の後に、要件と画面で食い違った項目の数と、画面の側だけで決めて後から要件に書き戻した件数を数え、返し方を見直す |
| 業務規則から画面の制御への置き換えを、不可・警告・確認・非表示の4つに閉じ、仮説・未確定の規則は「決定待ち」にする | 制御の種類が自由だと、テストケースと受入の試験が何を確かめるかが決まらず、仮説の規則が見た目を通って確定したように扱われるため | 4つで表せずに例外を書いた件数と、決定待ちが規則の確定の前に実装へ流れた件数を数え、語の数と関門を見直す |
| 画面で隠すこと、押せなくすることを守りとみなさず、守りが認可の判断に無ければ返す | 画面の制御だけで済ませると、画面を通らない呼び出しで規則が破られるため | レビューと試験で、画面の制御はあるのにサーバー側の守りが無かった件数を数え、返す条件を見直す |
| エラーと許可は設計の判断の識別子＋行の鍵で指し、画面には出し方と次の行動だけを書く | 文言や許可の表を写すと、設計の判断が直ったときに画面が古いまま残るため | 設計の判断の変更の後に、画面の設計に古い文言や許可が残っていた件数を数え、指し方を見直す |
| 既存の画面を踏襲するときは、殻・配置・文言・操作ごとの範囲の表を人と合意してから差分だけを設計し、値は今の実装から写す | 踏襲の範囲があいまいだと、変えるつもりの無い所が変わったり、推測の値で描いたりするため | 踏襲の合意の後に、範囲の外の変更として差し戻された件数と、値が実装と違っていた件数を数え、表の粒度を見直す |
| 画面と要件・受入条件の結びつきは画面の設計に一か所だけ置き、完了条件の一覧の「適用する画面」は範囲の宣言として残す | 結びつきを両側に書くと、片方だけが直されて食い違うため。画面の識別子は画面の設計が振るので、要件の側からは指せない時期がある | 網羅の点検で、要件の側の画面の名前と画面の設計の結びつきが食い違った件数を数え、宣言の書き方を見直す |
| 論点になる見た目（列の数、状態の色、重なりの順、最初の表示で見える範囲）は、受入条件の案として上流へ返す | 見た目の論点を画面の設計だけに置くと、試験で確かめられず、ワイヤーとの食い違いを判定する正本が無いため | 受入の試験や受入の証拠で、見た目の食い違いを判定できなかった件数を数え、返す見た目の範囲を見直す |
