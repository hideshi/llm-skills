# 新規開発

新しい機能を作るときの組み合わせ。規模に応じて設計と作業の分割を足し、要件・受入条件・テストケース・作業を識別子で結んで、抜け漏れを防ぐ。各工程の中身は単位に任せ、ここでは順序、引き渡す型、振り分けだけを決める。

## 工程

| 識別子 | 工程 | 単位 | 必須 | 受け取る型 | 渡す型 |
|---|---|---|---|---|---|
| `sizing` | 受付と規模の判定 | `dev-change-sizing` | 必須 | 完了条件の一覧（あれば）、原典の参照 | 規模の判定 |
| `req` | 要件を書く | `dev-requirements` | 必須 | 規模の判定、原典の参照、ドメインモデル、業務規則の一覧、一次情報の記録、確認事項の記録、完了条件の一覧（決まった要件を受けるとき、戻って直すとき）、画面の設計（`screen` から戻ったとき） | 完了条件の一覧、確認事項の記録、問題台帳 |
| `primary-source` | 一次情報を調べる | `dev-external-domain-survey`（つなぐ相手の仕様、業界団体の規格や標準）、`dev-statutory-grounding`（公的な規則） | 条件付き（規模の判定の「仕様化の契機」の一次情報に当たる。または設計で新しく外部に依存すると分かった） | 原典の参照、業務規則の一覧、ドメインモデル | 一次情報の記録、業務規則の一覧、確認事項の記録 |
| `domain-model` | モデルを作る | `dev-domain-model` | 条件付き（新しい概念・業務規則・状態・区分がある。または、今回の範囲で根拠にする業務規則に仮説・未確定がある（一次情報から推定したものを含む）） | 原典の参照、規模の判定、一次情報の記録、業務規則の一覧、確認事項の記録 | ドメインモデル、業務規則の一覧、確認事項の記録、問題台帳 |
| `req-ask` | 人に確かめる | （人） | 条件付き（今回の範囲に、仮説か未確定の業務規則がある。または、要件の確認事項に今回の範囲の未回答がある） | 確認事項の記録 | 確認事項の記録 |
| `screen` | 画面を設計する | `dev-screen-design` | 条件付き（画面の契機がある。定義は遷移の表の前書き） | 完了条件の一覧、原典の参照、ドメインモデル、業務規則の一覧、設計の判断、確認事項の記録、画面の設計（直すとき） | 画面の設計 |
| `wireframe` | ワイヤーを作る | `dev-wireframe` | 条件付き（人に画面を見せて確かめたい。依頼者が求めた、または判断を伴うユースケースがある） | 画面の設計、設計の判断、原典の参照 | ワイヤー |
| `screen-ok` | 画面の設計を採る | （人） | 条件付き（`screen` を行った。ワイヤーがあれば見せ、無ければ画面の設計を見せる） | 画面の設計、ワイヤー（`wireframe` を行ったとき） | 画面の設計、原典の参照 |
| `acceptance` | 受入条件を確かめる | `dev-acceptance-e2e` | 条件付き（画面をまたぐ流れがある、または受入条件が合否を判定できる形か疑わしい） | 完了条件の一覧、原典の参照 | 完了条件の一覧、テストケース表 |
| `design` | 設計する | `dev-responsibility-design`、`dev-authorization-design`（誰が何をできるかや、データの分離が変わる）、`dev-api-contract`（API・CLI・メッセージの契約を足す・変える）、`dev-error-design`（失敗のしかたや見せるエラーが増える・変わる）、`dev-data-design`（保存の構造、制約、同時更新が変わる）、`dev-async-execution-design`（ジョブ・キュー・バッチがある）、`dev-cross-system-design`（外部サービスや別のシステムとつながる）、`dev-logging-design`（ログの決まりを新しく決める・変える）、`dev-entry-safety-design`（入口の守りや応答の安全の設定の方式を新しく決める・変える）、`dev-agent-contract`（AI エージェントが呼ぶ道具として機能を公開する）、`dev-design-system`（画面で使う部品やトークンを足す・変える）、`dev-message-design`（人が読む画面の外の文面や帳票（メール、通知、SMS、帳票）を足す・変える） | 条件付き（規模の判定が、その観点を要るとした。または、部品やトークンの共通の定義に関わる画面への意見が残っている（デザインシステム）。通常の道では責務の配置を必ず行う） | 完了条件の一覧、原典の参照、業務規則の一覧、ドメインモデル、一次情報の記録、設計の判断（先に使った単位のもの）、画面の設計（`screen` を行ったとき）、個人情報の台帳（あれば） | 設計の判断 |
| `formal-check` | モデルで検査する | `dev-formal-model-check` | 条件付き（人が検査を依頼した） | 原典の参照、設計の判断 | 検証の記録、問題台帳 |
| `design-ok` | 設計を承認する | （人） | 条件付き（設計の判断がある。決定待ちを決め、担当の案を採るかを決める） | 設計の判断、問題台帳（`formal-check` を行ったとき）、検証の記録（`formal-check` を行ったとき） | 設計の判断 |
| `sizing-after-design` | 規模を判定し直す | `dev-change-sizing` | 条件付き（設計の判断がある） | 設計の判断、完了条件の一覧 | 規模の判定 |
| `test-cases` | テストケースを導く | `dev-test-case-design` | 必須 | 完了条件の一覧、原典の参照、設計の判断、業務規則の一覧 | テストケース表、追跡表 |
| `tasks` | 作業に分ける | `dev-task-breakdown` | 条件付き（通常の道） | 完了条件の一覧、テストケース表、設計の判断 | 作業の一覧、追跡表 |
| `implement` | 実装する | `dev-test-first`（既定）。外すときは（実装）。作業ごとの終わりに `dev-diff-check`（通常の道では必ず、軽い道では設計の判断があるか、差分が業務規則に触れるとき） | 条件付き（テストを先に書くのは既定で、外すのは、完了条件の一覧に理由と代わりの確かめ方を書いたときだけ。差分の点検の条件は単位の欄のとおり） | 完了条件の一覧、テストケース表、作業の一覧、設計の判断、業務規則の一覧、ドメインモデル、原典の参照 | 変更の事実、検証の記録、方針外の課題の記録、完了の主張、作業の一覧 |
| `sizing-after-implement` | 規模を判定し直す | `dev-change-sizing` | 必須 | 変更の事実、作業の一覧 | 規模の判定 |
| `ops-artifacts` | 運用の成果物と利用者向けの文書を作る | `dev-production-procedure`（運用の作業「本番の手順」が当たる）、`dev-credential-catalog`（続けて使う文書の「秘密の項目」が当たる）、`dev-personal-info-ledger`（「個人情報の扱い」が当たる）、`dev-user-manual`（「操作マニュアル」が当たる） | 条件付き（`sizing-after-implement` の規模の判定が、どれかに当てた） | 規模の判定、変更の事実、原典の参照、検証の記録、設計の判断、システムの地図、秘密の目録、個人情報の台帳、確認事項の記録、問題台帳（目録の事実確認の答えを反映するとき）、本番の手順（直すとき）、画面の設計、テストケース表、完了条件の一覧、操作マニュアル（直すとき） | 本番の手順、検証の記録、秘密の目録、問題台帳、個人情報の台帳、確認事項の記録、操作マニュアル |
| `ops-ok` | 運用の成果物と利用者向けの文書を承認する | （人） | 条件付き（`ops-artifacts` を行った。台帳は運営者が承認する。目録の事実確認にもここで答える。操作マニュアルの台帳の「未判断」の行もここで決める） | 本番の手順、秘密の目録、個人情報の台帳、検証の記録、問題台帳、操作マニュアル | 本番の手順、秘密の目録、個人情報の台帳、問題台帳、操作マニュアル |
| `evidence` | 受入の証拠を確かめる | `dev-evidence-check` | 条件付き（画面・録画・帳票が完了条件の証拠になる） | 検証の記録、テストケース表、完了条件の一覧、変更の事実 | 受入の証拠、検証の記録 |
| `review-round` | レビュー | `dev-review-brief`（依頼文を書く）→ `dev-review-conduct`（別の担当がレビューする） | 必須 | 変更の事実、原典の参照、検証の記録、レビュー結果（再依頼のとき） | レビュー依頼文、レビュー結果、方針外の課題の記録 |
| `audit` | 完了前に監査する | `dev-completion-audit` | 必須 | 完了の主張、完了条件の一覧、検証の記録、レビュー結果、方針外の課題の記録、作業の一覧（通常の道）、追跡表（通常の道）、テストケース表、設計の判断、規模の判定、業務規則の一覧（あれば）、ドメインモデル（あれば）、受入の証拠（`evidence` を行ったとき）、画面の設計（`screen` を行ったとき）、変更の事実、原典の参照（運用の成果物の所在と承認の記録） | 作業状態の控え、完了判定 |
| `final-ok` | 最終確認 | （人） | 必須 | 完了判定 | — |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。「原典の参照」は、この組み合わせの外（依頼、業務の規則、案件の既定の決定）から受け取る。

案件が続けて使う地図、秘密の目録、個人情報の台帳、本番の手順、操作マニュアルがあれば、外から受け取って `ops-artifacts` で更新する。

外から受け取る型: 原典の参照、システムの地図、秘密の目録、個人情報の台帳、本番の手順、操作マニュアル
外へ渡す型: 作業状態の控え、方針外の課題の記録、本番の手順、秘密の目録、個人情報の台帳、問題台帳、操作マニュアル

### 遷移

`primary-source`・`domain-model`・`req-ask` は、工程 `req`（要件を書く）から寄り道して `req` に戻る。`screen`・`wireframe`・`screen-ok` は本線で、要件を書き終えた後に通る。表の「画面の契機」は、規模の判定が画面の設計に当てたか、完了条件の一覧の「適用する画面」に、画面の設計が要る画面（型の一覧の「仕様化の契機」の画面の設計に当たる画面。「未割当」と書いた画面も含む）が書かれていること。「画面が済んでいる」は、画面の契機が無いか、画面の設計が今の要件に追随して `screen-ok` で採られていること。「設計から戻った画面」は、`design` → `screen` の遷移で直しに入った画面（途中で `req` を経ても変わらない。`design` → `req` → `screen` で初めて作る画面は含まない）。

| 元 | 先 | 条件 |
|---|---|---|
| `sizing` | `req` | — |
| `req` | `primary-source` | 一次情報の確かめが要り、まだ調べていない |
| `req` | `domain-model` | 新しい概念・業務規則・状態・区分があり、モデルをまだ作っていない。または、根拠にする業務規則に仮説・未確定がある |
| `req` | `req-ask` | 要件の確認事項に、今回の範囲の未回答がある |
| `primary-source` | `req` | — |
| `domain-model` | `req` | 今回の範囲に仮説・未確定が残っていない |
| `domain-model` | `req-ask` | 今回の範囲に仮説か未確定がある |
| `req-ask` | `req` | 回答の戻し先が要件か画面 |
| `req-ask` | `domain-model` | 回答の戻し先がモデル（業務規則の回答は、確定・変更・却下・一部・保留のどれでも `domain-model` で一覧に反映する） |
| `req-ask` | `ops-artifacts` | 回答の戻し先が台帳（`ops-artifacts` から確かめに来た） |
| `req` | `screen` | 要件を書き終え、画面が済んでいない |
| `req` | `acceptance` | 要件を書き終え、画面が済んでいて、画面をまたぐ流れがある、または受入条件が判定できる形か疑わしい |
| `req` | `design` | 要件を書き終え、画面が済んでいて、`acceptance` を行わず、設計の観点が要る |
| `req` | `test-cases` | 要件を書き終え、画面が済んでいて、`acceptance` も設計も要らない |
| `screen` | `req` | 受入条件の案か確認事項の候補を返した、または入力情報か判断が欠けている（`req` で採否を記録し、処理済みにする） |
| `screen` | `wireframe` | 人に画面を見せて確かめたい（依頼者が求めた、または判断を伴うユースケースがある） |
| `screen` | `screen-ok` | ワイヤーを作らない |
| `wireframe` | `screen` | 画面の設計への疑問を、変える案として返した（画面の設計を直してから作り直す） |
| `wireframe` | `screen-ok` | — |
| `screen-ok` | `req` | 意見がある、または採らない（`req` で確認事項の記録に行にして振り分ける。戻し先がモデルなら `req` から `domain-model`、画面なら `req` から `screen`。部品やトークンの共通の定義に関わる見せ方は、戻し先を画面のまま備考にそう書き、`design` のデザインシステムの単位で扱う） |
| `screen-ok` | `design` | 意見が無く、人が採り、設計から戻った画面だった（ほかの条件より先に見る）。または、設計から戻った画面ではなく、`acceptance` を行わず、設計の観点が要る |
| `screen-ok` | `acceptance` | 意見が無く、人が採り、設計から戻った画面ではなく、`req` の後と同じ条件で `acceptance` に当たる |
| `screen-ok` | `test-cases` | 意見が無く、人が採り、設計から戻った画面ではなく、`acceptance` も設計も要らない |
| `acceptance` | `req` | 受入条件の書き直しの案を採る（`req` で完了条件の一覧に反映する） |
| `acceptance` | `design` | 設計の観点が要る |
| `acceptance` | `test-cases` | 設計の観点が要らない |
| `design` | `req` | 設計で新しく外部に依存すると分かった（`req` から `primary-source` を通す）。または、完了条件に無い業務の決定（公開の可否、許す主体、守らない範囲など）が要ると分かった（`req` で人に確かめて反映する）。または、画面の契機が無いのに画面が要ると分かった（`req` で適用する画面に書き足し、`screen` へ進む） |
| `design` | `screen` | 画面の契機があり、認可・エラー・デザインシステム・文面の判断で、画面の制御・表示・部品・誘導が変わり、まだ画面の設計に反映していない |
| `design` | `formal-check` | 人がモデルの検査を依頼した |
| `design` | `design-ok` | — |
| `formal-check` | `design-ok` | — |
| `design-ok` | `design` | 反例を受けて設計を直す。または、決定待ちの決定や人の直しの求めで設計を直す（画面に及ぶものを含む） |
| `design-ok` | `sizing-after-design` | — |
| `sizing-after-design` | `test-cases` | — |
| `test-cases` | `tasks` | 通常の道 |
| `test-cases` | `implement` | 軽い道 |
| `tasks` | `implement` | — |
| `implement` | `design` | 軽い道の実装中に作業が2つ以上と分かり、設計の観点が要る。または、差分の点検で、設計の判断を変えるべきと分かり、依頼者が判断の見直しを決めた |
| `implement` | `tasks` | 軽い道の実装中に作業が2つ以上と分かり、設計の観点は要らない |
| `implement` | `sizing-after-implement` | 実装を終えた |
| `sizing-after-implement` | `req` | 承認済みの完了条件を承認し直す必要がある |
| `sizing-after-implement` | `ops-artifacts` | 運用の作業「本番の手順」か、続けて使う文書の「秘密の項目」「個人情報の扱い」「操作マニュアル」に当たる |
| `sizing-after-implement` | `evidence` | どれにも当たらず、画面・録画・帳票が証拠になる |
| `sizing-after-implement` | `review-round` | どれにも当たらず、証拠が要らない |
| `ops-artifacts` | `req-ask` | 台帳の確認事項に、今回の範囲の未回答がある |
| `ops-artifacts` | `req` | 完了条件を変える業務の決定（目的、保持の期間など）が要ると分かった |
| `ops-artifacts` | `implement` | 手元で流して、または画面を辿って、直す不具合が見つかった |
| `ops-artifacts` | `ops-ok` | — |
| `ops-ok` | `ops-artifacts` | 承認しない（直す）。または、操作マニュアルの台帳の「未判断」を「載せる」と決めた |
| `ops-ok` | `evidence` | 承認し、画面・録画・帳票が証拠になる |
| `ops-ok` | `review-round` | 承認し、証拠が要らない |
| `evidence` | `review-round` | — |
| `review-round` | `implement` | 変更要求（人の決定を待ったときは、その後） |
| `review-round` | `audit` | 承認 |
| `audit` | `implement` | 監査の判定が「止める」 |
| `audit` | `audit` | 監査の判定が「条件付き」。示された手順の後にやり直す |
| `audit` | `final-ok` | 監査の判定が「進めてよい」 |

完了条件の一覧には、項目ごとの識別子を書き、道はどの規模の判定に従うかを指す（道の正本は最新の規模の判定）。

## 振り分け

一言の依頼から、どの工程に入るかを決める。迷ったら、依頼者に一度だけ聞く。

| 依頼の言い方・状況 | 入る工程 |
|---|---|
| 「新しい機能を作りたい」「新規開発を進めて」 | `sizing` から |
| 「要件は決まったので設計して」 | `sizing`（完了条件の一覧を入力に）→ `req`（受けて、型と「要件を終えるときの検査」を確かめるだけ）→ `design` |
| 「要望から要件を起こして」「受入条件を書いて」 | `req` |
| 「ドメインモデルを作って」「業務の用語と規則を整理して」 | `domain-model` |
| 「この外部 API の仕様を調べて」「この計算が法令どおりか確かめて」 | `primary-source` |
| 「画面設計をして」「画面一覧を作って」「画面遷移を決めて」 | `screen`（完了条件の一覧が無ければ `sizing` から） |
| 「ワイヤーを作って」「画面のたたき台を見せられる形にして」 | `wireframe`（画面の設計が無ければ `screen` から） |
| 「デザインシステムを作って」「トークンを整理して」「この部品の仕様を決めて」 | `design`（デザインシステム。完了条件の一覧が無ければ `sizing` から） |
| 「タスクに分けて」「作業計画を立てて」 | `tasks`（テストケース表が無く通常の道なら `test-cases` を先に） |
| 「この機能のテストを洗い出して」 | `test-cases` |
| 「テストを先に書いて実装して」 | `implement` |
| 「コミットの前に差分を点検して」「この作業の実装が設計どおりか確かめて」 | `implement`（作業の終わりの点検） |
| 「形式手法で確かめて」 | `formal-check` |
| 「誰がこの操作をできるか決めて」「他人のデータが見えないようにしたい」 | `design`（認可。完了条件の一覧が無ければ `sizing` から） |
| 「アプリに MCP サーバーを組み込みたい」 | `sizing` から（`design` で認可とエージェント向けの契約） |
| 「この機能の本番の手順を作って」「個人情報の台帳も直して」 | `ops-artifacts`（`sizing-after-implement` の判定がまだなら `sizing-after-implement` から） |
| 「直したのでレビューして」 | `review-round` |
| 「もう閉じていい？」 | `audit` |

## 工程の間の決まり

- 業務規則が変わるときは、モデルを先に直し（`domain-model`）、要件はそれを根拠に書く（`req`）。了承は、画面ではなく規則の形で取る。
- 確かさが仮説・未確定の業務規則を、要件と設計の根拠にしない。一次情報から推定した規則も仮説なので、根拠にするなら `domain-model` と `req-ask` を通して確定させる。工程 `req`（要件を書く）を終える前に型の一覧の「仕様化を終えるときの検査」を、工程 `design`（設計する）を終える前に「設計を終えるときの検査」を通す。
- 業務規則についての回答は、どの結果（確定、変更、却下、一部、保留）でも `domain-model` に戻して一覧とモデルに反映する。要件や画面についての回答は `req` で反映する。
- 工程 `acceptance`（受入条件を確かめる）が受入条件の書き直しの案を返し、依頼者が採ったら、`req` に戻って完了条件の一覧に反映する（識別子は変えない）。
- 画面の工程（`screen`・`wireframe`・`screen-ok`）には、`req` で要件を書き終え、「仕様化を終えるときの検査」を通した後にだけ入る。仮説・未確定の業務規則を残したまま入らない。ワイヤーの単位が持つ仮説の箇所の印は、この組み合わせの中では使わない。
- 要件、回答、設計で、途中から画面が要ると分かったら、`req` で完了条件の一覧の「適用する画面」に書き足して画面の契機を立て、`screen` へ進む。規模の判定は、次の判定し直しでこの契機を拾う。
- 画面の設計を人が採るのは `screen-ok`。`screen` の後は、ワイヤーを作っても作らなくても、必ず `screen-ok` を通る。設計から戻って画面を直したときは、直した所だけを採り直す。採った後に画面の設計を変えたら、その所の採用は無効になり、直した所に結ばれた受入条件とテストケースを `test-cases` で確かめ直す。
- `req` に戻って完了条件の一覧を変えたら、変えた項目に結ばれた画面の採用は無効になり、`screen`・`screen-ok` を通り直す。項目を変えなかったら、採用は残る。
- `screen-ok` で出た意見は、どれも `req` に戻して確認事項の記録の行にし、振り分ける（規則はモデル、流れは要件、見せ方は画面）。見せ方のうち部品やトークンの共通の定義に関わるものは、戻し先を画面のまま備考にそう書き、`design` のデザインシステムの単位で扱う。この意見が確認事項の記録に残っていれば、規模の判定を待たずに、デザインシステムの観点が要るものとして `design` へ進む。規模の判定は、次の判定し直しでこれを拾う。画面の設計やワイヤーだけで直さない。同じ論点で2回続けて合意できなければ、人に戻す。
- `screen-ok` で人が採った版の所在を、原典の参照として下流（`acceptance`、`design`、`test-cases`）に渡す。受入の証拠（`evidence`）は、受入条件とテストケースを通して画面に結ばれる。
- 設計（`design`）の認可・エラー・デザインシステムの判断で画面が変わるときは、`design` → `screen` → `screen-ok` を通ってから `design-ok` へ進む。`design-ok` の結果（反例、決定待ちの決定、人の直しの求め）で画面が変わるときは、`design-ok` → `design` → `screen` と通る。
- 実装や差分の点検で画面の設計を変えるべき（画面の設計がまだ無い場合を含む）と分かったら、依頼者が決める。変えるなら、承認し直しとして `req` に戻ってから `screen` へ進む。`screen-ok` は直した所について必ず通る。ワイヤーで見せ直すかは、依頼者が決める。
- 設計の判断に人の決定待ちが残っている作業は、始めない。決定待ち以外の作業は止めない。
- 工程 `implement`（実装する）の差分の点検（`dev-diff-check`）は、実装した側の点検で、レビュー（`review-round`）の代わりにしない。高の指摘が残っている間は、`sizing-after-implement`・`ops-artifacts`・`ops-ok`・`evidence`・`review-round`・`audit`・`final-ok` のどれにも進まない。
- 差分の点検の記録のうち、レビュー依頼文（`review-round`）に写すのは、点検した範囲と見なかった観点だけ。観点ごとの「問題なし」と、指摘と直しの経緯は写さない。
- 差分の点検で、人が採った設計の判断と違う実装が見つかったら、実装を判断に合わせる。判断を変えるべきなら作業を止めて依頼者に戻し、見直すと決まったら `design` に戻って、`design-ok` で承認し直す。
- レビュー（`review-round`）や監査（`audit`）から `implement` に戻って直したときは、直した差分に絞って点検をやり直す。
- 実装は、テストを先に書くのが既定。外すのは、完了条件の一覧に範囲、理由、代わりの確かめ方が書かれた部分だけ。実装の途中で外したくなったら、完了条件の一覧に書き足して依頼者に確かめてから外す。外しても、受入条件ごとに結んだテストケースが通ることは求める。
- `design` の単位は、要るものを既定で次の順に使う: 責務の配置 → 認可 → システム間の連携 → データ → エラー → デザインシステム → 非同期の実行 → 文面 → ログ → 呼ばれる契約 → 応答と入口の安全 → エージェント向けの契約。後の単位が前の判断の前提を変えたら、前の判断を直し、その承認の状態を「担当の案」に戻す。
- 道が軽い道から通常の道に変わったら（`sizing-after-design` で変わった、作業に分けて2つ以上になった、軽い道の実装中に作業が2つ以上と分かった）、実装を止め、要る観点の設計（`design`）と `tasks` を通す。
- 工程 `sizing-after-implement`（規模を判定し直す）の判定で、承認済みの完了条件を承認し直す必要が出たら、実装を止めて `req` に戻る。道が変わったのに作業の一覧が無い、要る観点に設計の判断が無い、と出たら、`design` か `tasks` に戻る。
- モデルの検査は、規模の判定が候補に挙げても、人が依頼するまで始めない。反例の扱いは `design-ok` で人が決め、設計を直すなら `design` に戻る。
- 受入の証拠（`evidence`）は、確定してからレビュー（`review-round`）と監査（`audit`）に回す。確定の後に関係する所を変えたら、`evidence` をやり直す。
- 運用の成果物（`ops-artifacts`）は、規模の判定（`sizing-after-implement`）が当てたものだけを作り、受入の証拠（`evidence`）より前に作る（`ops-artifacts` から要件に戻ったときに、確定した証拠を無駄にしないため）。本番の手順、秘密の目録、個人情報の台帳、操作マニュアルの各単位の安全の決まり（本番に接続しない、本番で辿らない、値を読まない、法的な判断をしない）は、単位の手順に従う。
- `ops-ok` の承認は版に付き、「レビューに出してよい版の確定」として扱う。手順を承認することは、本番で流してよいという判断とは別。台帳は運営者が承認する。承認の後に中身が変わったら（`review-round`・`audit` からの戻り、台帳の回答、手元で流した後の直し）、`ops-artifacts`・`ops-ok` をやり直してから、直した所に絞ってレビューする。
- `ops-artifacts` で手元で流して不具合が見つかったら、`implement` に戻って直し、`sizing-after-implement` から通し直す。
- `ops-artifacts` で分かった決定のうち、完了条件を変えるもの（目的、保持の期間など）だけを `req` に戻して人に確かめる。手順の欄を埋めるだけの決定（止める時間帯、連絡、省く予行）は、`ops-ok` で人が決める。
- 台帳の確認事項は `req-ask` で確かめ、回答の戻し先が台帳なら `ops-artifacts` に戻る（戻し先が要件なら `req` で反映する）。運営者の回答が期限つきで保留になったら、その行を「未確定」のまま `ops-ok` に出してよい。未確定の行が残ることは、承認の記録と完了の主張に書く。
- 目録の事実確認（持ち主、用途、保管先）には、`ops-ok` で人が答える。答えで目録を直すなら `ops-ok` → `ops-artifacts` で直して承認し直す。直書きの秘密の所在は、`ops-ok` を待たずにすぐ人に伝える。
- レビュー（`review-round`）の変更要求や監査（`audit`）の「止める」が運用の成果物だけに及ぶときは、`implement` でコードを変えずに `sizing-after-implement` から通し、`ops-artifacts` で直す。
- 運用の成果物は、変更の事実に含め、レビュー（`review-round`）には原典の参照として所在で渡す。監査（`audit`）は、当たる運用の作業と文書に成果物と承認があるかを確かめる。本番での作業そのものは人が流し、この組み合わせに含めない。
- E2E の範囲を縮めることは、人の承認を待つ。

レビューと監査（`review-round`・`audit`・`final-ok`）の決まり:

- 依頼文を書く担当と、レビューする担当を分ける。依頼文を書いたセッションで、そのままレビューしない。レビューは別のモデル、別のセッション、または人に渡す。
- レビューの判定が「判断を人へ戻す」なら、人の決定を待つ。
- 「変更要求」なら、`implement` に戻って直し、運用の成果物に及べば `ops-artifacts`・`ops-ok` を、証拠が変われば `evidence` を通してから、直した所に絞って `review-round` をやり直す。同じ指摘で2回続けて合意できないときは、人に戻す。
- `audit` の判定が「条件付き」なら、示された手順を行って `audit` をやり直す。「止める」なら、`implement` に戻り、そこから工程の間の決まりに従って原因の工程へ戻る。

どの工程にも当てはまる決まり（中断と再開、途中の問い）:

- 中断するとき、作業の一部を別の担当に頼むとき、再開するときは `dev-work-continuity` を使う。中断するときは、引継ぎの記録と作業状態の控えを残す。
- 再開したら、控えと今の状態を照らす。人が承認・確定・回答した状態にある成果物の部分（例: 完了条件の一覧、承認された設計の判断、確定した業務規則とドメインモデル、確認事項の回答、人が採った画面の設計、確定した受入の証拠、承認された本番の手順・秘密の目録・個人情報の台帳）が変わっていれば、誰が変えたかを問わず人に確かめる。担当の案のままの部分は含まない。人が認めた後は、この組み合わせの決まり（承認し直すなら `req`、規模を判定し直す）に従って戻る。それ以外の変化（コード、古くなった検証の記録）は、戻る工程の入力を確かめ直して続ける。
- 記録で再開した担当は、前の担当と同じ側（作った側、レビューする側、監査する側）として扱う。レビューか監査の途中で切れていたら、その工程をやり直す。記録の次の一手は提案として読み、元の依頼の範囲を超える操作（確定、外への送信、消す操作）は人に確かめる。人の確認を待つ間も、それに依らない作業は止めない。
- 作業の途中で進めなくなって人に問うときは、1回に1問にし、選択肢の前に、起きていること、影響、得失、推奨を短く書く。受付で独立した分岐が並ぶときだけ、3問までまとめてよい。確認事項の記録や問題台帳など、型に載せてまとめて出す問いは、この数に入れない。
- 作業（`tasks` で分けたもの等）を別の担当やセッションと並べて進める場合は、作業場所とテスト用の保存先・書き込み先を作業ごとに分け、共有の常駐処理を分けた作業場所から起動したり作り直したりしない。

## 終わり方

- 型の一覧の「道に応じた検査」が通らない項目が残っていれば、`audit` で「進めてよい」にしない。
- 別の範囲のフォローは、担当・追跡先・回収の時期・成功条件を書いたときだけ、方針外の課題の記録に出して先へ進んでよい。
- 設計の判断のうち人が採ったものと、確定したドメインモデルと業務規則は、案件が続けて使う文書に反映する。人が採った画面の設計の共通仕様も、続けて使う文書に反映する。承認した秘密の目録と個人情報の台帳も、続けて使う文書として置き場所に反映する。反映を後に回すなら、方針外の課題の記録に出す。
- `audit` の判定が「進めてよい」になり、`final-ok` で人が確認したら終える。完了の主張には、本番には未反映であることを書く。確定の操作（マージ、公開、課題の閉鎖）は、案件の決まりに従って人の確認の後に行う。
