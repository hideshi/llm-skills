# Go の testing

本文の手順（テストする境界、正しい理由で落ちたかの確かめ、失敗を隠さない）を、Go の標準の `testing` で行うときの資料。

- 確かめた版: Go 1.27.1
- 確かめた日: 2026-11-12
- 【実行】は小さなパッケージを実際に動かして確かめたこと、【資料】は公式の資料で読んだだけのこと

## 表を元にした一括のテスト

テストケース表の行を、そのまま表にして回す（【実行】）。

```go
func TestTotal(t *testing.T) {
	cases := []struct {
		name string // テストケース表の識別子を入れると、結果と表を突き合わせやすい
		in   []int
		want int
	}{
		{"TC-01 空", nil, 0},
		{"TC-02 二件", []int{1, 2}, 3},
		{"TC-03 値引きの境界", []int{10000}, 9000},
	}
	for _, tc := range cases {
		t.Run(tc.name, func(t *testing.T) {
			if got := Total(tc.in); got != tc.want {
				t.Errorf("Total(%v) = %d, want %d", tc.in, got, tc.want)
			}
		})
	}
}
```

- 失敗の文には、入力と、得た値と、期待した値を入れる（どの行がなぜ落ちたかが、出力だけで分かる）。
- 【資料】`t.Parallel()` を使うときは、表の変数を各試験の中で使っても安全か確かめる（Go 1.22 から、繰り返しの変数は回ごとに別になった）。

## 正しい理由で落ちたかを確かめる

| 確かめること | コマンド（【実行】） |
|---|---|
| 書いた試験が本当に走ったか | `go test -count=1 -run '^TestTotal$' -v ./...` の `=== RUN` の行を、書いた試験と行（`TestTotal/TC-03_値引きの境界` のように、空白は `_` になる）で突き合わせる |
| 狙った理由で落ちたか | `--- FAIL` の行の下の、失敗の文を読む。ビルドの誤り（`[build failed]`）や準備の失敗で落ちたのは、RED と数えない |
| 件数 | `go test -count=1 -json ./...` の `"Action":"pass"`・`"fail"`・`"skip"` を数える。親の試験（`TestTotal`）も1件と数えられるので、表の行の件数と比べるときは、名前に `/` を含むもの（下位の試験）だけを数える |
| 試験の名前の一覧 | `go test -list '.*' ./...`。上の階層の試験だけが出て、表の行（下位の試験）は出ない |

## 落とし穴

- **絞り込みの名前を打ち間違えると、何も走らずに成功する**（【実行】）。`go test -run 'TestTotl'` は `ok ... [no tests to run]` を出して終了コード0で終わる。RED を確かめるときも GREEN を確かめるときも、`-v` で `=== RUN` の行があることを見る。
- **skip は、`-v` を付けないと見えない**（【実行】）。`t.Skip` があっても、普段の出力は `ok` だけ。skip が無いことを確かめるには、`-v` の `--- SKIP` か、`-json` の `"Action":"skip"` を数える。本文の決まりどおり、承認の無い skip を残さない。
- **結果の使い回し**（【資料】）。同じ入力で通った包みは、次の回に `(cached)` として前の結果が出る。外部の状態に依存する試験や、確かめ直すときは `-count=1` を付ける。
- 【資料】並行の誤りは、`-race` を付けないと見つからない。共有の状態を触る処理の試験では付ける。
- 時刻や乱数は、関数の引数か差し替えられる値にして、試験で固定する。
