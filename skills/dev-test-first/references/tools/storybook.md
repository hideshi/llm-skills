# Storybook

本文の手順（先に落ちる試験を書く、走った件数が書いた件数と合うかを見る）を、Storybook の story を試験として使うときの資料。部品の仕様と story の対応の照らし方は、デザインシステムを定める側の資料にある。

- 確かめた版: Storybook 10.6.7（`storybook`、`@storybook/html-vite`）、Node 22.23、Chromium 150、Linux
- 確かめた日: 2026-11-14
- 【実行】は小さなカタログを実際に組み立てて確かめたこと、【資料】は公式の資料で読んだだけのこと
- 公式の資料: https://storybook.js.org/docs/writing-tests 、https://storybook.js.org/docs/writing-tests/integrations/vitest-addon 、https://storybook.js.org/docs/writing-tests/interaction-testing
- 同じ版の資料が、この群のほかの単位にもある（部品の仕様との照らし方、受入の証拠）。版を上げるときは、片方だけを直さない。

## 何が1件の試験になるか

- 【資料】story は、描けるかの試験（描くときに誤りが出たら落ちる）になる。`play` の関数があれば、同じ試験の中で、それも流れる。`play` の無い story は、描けるかしか確かめない。
- 【資料】どの story を試験にするかは札で決める。既定では `test` の札の付いた story だけが対象。`exclude` の札の story は流れず、結果の数にも入らない。`skip` の札の story は流れないが、結果の数には入る。両方に入っていれば `exclude` が勝つ。
- 【実行】組み立てた後の `index.json` で、story ごとの札（`test`、`play-fn` など）が見える。書いた story の数と、`test` の札の付いた数を突き合わせる。

## 先に落ちる試験を書く

- 操作の試験は `play` に書き、操作の後の結果を `expect` で確かめる。確かめの無い `play` は、描けるかの試験と同じ強さしか持たない。
- 【実行】`play` は、ブラウザで story を開いたときにも流れる（手元で開いて、`play` が付けた印が描いた要素に残ることを確かめた）。開いて見えたことを、試験が通った証拠にしない。試験として流した結果で確かめる。

## 流し方と件数

- 【資料】Vite を使う枠組みでは、Vitest の拡張で流す（`vitest --project=storybook`）。既定は、Playwright の Chromium をブラウザの形で使う。Vitest の CLI は既定で見張りの形になるので、記録を取るときは一回だけ流す形にする。
- 【資料】絞り込みや札が1件も当たらなかったときの扱いは、資料に書かれていない。流した件数が、書いた story のうち試験にするつもりの数と合うかを、毎回見る。
- 【資料】描いた結果の写し（HTML の比べ）は、見た目の比べではない。

## アクセシビリティの点検の結果を残す

この節は 2026-11-17 に、10.6 の資料（「Accessibility tests」https://storybook.js.org/docs/writing-tests/accessibility-testing 、「Vitest addon」、「Testing in CI」https://storybook.js.org/docs/writing-tests/in-ci ）で確かめた。Storybook は動かしていない。

- 部品のカタログにアクセシビリティの点検（axe-core による拡張）を組み込んでいれば、流した結果を検証の記録に残す。残すのは、部品と状態（story）ごとの結果の種類、道具と版、`parameters.a11y.test` の値、`globals.a11y.manual` の値、無効にしたルール（既定で無効の `region` を含む）、対象の版、結果をどこから取ったか（手元の UI か、CI か）。
- 【資料】資料が挙げる結果の区分は、UI のアクセシビリティのパネルの Violations、Passes、Incomplete の3つのタブで、当てはまらない（inapplicable）には触れていない。CI の出力から区分ごとの結果を取り出す方法は、資料に書かれていない。
- 【資料】`'todo'` では、CI にアクセシビリティの誤りも警告も出力も出ず、結果は手元で流したときの UI に警告として出る。`'error'` では、違反が UI と CLI/CI で試験の失敗になる。試験の失敗の出力には、失敗した story へのリンクが出ると書かれている（試験一般の話）。CI では、公開した Storybook の URL を `storybookUrl` に渡していなければ、リンクは手元の `localhost:6006` を指す。違反したルールなど、アクセシビリティの違反だと分かる中身が出るかは、書かれていない。
- 【資料】手元の UI で結果を見る道は2つある。story を開くと自動で点検が流れ、結果がアクセシビリティのパネルに出る。試験として流すには、試験のウィジェットで Accessibility のチェックを入れて流し、結果はサイドバーに出る。`globals.a11y.manual` が `true` の story は、開いても Vitest の拡張で流しても自動では点検されないが、パネルで手で流すことはできる。`region` のルールは、Storybook が既定で無効にしている。
- 取れた区分だけを、取れた区分として残す。取れなかった区分は「取れていない」と書き、空や「当てはまらない」に読み替えない。当てはまらないは、資料に取り方が無いので、取れなければ「取れていない」と書く。実行の誤りは区分と別に残す。
  - 手元で流すときは、どの道で流したか（story を開いた、パネルで手で流した、ウィジェットで流した）を書き、パネルから3つの区分を写す（写した日と story を書く）。
  - 設定が `'error'` で CI で流したときは、失敗の出力から、アクセシビリティの違反による失敗だと分かる診断（story、違反したルールなど）が取れたものだけを「違反」として残す。出力のリンクから story を開き、UI のパネルで確かめてもよい（リンクが開けなければ、同じ版を手元で開いて確かめ、開いた版を書く）。描く誤りや `play` の失敗と見分けられない失敗は、違反とせず、実行の誤りか、理由を見分けられなかった失敗として残す。通ったことだけでは区分は取れていない（違反が無いとは書かない）。
  - 設定が `'todo'` のまま CI で流した結果は、試験の成否しか無いので、どの区分も取れていないと書く。設定を変えたいときは、ここでは変えず、設定を決める側へ戻す。
- 結果を読んで仕分けるのは、アクセシビリティの点検の記録を作る仕事で、ここでは残すまで。設定（どの値にするか）は、デザインシステムを定める側の資料にある。

## 隔離

- 【実行】組み立ては一時の場所で、Node のメモリの上限と時間の上限を付けて流した。組み立てた物は、`127.0.0.1` だけで待ち受ける配信で開いた。
- story に本番のデータや資格情報を入れない。試験として流すときは、許した宛先以外への通信を止めて記録し、外部への送信が無いことを確かめる。
