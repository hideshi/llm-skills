# テストを先に書いて実装する

落ちるテストを書き（RED）、最小の実装で通し（GREEN）、整える（REFACTOR）。手順そのものより、「正しい理由で落ちたか」と「失敗を隠していないか」を確かめることに重きを置く。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 条件付き（新しい振る舞いを作るとき必須） | 何を満たせば終わりか |
| テストケース表 | 任意 | あれば、書くテストの一覧として使う。無ければ、完了条件の項目ごとに成功と違反のテストを最低1件ずつ置く |
| 不具合の報告 | 条件付き（不具合を直すとき必須） | 再現テストの出どころ |
| 回帰の基準 | 任意 | あれば、変更の前後で通す |
| 作業の一覧 | 任意 | あれば、担当する作業の終わりの条件と、結んだテストケースを使う |
| 設計の判断 | 任意 | 置き場所、共通化の方針、旧の撤去の条件に従う |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

完了条件の一覧も不具合の報告も無いときは、書き始めずに、何を満たせば終わりかを依頼者に聞く。

## 出力

| 型 | 中身の補足 |
|---|---|
| 変更の事実 | 実装とテストの差分 |
| 検証の記録 | RED が落ちた理由と件数の突き合わせ、GREEN、既存のテストの結果、テストする境界の取り決め |
| 方針外の課題の記録 | 承認を得た skip と解除の条件、見つけた似た箇所 |
| 完了の主張 | 承認を求める報告 |
| 作業の一覧 | 入力にあったときだけ。担当した作業の状態と、行った変更の事実を書き足して返す |

## 使わない場面

- 何をテストするかを洗い出す（テストケース表を作る、別の仕事）。
- 画面をまたぐ受入の試験のシナリオを設計する。
- 変更をレビューする、完了を判定する。

## 手順

### 1. テストする境界を決める

- 実装の前に、どの公開の境界（関数、操作、API など）で何を確かめれば正しさが言えるかを、1行ずつ決めて検証の記録に書く。内部の作りに合わせた境界を選ばない。
- 守るべき規則ごとに違反のテストを1件以上、起きるべき出来事ごとに成功のテストを1件以上置く。

### 2. RED: 正しい理由で落ちたかを確かめる

- 対象のテストが見つかって実行され、狙った理由（期待との不一致、狙った例外）で落ちたことを、実行されたテストの一覧と、書いたテストの件数の突き合わせで確かめる。準備の失敗や、テストが拾われていないことで「落ちた」ように見えるのを、RED と数えない。
- 絞り込みの名前を打ち間違えると、何も走らずに成功として終わる道具がある。GREEN でも、走った件数が書いた件数と合うかを見る。件数の数え方と道具ごとの落とし穴は、道具の資料（[Go の testing](references/tools/go-testing.md)、[Vitest](references/tools/vitest.md)）があれば読む。無ければ公式の資料で確かめる。
- 書く前から通るテストは、何も確かめていない疑いがある。期待か入力を見直す。
- 実装の一部を一時的に外して落ちることを確かめたときは、元に戻ったことを差分で確かめる。

### 3. GREEN: 最小の実装で通す

- 通すのに必要な分だけ書く。先回りの一般化はしない。
- 内側の境界から外側の境界へ進める。全部の層を一つの操作で細く通す骨格を先に作るのもよい。

### 4. REFACTOR: 整える

- 置き場所、名前、重複を整える。似ているだけで意味の違うものを共通化しない。
- 古い版を並べて残したなら、撤去の条件を書く。
- 整えた後も、全部のテストが通ることを確かめる。

### 5. 失敗を隠さない

- skip、テストの無効化、コメントアウトで落ちるテストを消さない。どうしても skip するときは、理由と解除の条件を書き、人か作業を頼んだ側の承認を得てから行い、方針外の課題の記録に残す。
- 2〜3回直しても通らないときは、方針が誤っていると見て止め、人に上げる。
- 既存の落ちているテストを直すときは、「テストを今の動きに合わせる」のか「製品の不具合を直す」のかを先に決める。理由の分からない期待値を、今の出力に合わせて書き換えない。

### 6. 不具合から入るとき

1. 症状を1文で書く。
2. 再現するテストを書き、落ちることを確かめる。
3. どの境界で再現するかで、原因の場所を絞る。
4. 仮説を、最小のログや表明で確かめる。
5. 直す。再現テストは、回帰のテストとして残す。
6. 既存のテストが壊れていないかと、同じ形の箇所がないかを見る。

### 7. 動かすときの決まり

- 試験は隔離した環境で動かす。本番のデータや資格情報を使わず、外部への送信は捕まえる。
- 時刻や乱数のように揺れる要素は、固定する。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- テストする境界の取り決めが、検証の記録にある。
- すべての新しいテストについて、RED で狙った理由で落ちたことと、GREEN で通ったことの記録がある。
- 既存のテストが全部通っているか、落ちているものに理由と扱いが書かれている。
- 承認の無い skip や無効化が無い。
