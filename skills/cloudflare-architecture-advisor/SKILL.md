# Cloudflare Architecture Advisor

`cloudflare-requirements-framing` の制約シートと、`cloudflare-product-survey` の裏取りの結果を入力に、Cloudflare の構成案を出すときに使う。

## 前提

- 制約シートが無い場合は、先に `cloudflare-requirements-framing` で作るよう促す。
- 構成案の前に、[向かない条件を見る観点](references/fit-checklist.md) を読む。
- 公式の [Reference Architecture Diagrams](https://developers.cloudflare.com/reference-architecture/diagrams/) に近い型があれば、それを土台にし、差分を書く。
- **製品を勧めるときは**、次のどちらかが必須:
  1. 今回の `cloudflare-product-survey` での裏取り
  2. 取得日付きの、利用側の案件の調査結果。使う前に、その製品の変更履歴に取得日より後の項目が無いかを見る
- 案件固有の秘密・本番の数値・成果物は、利用側の案件に置く。スキルのディレクトリには書き込まない。

## 進め方

三案に使う製品は、案を作るまで決まらない。裏取りと案作りを一巡させる。

1. 制約シートと裏取りの結果から、三案の素案を作る。
2. 素案で使う製品のうち、裏取りの済んでいないものを挙げ、`cloudflare-product-survey` で確かめる。
3. 観点の一覧の問いを三案のそれぞれに当て、案を確定する。
4. 確かめられなかった製品は「候補だが未確認」とし、決定を妨げる未確認事項として挙げる。モデルの記憶だけで本命を決めない。

## 提案の型

必ず次の三案を比べる（成り立たない案は「不採用の理由」を書く）:

| 案 | 意図 |
| :--- | :--- |
| **本命** | 制約を満たしつつ、運用と拡張のバランスが良い構成 |
| **軽量** | 構成要素を減らし、コスト・学習の負担・障害点を抑える |
| **拡張** | 将来の急増、多地域、高度な状態の扱いなどに備える |

各案に含める:

1. 使う Cloudflare 製品と役割、前提のプラン
2. 経路（要求の経路・データの経路）の説明（箇条書きか簡単な図）
3. トレードオフ（レイテンシ、コスト、運用、ベンダーへの依存、制限への当たり方）
4. 選んだ理由と、向かない条件（観点の一覧の問いへの答え）
5. 依存する出典（公式 URL と取得日）
6. **未確認で決定を妨げる項目**（あれば必須）

## 出力テンプレ

```markdown
# Cloudflare 構成の提案

- 作成日:
- 入力: 制約シート / 裏取りの結果
- 前提のプラン:

## 要約（1段落）

## 比較表
| 観点 | 本命 | 軽量 | 拡張 |

## 本命の構成
### 構成要素
### 経路
### 選んだ理由と、向かない条件
### 出典

## 軽量 / 拡張
（同様）

## 未確認のブロッカー
| 項目 | なぜ必要か | 次の手 |

## 推奨の次の手
```

## 完了条件

- 三案の比較と、本命の構成がある。
- 三案のそれぞれに、選んだ理由と、観点の一覧に照らした向かない条件が付いている（不採用の案は不採用の理由）。
- 推奨する製品に、公式の出典と取得日がある。
- 未確認のブロッカーが隠れていない。
