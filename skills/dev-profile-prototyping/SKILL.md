# 試作（プロトタイピング）

確かめたい問いに、捨てる前提の試作で答える組み合わせ。試作は学びを得る道具で、製品に入れない。レビュー・監査・回帰の試験を省く代わりに、試作を本線に統合しないことと、学びを記録して次の組み合わせに渡すことを守る。各工程の中身は単位に任せ、ここでは順序、引き渡す型、振り分けだけを決める。

## 工程

| 識別子 | 工程 | 単位 | 必須 | 受け取る型 | 渡す型 |
|---|---|---|---|---|---|
| `intake` | 受付 | （人） | 必須 | 原典の参照 | 原典の参照、確認事項の記録 |
| `workspace` | 試作の場所を分ける | `dev-isolated-workspace` | 必須 | 原典の参照、作業場所の台帳（既存の割り当て。あれば） | 作業場所の台帳、作業状態の控え、検証の記録 |
| `build` | 動くコードで試作する | （実装） | 条件付き（確かめたい問いを動くもので確かめる。方式や性能を動かして答える問いと、画面の設計が無い案を動くモックで人に見せる問い） | 原典の参照、作業場所の台帳、確認事項の記録（受付で起こした人に聞く問い。戻ったときは意見と決定） | 変更の事実、検証の記録 |
| `wireframe` | ワイヤーで試作する | `dev-wireframe` | 条件付き（もとにする画面の設計があり、ワイヤーで確かめることにした） | 画面の設計、設計の判断（あれば）、原典の参照 | ワイヤー |
| `show-ask` | 人に見せて確かめる | （人） | 必須 | ワイヤー、変更の事実、検証の記録、確認事項の記録 | 確認事項の記録 |
| `direction-ask` | 進め方を人が決める | （人） | 必須 | 確認事項の記録、検証の記録、ワイヤー、変更の事実 | 確認事項の記録、原典の参照（進め方の決定と破棄の承認の所在） |
| `cleanup` | 片付ける | `dev-isolated-workspace` | 必須 | 原典の参照（破棄の承認を含む）、作業場所の台帳、作業状態の控え、検証の記録 | 作業場所の台帳、作業状態の控え、検証の記録 |
| `final-ok` | 最終確認 | （人） | 必須 | 確認事項の記録、検証の記録、ワイヤー、作業場所の台帳 | — |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。「原典の参照」は、この組み合わせの外（依頼、確かめたい問いと打ち止めの合意、試作を本線に入れない合意の記録）から受け取り、工程 `direction-ask`（進め方を人が決める）でも、人の決定と破棄の承認の所在を指すものを起こす。試作のもとにする画面の設計と、デザインシステムの判断があれば、外から受け取る。

外から受け取る型: 原典の参照、画面の設計、設計の判断、作業場所の台帳（既存の割り当て。あれば）
外へ渡す型: 確認事項の記録、検証の記録、ワイヤー、作業場所の台帳、原典の参照

### 受付で決めること

- 確かめたい問い。人に聞く問い（使い勝手、流れ、意向）は確認事項の記録に起こし、動くもので確かめる問い（方式が成立するか、性能が足りるか）は受付の文書に書いて原典の参照で指す。画面の設計が無い案をモックで人に見せる問いは、人に聞く問いとして確認事項の記録に起こしたうえで、動くもので確かめる問いとして扱う。
- 試作の形（動くコード、画面の設計に基づくワイヤー）と、作らない所。
- 打ち止め（期限、試作の周数、費用の上限）。
- 試作を本線（製品の枝、本番）に入れないことの合意。

### 遷移

| 元 | 先 | 条件 |
|---|---|---|
| `intake` | `workspace` | — |
| `workspace` | `build` | 動くもので確かめる問いがある（モックで人に見せる問いを含む） |
| `workspace` | `wireframe` | 動くもので確かめる問いが無く、もとにする画面の設計がある |
| `build` | `wireframe` | 画面の設計に基づくワイヤーでも確かめることにした（切り替えを含む） |
| `build` | `show-ask` | 確かめたい問いに見せられる形になった。または打ち止めに当たった（今ある所までを、限界を添えて見せる） |
| `wireframe` | `build` | ワイヤーでは答えが出ず、動くコードが要る |
| `wireframe` | `show-ask` | 確かめたい問いに見せられる形になった。または打ち止めに当たった（今ある所までを、限界を添えて見せる） |
| `show-ask` | `build` | 答えが出ず、試作を足す・直す（動くコード） |
| `show-ask` | `wireframe` | 答えが出ず、試作を足す・直す（ワイヤー） |
| `show-ask` | `direction-ask` | 確かめたい問いに答えが出た。または打ち止めに当たった |
| `direction-ask` | `build` | 人が「もう一周試作する」と決めた（動くコード） |
| `direction-ask` | `wireframe` | 人が「もう一周試作する」と決めた（ワイヤー） |
| `direction-ask` | `cleanup` | 人が「本開発に進む」か「捨てる」と決めた |
| `cleanup` | `final-ok` | — |

## 振り分け

一言の依頼から、どの工程に入るかを決める。迷ったら、依頼者に一度だけ聞く。

| 依頼の言い方・状況 | 入る工程 |
|---|---|
| 「〜できるか試して」「スパイクで調べて」「プロトタイプを作って」 | `intake` → `workspace` → `build` |
| 「モックで画面の案を確かめたい」（画面の設計が無い） | `intake` → `workspace` → `build` |
| 「この画面の設計をワイヤーで確かめたい」（画面の設計がある） | `intake` → `workspace` → `wireframe` |
| 「試作を人に見せて意見を集めて」 | `show-ask` |
| 「試作は終わりにして片付けて」 | `direction-ask`（人の決定が済んでいれば `cleanup`） |

途中の工程（`show-ask`、`direction-ask`、`cleanup`）から入る依頼で、受付の合意（確かめたい問い、打ち止め、試作を本線に入れない合意）が無ければ、工程 `intake`（受付）に戻って合意を取り、入ろうとした工程に進む（場所は分け直さない）。

要件が決まっていて製品に入れる変更の依頼は、この組み合わせではなく開発の組み合わせで扱う。

## 工程の間の決まり

- 試作のコードとワイヤーは、本線（製品の枝、本番）に入れない（統合しない）。工程 `cleanup`（片付ける）では、統合ではなく破棄の承認（工程 `direction-ask`（進め方を人が決める）の人の決定）を確かめてから片付ける。片付けでは、ワイヤーは試作の場所から退避して退避先と限界を検証の記録に書き、ワイヤーの所在を退避先に直す。動くコードは場所ごと破棄する。試作の一部を製品に入れたくなったら、試作としては破棄し、入れる変更は別の組み合わせで作り直す（試作のコードを写して持ち込まない）。
- 試作は、受付で決めた確かめたい問いに答えるためだけに作る。問いに要らない機能や見た目の仕上げを足さない。打ち止めを超えたら、今ある所までを限界を添えて人に見せて、工程 `direction-ask`（進め方を人が決める）に戻す。打ち止めに当たった後は、試作の直しには戻らない。続けるときは、人が打ち止めを更新してからにする。
- 試作では、本番のデータと資格情報を使わず、外部への送信を捕まえる。ダミーの値は最初から作り物にする。
- 画面の設計が無い案の試作（モックから要件を探るもの）は、ワイヤーを作る単位の対象外なので、工程 `build`（動くコードで試作する）で作る（単位は使わない）。ワイヤーの単位を使うのは、もとにする画面の設計があるときだけで、その場合は画面の設計に従って作り、画面の構成への疑問は、工程 `show-ask`（人に見せて確かめる）で確認事項の記録に起こして人に返す。
- 人に見せるときは、確かめたい問いと試作の限界（作っていない所、捨てる前提であること）を添え、誘導しない。意見は原文で残し、確認事項の記録に戻す。
- 「本開発に進む」と決まったら、学び（確認事項の記録、検証の記録、ワイヤーの所在）を指す原典の参照を起こして外へ渡し、受ける側の組み合わせの受付で要件のたねにする。試作のコードとワイヤーは実装に流用しない（ワイヤーは退避して退避先と限界を検証の記録に書き、動くコードは破棄する）。
- 「捨てる」と決まったら、捨てた理由を確認事項の記録か検証の記録に書いてから片付ける（次に同じ題材を試すときの判断材料にする）。
- 試作の直し（工程 `show-ask`（人に見せて確かめる）や工程 `direction-ask` から工程 `build`・`wireframe` に戻る）は、同じ場所で続ける。場所を分け直すのは、確かめたい問いが変わったときだけ。

どの工程にも当てはまる決まり（中断と再開、途中の問い）:

- 中断するとき、作業の一部を別の担当に頼むとき、再開するときは `dev-work-continuity` を使う。
- 再開したら、控えと今の状態を照らす。人が決めた状態にある成果物の部分（受付の合意、確認事項の回答、進め方の決定、破棄の承認）が変わっていれば、誰が変えたかを問わず人に確かめる。
- 作業の途中で進めなくなって人に問うときは、1回に1問にし、選択肢の前に、起きていること、影響、得失、推奨を短く書く。確認事項の記録など、型に載せてまとめて出す問いは、この数に入れない。

## 終わり方

- 工程 `cleanup`（片付ける）で作業場所の台帳が「片付け済み」になり、工程 `final-ok`（最終確認）で人が学びの記録（確認事項の記録、検証の記録、退避したワイヤーの所在と限界）を確かめたら終える。
- 「本開発に進む」決定があれば、学びを指す原典の参照を、次に起こす組み合わせの受付に渡す。試作のコードは渡さない。
- 外へ渡す型の置き場所は、案件の決まりに従う。
