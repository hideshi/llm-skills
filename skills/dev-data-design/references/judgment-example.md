# データの設計の判断の例

型: 設計の判断（部分例: 観点「データ」の判断ごとの共通の欄と、規則ごとの守り方、競合する操作の組、保存先の確かめ）
形の一例。正本は型の一覧の欄。形式・節名・置き場所は任意で、案件に既に形があればその形に従う。値はすべて作り物。

題材は、確定した請求書の明細を直せないようにする変更。この例は設計案・未実装で、人の決定を待っている。

## 判断ごとの共通の欄

| 欄 | 中身 |
|---|---|
| 識別子 | `DD-7` |
| 観点 | データ |
| 問いと答え | 確定した請求書の明細の追加、更新、削除を、どこで拒むか。選んだ案: 業務の判断で拒み、競合の制御として、明細を変える処理も確定の処理も、トランザクションの最初に請求書の行を排他のロックで読む（同じ請求書への処理は、その行のロックで直列になる）。選ばなかった案: DB のトリガーで拒む（エラーが呼び出し側でどのエラーになるかが読みにくく、試験で分岐を作りにくいため） |
| 根拠 | 完了条件 `AC-21`、業務規則 `BR-12`、`BR-13`、原典の参照 `docs/example-data-design.md` の「請求書」の節 |
| 承認の状態 | 人の決定待ち（選択肢: 上の案／トリガーの案。既定: 上の案） |
| 保証の宣言と前提 | 前提: DB は行のロックを持ち、ロックはトランザクションの終わりまで持つ（この例では分離は read committed）。ロックの待ちの上限は5秒。明細を変える経路と確定の経路が、それぞれの保存の処理を通る前提で、確定した請求書の明細は追加でも更新でも削除でも変わらず、確定した請求書の合計は確定の時の明細と合うことを保証する。DB を直接操作する保守の作業は保証の外 |
| 変更の区分 | 新規: 明細の表の版の列。既存の修正: 明細の追加、更新、削除の処理と、確定の処理（どれも先頭に請求書の行の排他のロックを足す）。触らない: `BR-13` の既存の検査の制約 |
| 波及と順序 | 明細を変える処理を呼ぶ箇所 6件、確定を呼ぶ箇所 1件（`InvoiceLineService` と `InvoiceService` を検索した結果）。順序は、既存のデータの確かめ → 版の列を足す移行 → 各処理の先頭のロック |
| 確かめる観点 | 下の一覧の「確かめる観点」の列。どれも設計の時点では流していないので「予定」 |
| 未確認 | 確定した請求書のうち、確定の後に明細が変わった行の件数（問い合わせ `CHK-DD7-1` は書いたが、まだ流していない）。0件でなければ、移行の前提が変わる。対象外とした観点は無い |

## 規則ごとの守り方

| 規則 | 守り方 | 競合したときの動き | 確かめる観点 |
|---|---|---|---|
| `BR-12` | 業務の判断で拒み（エラー `invoice_already_finalized`）、明細を変える処理は、請求書の行を排他のロックで読んで状態が下書きのときだけ変える | ロックで読んだ状態が確定なら `invoice_already_finalized` を返す。明細の版の条件で0行なら `line_conflict` を返す（下の `CF-2`）。ロックの待ちが上限を超えたら `invoice_busy` を返す | 確定した請求書の明細の追加、更新、削除が拒まれる（予定） |
| `BR-13` | 既存の DB の検査の制約と、業務の判断の両方（今回は触らない） | 当てはまらない（1行で完結し、競合しない） | 負の金額の保存が、業務の判断で `invalid_amount` になり、制約でも拒まれる（予定） |

対象の規則は、`AC-21` が指す業務規則の全件（2件）。外した規則は無い。

## 競合する操作の組

この例では、列の多い表を、鍵（`CF-` の番号）で2つに分けた。分母は、同じ請求書への操作（確定、明細の追加、更新、削除）の組み合わせの全件（10組）。挙げたのは4組（`CF-1` が3組、`CF-2` が1組）で、外した組と理由は次のとおり。

- 確定と確定、追加と追加、追加と更新、追加と削除: どれも請求書の行のロックで直列になり、後から来た処理は先の処理の結果を読んでから動く。新しい明細は別の行なので、版の競合も起きない。
- 更新と更新、削除と削除: 明細の版の条件で、`CF-2` と同じ守り方と結果になる。

| 鍵 | 競合する操作 | すり抜ける実行順序 |
|---|---|---|
| `CF-1` | 請求書の確定と、同じ請求書の明細の追加、更新、削除（3組） | 明細の処理が状態「下書き」を読む → 確定の処理が状態を「確定」にしてコミットする → 明細の処理が明細を書く |
| `CF-2` | 同じ明細の更新と削除 | 両方が画面で同じ版を読み、更新の後に削除が走る |

| 鍵 | 守り方 | 競合したときの結果 | 確かめる観点 |
|---|---|---|---|
| `CF-1` | どちらの処理も、最初に請求書の行を排他のロックで読む（共有のロックからの格上げをしないので、互いを待ち合う止まりも起きない） | 確定が先なら、明細の処理は待った後に確定の状態を読み、`invoice_already_finalized` を返す。明細の処理が先なら、確定は待った後に変わった明細で合計を計算する。待ちが上限を超えた側は `invoice_busy` を返す。どれも再試行しない | 確定と、明細の追加、更新、削除を、それぞれ並べて流し、確定の後に明細が変わらず、合計が明細と合う（予定） |
| `CF-2` | 明細の版の列を条件に入れた更新と削除 | 後から来た操作は0行になり、`line_conflict` を返す（版の不一致か、削除済み）。画面から読み直して再試行する | 更新と削除を並べて流し、片方だけが通り、もう片方が `line_conflict` になる（予定） |

## 保存先の確かめ

分母は、`AC-21` の画面の入力の全項目（3件: 数量、単価、品目）。

- 数量、単価、品目: 明細の表の既存の列（変更なし）。
- 外した項目: 無い。
- 入力に無い列を1つ足す: 明細の版（技術の目的: `CF-2` の版の条件）。
