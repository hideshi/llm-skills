# データの設計の判断の例

型: 設計の判断（部分例: 観点「データ」の判断ごとの共通の欄と、規則ごとの守り方、競合する操作の組、保存先の確かめ）

形の一例。正本は型の一覧の欄。形式・節名・置き場所は任意で、案件に既に形があればその形に従う。値はすべて作り物。

題材は、確定した請求書の明細を直せないようにする変更。今回の変更で決めたことを書く。人が採って実装で確かめた後は、案件が続けて使うデータの設計の文書に反映する。

## 判断ごとの共通の欄

| 欄 | 中身 |
|---|---|
| 識別子 | `DD-7` |
| 観点 | データ |
| 問いと答え | 確定した請求書の明細の更新と削除を、どこで拒むか。選んだ案: 業務の判断で拒み、最後の線として明細の更新を請求書の状態を条件に入れた更新にする。選ばなかった案: DB のトリガーで拒む（エラーが呼び出し側でどのエラーになるかが読みにくく、試験で分岐を作りにくいため） |
| 根拠 | 完了条件 `AC-21`、業務規則 `BR-12`（確定した請求書の明細は変えない）、原典の参照 `docs/example-data-design.md` の「請求書」の節 |
| 承認の状態 | 人の決定待ち（選択肢: 上の案／トリガーの案。既定: 上の案） |
| 保証の宣言と前提 | 明細を変える経路が、明細の保存の処理を通る前提で、確定した請求書の明細は変わらないことを保証する。DB を直接操作する保守の作業は保証の外 |
| 変更の区分 | 既存の修正: 明細の更新と削除の処理。触らない: 請求書の確定の処理、明細の追加の処理（確定の前だけ呼ばれる） |
| 波及と順序 | 明細の更新を呼ぶ箇所 3件、削除を呼ぶ箇所 2件（`InvoiceLineService` を検索した結果）。既存のデータの確かめを、更新の条件を変える移行より先に置く |
| 確かめる観点 | 下の一覧の「確かめる観点」の列。どれも設計の時点では流していないので「予定」 |
| 未確認 | 確定した請求書のうち、確定の後に明細が変わった行の件数（問い合わせ `Q-DD7-1` は書いたが、まだ流していない）。0件でなければ、移行の前提が変わる |

## 規則ごとの守り方

| 規則 | 守り方 | 競合したときの動き | 確かめる観点 |
|---|---|---|---|
| `BR-12` | 業務の判断で拒み（エラー `invoice_already_finalized`）、明細の更新は「請求書の状態が下書き」を条件に入れる | 条件付きの更新が0行なら、同じエラーを返す | 確定した請求書の明細の更新と削除が拒まれる（予定） |
| `BR-13`（明細の金額は0以上） | DB の検査の制約と、業務の判断の両方 | 当てはまらない（1行で完結し、競合しない） | 負の金額の保存が、業務の判断と制約の両方で拒まれる（予定） |

対象の規則は、`AC-21` が指す業務規則の全件（2件）。外した規則は無い。

## 競合する操作の組

行の多い表は、鍵（`CF-` の番号）で2つに分けて見せる。

| 鍵 | 競合する操作 | すり抜ける実行順序 |
|---|---|---|
| `CF-1` | 請求書の確定と、同じ請求書の明細の更新 | 更新の処理が状態「下書き」を読む → 確定の処理が状態を「確定」にする → 更新の処理が明細を保存する |
| `CF-2` | 同じ明細の更新と削除 | 両方が同じ行を読み、更新の後に削除が走る |

| 鍵 | 守り方 | 競合したときの結果 | 確かめる観点 |
|---|---|---|---|
| `CF-1` | 明細の更新を、請求書の状態を条件に入れた1つの更新にする（読んでから書くの間を空けない） | 更新は0行になり、`invoice_already_finalized` を返す。再試行しない | 確定と更新を並べて流し、確定の後に明細が変わらない（予定） |
| `CF-2` | 明細の版の列で条件付きの更新 | 後から来た操作が競合のエラーになる。画面から読み直して再試行する | 更新と削除を並べて流し、片方だけが通る（予定） |

## 保存先の確かめ

分母は、`AC-21` の画面の入力の全項目（3件: 数量、単価、品目）。

- 数量、単価、品目: 明細の表の既存の列（変更なし）。
- 外した項目: 無い。
- 入力に無い列を1つ足す: 明細の版（技術の目的: `CF-2` の条件付きの更新）。

設計の後に物理の定義を、コードから作り出した資料に置き換えるときは、その資料に作り出した元、版、DB の種類と版、作り直し方、照合した日を付ける。
