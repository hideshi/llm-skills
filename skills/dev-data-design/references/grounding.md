## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 業務の意味、論理・物理の設計、実際の定義、整合性の守り方の正本を分け、未実装の設計は「設計案・未実装」と書く | 今回の変更文書を唯一の正本にすると後続の変更で設計が陳腐化し、承認待ちを現行仕様と取り違えるのを防ぐため | 未実装案を現行仕様と誤認した実装やり直しや正本乖離の件数を記録し、印と正本分離の運用を見直す |
| 既存のスキーマ・コードから業務の正しさを逆算せず、原典不足や現行定義不明なら人に確かめるか「未確認あり」で止める | 既存テーブルの抜け漏れや暫定仕様を業務規則と誤認したまま制約を設計するのを防ぐため | 既存スキーマの逆算から誤った制約を入れて後から修正した手戻り件数を記録し、停止と確認の基準を見直す |
| 入力（画面項目、受入条件、規則）の全項目を分母にして、保存先か「保存しない理由」を確かめる | 論理から物理へ落とす過程で項目が抜け落ちるのを防ぐため | 実装段階や受入時に保存先漏れで見つかった列・項目追加の手戻り件数を記録し、分母照合のタイミングを見直す |
| 制約を足す前に既存データの違反行を探す問い合わせを書き、隔離環境で読み取り専用で確認する（問題台帳があれば再利用し、本番は許可時のみ） | 既存データに違反がある状態で制約を足して移行が失敗する事故と、監査クエリの重複や本番影響を防ぐため | 移行本番での制約追加失敗件数と事前確認で捕捉できた違反件数を比較し、確認の前提条件を見直す |
| 列を足すときはその表を読む全問い合わせを洗い出し、削除済み除外などの絞り込み条件をそろえる | 新しい列や結合先で絞り込み条件が抜け、論理削除済みの行が混ざる回帰を防ぐため | 列追加後に起きた削除済み行混入などの回帰件数を記録し、既存問い合わせの棚卸し範囲を見直す |
| 同時に起きうる操作の組を挙げて結果を書くとともに、実装後に実際のスキーマと設計を照合して検証の記録を残す | 「同じトランザクションで」という言葉だけで競合安全を保証した気になることと、設計と実スキーマの乖離を防ぐため | 実装後の競合不整合・実スキーマとの乖離が見つかった件数を記録し、照合と対の検査の書式を見直す |
