# データの保存を設計する

業務の意味から順に、論理、物理、制約と同時更新を決める。既存のスキーマやコードは今の状態の証拠として読み、業務の正しさをそこから逆算しない。手順は関係データベースを前提に書いている。ほかの保存の仕組み（文書型、キーと値など）では、正規化・参照の制約・実行計画を、その仕組みで同じ問いに答える方法に読み替える（どこで一意を守るか、どこで整合を守るか、検索をどう速くするか）。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 必須 | 設計の根拠。項目の識別子を判断に書く |
| 原典の参照 | 必須 | 業務の規則と用語、既存のデータ設計、画面の検索条件 |
| 現状の振る舞いの記録 | 条件付き（既存の表を変えるとき必須） | 今の定義、新しい制約を破る行の件数 |
| 業務規則の一覧 | 任意 | 規則ごとの守り方の表の行の鍵に、規則の識別子を使う。確かさが仮説・未確定の規則は根拠にせず、そのことを未確認の欄に書く |
| 問題台帳 | 任意 | 既存のデータの規則違反の監査の結果。今ある規則の違反の件数を、制約を足す移行の前提として使う |
| ドメインモデル | 任意 | 管理するもの、関係と多重度、一緒に変わるまとまり |
| 設計の判断 | 任意 | 責務の配置、認可（分離の方式と、所属の列・行の権限・保存先の分割の要求）、非同期の実行とシステム間の連携（保存と送信の順序） |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

業務の規則が原典に無いときは、制約を推測で決めず、人に確かめる。既存の表を変えるのに今の定義が分からないときは、設計を「未確認あり」として止める。

## 出力

| 型 | 中身の補足 |
|---|---|
| 設計の判断 | 観点は「データ」。論理と物理の対応、規則ごとの守り方の表、競合する操作の組、移行の段取り、既存のデータを確かめる問い合わせ、確かめる観点 |
| 検証の記録 | 条件付き。実装の後に、実際のスキーマと設計を照合したとき |

## 使わない場面

- ロジックの置き場所を決める。
- 公開する操作やエラーの形を決める。
- 本番への反映、戻し方の手順、データの移行の実行そのもの。
- 実装する。

## 手順

### 1. 正本を分ける

- 業務の意味、論理の設計、物理の設計、実際の定義（移行のファイル）、整合性の守り方を、それぞれどこに置くかを決める。今回の変更の文書だけを、続けて使う正本にしない。
- まだ実装していない設計は「設計案・未実装」と明記し、承認待ちを今の姿として書かない。

### 2. 導く

1. 業務の意味と規則を挙げる。
2. 論理: 1行が何を表すか、候補キー、従属関係、多重度を決め、正規化する。正規化を崩すときは理由を書く。代理キーを足しただけで、業務上の一意性を解決したことにしない。
3. 物理: データベースの種類と版、型、空を許すか、既定値、制約、索引を決める。
4. 制約と同時更新: 規則ごとに、守り方、競合したときの動き、確かめる観点を対応づける。
5. 漏れの確認: 入力（画面の項目、受入条件、規則）の全項目を分母にして、どこに保存されるかを確かめる。

### 3. 規則をどこで守るか

| 規則の形 | 守り方 |
|---|---|
| 1行で完結する（範囲、必須） | データベースの制約と、業務の判断の両方 |
| 一意性 | 一意の制約を必ず付ける（業務の判断だけでは、同時の登録で抜ける） |
| 複数の行にまたがる | データベースで表せる部分は制約で、残りは処理と競合の制御で |
| 状態の遷移 | 可否の判定と、条件付きの更新（今の状態を条件に入れる） |

- 業務の判断を第一の線、データベースの制約を最後の線として、二重に守る。
- 制約違反がどのエラーとして呼び出し側に見えるかを、確かめる観点に書く。
- 参照の制約（外部キー）は、関係ごとに付けるかを判断する。整合性の単位の境界とは別に決める。

### 4. 既存のデータを確かめる

- 制約を足す前に、それを破っている行を探す問い合わせを設計に書く。件数が分かるまで、制約を足す移行を確定しない。今ある規則について、既存のデータの監査の結果（問題台帳）があれば、その件数を使い、同じ問い合わせを作り直さない。ここで扱うのは、今回足す・変える制約の前提の確認だけで、今ある規則の違反の仕分けや再現はしない。
- 問い合わせを自分で流すときは、読み取りだけにし、隔離した環境か複製で行う。本番のデータに流すのは、人の許可を得たときだけ。
- 列を足すときは、その表を読む問い合わせを全部洗い出し、業務の絞り込みの条件（削除済みを除くなど）を、全部の箇所でそろえる。

### 5. 索引

検索の使い方（画面の検索条件、並び順、結合）から決め、実行計画で効くことを確かめる観点を書く。

### 6. 移行の段取り

- 戻せるようにする。大きな変更は、拡張（新しい列や表を足す）→ データを移す → 縮小（古いものを消す）の3段に分ける。
- 大量の更新は分割する。データの移行とスキーマの変更を、同じ移行に混ぜない。
- どの環境にも適用していない移行は直してよい。適用済みの環境があるなら書き換えず、打ち消す移行を足す。
- 戻し方の手順と食い違わないかを、確かめる観点に書く。

### 7. 保存の単位と同時の操作

- 一度に整合を守る単位ごとに保存する。一覧の表示で、行ごとに問い合わせを繰り返さない（まとめて読む）。読むだけの一覧は、別の読み出しの形にしてもよい。
- 複数の単位を一度に保存するときは、すぐに整合させるか、後で整合させるかを理由を付けて選ぶ。
- 同時に起きうる操作の組（同じ行の更新と削除、二重の登録など）を挙げ、それぞれの結果を書く。「同じトランザクションで」と書いただけで、保証したことにしない。

### 8. 実装の後

実装の後に呼ばれたら、実際のスキーマを読み、承認した設計と照合して検証の記録に残す。設計の完了と実装の完了を混ぜない。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 設計の判断に、判断ごとの共通の欄（識別子、観点、承認の状態、確かめる観点、未確認）がそろい、一覧の行に鍵がある（[型の一覧](../dev-shared/references/artifact-types.md)の「設計の判断の書き方」）。
- 入力の全項目に、保存先か「保存しない理由」がある。
- すべての規則に、守り方、競合したときの動き、確かめる観点がある。
- 制約を足すなら、既存のデータを確かめる問い合わせと、その結果か「未確認」がある。
- 移行に段取りと戻し方の観点があり、適用済みの移行を書き換えていない。
