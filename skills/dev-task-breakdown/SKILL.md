# 作業に分ける

完了条件を、一つずつ終わったと判定できる作業に分ける。作業には識別子を振り、受入条件とテストケースに結ぶ。結びつきの決まりと抜け漏れの検査は、[型の一覧](../dev-shared/references/artifact-types.md)の「識別子と結びつき」に従う。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 必須 | 作業から受入条件への結びつきの出どころ |
| テストケース表 | 条件付き（通常の道では必須） | 作業からテストケースへの結びつき |
| 設計の判断 | 任意 | 変更の区分、波及、順序の制約、人の決定待ち。受入条件に対応しない作業の出どころ |
| 原典の参照 | 任意 | 構成の方針、案件の作業の書式 |
| 問題台帳 | 任意 | 受入条件に対応しない作業の出どころ |
| 回帰の基準 | 任意 | 同上 |
| 是正の対応表 | 任意 | 同上（同じ形の箇所をまとめて直すとき） |
| 方針外の課題の記録 | 任意 | 同上 |
| 作業の一覧 | 任意 | 別の道具が作った作業の文書を受けて確かめるとき |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

- 完了条件の項目に識別子が無いときは、分けずに止め、識別子を振るよう依頼者に頼む。
- 通常の道でテストケース表が無いときは、作業からテストケースへの結びつきを空けたまま進めず、先にテストケースを導くよう返す。
- 別の道具が作った作業の文書を受けたときは、作り直さずに型を満たすかだけを確かめる（手順8）。

## 出力

| 型 | 中身の補足 |
|---|---|
| 作業の一覧 | 型の中身に従う。人の決定待ちの作業は状態を「決定待ち」にする |
| 追跡表 | 要件から作業までの結びつきを集めたもの。抜け漏れの検査の結果を添える |

## 使わない場面

- 何をテストするかを洗い出す（テストケース表を作る仕事）。
- 設計の判断を作る。
- 作業を実装する、進み具合を管理する。

## 手順

### 1. 成果物を逆算する

完了条件の項目ごとに、何ができていれば満たせるか（変える処理、足すデータ、変える画面、撤去するもの）を書き出す。

### 2. 触る箇所を特定する

成果物ごとに、触る箇所を実際に検索して特定する。件数は推測しない。設計の判断に波及の件数があれば、検索し直して食い違いを確かめる。

### 3. 分ける

- 一度に整合を守る単位を2つ以上またぐ作業は分ける。同じ単位の中の変更は、無理に分けない。
- 全部の責務（入出力から保存まで）を含む作業は原則分ける。ただし、小さくまとまった変更は1つでよい。
- 共通の核と、それを使う側は別の作業にする。
- 1つの作業は、レビューで一度に見られる大きさにする。1つの作業が多くの受入条件（目安: 8件以上）に結ばれているときや、ある受入条件の対応先が、ほかにも多くの受入条件（目安: 5件以上）を抱える作業1つだけのときは、分け方を見直す。
- 「確定する」「整理する」だけの作業には、何ができたら終わりかという成果物を補う。

### 4. 依存と順番を書く

- 型や契約の変更元 → 波及先。共通の核 → 使う側。正本（フラグ、列、操作）→ それを読む側。
- 別の作業場所（別のリポジトリ、別の担当）の最初の作業は、実装ではなく範囲の要約にする。
- 旧の撤去を伴うなら、撤去の作業を置き、移行の作業の後に依存させる。

### 5. 並べて進められるかを決める

次を全部満たす作業どうしだけを、並べてよいとする。

- 触るファイルが重ならない。
- 間のインターフェースが確定している。
- 依存が一方向。
- 多くの作業が集まるファイル（設定、経路の定義など）を触らない。

補う確認（追加の監査、探索の拡張）の完了を、次の段階の前提にしない。

### 6. 終わりの条件を書く

- 結んだテストケースが通ること。既定では、テストを先に書いて落ちることを確かめ、通し、整える、を作業ごとに行う。テストを最後にまとめる作業を作らない。
- 完了条件の一覧で、テストを先に書かないと決めた範囲（試作、見た目の調整、テストの仕組みがまだ無い、など）の作業は、そう明記し、書かれた代わりの確かめ方を終わりの条件にする。結んだテストケースが通ることは外さない。
- テストで確かめない作業（文書の更新など）は、そう明記し、確かめ方を書く。
- 旧の撤去を伴う作業は、撤去も終わりの条件に入れる。

### 7. 規模を見積もる

小／中／大で書き、根拠（触る箇所の数、不確実さ、新しい概念の有無）を添える。

### 8. 結びつきを確かめる

- 識別子は原典（完了条件の一覧、テストケース表、設計の判断）から写す。見出しや文の似かたから、結びつきを推論しない。
- 型の一覧の「作業に分けるときの検査」を行う。そこで指摘として返すとされた欠けは、直さずに返す（直すのは、それぞれを作る側）。
- 別の道具が作った作業の文書なら、要件にしか結ばれていない作業、両側に書かれた関係の食い違いを指摘にする。

### 9. 終える前の点検

- すべての成果物に、作業と触る箇所が対応している。
- 人の決定待ちの作業が「決定待ち」になっている。決まるまで始めない。
- 分け方に複数の案があったら、推奨を1つ選び、理由を書く。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- すべての作業に、受入条件か出どころの識別子がある。
- 作業に分けるときの検査が通っているか、通らない項目と理由が追跡表に書かれている。
- すべての作業に、判定できる終わりの条件と、依存と、並べてよいかの判断がある。
- 決定待ちの作業が、そうと分かる。
