# 受入の証拠を確かめる

「テストが通った」「工程が終わった」「API が成功した」は、人に見せる証拠として使えることと同じではない。字幕や手順の名前は注釈で、証明にならない。この単位は、証拠そのものを開いて、主張する結論を中身が裏付けているかを確かめ、確かめてから確定する。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 検証の記録 | 必須 | 証拠を取った実行の記録 |
| テストケース表 | 条件付き（完了条件の一覧が無いとき必須） | 証拠が何を示すべきか |
| 完了条件の一覧 | 条件付き（テストケース表が無いとき必須） | 証拠が何を示すべきか |
| 変更の事実 | 任意 | 証拠を取った版と、その後の変更の突き合わせ |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

証拠が何を示すべきかが分からないときは、確かめずに止める。

## 出力

| 型 | 中身の補足 |
|---|---|
| 受入の証拠 | 証拠ごとの対象、版と環境、所在とハッシュ、注釈と結論、自己視聴の結果、確定の状態、確かめていない範囲 |
| 検証の記録 | 証拠を取り直したときの実行 |

## 使わない場面

- テストケースや E2E のシナリオを設計する。
- 変更の良し悪しをレビューする。証拠を作った者とは別の担当が見る場合も、その段取りは使う側が決める。
- 作業全体が完了したかを判定する。

## 手順

### 1. 確かめる順を守る

1. 製品の経路で、狙った画面に到達する。API の結果だけで済ませない。
2. 録画なしで全部通す。
3. 必要な画面を全部取る。別の利用者や、別のアプリの画面に結果が出るなら、それも含める。
4. 完成品（提出する形）に組み立てる。
5. 提出する者が、最初から最後まで自分で見る。
6. その後でやっと、確定、成功の宣言、レビューへの引き渡しをする。

下流（6）を上流（1〜5）より先にしない。

### 2. 組み立てた成果物で取る

- 見た目の証拠は、配る形に組み立てた成果物で動かして取る。開発用の表示や、古いビルドの成果物で取らない。
- 構造のテストが通ることは、見た目を保証しない。

### 3. 完了とする条件

- 注釈が言う場面が、その時に実際に映っている。注釈があっても画面が違う、中身が空の画面だった区間は、失敗した証拠として扱う。
- 人の名前などを伏せる表なら、伏せ字以外の実際の行が1件以上映っている。伏せ字だけの表は、中身が空の画面と同じ扱い。
- 製品が実際に進んだことを、試験のための仕掛け（独自のイベント、広すぎるクリック、経路の差し替え）で代用していない。

### 4. 自分で最後まで見る

- 対象の操作と結果が画角に収まっているか。
- 内容が読める状態になってから、十分な時間止まっているか。止める時間を、待機や表明の代わりに使っていないか。
- 作り直したときに、前の版にあった必須の場面が消えていないか。
- 映っていないものは提出しない。

録画の見やすさの作り方は [録画の見やすさ](references/recording-visibility.md) を見る。

画面の操作と録画、動画の組み立てと検査を道具で行うときは、道具の資料（[Playwright](references/tools/playwright.md)、[ffmpeg](references/tools/ffmpeg.md)、部品のカタログを証拠に使うなら [Storybook](references/tools/storybook.md)）があれば読む。無ければ公式の資料で確かめる。フォントの欠け、録画の縮小、切り出しや連結の崩れなど、成功で終わるのに証拠が壊れる落とし穴は、道具ごとに違う。

### 5. 確定する

- 確定の対象は、動画や画像の単体ではなく、記録と実物のまとまり全体。記録にある所在とハッシュが、実物と一致していること。
- 焼き込んだ文字列と、予定していた文字列を取り違えない。
- 作り直したら、確定を外す。途中で失敗した更新を確定しない。
- 確定は、自己視聴と提出の判断の後に、独立した操作として行う。

### 6. 別の担当として証拠を見るとき

- 作った者とは別の担当が、作った者の説明を引き継がずに、観察だけをする。字幕や「通った」を根拠にしない。
- 全編を見て、切り替わりの前後は細かく確かめる。見ていない区間と限界を書く。
- 「証拠で見えた事実」「コードや記録から分かった事実」「確かめていない疑い」を分ける。確かめていない疑いを、確定した問題として書かない。
- 証拠の作りの問題（画角、止める時間）を、製品の不具合と混ぜない。
- 親切な説明を足す改善案は、情報が漏れないか（利用者がいるかどうか、トークンの状態、内部の情報）を点検してから出す。

### 7. 画面の検証の3層

画面の変更を含むときは、次の3つを使い分ける。

- 自動の表明: 壊れた画像やコンソールのエラーが0件であることまで確かめる。
- 基準の画像との比較: 意図した変更のときだけ基準を更新し、その差分をレビューに回す。
- 目視: 上の2つで確かめられない見た目を確かめる。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- すべての証拠に、対象、版と環境、所在とハッシュ、注釈と結論、自己視聴の結果がある。
- 確定した証拠は、自己視聴の後に確定され、記録と実物が一致している。
- 映っていない、または結論を裏付けない証拠が、確定されていない。
- 確かめていない範囲が書かれている。
