# 外の失敗の分け方

外部サービスや別のシステムを呼んだときの失敗を、どう分け、どう扱うかの表。同期で呼ぶときも、裏で（ジョブやキューから）呼ぶときも、この分け方を使う。決めた分け方は設計の判断に書き、裏で呼ぶときは、非同期の実行の設計がそれを受け取る。

## 2段の分け方

1. 第1段: 相手で実行されたかどうか。
   - 送る前の失敗（接続できない、名前を引けない）: 実行されていない。
   - 送った後の時間切れ、接続断、相手の内部の障害: 実行されたか分からない。一律に再試行しない。
   - 相手が確定して断った（入力の誤り、権限が無い、在庫が無い）: 実行されていない。
2. 第2段: 再試行してよいか。
   - 実行されていない、または冪等キーで二重実行を防げる: 再試行してよい。
   - 回数の制限に当たった: 相手が示す待ち時間の後に再試行する。
   - 確定した拒否: 再試行しない。
   - 実行されたか分からず、冪等キーも無い: 再試行しない。照会してから決める。

分け方は1か所にまとめ、どの規則で分けたかを記録に残す。

## 同期で呼ぶとき

- 時間切れの長さを、利用者が待てる時間と、相手の通常の応答時間から決める。
- その場で再試行してよいのは、第2段で「再試行してよい」に当たり、かつ利用者が待てる範囲だけ。回数（例: 1回）と間隔を決める。
- 実行されたか分からないまま利用者に応答を返すときは、二重に実行された可能性を隠さない。後でどう確かめて、どう知らせるかを決める（裏の照会に回すなど）。

## 結果が分からないとき

- 相手に照会する手段があれば、照会して確定する。
- 照会で見つからないことを、「実行されていない」の確定にしない（反映が遅れているだけのことがある）。相手の契約で確定と言える条件を調べて書く。
- 利用者への文言では、重複して送られた可能性を隠さない。「確認中」のように、誰が何を確かめているのかがあいまいな表現を避ける（文言そのものはエラーの設計で決める）。

## 相手の失敗を自分の側のエラーに写す

相手の失敗の種類（相手のエラーのコード、状態コード）ごとに、自分の側のどのエラーの種類として扱うかを表にする。利用者への文言や記録の分け方は、エラーの設計の判断に従う。相手の内部の情報（相手のエラーの文、識別子）を、利用者にそのまま見せない。
