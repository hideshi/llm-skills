# 案件の既定の決定の例

型: なし（継続の文書: システム間の連携の、案件の既定の決定）
形の一例。型の外の文書で、正本は案件の文書。形式・節名・置き場所は任意で、案件に既に形があればその形に従う。値はすべて作り物。

この例の文書は、型の一覧のどの型でもない。とくに設計の判断とは別のものである。設計の判断は今回の変更で決めたことを入れる型で、識別子、選ばなかった案、承認の状態を持つ。この例の文書は、人が採って実装で確かめた判断のうち、案件で続けて従うものだけを反映した文書で、反映した後はこの文書を原典の参照として読む。節は、問いの一覧の別紙にある「既定の決定の記録の項目」（背景、決定、対象外、見直す契機）に合わせた。

題材は、請求のシステムと配送のシステムをつなぐ案件。

## 背景

請求のシステムが、配送のシステムの内部の API を呼んで、出荷の状態を照会する。どちらも同じ組織が運用する。照会の機能ごとに同じ問いに答えていたので、既定にした。

## 決定

| 項目 | 既定 | 決めた判断と確かめた所在 |
|---|---|---|
| 内部の API の置き場所 | 呼ばれる側の既存の内部の接頭辞（`/internal/`）に乗せる | `DD-21`（2026-02-10 に人が採った。`example-repo` の `4d5e6f7` で確かめた） |
| 相手の識別子 | 出荷の識別子だけを持ち、配送の状態は写さずに毎回照会する | `DD-21`（同上） |
| 相手が止まっているとき | 呼ぶ側の操作を失敗にする（部分的に続けない）。配送の側の 5xx は、自分の側のエラー `upstream_unavailable` に写す | `DD-22`（2026-03-02 に人が採った。`example-repo` の `7a8b9c0` で確かめた） |

## 対象外

機能ごとの設計の判断で決める: 時間切れの長さ、再試行の回数、補償の認可、冪等のキーが要るか。

## 見直す契機

内部の入口の仕組みを入れ替える、配送の状態を請求の側に持つ画面を足す、相手が止まっていても続けてよい画面を足す。
