# 案件の既定の決定の例

型: なし（継続の文書: システム間の連携の、案件の既定の決定）

形の一例。型の外の文書で、正本は案件の文書。形式・節名・置き場所は任意で、案件に既に形があればその形に従う。値はすべて作り物。

これは設計の判断ではない。設計の判断は今回の変更で決めたことを入れる型で、識別子、選ばなかった案、承認の状態を持つ。この文書は、人が採って実装で確かめた判断のうち、案件で続けて従うものだけを反映した後の写しで、次からは原典の参照として読む。案のままの行や、人がまだ採っていない行は書かない。

題材は、請求のシステムと配送のシステムをつなぐ案件。

## 前提

請求のシステムが、配送のシステムの内部の API を呼んで、出荷の状態を照会する。どちらも同じ組織が運用する。

## 既定

| 項目 | 既定 | 決めた判断 |
|---|---|---|
| 内部の API の置き場所 | 呼ばれる側の既存の内部の接頭辞（`/internal/`）に乗せる | `DD-3`（2026-02-10 に人が採った） |
| サービスの認証 | 既存の内部の API と同じ方式 | `DD-3` |
| 相手が止まっているとき | 呼ぶ側の操作を失敗にする（部分的に続けない） | `DD-5`（2026-03-02 に人が採った） |
| 相関の識別子 | 境界で `X-Example-Request-Id` を渡す | `DD-5` |

## この文書で決めないこと

機能ごとの設計の判断で決める: 時間切れの長さ、再試行の回数、補償の認可、冪等のキーを要るか。

## 見直すきっかけ

内部の入口の仕組みを入れ替える、認証の方式を変える、相手が止まっていても続けてよい画面を足す。
