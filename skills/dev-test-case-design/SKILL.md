# テストケースを導く

完了条件や仕様から、何をテストすれば正しさが言えるかを導き、表にする。どう書いて回すか、試験用のデータをどう作るかは扱わない。表は、実装の前に作れば試験を先に書く材料になり、実装の後に作れば試験の不足を見つける材料になる。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 条件付き（新しい振る舞いを試すとき必須） | ケースの出どころ。各ケースを項目に対応づける |
| 原典の参照 | 任意 | 仕様、業務規則、画面やエラー文言の正本 |
| 追跡表 | 任意 | あれば、テストケースから受入条件への結びつきを足す |
| 現状の振る舞いの記録 | 条件付き（今の動きを仕様の代わりにするとき必須） | 改修で、今の動きを固める検証点を層ごとに振り分ける |
| 問題台帳 | 任意 | 問題に関わるケースに識別子を付ける |
| 設計の判断 | 任意 | 「確かめる観点」をケースにする。設計に由来するケースは、判断の識別子を出どころにする |
| 業務規則の一覧 | 任意 | 規則ごとに満たす・破るのケースを作り、確かめる規則の識別子を書く |
| 是正の対応表 | 任意 | 不具合を直す箇所ごとの再現と、直った後の確かめ方をケースにする。受入条件に結ばないケースは、対応表の番号を出どころにする |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

完了条件の一覧も現状の振る舞いの記録も無いときは、導かずに止め、何を基準にするかを依頼者に聞く。定義の無い用語、意図か漏れかを判定できない条件、範囲が複数の機能にまたがる条件は、推測で埋めずに人への問いにする。

完了条件の項目に識別子が無いときは、項目の順に番号を振り、番号と項目の対応を表の前に書いて返す。振った番号は、原典に書き戻すよう依頼者に伝える。

## 出力

| 型 | 中身の補足 |
|---|---|
| テストケース表 | 下の「表の列」に従う |
| 追跡表 | 入力にあったときだけ。テストケースから受入条件への結びつきを足して返す |

## 使わない場面

- テストコードを書いて、落ちることと通ることを確かめる（テストケース表を受け取る、別の仕事）。
- 画面をまたぐ受入の試験（E2E）のシナリオを設計する。ここでは、ケースを E2E の層に置くと決めるところまで。
- 実装する、不具合を直す。

## 手順

### 1. 入力を構造にする

条件ごとに、入力の型、有効な範囲、閾値、列挙値、状態を書き出す。

### 2. 同値分割と境界値

- 区間は両端を全部挙げる（N、N±1、代表値）。列挙値は全値。数量は、ゼロ・最小・境界±1・上限。
- 特殊な値（未設定、空、負数、丸め、桁あふれ）を考える。

### 3. 暗黙の前提を違反のケースにする

- 並び順、重複なし、正の値、空でない、型、存在、一意、連続などの前提を挙げ、破ったときのケースを作る。
- 前提が一つも見つからないときは、見落としを疑う。

### 4. 業務規則と不変条件

- 規則ごとに「満たす」「破る」のケースを1件ずつ以上作る。
- 破る入力は、ほかの検証を通ったうえで、狙った規則だけに違反するようにする。先の検証で弾かれると、確かめたつもりで何も確かめていない。

### 5. 状態遷移と二重実行

- 状態があるなら、状態×操作の表を作り、許可と禁止を全部埋める。禁止は「許可の逆」だけとは限らない。
- 二重実行や再試行があるなら、2回目の結果、副作用の回数、外部への呼び出しの回数、件数を確かめるケースを作る。失敗の後に状態が変わっていないことも確かめる。

### 6. 組み合わせを絞る

条件が4つ以上なら、ペアワイズか代表値に絞る。展開しなかった組み合わせは、表に注記する。

### 7. 層を決める

- 副作用の有無、保存、外部との通信、画面で、どの層（単体、結合、画面をまたぐ受入）に置くかを決める。下の層で確かめられるものは上の層に置かない。
- 複数の機能をまたぐ振る舞いは、呼び出す側の試験に置く。
- テストではなく、レビューや構造の検査で確かめる規則は、そう注記する。
- 業務規則の一覧があれば、種類から層の既定を引く: 不変条件と計算と状態遷移の可否は単体、まとまりをまたぐ規則は結合、一意性は保存の制約まで通す結合（同時の操作を含む）。既定と違う層に置くなら理由を書く。

### 8. 表の列

| 列 | 書くこと |
|---|---|
| 識別子 | ケースの識別子。一度振ったら変えない、使い回さない |
| 対応 | 完了条件の項目の識別子（1つ以上）。完了条件の一覧から写す。無ければ出どころの識別子 |
| 確かめる規則 | 業務規則の識別子と、満たすケースか破るケースか（規則を確かめるケースのとき）。業務規則の一覧から写す |
| 分類 | 正常／境界／前提違反／業務規則／状態遷移／二重実行 |
| 条件節 | 確かめる条件の一文 |
| 入力と前提 | 値そのもの |
| 期待結果 | 戻り値だけでなく、否定（起きてはならないこと）と副作用 |
| 層 | 単体／結合／画面をまたぐ受入 など |
| 必須度 | 必須／推奨。ケースが1件しかない完了条件の項目は必須 |

### 9. 自己点検

- 境界、前提、規則、遷移、二重実行の観点に抜けがないか。
- 否定を含む完了条件の項目に、正常系以外のケースがあるか。
- 横断の関心事（権限、利用者の分離、入力検証など）ごとに、否定のケースがあるか（権限の無い人が操作できない、別の利用者のデータが見えない、管理用や一括の経路でも検証が通る）。出どころは、横断の関心事の一覧の所在か、認可の設計の判断の許可の表の行（判断の識別子＋行の鍵）。
- 偽陰性: 不具合が戻ったら、そのケースは必ず落ちるか。欠落を不等式で隠していないか（「1件以上」ではなく正確な件数か）。呼び出しの回数を数えているか。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 型の一覧の「テストケースを導くときの検査」を満たす。完了条件の全項目に、対応するケースが1件以上あるか、テストで確かめない理由が書かれ、否定を含む項目には否定のケースがある。
- すべてのケースの「対応」が、完了条件の一覧にある識別子か、出どころの識別子になっている。
- すべてのケースに、層と必須度と、否定・副作用を含む期待結果がある。
- 展開しなかった組み合わせと、人への問いが一覧になっている。
