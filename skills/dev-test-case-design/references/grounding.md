## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 完了条件の一覧も現状の振る舞いの記録も無いときは止め、定義の無い用語や複数機能にまたがる条件は推測で埋めず人への問いにする | 根拠のない推測を期待値として表にすると、誤った仕様で試験を通した偽の安心を生むため | 曖昧条件を推測で埋めて期待値違いが出た手戻り件数と質問停止による停滞時間を比べ、停止基準を見直す |
| 暗黙の前提（並び順・重複なし・正の値・空でない・一意・連続など）を違反のケースにし、一つも見つからないときは見落としを疑う | 仕様書に明記されない暗黙の前提の破綻が、境界や異常系の漏れになりやすいため | 暗黙の前提0件で通した変更から検証の記録や案件の問題台帳（あれば）に前提破綻の不具合が出た件数を記録し、見直し条件を見直す |
| 期待結果に否定（起きてはならないこと）と副作用を書かせ、自己点検で横断の関心事と偽陰性（不等式ごまかし・呼び出し回数未確認）を見る | 正常な戻り値だけを見ると、裏側の副作用や権限漏れ・欠落を見逃すため | 不等式や件数未確認によるテストすり抜け件数と副作用・権限漏れの見逃し数を記録し、自己点検項目を見直す |
| 二重実行や再試行では、2回目の結果だけでなく副作用の回数、外部呼び出し回数、失敗後の状態不変を確かめる | 冪等性の欠陥は2回目の応答だけでは見えず、重複した副作用や中途半端な状態残りに現れるため | 2回目応答だけを確認したケースで二重副作用・半端状態が露見した件数を記録し、期待結果の必須観点を直す |
| ケースの識別子を固定して使い回さず、完了条件に識別子が無ければ仮番号を振って原典への書き戻しを伝える | 後工程の実装や記録と表の対応が途中でずれるのを防ぐため | 識別子ずれ・仮番号の書き戻し漏れで追跡不能になった件数を記録し、採番と同期手順を見直す |
