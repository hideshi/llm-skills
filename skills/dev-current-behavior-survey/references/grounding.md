# 根拠と変えたところ

既存システムの今の振る舞いを調べて記録する手順が、どの先行の手法に基づき、どこを変え、どこが独自の判断かを書く。手順そのものは SKILL.md が正本で、ここは読む人が元の考え方をたどるための別紙。

- 確かめた日: 2026-11-13
- 確かめた水準: 「原典を読んだ」「書誌と二次資料で確かめた」「未確認」

## 先行の手法

| 手順の箇所 | 手法 | 出典 | 確かめた水準 | 同じところ | 変えた・足したところ |
|---|---|---|---|---|---|
| 全体・2. 実装をたどる | リバースエンジニアリングと設計回復（Reverse Engineering and Design Recovery） | Elliot J. Chikofsky, James H. Cross II「Reverse Engineering and Design Recovery: A Taxonomy」IEEE Software 7(1), 13–17, 1990（DOI 10.1109/52.43044） | 書誌と二次資料で確かめた | 対象システムを変更せずに構成要素・関係・振る舞いを解析し、別の表現（文書や記録）へ起こし直す | 「コードがそう動く」ことと「そう動くよう意図された」ことを切り分け、変更履歴や記録から意図が追えないものは「未確認」にする決まりを足した |
| 全体（正しさを決めずに今の動きを記録する） | 特性テスト（Characterization Test）の前提となる現状観察 | Michael Feathers『Working Effectively with Legacy Code』Prentice Hall、2004、第3章「Sensing and Separation」・第13章「I Need to Make a Change, but I Don't Know What Tests to Write」 | 書誌と二次資料で確かめた（本文は未読） | 今の動きが業務上正しいかを判定せず、実際の振る舞いをそのまま捉えて記録する | この段階では試験コードで固定するところまで踏み込まず、観察の事実・版・根拠・推測・未確認を分けた記録と問題台帳を作るまでに範囲を切った |
| 3. 既存の資料と照らす | 文書の陳腐化（Documentation Drift）への対処 | Timothy C. Lethbridge, Janice Singer, Andrew Forward「How Software Engineers Use Documentation: The State of the Practice」IEEE Software 20(6), 35–39, 2003（DOI 10.1109/MS.2003.1241364） | 書誌と二次資料で確かめた | 実装の変更に対して既存の文書や仕様書が追従せず古くなりがちであることを前提に、現在のコードと照合する | 既存テスト資料の「合格」も今の実装で確かめ直すまで結果として転記禁止とし、文書との食い違いを差として記録するだけにとどめ正誤を決めない規則にした |
| 5. 動かして確かめるとき | テストダブル | Gerard Meszaros「Test Double Patterns」（`xUnitPatterns.com`、2007、http://xunitpatterns.com/Test%20Double%20Patterns.html ） | 原典を読んだ（2026-11-13 に Web 公開の分類ページと各パターン要約を確認） | 本物の外部依存を試験用のテストダブル（Test Stub / Test Spy / Mock Object / Fake Object 等）に置き換えて観測・隔離する | 疑似にした外部の仕組みが「何を保証し何を保証しないか」を書かせ、疑似が多い実行を「全体の試験」と呼ばない制約を足した |
| 5. 動かして確かめるとき（時刻と隔離） | 非決定的な要素の隔離 | Martin Fowler「Eradicating Non-Determinism in Tests」（martinfowler.com、2011、https://martinfowler.com/articles/nonDeterminism.html ） | 原典を読んだ（2026-11-13 に本文を確認） | 共有環境の状態汚染を避けて実行ごとの再現性を保つ | 原典はシステム時計を包んで差し替える方法を勧め、データ側を現在日時に合わせるやり方を脚注で「手間が大きい」と退けている。本手順では実システムの時計を動かせない調査のため、あえて逆のデータ側で日時をそろえる規則（SKILL.md）を採った |

## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 確認の水準を「実行／静的／公開情報／未確認」の4つに固定し、観察した事実・根拠・対象の版と、推測を別欄に分ける | コード読みや古い資料を実際に動かした結果と混ぜると、後続の基準づくりや是正の前提が崩れるため | コード読みや推測を実行結果と混ぜて後続の回帰基準や是正が覆った手戻り件数を記録し、4水準の分け方を見直す |
| 問題ごとに「判断の区分（作る側で決められる／設計で決める／依頼側の判断待ち／別の計画で扱う／本番の事実確認待ち）」を付け、重大度・確認の水準・許可と別軸で扱う | 誰が判断権を持つかを切り分けないと、作る側が仕様を勝手に決めたり調査が詰まったりするため | 権限の違う担当へ回ったり作る側が独断決定して差し戻された件数を記録し、5区分の境界を見直す |
| 仕様の質問（依頼側に決めてもらうこと）と事実確認（本番などで確かめること）を別表に分け、回答待ちの間も依存しない調べを進める | 未回答の論点があるたびに調査全体が止まるのを防ぎつつ、未確定事項の引き継ぎ漏れを無くすため | 回答待ちによる調査停止の回数と仕様・事実混在による回答の手戻りを記録し、別表の分け方を見直す |
| 新しい識別子を振る前にシステムの責任と既存課題との重複を確かめ、根が同じものをまとめる | 同じ根本原因から出た複数の症状が別々の問題として重複起票されるのを防ぐため | 調査後に同一原因の重複起票や別原因の誤統合が見つかった件数を記録し、統合の基準を見直す |
| 改修の範囲が決まっていないときは調べ始めずに範囲を確定し、システム全体の仕様化へ広げない | 対象外まで調べる過剰調査で時間を使い果たすのを防ぐため | 範囲外の仕様化による調査時間超過と前提見直しでの手戻り件数を比較し、着手前の合意粒度を見直す |
