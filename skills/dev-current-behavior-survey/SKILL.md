# 既存の振る舞いを調べる

改修や是正に入る前に、既存システムが今どう動いているかを、根拠つきで記録する。目的は、今の動きを再現できる材料をそろえることで、その動きが正しいかを決めることではない。今の動きと一致することは、業務上の正しさや安全性の承認にならない。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 改修の範囲 | 必須 | 調べる機能と経路、対象の版、共有の処理とそれを使う側を決める |
| 原典の参照 | 任意 | 既存の仕様書・試験の資料・課題の一覧。無い、または信用できない案件もある |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

改修の範囲が決まっていないときは、調べ始める前に、機能・経路・対象の版を依頼者と決める。全体の仕様化へ広げない。

## 出力

| 型 | 中身の補足 |
|---|---|
| 現状の振る舞いの記録 | 観察ごとの事実・対象の版・確認の水準・根拠と、推測・未確認の欄 |
| 問題台帳 | 見つけた問題と判断の区分、仕様の質問と事実確認の別表 |

## 使わない場面

- 今の動きを回帰の試験として固める（出力の記録と台帳を受け取る、別の仕事）。
- 見つけた問題を直す。
- 正しい動きを決める。業務の判断は依頼側に、設計の判断は設計の場に戻す。

## 確認の水準

| 水準 | 意味 |
|---|---|
| 実行 | 自分で動かして確かめた。どの境界まで本物を通し、どこを疑似にしたかを書く |
| 静的 | コードや設定を読んで導いた |
| 公開情報 | 外部の文書や仕様から読み取った |
| 未確認 | 確かめていない |

## 手順

### 1. 範囲を固める

- 調べる機能、入口（画面・API・バッチ・外部からの受信）、対象の版を書き出す。
- 共有の処理に触るなら、それを使うほかの側を一覧にする。改修の影響はそこにも及ぶ。

### 2. 実装をたどる

- 入口から、処理、保存や外部連携、画面への表示までを順にたどる。
- 観察した事実、根拠（ファイルと箇所、実行の記録）、対象の版を記録する。推測は別の欄に書く。
- 「コードがそう動く」ことと「そう動くよう意図された」ことを分ける。意図は変更の履歴や記録で調べ、分からなければ未確認とする。

### 3. 既存の資料と照らす

- 既存の試験の資料にある「合格」は、今の実装で確かめ直すまで、今の結果として扱わない。過去の合格を転記しない。
- 資料と今の動きが違うところは、差として記録する。どちらが正しいかはここで決めない。

### 4. 問題を台帳にする

- 新しい識別子を振る前に、どのシステムの責任か、既存の課題と重ならないかを確かめる。根が同じものはまとめる。
- 確かめていない疑いを、確定した問題として書かない。疑いのまま、確かめ方を添える。
- 問題ごとに、判断の区分を一つ付ける。重大度、確認の水準、直してよいかの許可とは別の軸として扱う。

| 判断の区分 | 意味 |
|---|---|
| 作る側で決められる | 誤りが明らかで、正しい動きを作る側で決められる |
| 設計で決める | 誤りは明らかだが、直し方は設計の判断が要る |
| 依頼側の判断待ち | 依頼側の仕様の判断がないと、正しい動きが決まらない |
| 別の計画で扱う | 既に別の計画や課題の範囲にある |
| 本番の事実確認待ち | 本番の環境やデータの事実を確かめないと決まらない |

- 仕様の質問（依頼側に決めてもらうこと）と事実確認（本番などで確かめること）は、別の表に分ける。回答を待つ間も、それに依存しない調べは進める。

### 5. 動かして確かめるとき

- 本番のデータや資格情報を使わない。汚れのない隔離した写しで動かし、外部への送信は捕まえる。
- 疑似にした外部の仕組みが、何を保証し何を保証しないかを書く。
- 時刻に依存する動きは、ホストの時計ではなく、データの側で日時をそろえて再現する。
- 試験の段階（内部の結合、外部との結合、全体）の意味を先に決める。疑似が多い実行を、全体の試験と呼ばない。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 範囲に挙げた機能と経路のすべてに、観察の記録があるか、未確認と書かれている。
- 問題台帳のすべての行に、判断の区分と確認の水準がある。
- 仕様の質問と事実確認が、それぞれの表に分かれている。
- 現状の振る舞いの記録の冒頭に、範囲、確認の水準の内訳、回答待ちの一覧、未確認の範囲が書かれている。
