# Cloudflare Requirements Framing

利用者が機能要件（FR）・非機能要件（NFR）、またはワークロードの説明を持っており、**製品を選ぶ前に** Cloudflare 前提の制約を整理したいときに使う。

## 目的

後続の `cloudflare-product-survey`（製品の裏取り）と `cloudflare-architecture-advisor`（構成の提案）が使える **要件・制約 Markdown** を作る。この段階では **製品選定・構成の提案をしない**。

## やってよいこと / やってはいけないこと

- **する**: FR/NFR を制約軸に分解し、未決事項を明示する。曖昧な点は質問して埋める（推測で埋めない）。
- **しない**: Workers / R2 などの製品名を「本命」として決め打ちしない。モデルの記憶だけで制限値を断定しない。

## 制約シートに含める軸（最低限）

次の軸をテーブルまたは見出しで網羅する。該当しない軸は「対象外」と理由を書く。

| 軸 | 確認例 |
| :--- | :--- |
| レイテンシ / SLA | 最初の応答までの時間、p99、同期/非同期 |
| リージョン / データ所在 | 居住地、利用者に近い拠点、データを置く国・地域の制約 |
| 認証・認可 | エンドユーザー、サービス間、ゼロトラスト |
| コスト感度・前提のプラン | 無料枠優先、従量、固定費上限。Free か有料プランか（制限と使える製品が変わる） |
| コンプライアンス | 個人情報、監査ログ、保持期間 |
| トラフィックパターン | スパイク、常時、バッチ、地理的な偏り |
| 状態性 | ステートレス、セッション、強整合、書き込む者が一つ |
| 入出力・外向き通信 | 帯域、オリジンへの戻り、外部 API の呼び出し |
| 実行時間・制限感度 | CPU 時間、同時実行、リクエストサイズ（製品の上限は**この段階で数値を断定しない**） |
| ストレージ特性 | オブジェクト、キーと値、SQL、一時キャッシュ |
| 運用 | デプロイ頻度、観測、ロールバック、チームのスキル |

## 出力形式

次の Markdown を成果物とする。置き場所は作業中の案件の文書とし、スキルのディレクトリには書き込まない。

```markdown
# Cloudflare 要件・制約シート

- 作成日:
- 入力資料:
- ステータス: draft | ready-for-survey

## 1. ワークロード要約
（1段落）

## 2. 機能要件（FR）
| ID | 要件 | 優先度 | 備考 |

## 3. 非機能・制約
| 軸 | 制約 | 必須/希望 | 根拠・未決 |

## 4. 明示的な非目標（Non-goals）

## 5. 後続調査への引き渡しメモ
- 裏取りで確認すべき製品カテゴリ（まだ選定ではない）:
- 構成の提案の前に必須の未確認事項:
```

## 完了条件

- 制約シートが後続スキルの入力として自己完結している。
- 製品の「本命」提案が含まれていない。
- ステータスを `ready-for-survey` にするのは、必須の軸に「未決」が残っていないときだけ。残っていれば `draft` のまま、未決の項目と、誰に何を確かめるかを書く。
