# 非同期の実行を設計する

その場で結果を返さない処理（ジョブ、キュー、定期のバッチ、イベントを受けて動く処理）を、途中で止まっても、二重に動いても、壊れない形にする。外部サービスを呼ぶかどうかは問わない。外部を呼ぶときに要る扱い（結果が分からない場合）も、ここで決める。状態の遷移と失敗の分け方の詳しい表は [実行の設計](references/execution.md) に分ける。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 必須 | 設計の根拠 |
| 原典の参照 | 任意 | 処理する量と時間帯の要件 |
| 一次情報の記録 | 任意 | 外部の契約を調べた結果（冪等キー、回数の制限、照会の手段）と、どの判断を縛るか |
| ドメインモデル | 任意 | ドメインイベントの整合性の要件（すぐか、後でよいか） |
| 設計の判断 | 任意 | 責務の配置、エラーの一覧（再試行してよいか）、システム間の連携（外部を呼ぶとき） |
| 現状の振る舞いの記録 | 条件付き（既にあるジョブやバッチを変えるとき必須） | 今の起動のしかた、件数、かかる時間、失敗の扱い |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

量や時間帯の要件が分からず、選ぶ分岐に影響するときは、その分岐の判断を保留して人に確かめる。

## 出力

| 型 | 中身の補足 |
|---|---|
| 設計の判断 | 観点は「非同期の実行」。非同期にする理由、中核の原則への適合、状態の遷移、再試行と失敗の分け方、一部の失敗の扱い、起動の排他、止まったものの検出、見せる導線、保証の宣言、選ばなかった案と理由、確かめる観点 |

## 使わない場面

- その場で結果を返す処理（同期の処理）。
- 複数のシステムのどれが正本か、途中で失敗したときの補償、起動の安全を決める。
- 公開する操作の形を決める、実装する、本番で流し直す。

## 手順

### 1. 非同期にする理由を確かめる

- 利用者がその場で結果を必要とするか、処理が長いか、外部が遅い・止まることがあるか、時間帯を決めて流したいか、で決める。非同期を一律にしない。
- 非同期にすると決めた処理だけに、以下を当てる。

### 2. 中核の原則

1. 業務のデータと、処理を実行する意図を、同じトランザクションで保存する（意図だけ残る、業務のデータだけ残る、を防ぐ）。
2. 状態の正本はデータベースなどの永続の場所に持つ。実行の権利は原子的に取り、取れた者だけが実行する。試行ごとに識別子を持たせる。
3. 実行の回数の保証（少なくとも1回か、高々1回か）を正直に宣言する。少なくとも1回なら、処理は冪等にする。相手に届くことと相手の業務への反映の保証は、システム間の連携の判断に従う。
4. 再試行してよい失敗と、してはいけない失敗を分ける。
5. 失敗と止まったものを、人に見せる導線を1つ以上持つ。
6. 外部を呼ぶときは、結果が分からないもの（送ったが応答が無い）を、失敗と分けて隔離する。

### 3. 状態と再試行

- 状態の遷移、止まったものの扱い、失敗の2段の分け方は [実行の設計](references/execution.md) の表で決める。
- 実行中のまま止まったもの（担当が落ちた）は、決めた時間の後に検出する。外部を呼ばない処理なら、冪等であることを確かめたうえで待ちに戻してよい。外部を呼ぶ処理なら、結果不明として扱う。
- 再試行の回数、間隔（だんだん広げる）、断念したときの扱いを決める。

### 4. バッチと一括の処理

- 起動の排他: 同じバッチが二つ同時に動かないようにする（前の回がまだ動いているときの扱いを決める）。
- 分けて進める: 大量の件は区切って処理し、区切りごとに進み具合を保存する。途中で落ちたら、終わった所の続きから再開できるようにする。
- 一部の件の失敗: 1件の失敗で全体を止めるか、失敗した件を集めて続けるかは、エラーの一覧の決まりに従う（正本はエラーの設計。無ければ仮に決めて未確認に書く）。続けるなら、失敗した件の一覧を残し、その件だけを流し直せるようにする。
- 時間帯と負荷: 流す時間帯、ほかの処理とのぶつかり（ロック、負荷）、終わるまでの上限の時間を決める。上限を超えたときの扱いも決める。
- 結果の報告: 処理した件数、成功、失敗、飛ばした件を、終わりに残す。

### 5. 見せる導線と流し直し

- 失敗、断念、止まったものの一覧を、受け取る側（運用者、利用者）が見られるようにする（画面、通知、定期の報告のどれか）。
- 利用者に知らせるなら、宛先、経路（画面、メール、通知）、まとめ方（1件ごとか、まとめてか）、知らせる時機を決める。文言はエラーの設計に従う。
- 手での流し直しは、1回きりの明示した試行として記録する。自動の再試行の回数を戻さない。

### 6. 分岐の記録

選んだ方式（キューの仕組み、定期の起動のしかた、結果を待つか）ごとに、選ばなかった案と理由を1行ずつ書く。

### 7. 確かめる観点を渡す

二重の起動、同じ意図の二重実行、途中で落ちてからの再開、一部の件の失敗、再試行の上限、止まったものの検出、流し直しの記録を、確かめる観点として設計の判断に書く。試験では外部への送信を捕まえ、本物の外部へ送らない。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 設計の判断に、判断ごとの共通の欄（識別子、観点、承認の状態、確かめる観点、未確認）がそろい、一覧の行に鍵がある（[型の一覧](../dev-shared/references/artifact-types.md)の「設計の判断の書き方」）。
- 非同期にする理由と、中核の原則への適合が書かれている（外部を呼ばない処理では、原則6を「対象外」とする）。
- 状態の遷移、再試行の決まり、止まったものの扱い、見せる導線がある。
- バッチなら、起動の排他、再開のしかた、一部の失敗の扱い、結果の報告がある。
- 分岐ごとに、選ばなかった案と理由がある。
