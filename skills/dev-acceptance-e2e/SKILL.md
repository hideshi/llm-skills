# 受入条件と E2E を設計する

受入条件を、修正を知らない第三者が合否を判定できる形に整え、画面や外部とのやり取りをまたいで確かめるシナリオに変える。E2E は要の流れだけに絞り、下の層で確かめられるものは下の層に任せる。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 完了条件の一覧 | 必須 | 受入条件の出どころ |
| 原典の参照 | 任意 | 画面の仕様、利用者向けのエラー文言の正本、業務規則 |
| テストケース表 | 任意 | 下の層に置いたケース。E2E に重ねない |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

完了条件の一覧が無いときは、設計せずに止める。

## 出力

| 型 | 中身の補足 |
|---|---|
| テストケース表 | 層は E2E。シナリオの分類、前提データ、操作、検証点とその層、負の検証、既存の E2E への影響表を足す |
| 完了条件の一覧 | 合否を判定できない受入条件に、書き直しの案を付けて返す。採るかは人が決める |

## 使わない場面

- 単体や結合の層のテストケースを洗い出す（テストケース表を作る、別の仕事）。
- テストコードを書いて回す。
- 録画や画面の証拠が、人に見せられる状態かを確かめる。

## 手順

### 1. 受入条件を判定できる形にする

各条件が次を満たすかを確かめ、満たさないものに書き直しの案を付ける。

- 前提・操作・期待結果の3つが読み取れる。
- 期待結果が観測できる言葉で書かれている（「正しく保存される」ではなく、何が見えるか）。登録や更新の後に読み直した表示が一致することまで書かれている。
- 誰が、どの状態のデータで行うかが明確。
- 内部の語（モデル名、列名、内部の識別子）を使っていない。
- 修正を知らない第三者が、実演を見て合否を判定できる。

### 2. シナリオにする

- 1つの受入条件を1つのシナリオにするのを原則とし、識別子で対応を記録する。
- 前提・操作・検証点の形で書く。検証点は要素があることで止めず、文言、状態、遷移先、通知の中身まで確かめる。
- 主分類を一つ決める: 主経路、分岐（条件の組み合わせの1つ）、異常・取消・やり直し、時間依存、定期処理との連動。定期処理は、動く場合と動かない場合を対で書く。
- 不具合の回帰であることだけを理由に主経路に入れない。操作が似ていても、観測できる経路や結果が違うものはまとめない。

### 3. 検証点を割り当てる

- 画面、保存されたデータ、通知、帳票のどこで確かめるかを決める。保存されたデータは、計算の規則込みの期待値で確かめる。
- 負の検証を入れる: 送られてはいけない、見えてはいけない、件数が0。
- 外から観測できない内部の分岐は E2E にせず、その理由を注記する。

### 4. 絞る

- E2E は要の流れだけにする。下の層で確かめられるものは下の層に置く。
- 業務の流れに関係しない変数は、代表の1本でまとめてよい。ただし、処理の経路や観測できる結果が変わる差（初期値、権限、送る中身、保存の結果、過去の不具合の再現条件）はまとめない。
- 優先の順: 全部の流れの主経路を先にそろえ、次に時間依存と定期処理の重要なもの、分岐と異常の代表、補完の順。
- E2E の範囲を縮めることは、人が決める。

### 5. 既存の E2E を棚卸しする

状態や導線を変えるときは、既存の E2E を必ず棚卸しする。

| 扱い | 意味 |
|---|---|
| そのまま | 影響しない |
| 付け替え | 対応する受入条件や名前だけを直す |
| 更新 | 手順や期待値を直す |
| 廃止 | 人の承認が要る |

全部の識別子に扱いと範囲（今回の対象か）を付ける。既存の E2E が無いときも、探した範囲を記録する。

### 6. 安定させる作りにする

- 要素は、試験のための専用の目印で選ぶ。
- 準備は冪等にし、実行の順に依存させない。シナリオごとにデータを分ける。前提データは業務として現実的な状態にし、根拠の規則を添える。
- 準備と操作を分ける。裏口で結果の画面に直接たどり着かない。
- 外部のサービスは接続先を差し替える。製品のコードに試験のための分岐を入れない。
- 時刻はデータの側で作り、動かしている機械の時計を変えない。
- 一定時間の待機ではなく、条件がそろうのを待つ。
- 隔離した環境で動かし、本番のデータや資格情報を使わない。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- すべての受入条件に、対応するシナリオがあるか、E2E にしない理由が書かれている。
- 判定できない受入条件に、書き直しの案が付いている。
- すべてのシナリオに、主分類、検証点とその層、負の検証の有無がある。
- 状態や導線を変えるなら、既存の E2E の影響表があり、廃止には人の承認の欄がある。
