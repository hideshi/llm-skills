# Jev Candidate Detector

工程名（日本語）: **候補検出**（スキル ID との対応は `../jev-shared/references/jev-lifecycle-status.md` §7）。

本スキルでは、Kiro/cc-sdd の `requirements.md` と、特定の仕様駆動開発フレームワークに依存しない一般的な要件定義書を総称して**「要件文書」**と呼びます。

このスキルは要件文書を主な対象とし、Kiro/cc-sdd では `design.md`・`tasks.md` も参照します。必要に応じてドメインモデル、ユースケース、業務フロー、画面設計書、API仕様書、テーブル定義書等で補完し、**TypeSafe AI の決定特化型モデル「Jev (System One)」が適用可能な業務ロジックを抽出・アタリ付け**します。さらに、フォールバック確率を含めた期待TCO（総保有コスト）およびレイテンシの削減効果を試算します。関連文書はファイル名・形式ではなく役割で識別します。

---

## 1. 適合判断の厳密な判定基準（ゲートウェイ方式）

エージェントごとのブレをなくすため、**「ハードゲート」→「除外条件」→「加点項目」** の順序で客観的に評価します。

### 🚪 Step 1: ハードゲート（全項目合格が必須。1つでも不合格なら候補外）
- [ ] **意味理解の必要性**: 単なる静的ルールやキーワード検索では解釈できず、自然言語やコンテキストの意味理解を伴うか？
- [ ] **有限の出力空間**: 出力が有限の選択肢（Choice）、順序尺度（Score）、またはYes/No確率（Noul）として事前定義できるか？
- [ ] **即時判断可能性**: 人間のドメイン専門家が見て、数秒の直感（System One）で答えられる判断か？（長い論文調査や深い論理展開が不要か）
- [ ] **非生成要件**: 新規のテキストやコード生成、自由対話を必要としないか？
- [ ] **証拠の充足性**: 判定に必要な情報（State）が入力時点で全て揃っているか？

### 🚫 Step 2: 除外条件（1つでも該当すれば即座に不採用）
- ❌ **決定論的ロジック**: 数値計算、日付比較、DB検索、固定権限ロール判定（`role === 'ADMIN'`）などで完全にコード化できる。
- ❌ **数え上げ・日付/数値演算を本質とする判定**: Jev は計算機ではなく、個数のカウント（対象が大きいほど誤差が増大）、日付の前後関係・期間・ウィンドウ判定の精度は保証されない（2026-09-19 調査）。これらはコードで処理すること。**意味理解と計算の複合判定は分割を検討**する（例: 「この段落はバージョン番号・価格を述べているか？」は Noul で意味抽出し、新旧の比較はコードで行う）。抽出（意味判断）は Jev、集計・順序付け（算術）はコード、という分担が前提。
- ❌ **不可逆な高リスク単独操作**: 誤判定時に取り返しのつかない操作（送金実行、データ完全消去等）を、人手確認やフォールバックなしにモデル単独で行おうとしている。
- ❌ **可変長・未知の出力**: 出力すべき候補が事前に列挙できず、動的に無限に増える。

> **📚 数え上げ・日付演算の除外根拠**: DEV Community「How to Use Jev」/ flaviocopes「A deep dive into Jev」（2026-09-19確認）— "It is not a calculator. It does not count reliably" / "Dates are text to it, not ordered quantities"。

### ⭐️ Step 3: 適格性判定 & 適合度スコアリング (Eligibility & Scoring)

- **🚫 不適格 (`Not Eligible`)**:
  Step 1 のハードゲートに1つでも不合格、または Step 2 の除外条件に該当する場合は即座に候補外とする。星は付与しない。

- **✅ 適格 (`Eligible`)**:
  ハードゲート全項目をクリアし除外条件に該当しないもののみ、以下の基準で★3〜★5を判定する。

| スコア | 判定基準 | 適用推奨度 |
| :--- | :--- | :--- |
| **Eligible ★★★★★ (最優先PoC推奨)** | 月間10万回超の高トラフィック ＋ p95 < 200ms の低遅延要件 ＋ 誤判定時の安全な縮退先（Safe Default）が定義可能。 | 最優先でPoC・評価対象に選定 |
| **Eligible ★★★★☆ (積極PoC推奨)** | 月間1万回〜10万回程度の中規模トラフィックだが、現行LLMのAPIコスト削減またはユーザー体感速度（TTFB）改善効果が顕著。 | 積極的なPoC・評価対象に選定 |
| **Eligible ★★★☆☆ (条件付き検討)** | Jev化は可能だが、月間数千回以下の低頻度、または現行手段からのコスト/レイテンシ改善幅が小さく投資対効果が限定的。 | コスト/保守性のトレードオフで検討 |

> **📊 スコア根拠データの入手元**:
> トラフィック量・レイテンシ要件（p95等）は、まず要件文書の**非機能要件セクション**（性能・可用性要件等）を参照する。記載がない場合は推測でスコアを付けず、**ユーザーに確認（HITL）**する。確認が得られるまでスコアは `TBD` として出力する。

## 2. 実行ワークフロー

1. **ドキュメントの静的スキャン & Requirement ID特定**
   - **要件文書（一次資料）**: Kiro/cc-sdd の `requirements.md`、または他のフレームワークや独自プロセスにおける同等の要件定義書から、業務要件、判断条件、制約、非機能要件およびトレーサビリティを抽出する。
   - **設計・実装計画**: Kiro/cc-sdd の `design.md`・`tasks.md`、または同等の設計書・タスク定義から、現行設計、技術的制約、実装・変更予定を確認する。要件文書の代替にはしない。
   - **業務補完資料**: ドメインモデル、ユースケース、業務フローから、アクターの責務、業務判断、承認、状態遷移、例外処理を抽出する。
   - **実装補助資料**: 画面設計書、API仕様書、テーブル定義書から、既存の操作・入出力・分類値・承認履歴等を確認する。ただし、これらだけから業務ルールを推測しない。
   - 必ず **Requirement ID**（なければドキュメント内の安定した見出し）と原文フレーズを記録する。行番号（`#L45` 等）は追記・整形でずれやすいため、補助情報としても用いない。
   - 補助資料のみから抽出した候補は確定的に扱わず、根拠資料区分を `supplementary-only` として、業務要件との整合をドメインエキスパートへの確認事項（HITL）にする。
   - **対象ドキュメントの特定（フォールバック手順）**:
     1. まず Kiro/cc-sdd の既知の慣例パス（例: `.kiro/specs/**/requirements.md`、同一仕様ディレクトリ内の `design.md` / `tasks.md`）を探索する。
     2. 次に、ユーザー指定またはプロジェクトの文書索引・規約で明示された関連資料を参照する。曖昧なファイル名から内容を推測しない。
     3. 対象文書を特定できない場合は、ユーザーに分析対象ドキュメントのパスを確認する。

2. **ゲートウェイ適格性判定（§1 の適用）**
   - 抽出した各判断ポイントに対し、§1 の「ハードゲート → 除外条件 → スコアリング」を順に適用し、`Eligible` / `Not Eligible` と★スコアを確定する。
   - ハードゲートのうちドメイン知識を要する判定（例: 「ドメイン専門家が数秒の直感で答えられるか」）に確信が持てない場合は、推測で合格にせず**ドメインエキスパートへの確認事項（HITL）**としてレポートに記録する。
   - 候補が0件の場合も、スキャン対象ドキュメントと判定結果（0件である旨）を簡易レポートとして出力する。

3. **3プリミティブの適合分類**
   - **`Choice`**: 定義された選択肢からの排他分類（カテゴリ、問い合わせ種別：請求 / 技術 / 営業、コンテンツモデレーション種別：スパム / ヘイト / 規約違反 など）
   - **`Score`**: 順序性のある段階評価（緊急度 Low/Med/High、品質スコア 1〜5）
   - **`Noul`**: Yes/No の確率判定（スパムか否か、規約違反か否か、エスカレーション要否）
   - **HITL / 確認事項（複合・Score）**:
     - 複合ラベルが想定される候補は、**主タイプ優先規則の要否**を確認事項に上げる（未定義のまま後段へ送らない）。
     - Score を含む候補は、**測っている意味が一意か**（違反強度と温度／自動公開リスクの混同がないか）を確認事項に上げる。`none` でも medium/high があり得るなら明示が必要。

4. **💰 期待TCO & レイテンシ試算**
   - `references/cost-estimation-reference.md` に基づき、単なる呼出費だけでなくフォールバック（LLM・人手）を含めた期待コストを試算する。
   - **試算前に必ず各ベンダーの公式価格ページから最新単価を取得し直す**こと。リファレンスの価格表は調査日時点の参考値であり、そのまま使用しない。取得した価格の出典と取得日をレポートに記録する。
   - 現在の判定手段が**人手**の場合は、生成LLMベースラインではなく**人手業務ベースライン**（N × 1件あたり処理時間 × 人件費単価）と比較し、既存機能の廃止・変更に伴う一時移行コスト (C_migration) と投資回収期間も記録する。
   - 試算の入力データ（月間リクエスト数 N、現行API費用、1件あたり処理時間、人件費単価等）は推測せず、**利用部門・経理/財務・インフラ担当等から提供された実データ**を使用する。入手できない項目は「仮定値」と明記し、感度分析で幅を示す。

5. **業務・上位成果物への影響分析**
   - 人の確認・承認業務を代替する候補は、実装（design.md / tasks.md）だけでなく業務プロセスと上流成果物が変わる。影響を受ける **ドメインモデル・ユースケース・画面設計・requirements.md** を特定し、レポートの「業務・上位成果物への影響」セクションに Requirement ID 紐付けで記録する。
   - **本スキルの責務は影響の特定・記録までとし、上流成果物の更新自体は行わない。** ドメインモデル・ユースケース・画面設計等の更新は、人間の承認後に専用スキル（要件定義・ドメイン設計・画面設計等）または SDD フロー（Kiro/cc-sdd）の更新プロセスへ委譲する。レポートはその委譲先への引き継ぎ契約として機能させる。
   - オペレーターの役割変更・人員配置・教育等の**組織的な変更（チェンジマネジメント）**が必要な場合は、その旨を記録する。実行は業務部門・人事へ委譲する。

6. **フェーズ間契約レポートの出力**
   - `templates/jev-candidate-report-template.md` に従い出力。
   - 各候補のステータスは `decision: proposed` として出力し、人間の承認（`decision: approved`）を待つ状態にする。業務変更を伴う候補の承認は、技術承認に加えて**業務側ステークホルダーの承認**を含む。
   - 個人情報・機密データを外部APIへ送信する候補には**セキュリティ・プライバシー審査の要否**を記録する（審査自体はセキュリティレビュー・法務等の専門プロセスへ委譲）。
   - 与信・採用・医療等の規制業界や自動意思決定に関わる候補には、**法的・規制要件の確認要否**を記録する（確認自体は法務・コンプライアンスへ委譲）。
   - **ADR要否の判定基準**:
     - **全社基盤ADR**: Jev基盤の導入自体が複数チーム・全社横断の意思決定に相当する場合。
     - **機能別ADR**: 高リスク（決済・BAN等の不可逆性の高い判定）にJevを適用する場合。
     - **design.md内の記録で十分**: 低〜中リスクの機能内判断に留まる場合。

## 後段スキル鎖（承認後）

`decision: approved` の後は、設計（`jev-logic-architect`）に続き、評価セット freeze（`jev-eval-set`）と閾値較正（`jev-calibration`）へ進む。状態語彙と差し戻しは `../jev-shared/references/jev-lifecycle-status.md` を参照する。本番適用は本鎖の外（リリース管理）とする。区切り到達時の利用者向け定形要約は `../jev-shared/templates/jev-pipeline-result-report-template.md`（**完了版は `jev-calibration` が出力する**）。
