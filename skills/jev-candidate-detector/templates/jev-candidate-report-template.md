## 4. 業務・上位成果物への影響（フィードバック）

Jev が人の確認・承認業務を代替する場合、変わるのは実装（design.md / tasks.md）だけでなく**業務プロセスそのもの**です。影響が遡る上流成果物を Requirement ID 紐付けで記録してください。

| 影響先 | 変化内容（記入例） | 関連 Requirement ID | 対応要否 |
| :--- | :--- | :--- | :--- |
| **業務プロセス** | 全件目視承認 → 例外件のみレビュー | `REQ-XXX` | [要改訂 / 影響なし] |
| **ドメインモデル** | 「承認者」アクターの責務変更・削除、「承認待ち」ステータス遷移の消滅 | `REQ-XXX` | [要改訂 / 影響なし] |
| **ユースケース** | 承認フローのUC削除・変更 | `UC-XX` | [要改訂 / 影響なし] |
| **画面設計** | 承認画面・レビューキューの廃止 / 確信度モニタリング・オーバーライドUI・監査ログ画面の新設 | `SCR-XX` | [要改訂 / 影響なし] |
| **requirements.md** | 判定手段・承認プロセスに関する要件の改訂 | `REQ-XXX` | [要改訂 / 影響なし] |
| **既存機能の不要化・変更** | [不要になる機能・別操作に変わる操作を列挙] | `REQ-XXX` | [要改訂 / 影響なし] |
| **新規に必要になる機能** | [オーバーライドUI、監査ログ等] | - | [新規起票] |

> **承認の範囲**: 業務変更を伴う候補の `decision: approved` は、技術承認に加えて**業務側ステークホルダーの承認**を含むこと。
>
> **スコープ境界**: 本レポートは影響の特定・記録までをスコープとする。上流成果物（ドメインモデル・ユースケース・画面設計等）の実際の更新は本スキルでは行わず、承認後に**専用スキル（要件定義・ドメイン設計・画面設計等）または SDD フロー（Kiro/cc-sdd）の更新プロセスへ委譲**すること。

## 5. 次フェーズ（`jev-logic-architect`）への移行条件
人間によるレビューの上、採用する候補の `decision` を **`approved`** に更新してください。
高リスクな判断については、プロジェクト内に ADR を作成（または `design.md` の Decision 節に起票）した上で `jev-logic-architect` を実行します。
