# レビュー依頼文の例

型: レビュー依頼文
形の一例。正本は型の一覧の欄。形式・節名・置き場所は任意で、案件に既に形があればその形に従う。値はすべて作り物。

題材は、確定した請求書の明細を直せないようにする変更の、最初のレビューの依頼。依頼文はそのまま渡せる文だけで、前後に説明や渡し方の指示を付けない。この例では、依頼文の中身をそのまま見せる（以下、線の内側が依頼文）。

---

対象の識別子: 要件 `REQ-7`（完了条件の一覧 `docs/example-completion.md`）

変更の事実:

- 変更したファイル: `InvoiceLineService.ts`、`InvoiceService.ts`、`InvoiceLines.vue`、`InvoiceLineService.test.ts`、移行 `db/example-migration-01`
- 差分の範囲: `example-repo` の `b2c3d4e..c3d4e5f`

原典の参照（節まで。中身は要約しない）:

- 完了条件の一覧 `docs/example-completion.md` の `REQ-7`、`AC-21`〜`AC-23`
- 業務規則の一覧 `docs/example-rules.md` の `BR-12`。設計の判断 `docs/example-judgments.md` の `DD-7`
- 画面の設計 `docs/example-screen.md` の `SC-3`。共通仕様 `docs/example-screen-common.md` の「エラーの形」と「文言の決まり」

検証の記録:

- `python3 -I scripts/run_invoice_tests.example`（2026-11-12 15:00、手元の写し）: `TC-41`〜`TC-43` が通る
- 未実施: 画面の確かめ（`TC-44`）

発見を求める観点:

- 原典の要求のうち、変更と試験のどちらでも扱われていないものはどれか。
- この変更が誤った結果を返す入力・状態・順序を、具体的に一つ以上挙げよ。
- 試験は原典から導かれているか（実装の写しになっていないか）。確かめ方は、結果・否定・副作用まで具体的に見ているか。検証されていない領域はどこか。

出力の形の要求:

- 結果の冒頭に、対象の識別子を書くこと。
- 「問題なし」とするなら、観点ごとに根拠（どこを読み、何を試したか）を書くこと。根拠のない承認は、承認として扱わない。
- 指摘には、証拠の種類（実行で確認／読んで導いた／仮説など）を付けること。

---

この例の依頼文には、作った側の解釈・要約・評価の言葉（「よく動く」「軽微な修正」など）が無い。変更の理由は、原典の参照で指すだけにした。

発見を求める観点は、単位の本文が「少なくとも次を含める」と求める項目。この例では5項目を3つにまとめて見せた。また、`AC-23` は既存の振る舞いを保つ条件で、変更はデータを変える手順（移行）を含むので、実際の依頼文には条件付きの観点「変更前と結果を比べたか」と、手順の戻し方を問う観点も要る。
