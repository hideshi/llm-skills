# 要件を書く

求める動きを、検証できる要件と受入条件にする。基準は、顧客の要望、公的な規則、今の動きとの差のどれか（複数でもよい）。業務規則そのものはドメインモデルの側で決め、ここではそれを根拠に要件を書く。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 原典の参照 | 必須 | 顧客の要望、画面の案（モック）、文案 |
| ドメインモデル | 任意 | 用語と、状態・区分 |
| 業務規則の一覧 | 任意 | 要件の根拠にする規則。確かさが仮説・未確定のものは根拠にしない |
| 一次情報の記録 | 条件付き（公的な規則や外部の仕様が基準のとき必須） | 基準の項目 |
| 現状の振る舞いの記録 | 条件付き（既存のシステムを変えるとき必須。信用できる仕様書や設計書を原典の参照として受けたときは、それで代えてよく、代えた文書と節を書く） | 今の姿 |
| 問題台帳 | 任意 | 直す差、仕様の質問 |
| 規模の判定 | 任意 | 道と、横断の関心事の格上げ |
| 確認事項の記録 | 任意 | 前の回の回答 |
| 完了条件の一覧 | 条件付き（前の版を直す・承認し直すとき、別の道具や人が書いた要件を受けるとき必須） | 直す元。識別子はそのまま使う |
| 画面の設計 | 任意 | 画面の設計が返した受入条件の案と確認事項の候補 |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

基準が一つも無いときは、書かずに止め、何を基準にするかを依頼者に聞く。

## 出力

| 型 | 中身の補足 |
|---|---|
| 完了条件の一覧 | 要件ごとの目的、受入条件（識別子と、属する要件、確かめる業務規則の識別子）、やらないこと、適用する画面（範囲の宣言）。画面に関わる要件は、利用者、入力情報、判断 |
| 確認事項の記録 | 質問文・備考・回答の3層 |
| 問題台帳 | 今の姿との差のうち、直す差 |

## 使わない場面

- 業務の用語と規則そのものを決める、モデルを作る。
- 受入の試験のシナリオを設計する、テストケースを導く。
- 設計、実装。

## 手順

### 0. 既にある完了条件の一覧を受けるとき

- 別の道具や人が書いた要件を受けるときは、作り直さずに型を満たすかと、型の一覧の「要件を終えるときの検査」を確かめ、欠けを確認事項か指摘にして返す。
- 画面の設計が受入条件の案や確認事項の候補を返してきたときは、案ごとに採るか採らないかを依頼者に確かめ、採ったものを完了条件の一覧か確認事項の記録に入れる。採らなかったものも、理由と一緒に出力に残す。入力情報や判断が欠けていると返されたら、画面の側ではなく、ここで要件に書き足す。
- 前の版を直すとき（承認し直し、受入条件の書き直しの案を採ったとき）は、識別子を変えない。要らなくなった項目は消さずに廃止の印を付け、新しい項目には続きの識別子を振る。直した項目と理由を、出力の先頭に書く。

### 1. 求める姿を取り込む

- 要望の文書と画面の案を、漏れなく写す。画像の中の文字も写す。
- 画面の文案は、要約せず、文字単位で一致させる。
- 画面か機能の単位で束ねる。

### 2. 事実と意向を分ける

- 事実の曖昧さ（今どうなっているか）は、関係者に聞く前に、コード、データ、今の動きの記録で潰す。
- 意向（どうしたいか）だけを、確認事項にする。
- 似た概念は、構造の差を先に固める（金額が同じだけでは同じものとはいえない）。

### 3. 確認事項を往復する

- 質問文はそれだけで意味が通るように書き、備考に今の仕様と推測の根拠、回答は原文のまま書く。
- 人づての回答は、伝えた人も記録する。回答で前提が後退することもあるので、状態を付ける。
- 回答の戻し先を振り分ける: 規則が変わるならドメインモデル（モデルを先に直す）、流れなら要件、見せ方なら画面。迷ったら「画面を作り直しても残る話か」で決める。個人の情報の扱い（何を取り、どこへ送り、どの目的で、いつまで持つか）の事実を答えたものは台帳に戻し、個人情報の台帳を作る単位が反映する。ただし、その答えで完了条件（目的や保持の期間など）が変わるなら、要件にも戻す。
- 了承は、画面ではなく規則の形で取る。
- 画面やワイヤーへの意見は、1件ずつ確認事項の記録の行にする。対象に画面の識別子と箇所を書き、質問文は「この意見をどう扱うか」の形にし、意見の原文（長ければ所在）を備考に写す。1件に規則・流れ・見せ方が混ざっていたら、層ごとに行を分ける。振り分けた結果（どの戻し先にしたか）を行ごとに1行残す。見せ方のうち、部品やトークンの共通の定義に関わるもの（ほかの画面にも効くもの）は、そのことを書いて返す。
- 確定した前提の帰結から、次の論点を広げる。用語のずれも確認事項にする。

### 4. 今の姿と比べる（既存のシステムを変えるとき）

- 今の姿は、今の動きの記録から取る。仕様書と実装が食い違うときは、どちらを今の姿とするかを書く。
- 今の画面でできることを、要件の根拠にしない。差は、直す差として問題台帳に載せる。
- 公的な規則が基準のときは [規則を基準にした比べ方](references/regulation-based.md) で比べる。

### 5. 要件を書く

- 要件ごとに目的を書く。受入条件は検証できる形で書き、否定（起きてはならないこと）も書く。
- やらないことを、はっきり宣言する。
- 適用する画面や入口を、範囲の宣言として明示する（入口、既存の画面の名前、まだ画面が決まっていなければ「未割当」）。画面の識別子との結びつきは、画面の設計の側に置き、ここには書き戻さない。表示だけを変え、保存する値は変えないなら、そう書く。
- 画面に関わる要件には、利用者、目的、入力情報（判断のために何を見るか）、判断（何を決めるか。決めることが無ければ「なし」）を書く。画面の契機があるとき（規模の判定が画面の設計に当てたか、適用する画面に、型の一覧の「仕様化の契機」の画面の設計に当たる画面（「未割当」を含む）を書いたとき）は必須にする。画面の側で聞き直して決めない（正本はここ）。途中で画面が要ると分かったら、適用する画面に書き足す。
- 横断の方針（権限、監査、通知など）は、別の要件に分ける。危険の大きい種類（権限の昇格、外への送信、課金）は、専用の受入条件を立てる。
- 確かさが仮説・未確定の業務規則を、要件の根拠にしない。
- ユースケースの形で書くときは、利用者と目的、入力情報、判断、前提、主な流れ、例外の流れ、結果を書き、要件の識別子をそのまま使う。
- 文書の品質は [要件の文書の品質](references/document-quality.md) で確かめる。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- すべての要件に目的があり、すべての受入条件が合否を判定できる形で、属する要件の識別子を持つ。
- やらないことと、適用する画面（範囲の宣言）が書かれている。画面の契機があるなら、画面に関わる要件に入力情報と判断がある。
- 画面の設計から返された案と、画面への意見は、どれも採否か戻し先が記録されている。
- 型の一覧の「要件を終えるときの検査」を満たす。
- 確認事項で未回答のものが、状態付きで残っている。今回の範囲の未回答があれば、そのことを出力の先頭に書く（要件を確定したことにしない）。
