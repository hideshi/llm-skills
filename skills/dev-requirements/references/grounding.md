## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 事実の曖昧さはコードと今の動きの記録で先に潰し、意向だけを質問にする。確認事項は質問文・備考・回答原文の3層で書き、人づての伝えた人も残す | 調べれば分かる事実を相手に聞いて時間を奪うのを防ぎ、伝言や要約による前提のすり替わりを残さないため | 調査で分かる質問の差戻し数や要約ズレによる手戻りの件数を記録し、質問前の調べ方と3層記述を見直す |
| 回答の戻し先を規則（モデル）・流れ（要件）・見せ方（画面）に振り分け、迷ったら「画面を作り直しても残る話か」で決める。了承は画面ではなく規則で取る | 画面の見た目に合わせた議論で業務規則や要件の骨格が歪むのと、モックへの同意を規則の了承と取り違えるのを防ぐため | モック同意後の規則覆り件数と戻し先誤りによる修正件数を記録し、振り分け基準と了承単位を見直す |
| 既にある一覧を受けるときは作り直さず型と検査で欠けを返し、直すときは識別子を変えず廃止印と続き番号を使う | 下流の設計・試験や過去の確認事項から張られた参照（識別子）が、作り直しや番号の詰め直しで壊れるのを防ぐため | 識別子の再利用や番号詰め直しによる下流の参照切れ件数を記録し、採番と廃止の運用を見直す |
| 要望と画面文案は文字単位で一致させ、画像内の文字も写す。今回の範囲の未回答が残れば出力の先頭に書く | 要約や転記漏れで顧客固有の語が欠けるのを防ぎ、未回答を抱えたまま確定済みとして設計へ渡るのを止めるため | 転記漏れ・語の揺れ指摘件数と未回答見落としによる手戻り件数を記録し、転記照合と先頭注記の規則を見直す |
| 画面に関わる要件に入力情報と判断を書き、画面の契機があるときは必須にする。正本は要件に置き、画面の側では聞き直さない | 判断を支える情報が画面の側だけに書かれると、画面を作り直したときに業務の判断の根拠が失われ、正本が画面と要件の2か所に分かれるため | 画面の設計から「入力情報か判断が欠けている」と返された件数と、画面の側だけで決めて後から要件に書き戻した件数を数え、必須にする条件を見直す |
| 画面やワイヤーへの意見は1件ずつ確認事項の記録の行にし、層（規則・流れ・見せ方）が混ざれば分け、振り分けの結果を行ごとに残す | 混ざった意見をまとめて画面だけで直すと、規則や流れの変更がモデルと要件に届かないため | 画面を見せた後に、モデルか要件に戻すべき意見が画面だけで直されていた件数を数え、分け方と記録の形を見直す |
| 規範の正本を一つに保ち（差の表と本文で重複させない）、顧客向け文書には内部識別子を直接出さず末尾の対応表に逃がす | 同じ規範を二か所に書いて片方だけ古くなる不整合と、顧客が読みにくい内部記号が本文に混ざるのを防ぐため | 差の表と本文の規範食い違い件数や顧客確認での内部記号混入指摘数を記録し、正本配置と末尾退避の基準を見直す |
