# 不具合を是正する

不具合を1か所直して終わりにしない。直すと言える状態を先に決め、方針を選び、コード・文書・試験をそろえて直し、同じ形の箇所を探して提案するところまでを一つの仕事にする。「試験が通った」「レビューに通った」は作業の状態で、決めたとおりになったことの報告の代わりにならない。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 不具合の報告 | 条件付き（利用者からの報告のとき） | 症状・期待・環境と、観測の経路 |
| 問題台帳 | 条件付き（調査や監査で確定した問題のとき） | 対象の行と、判断の区分 |
| 原典の参照 | 任意 | あるべき動きが書かれた資料（旧システム、仕様、規則）があるとき |
| 回帰の基準 | 任意 | あれば、修正の前後で通す |
| 作業の一覧 | 任意 | 同じ形の箇所をまとめて直すと決まり、作業に分けたとき。担当する作業の範囲と終わりの条件に従う |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

不具合の報告も問題台帳も無いときは、受付で症状・期待・環境を3行にまとめ、不具合の報告にしてから始める。

## 出力

| 型 | 中身の補足 |
|---|---|
| 是正の対応表 | 方針表、確認後の結果表、同じ形の箇所の表 |
| 変更の事実 | 直した対象の識別子と差分 |
| 検証の記録 | 症状を捕まえる試験と、修正後の実行 |
| 方針外の課題の記録 | 残した穴、別の環境のフォロー、別の課題として起こすもの。担当・追跡先・回収の時期・成功条件を付ける |
| 完了条件の一覧 | 軽量な完了条件として、報告の「期待」と方針表の「決めた動き」、下の「直したと言える状態」の7項目。ほかに完了条件の一覧があれば、それを使う |
| 完了の主張 | 承認を求める報告。結果表を付ける |

結果表の形の一例は、[結果表の書き方](references/result-table.md)の末尾の「例」の節。形は任意で、欄がそろっていればよい。

## 使わない場面

- 既存の動きを調べて記録する、回帰の基準を作る（それぞれ別の仕事。あれば入力として受け取る）。
- 変更をレビューする、作業全体が完了したかを判定する。
- 正しい動きが決まっていない問題を直す。依頼側の判断を待つ。

## 直したと言える状態

次をすべて満たしたときだけ、直したと報告する。

1. 再現した、または再現しないことが証拠つきで確定している。
2. 方針が書かれていて、選ばなかった案も1行ずつ残っている。
3. コードを直した、または直さなくてよい根拠がある。
4. 回帰の試験がある、または試験で捕まえられない理由が書かれている。
5. 文書と課題の記録を更新した。
6. 同じ形の箇所の探索の結果がある（0件でも、探した範囲と0件を書く）。
7. 結果表を付けて承認を求めた。

## 手順

### 1. 受付

- 症状・期待・環境を3行にまとめる。報告された日も書く。
- 観測の経路を分ける（例: サーバーの応答、画面の表示、配備や環境、コマンドの出力、ログ。案件の入口に合わせて決める）。同じ症状でも、経路が違えば原因が違う。

### 2. 現実を確かめる

- 既に直したコミットがないか、報告の日とコミットの日の前後を比べる。
- 今のコードで、報告と同じ経路・同じ種類の入力で動かして再現する。調査のメモが古くなっていないかを疑う。
- 再現のために動かすときは、隔離した環境で動かす。本番のデータや資格情報を使わず、外部への送信は捕まえる。本番でしか再現しないときは、人に確かめてから手順を決める。
- 「再現しない」と言うのは、同じ経路で試し、環境の差の仮説を挙げ、「既に直っている」と「調べ足りない」を区別する根拠を書いたときだけ。手元で再現しないことだけを根拠に、別の環境も直っているとは言わない。

### 3. 方針を選ぶ

上から順に検討し、プロジェクトの既存のやり方に合うものを選ぶ。

| 方針 | 向いている場合 | 気をつけること |
|---|---|---|
| 局所で固定する | 1画面・1つの API の症状で、周りも局所で決めている | 同じ形の取りこぼし（手順6で探す） |
| 共有の仕組みに寄せる | 同じ形が既に2か所以上ある | 寄せた先を使う側すべての試験 |
| 横断の設定を変える | 未対応が広く、プロジェクトの方針も横断で決めている | 正本が二つになる、試験の無い所への波及 |
| 文書・配備のフォローだけ | コードは正しく、環境に反映されていない、または意図した差 | 誤解されないよう記録を残す |
| 直っていることを確かめ、保証を強める | 今のコードが正しいと証拠つきで確定した | 保証の試験を足す。別の環境のフォローが要ることが多い |

横断の設定を変えるより、既にある局所のやり方に合わせるほうが安全なことが多い。横断の設定は、同じ形の箇所の結果を見てから提案し直す。

直す箇所が複数あるときは、箇所ごとに1行の方針表（原典にある動き／直す前の動き／決めた動き／理由）を作り、実施の前に示す。同じ番号と粒度を、最後の結果表まで保つ。

次は人に決めてもらう。それ以外は、方針表を示したうえで進めてよい。
- 意図した差（今のまま残すか、直すか）の採用
- 横断の設定を変える方針への切り替え
- 本番のデータや外部のサービスの設定の変更
- 同じ形の箇所を今まとめて直す範囲への拡大

### 4. 直す

- 症状を捕まえる試験、最小の修正、文書の順に行う。プロジェクトに「文書が先」の決まりがあれば従う。どちらの順でも、両方を終える。
- 試験は、報告された項目だけでは足りない。範囲を表にし、落とし穴を試験に書き、望ましくない出力が無いことまで確かめる。
- 回帰の基準があれば、修正の前後で通す。期待値が変わった検証点は、区分と方針の番号を添えて報告する。
- 今回直さない穴は、方針外の課題の記録に既知のリスクとして残す。

### 5. 古い記録を片づける

- 古い調査のメモや課題の記録を、放置したまま完了にしない。
- 「コードは直ったが、別の環境は未確認」は条件付きの完了として、方針外の課題の記録に、担当・追跡先・回収の時期・成功条件を書く。

### 6. 同じ形の箇所を探す

- 直した箇所の名前ではなく、ほかにも当てはまる言い方で、探す形を書く。
- 打ち止めを決める（目安: 形ごとに検索2本、表は10行まで）。
- 見つけたものは「今含める（人の承認の後）」「別の課題として起こす」「既知のリスク」のどれかに振り分ける。勝手に実装を広げない。
- 繰り返し出る形は、試験や機械の検査で止められないかを1行書く。

### 7. 結果表を作って報告する

方針表の各行に、実際に確かめた値や動き、確かめ方、確かめた結果を書き足す。書き方は [結果表の書き方](references/result-table.md) に従う。

## 探索を短くする条件

次をすべて満たすときは、手順6の探索を、形1つにつき検索1本で終えてよい。この条件は探索の量だけを決め、型の一覧の「二つの道」（軽い道・通常の道。正本は規模の判定）は変えない。修正が1ファイルで済む、既存のやり方を踏襲する、横断の設定・本番の設定・意図した差に触れない。探索で今含める候補が見つかったら、短くするのをやめて通常の手順6に戻る。短くしても、「直したと言える状態」の7項目は省かない。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 「直したと言える状態」の7項目がすべて満たされているか、満たせない項目に理由がある。
- 是正の対応表の方針表と結果表が、同じ番号で対応している。
- 方針外の課題の記録の各行に、担当・追跡先・回収の時期・成功条件がある。
