# Cloudflare Product Survey

Cloudflare の仕様は変わり続け、モデルの学習データは古く、捏造されうる。このスキルは、仕様を**記憶で書かず、その都度公式資料を読んで**答えるときに使う。調べた内容をスキルのディレクトリに蓄えない。仕様の正本は公式の文書であり、その書き換えの履歴は公式の Git リポジトリにある。

## いつ使うか

- 会話で Cloudflare の仕様・制限・価格・提供状態・地域の条件を答えるとき
- 制約シート（要件の整理の成果物）に触れる製品を、構成の提案の前に裏取りするとき
- 構成案の素案で使う製品のうち、裏取りの済んでいないものを確かめるとき

## やらないこと

- モデルの記憶だけで仕様・制限・価格を書く
- 検索結果の抜粋だけを仕様の根拠にする
- 制約に触れていない製品まで全部調べる
- スキルのディレクトリに書き込む。成果物は作業中の案件の文書に置く
- 案件固有の構成・秘密・本番の数値を、案件の外に書く
- 自分たちのシステムが今どう動いているかの調査（コードや設定を読む仕事で、公式資料の裏取りではない）
- AWS / GCP / Azure を知っている前提の説明で製品を定義する（例: 「S3 互換の blob ストレージ」だけで終わる書き方）

## 公式資料の読み方

所在、Markdown 版、変更履歴の追い方、ライセンスと表示の仕方は [公式資料の引き方](references/official-sources.md) にまとめている。最初に読む。

### 所在を探す段階と、根拠にする段階を分ける

| 段階 | 手段 | 用途 | 仕様の根拠にできるか |
| :--- | :--- | :--- | :--- |
| 所在を探す | Web 検索、検索結果の抜粋、`llms.txt` の索引、コミュニティ記事 | 公式ページの URL を見つける | **できない** |
| 根拠にする | 公式ページ（またはその Markdown 版）、公式 SDK、cloudflare-docs の原稿を直接読む | 仕様を書く | できる |

- 検索結果の抜粋を仕様の根拠にしない。公式ページを直接読んで初めて根拠になる。
- 公式ブログと変更履歴は、提供開始や変更の時期の根拠にできる。ただし上限や価格は、製品の文書の Limits / Pricing ページを優先する。食い違えば両方を示す。

### 主張ごとに残すもの

1. **出典 URL**
2. **取得日**（公式ページを読んだ日）
3. **該当箇所の要約**（単独の数値だけを根拠なしで書かない）

出典のない記述（「〜とされる」「おそらく」「一般的には」）を残さない。根拠がある記述は言い切る。

## 調査項目の 3 状態

| 状態 | 意味 |
| :--- | :--- |
| **対象外** | 今回の問いや制約に触れない |
| **確認済み** | 公式資料で裏取りした |
| **未確認** | 必要だが、まだ取れない／公式に書かれていない |

- 取れない項目は **未確認** と明記する。**推測で埋めない**。「公式に記載が見つからなかった」と「無い」を区別する。
- **採用判断・設計の分岐に影響する未確認**はブロッカーとして示し、判断を保留する。
- ログインが必要などで取れないときは、その旨と、人が確かめる方法（ダッシュボードの画面など）を書く。
- 未確認の事項は、それを前提に設計する利用側の案件の文書に残すよう、利用者に促す。

## 調べる範囲

製品の全部を調べない。問いや制約シートが**触れる部分だけ**を調べる。制限と価格はプランで変わるので、前提のプラン（Free か Paid か）を先に確かめる。

| 軸 | 調べること | 設計への影響 |
| :--- | :--- | :--- |
| 位置づけ | 何をする製品か、提供状態（一般提供・ベータ・クローズドベータ）、提供されるプラン | 採用の可否 |
| 制限 | CPU・経過時間・メモリ・サイズ・レート等、プランごとの差 | 構成の可否 |
| 価格 | 課金単位、込み分、必要なプラン | コスト |
| 地域・利用者の条件 | 提供される地域、拠点の条件 | 採用の可否 |
| 認証 | API トークン、権限 | 秘密の管理 |
| 冪等・再送 | キーの有無、重複の可否 | 再試行 |
| エラー | 確定的な拒否と一時的な障害の区別 | 失敗の分類 |
| 結果確認 | Webhook、ポーリング、確認 API | 非同期の設計 |
| 環境 | ローカルの検証と本番の差 | 試験 |

## 答え方と成果物

### 会話の一問一答

結論を先に書き、主張ごとに出典 URL と取得日を付ける。保存はしない。答えの末尾に、確かめられなかったことを「未確認」として並べる。

### 案件の調査

制約シートに沿った調査は、[調査結果のひな形](templates/survey-result-template.md) で書く。保存先は利用側の案件の文書にする。

### 鮮度

- 取得日のある過去の調査結果を設計の根拠に使う前に、その製品の変更履歴（Changelog）に、取得日より後の項目があるかを見る。あれば該当ページを読み直す。
- 無くても、取得日を利用者に見せ、読み直すかを確かめる。ベータの製品は読み直しを勧める。

## 書き方

利用者の指定が無いときは、伝統的なクラウドに詳しくないアプリケーションエンジニアを読者として書く。用語の定義は、案件の調査結果では必ず、一問一答では答えに出てくる分だけでよい。

- 製品は、Cloudflare 上の課題と振る舞いで説明する（何を置き、何が安く／速くなり、いつ向かないか）。
- 専門用語（TLS 終端、TTL、anycast、権威 DNS、ゾーン、ingress など）は初出で一言定義する。
- 直訳調（「耐久的な〜」「デバイス姿勢」）は、平易な日本語に言い換え、英語の原文を括弧に一度だけ添える。
- 製品や概念の呼び方は、公式の製品ページの表記に従う。公式に無い短縮（「マネージド SQL」など）を作らない。
- 公式が互換を名乗る場合（D1 の SQLite、R2 の S3 互換 API など）、「互換」で終えない。公式が「一部だけ」「非対応」と書いた機能を確かめる。公式に差分の記載が無ければ「完全互換」と書かず、未確認にする。
- 表の項目は日本語に英語の原文を添え、数値・単位・プラン名は公式の表記のまま書く（換算したときは換算と明記する）。

## 手順

1. **問いの確認**: 問いや制約シートから、触れる軸と、前提のプランを挙げる。対象外は理由を付ける。
2. **候補の製品を挙げる**: 制約シートが製品のカテゴリだけを渡しているときは、[公式資料の引き方](references/official-sources.md) の製品の一覧、ストレージの選び方、構成図を読んで候補を挙げ、「候補（未選定）」として記録する。記憶で候補を決めない。
3. **所在を探す**: 候補ごとに、Limits / Pricing / 製品の文書 / 変更履歴 / API の URL を見つける。
4. **読む**: ページを直接読み、出典と取得日を付けて書く。
5. **まとめる**: 確認済み・未確認・対象外を分け、決定を妨げる未確認をブロッカーとして示す。
6. **引き渡す**: 構成の提案に進むなら、確認済みの知見とブロッカーを短くまとめて渡す。構成案の素案から裏取りを頼まれたときは、その製品だけを同じ手順で調べて返す。

## 完了条件

- 問いや制約に触れる製品・軸について、確認済みか未確認かが明示されている。
- 主張ごとに出典 URL と取得日がある。
- 記憶だけに基づく仕様の記述が無い。候補の製品は公式の一覧や構成図から挙げている。
- 決定を妨げる未確認事項が隠れていない。
- 呼び方が公式の表記に従っている。案件の調査結果では、専門用語が初出で定義されている。
