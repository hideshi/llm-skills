# 根拠と変えたところ

実装を終えた作業の差分を、実装した側が設計の判断と仕様に照らして点検する手順が、どの先行の手法に基づき、どこを変え、どこが独自の判断かを書く。手順そのものは SKILL.md が正本で、ここは読む人が元の考え方をたどるための別紙。

- 確かめた水準: 「原典を読んだ」「書誌と二次資料で確かめた」「未確認」

## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 差分を読む前に「期待の一覧」を原典から集めて検証の記録に書く | 実装した本人が差分を先に読むと、書いたコードに合わせて仕様や受入条件の解釈を読み替えてしまうため | 期待の一覧を作った検証の記録でも後続のレビュー結果や受入で仕様抜けが見つかった割合を数え、事前収集の必須条件を見直す |
| 冒頭に「実装した側が読んで点検した記録」と書き、判定を出さず未実施の検証に「独立したレビュー」を必ず書く | 実装者の自己点検が、独立したレビューや実行検証の代わりに使われてしまうのを防ぐため | 自己点検が独立レビューの代わりに完了扱いとなった逸脱件数を記録し、冒頭注記と判定禁止の書式を見直す |
| 高の指摘で設計の判断を変えるべきと考えるときは、実装側で判断を変えず作業を止めて依頼者に戻す | 点検の場で実装者が勝手に設計の判断を書き換えると、合意済みの前提や波及調査が崩れるため | 自己判断で設計の判断を書き換えて後戻りや不整合が起きた件数を記録し、停止・差し戻しの条件を見直す |
| 出どころが無く害も示せない指摘は「好み（低）」、出どころは無いが害を示せる指摘は「仕様の欠け（依頼者への問い）」とする | 根拠のない好みで作業を止めることと、逆に仕様の穴を見過ごすことの両方を防ぐため | 「好み」に下げた指摘からの実害件数と仕様の問い返しで防げた欠陥件数を記録し、切り分け基準を見直す |
| 差分の外で見つけた食い違いは、この作業の指摘に混ぜず「方針外の課題の記録」に出す | 作業の差分が際限なく膨らむのを防ぎつつ、見つけた問題を捨てないため | 差分外の発見を混ぜて作業が肥大化・遅延した回と台帳へ分離した回の手戻り件数を比べ、切り分け基準を見直す |
| 仕様の9観点（受入条件・業務規則・状態遷移・イベント・横断の関心事・絞り込みのそろい方・設計の判断・既存の動き・テスト）で差分を読む | コードの作りの点検だけでは拾えない要件漏れ・規則の迂回・条件の食い違いを、自己点検でも網羅して見つけるため | 独立レビューで見つかった欠陥のうち9観点のどれで拾えるべきだったかの割合を記録し、観点の項目を見直す |
