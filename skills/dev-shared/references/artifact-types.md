# 開発スキル群の成果物の型

`dev-` で始まる単位とプロファイルが、入力と出力に使う成果物の型の一覧。単位どうしは名前で呼び合わず、この型でつながる。型の名前は、この表にあるものだけを使う（`scripts/check_dev_skills.py` が検査する）。

型は、ファイルの形式や置き場所を決めない。どの道具で作っても、表の「中身」を満たせばその型として扱う。中身の欄の項目が足りないときは、足りない項目を明記して渡す。

その型として受け取れるかは、中身の欄がそろっているかで判定し（足りないと明記した欄と、条件に当たらないので書いていない欄は、そろっているとみなす。中身の正しさは、受け取った単位がそれぞれの手順で確かめる）、単位に置いた例と形（表か箇条書きか、節の名前、欄の順）が違うことを指摘にしない。既にある成果物を、例に合わせて作り直さない。

| 型 | 中身 | 主に作る工程 |
|---|---|---|
| 変更の事実 | 対象の識別子（課題番号・仕様の識別子など）、変更したファイル、差分の範囲（例: コミットの範囲）、変更の種類。指摘を受けて直したときは、対応する前回の指摘の識別子 | 実装 |
| 原典の参照 | 判断の基準になる文書（要件・設計・規則・受入条件）の所在と節。中身の要約は含めない | 仕様化 |
| 検証の記録 | 実行した検証ごとの対象（テストケースの識別子があれば書く）・範囲・日時・コマンドまたは手順・結果と、未実施の検証の一覧。範囲を絞った検査（モデルの検査など）では、置いた仮定と探索した範囲。結果を、確かめた所と違う環境（本番、利用者の環境など）での振る舞いの根拠にするときは、二つの環境の差（本物と疑似の境界、代わりに使ったもの、確かめていない所） | 実装・試験 |
| レビュー依頼文 | 変更の事実・原典の参照・検証の記録と、発見を求める観点、出力の形の要求をまとめ、そのまま渡せる文 | レビューの準備 |
| レビュー結果 | 対象の識別子、判定（承認／変更要求／判断を人へ戻す）、証拠の種類と重大度が付いた指摘、検証と探索の記録、人への問い、レビューしたモデルの自己申告 | レビュー |
| 方針外の課題の記録 | 今は直さない課題（方針外の改善、既知のリスク、別の環境のフォロー、別の課題として起こすもの）ごとの識別子、見つけた所、方針との関係、影響、状態、担当、追跡先、回収の時期、成功条件、見直すきっかけ。点検で見つけた問題を直さずに受け入れたもの（既知のリスク）は、受け入れの正本をここに置き、承認した人と日、受け入れる範囲、見直す期限、問題台帳の識別子を書く（受け入れの結びつきは、ここから問題台帳を指す一方向だけ） | レビュー・是正 |
| 完了の主張 | 実装やレビューの担当が「終わった」と述べた報告。根拠として採用する前のもの | 実装 |
| 完了条件の一覧 | その時点で有効な要件と受入条件、または軽量な完了条件の全項目。項目ごとの識別子（軽い道では番号でよい）。受入条件なら属する要件の識別子（1つ以上）と、確かめる業務規則の識別子（あれば）。画面に関わる要件は、利用者、目的、入力情報（何を見るか）、判断（何を決めるか。無ければ「なし」）を持つ（画面の契機があるとき、つまり規模の判定が画面の設計に当てたか、適用する画面に画面の設計が要る画面（下の「仕様化の契機」の画面の設計に当たる画面。「未割当」と書いた画面も含む）が書かれているときは必須）。適用する画面は、範囲の宣言（入口、既存の画面の名前、未割当）として書き、画面の識別子との結びつきは画面の設計に置く。途中で画面が要ると分かったら、適用する画面に書き足す。廃止した項目は、消さずに廃止の印。テストを先に書かない範囲があれば、その範囲、理由、代わりの確かめ方、依頼者の確認の記録 | 仕様化 |
| 追跡表 | 下の「識別子と結びつき」の結びつきを、要件から変更の事実まで辿れる形に集めたもの。通常の道で持つ。軽い道では持たない | 仕様化・計画 |
| 作業の一覧 | 作業ごとの識別子、対応する受入条件の識別子（無ければ出どころの識別子）、足す・通すテストケースの識別子、先に終わっている必要がある作業、並べて進められるか、終わりの条件、規模の見積もり、状態（未着手／決定待ち／進行中／終わり）、区分（設計の判断があればその識別子で指す。無ければ直接書く）。実装の後は、行った変更の事実（コミットや差分の範囲） | 計画・実装 |
| 設計の判断 | 下の「設計の判断の書き方」に従う。判断ごとの共通の欄と、観点ごとの一覧からなる | 設計 |
| 規模の判定 | 判定の時点（着手／原因や設計の確定の後／終わる時）、根拠が予測か実際の差分か、道（軽い道／通常の道）、観点ごとの要る・要らないとその理由（下の「設計の観点と契機」による）、仕様化の作業ごとの当たる・当たらない（下の「仕様化の契機」による。設計の判断は求めない）、運用の作業ごとの当たる・当たらない（下の「運用の契機」による。成果物と承認の有無は監査が確かめる）、引き上げと抑制の根拠、影響する継続の文書の分類、承認済みの完了条件への影響、範囲外の疑い。モデルの検査を候補にするときは、人の依頼の記録の所在 | 受付・監査 |
| 作業状態の控え | ある時点の版（コミット）、作業ツリーの変更の有無、監視するパスの内容のハッシュ、退避の所在（控えの枝、退避したファイルの置き場。あれば） | 監査・引継ぎ・版管理 |
| 引継ぎの記録 | 宛先（次のセッション／交代する担当）と書いた時点、作業の場所（リポジトリ、枝、作業ツリー、消えうる一時の環境）、記録の状態（有効／再開済み／置き換え。置き換えなら後の記録の所在）、基準の作業状態の控えの所在、未確定の変更とコミットしない理由、進めていた位置（使っていた組み合わせと工程（工程は組み合わせの工程の識別子で書く）、そこまでの判定と選んだ道、繰り返しの回数、最後に流した検証と結果。落ちたままのものはその理由）、この担当の役割（作った側／レビューする側／監査する側）、作業の状態（作業の一覧があれば識別子で指し、進行中の作業の最後に触った所だけ。無ければ作業ごとに未着手／決定待ち／進行中／終わり）、人の決定（所在で指す）と決定待ち、担当や委任先が自分で下した判断（人の決定と分ける）、委任中の作業（委任の依頼文の所在、宛先、状態: 送った／受け取った／終わり／失敗と理由）、届いていない連絡（内容、宛先、届かなかった日時と理由、要る対応）、今止めているものと回避、次の一手（3つまで、優先の順。提案として読む）、次に読む原典と読む理由。再開したら再開の記録（選んだ記録、照らした控えとの差と分け方、人に確かめたこと）。資格情報と個人のデータは所在で示す | 引継ぎ |
| 委任の依頼文 | 作業の一部を別の担当に頼むときに、そのまま渡せる文。背景（切り出した範囲に要る所だけ）、ゴールと完了条件、触ってよい範囲と触らない範囲、正本（原典の参照、人の決定の所在。人が「やらない」と決めたことを含む）、返す形（結果、変えたもの、委任先が自分で下した判断を分ける）、制約（追加の質問の仕方、コミットと公開の可否、再委任の可否、時間）。資格情報と個人のデータは所在で示す。レビューを頼むときはレビュー依頼文を使う | 引継ぎ |
| 完了判定 | 判定（進めてよい／条件付き／止める）、完了条件の項目ごとの証拠と証拠の強さ、指摘、残作業の分類、確定の候補と除外、人に聞く一言、実施しなかったこと | 監査 |
| 不具合の報告 | 識別子、症状・期待・環境（各1行）、報告された日、観測の経路（例: サーバーの応答、画面の表示、配備や環境、コマンドの出力、ログ。案件の入口に合わせて決める）、出どころ、確認の水準 | 受付 |
| 改修の範囲 | 変える・調べる機能と経路、対象の版、共有の処理とそれを使う側、関係する既存の課題や計画の所在 | 受付 |
| 現状の振る舞いの記録 | 観察ごとの事実、対象の版、確認の水準（実行／静的／公開情報／未確認）、実行なら本物を通した境界と疑似の部分、根拠、推測と未確認の欄、既存の資料との差 | 調査 |
| 問題台帳 | 問題ごとの識別子、概要、責任を持つシステム、今の影響と変えた後の影響、確認の水準、根拠、状態、判断の区分（誰が決めるか: 作る側で決められる／設計で決める／依頼側の判断待ち／別の計画で扱う／本番の事実確認待ち）とその承認の状態、人の決定（決めたときだけ: 直す／受け入れる／事実を確かめるまで保留と期限。受け入れたら方針外の課題の記録が問題の識別子を指す）。仕様の質問と事実確認の別表 | 調査 |
| 回帰の基準 | 検証点ごとの識別子と期待値、区分（保持／変更予定／回答待ち）、関係する問題の識別子、置いた層、本物と疑似の境界、繰り返しと誤りの注入の結果、対象の版 | 試験 |
| 是正の対応表 | 箇所ごとの番号、原典にある動き（旧システム・仕様・規則。あれば）、直す前の動き、決めた動き、理由、選んだ方針と選ばなかった方針。確認後は結果・確かめ方・確かめた結果・回した版と環境。同じ形の箇所の表（探した形、探し方、件数、扱い）。依存の版上げでは、部品ごとの旧版と新版、選んだ候補と選ばなかった候補と人が決めた記録、ロックの差の要約、範囲内の最新化の扱い、改造の載せ直しの記録、人が採った差が出てよい一覧 | 是正 |
| 安全の点検の記録 | どこまで見たかの証拠。点検の種類（告知の照合／入口の点検）ときっかけ（特定の告知／定期／点検し直し）、点検の時点と対象の版（コミット、ロックのハッシュ。本番の版はその根拠と取得日、無ければ「本番は未確認」）、要求を送ってよい相手の許可の所在（入口の点検のとき）、範囲（対象ごとに実行した／実行しなかった／対象外と理由、母数と網羅の状態）、項目ごとの行（識別子、出典（告知の識別子と別名、公式の所在、公開日と更新日、取得日）、適用（必須／触れたら／対象外／方針が無い）、判定（告知の照合: 当たる／版は対象だが当たらない（理由と確かめ直す条件）／版が対象外／確認不能（足りない条件）。入口の点検: 合格／問題がある／誤検知／環境による（本番で確かめたか、本番は確認不能か）／確認不能（足りない証拠））、条件ごとの成否と根拠の所在、問題台帳に載せた行はその識別子。受け入れたかは、問題台帳の人の決定と方針外の課題の記録で持ち、ここには写さない）、前回との差（新規、消えたものとその理由、判定の変化。初回は比較元なし）。実行の事実（コマンド、結果、日時）は検証の記録を所在で指す | 点検 |
| 秘密の目録 | 値を持たない秘密の項目の一覧。対象の版と環境、取り出し方（名前だけを取り出した方法か、人が用意した値の無い一覧か）と見なかった所。項目ごとの識別子、キーの名前、種類（パスワード、API キー、トークン、署名や暗号の鍵、そのほか）、使う場所（設定とコードの所在。名前で）、使う環境、置き場所の種類（設定のファイル、環境の変数、保管の仕組み、コードに直書き）、保管先の項目の名前（値と認証つきの所在は書かない）、持ち主、用途、入れ替えの記録の有無、確認の水準、問題台帳の識別子（直書き、持ち主が分からない、など）。人しか知らない欄（持ち主、用途、保管先）を人が確かめたかと、承認の状態（版と日） | 棚卸し |
| 個人情報の台帳 | 扱う個人の情報の一覧。行は「ある情報が、ある経路で、ある目的のために扱われる」こと。行ごとの識別子、情報（利用者に分かる言葉）、本人の種類、取得の経路、扱い（取得／送信／一時処理／保存）、目的（運営者の言葉。述べた所在）、送り先と保存場所、保持期間（起算点つきの最長。複製に残る期間）、削除の方法と消えないもの、根拠（コード、設定、文書の所在。名前で）、運営者や文書が述べた法的な根拠の所在（写すだけ。無ければ確認事項の番号）、確認の水準、確認事項の番号。別表: 外部の送り先（名称、送る項目、相手での使われ方、保存の場所、残る期間、確かめた資料の所在と日）、端末に残る情報（Cookie、ブラウザの保存領域の名前、目的、期限、発行者）、取得しない情報。付属: 公開する文の草案（台帳の事実の写しだけ。確認待ちの所に確認事項の番号の印）。実データの例は書かない。承認の状態（承認した運営者、日、版） | 棚卸し |
| 本番の手順 | 本番で人が流す手順。核の欄: 対象の環境と種類（初回か2回目以降か、データを変えるか）、載せる版と成果物のキー（「最新」や「1つ前」で指さない）、承認の状態（版と日と承認した人。手順の承認と、本番で流してよいという判断は別の欄）、先に済ませる作業と済んだかの確かめ、始めてよい条件（使われていないか、定期の処理とキューが空いているか）、担当×ホスト×利用者の表、段ごとの欄（印（下の「段に付ける印」）、読むだけか変更か、出どころ（保守されている正本の手順書の今の版のまま／それを変えた／前の作業の写し／新しく作った）、確からしさ（手元で流した／読んで導いた／未確認）、その段だけで判定できる確かめ方、期待する結果、止める条件と止めた後の行き先（立て直しか、戻しのどの段か））、戻し（組にするもの: 成果物、DB、設定。判断の基準と基準ごとのコマンド）、途中の失敗の表（すぐの失敗、遅い失敗、中断、流す利用者の取り違えごとに、そのときの状態、戻し方、確からしさ。未確認のまま受け入れるなら承認の所在）、流した記録の所在、使う資格情報の所在（値は書かない）。条件付きの欄: 止まる区間と見込みの時間、影響を受ける人への連絡、予行（記録と本番との差は検証の記録を所在で指す。予行のために変えた所、省いた予行と理由と決めた人、予行の起点）、バックアップをどこまで確かめたか（終わりの印と表の数／使い捨ての DB に戻してみた／本番のバックアップを戻した）、直前と直後の確かめ（回帰の基準や指紋の所在、除いた道筋と理由）、後片付け（控え、古い版、作業用の試験の利用者）の期日 | 本番の作業 |
| システムの地図 | 引き継いだシステムの、どこに何があるかの目録。動きは書かない。範囲と対象の版、動く単位ごとの名前と役割（1行）と言語・枠組み・版、環境（本番、検証、手元）の所在と違い、入口（画面、窓口、定期の処理、キュー）の一覧の所在、外部とのつながり（相手と向き）、主なデータの置き場所、横断の仕組み（認証、認可、ログ、監視）の所在、手順と資料（起動、配備、運用）の所在と、手順どおりに動かない所、秘密の目録・個人情報の台帳・問題台帳の所在、変更の多い所の候補、項目ごとの確かめ方（機械で確かめた／読んで推定した／人が答えた／未確認）と根拠の所在、分からない所の一覧、正誤の履歴（訂正の日、答えた人、直した項目、前の記述） | 棚卸し |
| テストケース表 | ケースごとの識別子、対応する完了条件の項目（無ければ出どころ）、確かめる業務規則の識別子と、満たすケースか破るケースか（あれば）、分類、確かめる条件節、入力と前提（値そのもの）、期待結果（否定と副作用を含む）、置く層、必須度。展開しなかった組み合わせの注記。E2E のシナリオなら、主分類、前提データ、操作、検証点とその層（画面・保存・通知・帳票）、負の検証、既存の E2E への影響表（識別子、扱い、範囲、根拠） | 試験 |
| 受入の証拠 | 証拠（画面の写し、録画、帳票など）ごとの対象（ケースの識別子か完了条件の項目）、取得した版と環境、所在とハッシュ、注釈と主張する結論、自己視聴の結果、確定の状態（未確定／確定）、確かめていない範囲 | 試験 |
| ドメインモデル | 範囲（対象の業務、範囲外、一つのシステムかサービス群か）、用語（識別子を勧める。日本語名、英語名、定義。同名異義は修飾する）、管理するもの（主な属性、関係と多重度、一緒に変わるまとまり、操作の名前）、状態と遷移（状態を持つ属性ごとの遷移ときっかけ・主体。無ければ「遷移なし」）、区分（値の一覧、どの値にも入らない場合の扱い）、計算の規則（式と端数処理。式ごとに、結論を置いた業務規則の識別子を指す）、ドメインイベント（識別子、きっかけになる遷移か操作、整合性の要件。イベントを使わない案件では「使わない」と書く）、外部との関係（要約と一次情報の記録の所在）、未確定事項。規則の本文は持たず、業務規則の一覧の識別子で指す（遷移のガード、区分の制約、計算の規則から） | 仕様化 |
| 業務規則の一覧 | 規則ごとの識別子（一つの系列。所有が移っても変えない）、本文（結論だけ）、種類（不変条件／まとまりをまたぐ／一意性／状態遷移の可否／計算／構造・方針）、所有（違反を拒むガードを置く側。一つ）、根拠（関係者の決定（確認事項の番号）／担当の裁量／公的な規則（一次情報の記録の項目の識別子）／外部の仕様（同）／業界の慣行／推測／実装で受け入れた動作／不明（由来が分からない既存の規則を含む）、と出典。問うている確認事項があれば、その番号も）、確かさ（確定／仮説／未確定／保留と期限）、守っている箇所（層ごと。確認の水準を付ける）と守られていない経路、確かめる手段（テスト／レビューや構造の検査と理由）、関係するイベント、有効期間、廃止の印 | 仕様化 |
| 一次情報の記録 | 対象（外部のシステム・業界団体の規格や標準か、公的な規則）と今回触れる範囲、項目ごとの識別子（ほかの成果物から指す鍵。一度振ったら変えない）と出典（名、段、URL、取得日、版や施行日）と引用（原文のまま、省いたら明記）、状態（対象外／確認済み／未確認）、抽出したもの（用語の対訳、寿命、制約、操作の原子性、規則が求める値（期限、率、端数処理など））、どの判断を縛るか、再調査のきっかけ | 仕様化 |
| 確認事項の記録 | 通し番号（変えない）、質問文（それだけで意味が通る）、備考（今の仕様と推測の根拠）、回答（原文のまま）、回答日、答えた人と伝えた人、論点の名（規則との結びつきは、業務規則の一覧の根拠の欄にだけ書く）、対象（画面への意見なら、画面の識別子と箇所。あれば）、状態（未回答／確定／変更／却下／一部／保留と期限／担当に任せた／取り下げ）、回答の戻し先（モデル／要件／画面／台帳） | 仕様化 |
| 画面の設計 | 範囲（対象の画面群。Web の画面に限り、帳票・メール・通知の文面は含まない）と、もとにした完了条件の一覧の版、承認の状態（担当の案／人が採った（採った版、日、採った人）／採り直し待ち（直した所））。共通仕様（案件が続けて使う文書にあれば原典の参照で指し、ここに写さない。無ければここに書く: 画面の種別（管理面／公開面・訴求／公開面・道具／混在）と、決めた問いの答え（認証の有無、主な目的、成功の目安、流入元、移動の形）、利用者ごとの端末と優先する幅、対象の言語と地域、日付と数値の書式、完了の知らせ方、文言の決まり、アクセシビリティの目標の水準）。画面一覧（画面ごとの識別子、名前、目的（一つのタスク）、利用者、入口、データの範囲（本人／組織／横断）、支える要件と受入条件の識別子）と、導いたが作らない画面と理由。画面の流れ（遷移ごとの元、操作、先、開き方（ページ／ダイアログ／横のパネル／その場で編集）、条件。失敗と権限の遷移を含む）。画面ごとの仕様（見せる情報と出どころ（要件の入力情報）、操作と出どころ（要件の判断）、業務規則ごとの画面の制御（規則の識別子、制御（不可／警告／確認／非表示）、理由の見せ方）、エラーと許可の出し方（設計の判断の識別子＋行の鍵で指す）、状態（通常、空、読み込み中、失敗、権限なし、権限の変化）、内容の極端（長い文字、0件、大量、一部の失敗、取り消せない操作）、未保存の変更と再試行、文言、個人情報の見せ方と伏せ方（決まりは設計の判断を指す）、アクセシビリティの要件、計測点（公開面のとき）、類似の画面との差、使う部品の名前（デザインシステムがあれば））。既存の画面を踏襲するときは、踏襲する範囲（殻、配置、文言、操作ごとに、踏襲／差分／未定）と合意の所在。上流へ返すもの（受入条件の案、確認事項の候補、設計の判断で決めてほしいこと（公開面で入力を保持するときの保存場所・期間・削除、個人情報の見せ方の決まりなど））と、決定待ちの所 | 仕様化 |
| ワイヤー | 画面の設計を人に見せられる形にしたもの。形式は問わない。対象の画面の識別子と状態、操作できる範囲、忠実度（低／中）、所在、もとにした画面の設計の版、限界（作っていない所。実装に流用しない）、ダミーデータの出どころ（作り物であること）、仮説の業務規則に頼る箇所と付けた印（あれば）、画面の設計との照合の結果（食い違いと、どちらを直したか） | 仕様化 |
| 統合の判断表 | 操作の種類、基準・自分側・相手側の位置、未解決のパスの一覧、判断ごとの行（識別子、パス、各側の意味、契約の変化の区分、採否、根拠）、隠れ衝突の点検行、省いたパスとその理由、未決で人に聞くこと | 版管理 |
| 作業場所の台帳 | 作業ごとの識別子（作業の一覧があればその識別子）、場所、枝、目的、専用の資源（テスト用保存先・実行環境の枠・排他の識別子と置き場）、状態（使用中／統合済み／破棄承認済み／片付け済み）、片付けの確かめ（未確定の変更・未反映の履歴・除外された成果物の退避、破棄の承認（未統合のまま捨てる場合）、専用資源の解放） | 版管理 |
| 破壊的操作の計画 | 採る手順、対象と影響の範囲（共有済みか未反映か。共有済みなら知らせる相手）、操作ごとの印（下の「段に付ける印」。読むだけの操作には付けない）、履歴の書き換え・強制の送信・外部道具の導入の要否、強制送信を行うときは対象の参照と確認済みの版、控えの枝と戻し方、確認の結果、承認の状態（案／承認／中止）と承認者・日時 | 版管理 |

問題台帳の「仕様の質問と事実確認」と確認事項の記録の使い分け: 今の動きやデータの事実を問うもの（調べて見つけた食い違い、由来の確認）は問題台帳に、関係者の意向と業務規則を問うもの（どうしたいか、規則をどう決めるか）は確認事項の記録に置く。同じ問いを両方に書かない。

## 設計の判断の書き方

設計の判断は、判断ごとの共通の欄と、観点ごとの一覧からなる。設計の単位は、どれも共通の欄をそろえて出す。

### 判断ごとの共通の欄

| 欄 | 中身 |
|---|---|
| 識別子 | 観点をまたいで一つの系列（例: `DD-`）。一度振ったら変えない。複数の単位や別のセッションで書くときも、同じ系列の続きを振る |
| 観点 | 下の「設計の観点と契機」の観点のどれか |
| 問いと答え | 何を決めたか、選んだ案、選ばなかった案とその理由 |
| 根拠 | 原典の参照、完了条件の項目の識別子、業務規則の識別子、一次情報の記録の項目の識別子 |
| 承認の状態 | 担当の案／人が採った／人の決定待ち（決定待ちなら選択肢と既定） |
| 保証の宣言と前提 | 何をどの前提で保証するか（あれば） |
| 変更の区分 | 既存を変えるとき: 新規／既存の修正／触らない／廃止。触らない既存を1件以上 |
| 波及と順序 | 影響する箇所と件数（検索した結果）、先に置くものの制約 |
| 確かめる観点 | テストケースへ渡すもの |
| 未確認 | 未確認の事項と、判断への影響。対象外とした観点と理由 |

### 観点ごとの一覧

エラーの一覧、操作の一覧、規則ごとの守り方の表のように、行が多い中身は、判断の中の一覧として書く。

- 行は、ほかから指されるときの鍵を持つ。鍵は、安定した名前かコード（エラーのコード、操作の名前、規則の識別子など）にする。
- ほかの成果物からは「判断の識別子＋行の鍵」で指す（例: `DD-3` のエラー `invoice_already_finalized`）。テストケースや作業の出どころも、この形で書ける。
- デザインシステムの一覧（トークン、部品）は、名前を行の鍵にする。画面の設計とワイヤーは、部品とトークンをこの名前で指す。

### 設計の判断と継続の文書

設計の判断は、今回の変更で決めたことを入れる型。人が採り、実装で確かめた後は、案件が続けて使う文書（データ設計、公開する契約、横断の関心事の一覧、許可の表など）に反映し、それ以降はその文書を原典の参照として扱う。今回の変更の文書だけを、続けて使う正本にしない。

## 設計の観点と契機

規模の判定が「要る観点」を決めるときの表。観点を足すときは、この表と、使う単位を名指しするプロファイルだけを直す。

| 契機 | 観点 |
|---|---|
| 新しい状態や分岐先、責務の置き場所の迷い、共通の計算を変える | 責務の配置、共通化と契約の変更 |
| 横断の関心事（権限、監査、通知、入力検証、利用者の分離）に新しい分岐が生まれる、またはそれらを通る新しい入口ができる | 責務の配置（守る場所） |
| 誰が何をできるかが変わる（新しい操作や役割、所有や所属による区別、組織のデータの分離、権限の委任や代行、危険の大きい操作） | 認可（誰に何を許すか） |
| プログラムやシェルから呼ばれる契約（API、CLI、メッセージ）を足す・変える | 呼ばれる契約 |
| AI エージェントが呼ぶ道具（MCP のツールなど）として機能を公開する・変える | エージェント向けの契約 |
| 新しい失敗のしかたや、利用者に見せるエラーが増える・変わる | エラー |
| 保存の構造、制約、同時更新、移行が変わる | データ |
| その場で結果を返さない処理（ジョブ、キュー、定期のバッチ）を足す・変える | 非同期の実行 |
| 外部サービスや別のシステムを呼ぶ、またはそれらから呼ばれる | システム間の連携 |
| 記録する出来事の種類、出来事ごとの欄、相関の付け方、段、保持、書かないもの、数える項目の決まりを、新しく決める・変える | ログ |
| 入口での形の検査（大きさ、型、文字集合、回数）、外からの値を危険な処理（画面への出力、問い合わせ、式やテンプレート、外部のコマンド）へ渡す方式、状態を変える要求の出どころの確かめ方、応答の安全の設定（ヘッダ、Cookie の属性、オリジンの扱い、外から読む資源）、セッションの作り直しの方式、使わない窓口の閉じ方を、新しく決める・変える | 応答と入口の安全 |
| 画面で使う部品やトークン（色、文字、余白などの名前の付いた値）を新しく足す・変える、または部品とトークンの決まりを新しく定める・広げる | デザインシステム |
| 並行実行や状態遷移の性質を、人が厳密に確かめたいと言った | モデルの検査（人の依頼の記録の所在を書く） |

ログと、応答と入口の安全は、方式や決まりを新しく決める・変えるときだけ当たる。決まっている方針に合わせる直し（決まった欄でログを1行足す、決まった設定を入れ忘れた入口に足す）は当たらず、是正や改修の中で直す。境目は次のとおり。

- 拒否や危険の大きい操作を記録するかは認可、失敗ごとに記録に要る意味の情報と監視で数えるかはエラーが決め、どの欄でどう書くか、数える項目をどう集めるかはログの決まりに従う。
- 業務の値として正しいかの検証は業務規則の側、検査をどこに置くかは責務の配置が決める。応答と入口の安全は、入口で形を拒む方式と応答の設定だけを決める。
- セッションの寿命は認証の方式の側（下の文）、作り直しの方式は応答と入口の安全の側。

認証の方式（ログイン、トークンの発行と失効、セッションの寿命）、監査の記録の保証（改ざんの防ぎ方、保持の義務）、通信の暗号化、秘密の保管の方式（置き場所、入れ替え）は、どの観点にも無い。監査の記録の出来事の種類と欄はログの観点で決めるが、保証は含めない。これらが変わる変更は、規模の判定にその旨を書き、どう扱うかを人に確かめる。

## 仕様化の契機

規模の判定が、仕様化の作業（モデル、規則の抽出、一次情報、画面の設計）を要るかを決めるときの表。ここに当たっても設計の判断は作らないので、上の「要る観点」とは別に「当たる・当たらない」で書く。

| 契機 | 仕様化の作業 |
|---|---|
| 新しい概念・業務規則・状態・区分ができる、または変わる。または、今回の範囲で根拠にする業務規則に仮説・未確定がある | ドメインモデル |
| 業務規則が文書に無く、コードやデータに散らばっている | 規則の抽出 |
| 外部の仕様（つなぐ相手、業界団体の規格や標準）や公的な規則が、要件や設計の成否を決める | 一次情報 |
| Web の画面を足す、または画面の流れ、見せる情報、操作が変わる | 画面の設計 |

画面の設計に当たらない変更（決まった文言の直し、決まった部品の入れ忘れ）は、是正や改修の中で直す。部品とトークンだけが変わるときは、上の「設計の観点と契機」のデザインシステムで判定する。

## 運用の契機

規模の判定が、運用の作業を要るかを決めるときの表。ここに当たっても設計の判断は作らないので、「当たる・当たらない」で書く。秘密の項目、個人情報の扱い、ログの決まりのように、続けて使う文書で持つものは、ここではなく「続けて使う文書への影響」で判定する。

| 契機 | 運用の作業 |
|---|---|
| 本番への反映に、データの移行や作り替え、実行環境（言語の実行環境、DB、Web サーバー、OS のパッケージ）の版上げ、設定か秘密の項目の追加・変更、利用者に見える停止、順序の制約のどれかがある | 本番の手順 |
| 部品か実行環境を足す、または版を変える | 依存（告知が当たるかの点検を、別の組み合わせとして起こすかを人に確かめる） |

保守されている標準の手順で足りる反映（手順書の今の版のまま流せる）は、本番の手順に当てない。

規模の判定は、運用の作業と、続けて使う文書の分類（秘密の項目、個人情報の扱い、ログの決まり）が当たるかだけを書く。当たるものに成果物と人の承認があるかは、完了前の監査が監査の時点で確かめる（判定の後に作られる成果物があるため）。

## 段に付ける印

人が流す手順の段、承認を待つ操作に付ける印。記号ではなく言葉で書き、当たるものを全部付ける。手順を作る単位と、操作の計画を作る単位が、同じ語を使う。読むだけの段には印を付けない（読むだけか変更かは、段の欄で示す）。

| 印 | 当たる操作 |
|---|---|
| 取り返せない | 消す、上書きする、履歴を書き換える、外へ出した後で取り消せない |
| データを変える | データの更新・移動・削除、権限や持ち主の変更、移行 |
| 止まる | 利用者に見える停止、受付の停止、常駐の処理の入れ替え |
| 外へ送る | メール、通知、課金や決済、外のサービスへの書き込み |
| 変える | 上のどれにも当たらない変更（止まらずに取り返せる、設定の書き換えや成果物の置き換え） |

## 本番の事実と、記録の扱い

本番の事実を使う単位と、弱点や内部の構成を記録する単位が従う決まり。単位は、この節を指して従う。

本番の運用の読み取り（サーバー、DB、記録、配備の状態、保管先）:

- 担当は、読み取りでも本番に接続しない。読み取りの手順を作り、人に流してもらい、出力を受ける。人が流した出力が無ければ「本番は未確認」か、問題台帳の本番の事実確認にする。
- 手順は、全体を先に示してから一つずつ渡す。秘密が映る表示（設定の全文、環境の変数の一覧）と、読み取りでも常駐の処理を起こすなどの副作用のある道具を避ける。
- 出力は、秘密と個人の情報を伏せてから受ける。伏せ損ねた値が届いたら、記録に写さず、人に伝える。

公開の入口への限定した要求（入口の点検）は、上の読み取りとは別に扱う。人が許可の記録で許した、自分たちが管理するホストへの、普通の利用者と同じ状態を変えない要求だけを送る。

記録そのものが機微なもの（未修正の弱点、内部の構成、秘密の所在、個人の情報の所在の一覧）:

- 置き場所と共有の範囲は、案件の決まりに従う。決まりが無ければ、人に確かめる。
- 外のモデル、外の道具やサービス、公開の課題に渡す前に、渡してよいかを確かめる。
- 秘密の値、Cookie やトークンの値、個人の情報の実データ、攻撃の手順を書かない。

## 応答と入口の安全の項目

応答と入口の安全を設計する単位と点検する単位が、同じ名前で指す項目。設計は項目ごとに「何を決めるか」を、点検は「何を観測するか」を、それぞれの単位に書く。ここには項目の名前と、普通の応答だけで判定できるかの区分だけを置く。

| 区分 | 項目 |
|---|---|
| 応答だけで判定できる（普通の要求の応答の見出し、本文、タグから、値を変えずに分かる） | 埋め込みの拒否、内容の種類の推測の抑止、読んでよい資源の制限、暗号化した通信の強制、版や構成を明かす見出し、別の出どころからの呼び出しの許し方（応答に出た値）、Cookie の属性（応答に出た値）、外から読む資源の中身の確かめ、使っていない読み込み、内部の情報の露出（スタック、一覧の表示）、暗号化した画面での暗号化しない資源の混在 |
| コードや設定を読むか、入力・利用者・状態を変えないと判定できない | 秘密の露出、1件ごとに触ってよいかの確かめ、外からの文字の出力の変換、状態を変える要求の出どころの確かめ、問い合わせ・コマンド・パスの組み立て、受け付ける項目の制限、セッションの作り直しと無効化、認証の関門の退行、ファイルの受け付け、別の出どころからの呼び出しの許し方（設計）、移動先の制限、サーバーが外の所在を取りに行く処理、回数の制限、使わない窓口 |

応答だけで判定できる項目を見たことを、もう一方の区分の項目を確かめたことにしない。

## 識別子と結びつき

要件・受入条件・テストケース・作業に識別子を振り、結びつけておくと、抜け漏れを文の意味ではなく識別子の突き合わせで見つけられる。業務規則、ドメインイベント、確認事項にも識別子を振り（用語にも勧める）、同じ決まりで結ぶ。

### 二つの道

| 道 | 使う場面 | 求めること |
|---|---|---|
| 軽い道 | 1か所の是正、小さな変更 | 完了条件に番号を振る。テストケースは番号で対応づける。作業の一覧と追跡表は持たない |
| 通常の道 | 作業が複数に分かれる改修や新規開発 | 要件・受入条件・テストケース・作業に識別子を振り、下の結びつきを書き、追跡表に集める |

- 道の正本は、最新の規模の判定。完了条件の一覧には、どの規模の判定に従うかを指すだけにする（道を二か所に書かない）。
- 着手の時は作業の数の見込みで決め、作業に分けた後や設計が固まった後に変わったら、規模の判定をやり直す。
- 作業の一覧を作ったら、通常の道とする。

### 識別子の書き方

- 形式は案件に任せる。種類ごとに接頭辞を付ける（例: `REQ-`、`AC-`、`TC-`、`TASK-`、`DD-`、`BR-`、`EV-`、`Q-`、一次情報の項目の `SRC-`、画面の `SCR-`）。業務規則の種類（不変条件など）は接頭辞で分けず、種類の欄で見分ける（種類が変わっても識別子を変えないため）。既に別の道具が振った識別子があれば、そのまま使う。
- 一度振った識別子は、変えない、使い回さない。項目が要らなくなったら、番号を詰めずに廃止の印を付ける。
- 識別子は記憶から書かない。書く直前に、その識別子を持つ原典を開いて写す。

### 結びつき

一つの関係は、一か所だけに書く。二か所に書くと、片方だけ直されて食い違う。

| 結びつき | 書く場所 | 多さ |
|---|---|---|
| 受入条件 → 要件 | 完了条件の一覧の受入条件の項目 | 1つ以上 |
| テストケース → 受入条件 | テストケース表のケース | 1つ以上（無ければ出どころ） |
| 作業 → 受入条件 | 作業の一覧の作業 | 1つ以上（無ければ出どころ） |
| 作業 → テストケース | 作業の一覧の作業 | その作業で足す・通すケース |
| 作業 → 作業 | 作業の一覧の作業 | 先に終わっている必要がある作業 |
| 作業 → 変更の事実 | 作業の一覧の作業（実装の後） | 行った変更 |
| 受入条件 → 業務規則 | 完了条件の一覧の受入条件の項目 | 0以上（規則を確かめる受入条件のとき） |
| テストケース → 業務規則 | テストケース表のケース（確かめる規則） | 0以上 |
| 設計の判断 → 業務規則 | 設計の判断の根拠の欄（行で守り方を決めるときは、行の鍵に規則の識別子を使う） | 0以上 |
| 業務規則 → ドメインイベント | 業務規則の一覧の行 | 0以上 |
| 業務規則 → 確認事項 | 業務規則の一覧の根拠の欄（問うている間も、回答で確定した後も） | 0以上 |
| 業務規則 → 一次情報の項目 | 業務規則の一覧の根拠の欄 | 0以上（根拠が公的な規則か外部の仕様のとき1つ以上） |
| ドメインモデルの要素（遷移のガード、区分の制約、計算の規則）→ 業務規則 | ドメインモデル | 0以上 |
| 画面 → 要件・受入条件 | 画面の設計の画面一覧 | 1つ以上 |
| 画面の制御 → 業務規則 | 画面の設計の画面ごとの仕様 | 0以上 |
| 画面 → 設計の判断の行 | 画面の設計の画面ごとの仕様（エラー、許可、個人情報の見せ方、部品） | 0以上 |
| ワイヤー → 画面 | ワイヤー | 1つ以上 |

- 画面と要件・受入条件の結びつきは、完了条件の一覧に書き戻さない。設計の判断の側に「影響する画面」を書くときは、波及の欄に検索の結果として書き、正本にしない。

- 作業から要件へは直接結ばない。受入条件を経由して辿る。
- 受入条件に対応しない作業（下ごしらえ、整理など）とテストケースは、出どころを書く。出どころは、問題台帳の問題、回帰の基準の検証点、是正の対応表の番号、方針外の課題の記録、設計の判断（判断の識別子か、判断の識別子＋行の鍵）、業務規則の一覧の規則、原典の参照（所在と節。続けて使う文書にある横断の関心事など）のどれか。出どころの無い作業は認めない。
- 人の決定を待つ作業は、状態を「決定待ち」にし、決定の中身は設計の判断に置く。

### 別の道具が作った成果物を受けるとき

- 別の道具（仕様駆動の道具など）が作った要件・作業・テストケースの文書は、作り直さずにこの型として受け、中身が型を満たすかだけを確かめる。
- 作業が要件にしか結ばれていないときは、欠けていると明記し、結ぶ受入条件の案を添えて人に確かめる。
- 同じ関係が両側に書かれているとき（テストケースの側にも作業の列があるなど）は、上の表の「書く場所」の側を正本とし、もう一方は写しとして突き合わせるだけにする。食い違いは指摘にする。

### 抜け漏れの検査

検査の項目と、どの場面でどれを確かめるかは、ここにだけ書く。単位とプロファイルは「道に応じた検査」「作業に分けるときの検査」と名前で指し、番号を写さない。

1. すべての要件に、受入条件が1つ以上ある。
2. すべての受入条件に、テストケースが1つ以上ある。無ければ、テストで確かめない理由が書いてある。否定を含む受入条件には、否定のケースがある。
3. すべての受入条件が、どれかの作業に結ばれている。
4. すべての作業に、受入条件か出どころがある。
5. 新しく足すテストケースは、どれかの作業に結ばれている。
6. 終わったとする作業（軽い道では完了条件の項目）は、結んだテストケースが通った記録を持つ。
7. 今回の範囲で有効な業務規則（廃止されておらず、確かさが確定か、了承と期限のある保留のもの）のうち、確かめる手段がテストのものには、満たすケースと破るケースがそれぞれ1つ以上ある。テストで確かめない規則には、手段と理由がある。
8. 受入条件と設計の判断が指す業務規則は、存在し、廃止されておらず、確かさが仮説・未確定でない（保留は、了承の記録と期限があるときだけ）。
9. ドメインモデルで、状態を持つ属性すべてに遷移か「遷移なし」があり、指す先の無い参照が無い。
10. ドメインイベントは、どれも、きっかけになる遷移か操作に結ばれている。
11. 画面の設計で、今回の範囲の画面に関わる受入条件は、どれかの画面に結ばれ、どの画面も要件か受入条件を1つ以上持つ。画面を持たない受入条件（バッチ、API、通知など）は、対象外と理由がある。
12. 画面の設計が指す要件・受入条件・業務規則・設計の判断の行は存在し、廃止されていない。画面の制御が指す業務規則は、確かさが仮説・未確定でない（保留は、了承の記録と期限があるときだけ）。
13. 今回の範囲の画面は、承認の状態がどれも「人が採った」で、決定待ちの所が残っていない（担当の案と採り直し待ちは通さない）。

業務規則に識別子を振る目安は、「テストやレビューで個別に識別したい制約か」。説明の文には振らない。

| 検査の組 | 項目 |
|---|---|
| 道に応じた検査（通常の道） | 1〜8。ドメインモデルがあれば 9、10 も。画面の設計があれば 11〜13 も |
| 道に応じた検査（軽い道） | 2、6。業務規則に触れるなら 7、8 も。画面の設計があれば 11〜13 も |
| 作業に分けるときの検査 | 3〜5（1 と 2 は、欠けを見つけたら指摘として返す） |
| テストケースを導くときの検査 | 2。業務規則の一覧があれば 7 も |
| 要件を終えるときの検査 | 1。8 を受入条件が指す規則について |
| モデルを終えるときの検査 | 9、10 |
| 画面の設計を終えるときの検査 | 11、12 |
| 仕様化を終えるときの検査 | 要件を終えるときの検査と、ドメインモデルがあればモデルを終えるときの検査（設計の判断が指す規則は、設計の後の道に応じた検査の 8 で確かめる） |
| 設計を終えるときの検査 | 8 を設計の判断が指す規則について |

結びつきがそろっていても、中身を満たしたことにはならない。この検査は、意味の確認の代わりにしない。

## 確からしさの物差し

単位ごとに、確からしさを表す物差しを使い分ける。目的が違うので、同じ段に読み替えない。

| 物差し | 使う所 | 段 |
|---|---|---|
| 証拠の種類 | レビュー結果の指摘 | 実行で確認／読んで導いた／仮説／人の決定が要る／人か環境の証拠が要る |
| 証拠の強さ | 完了判定の項目 | 今ここで確認／今の状態に対応する証跡／古くなった証跡／主張だけ／未確認 |
| 確認の水準 | 現状の振る舞いの記録、問題台帳、不具合の報告、業務規則の一覧の守っている箇所、秘密の目録、個人情報の台帳 | 実行／静的／公開情報／未確認 |

## 型を足すとき

- 既存の型で表せないかを先に確かめる。名前だけ違う同じ中身の型を作らない。
- 中身は、作り方ではなく、受け取る側が判断に使う項目で書く。受け取る側の判断に要らない作業の覚え書き（かかった時間、試した順番など）は欄にしない。
- 型を足したら、その型を出力する単位か、入力に取る単位が少なくとも1つあるようにする。
- 値を選んで答える欄（状態、判定、区分など）は、選べる語を括弧の中に「／」で区切って並べて閉じる。「例:」で始まる括弧や「、」で並べた括弧は例示で、語を閉じない。今の型の行には、「、」や「・」で並べた選ぶ欄や、括弧の外に「／」で並べた欄も残っている。語彙の表を広げて書き直すまでは、それらも型が並べた語から選ぶ。語と別の欄の間に制約があるときは、制約を型の行か、その型の決まりの節に書く（たとえば作業の一覧の「決定待ち」は、「識別子と結びつき」の節の、決定の中身を設計の判断に置く決まりと結ぶ）。
- 観察や調べの結果を持つ型は、事実と推定を分ける欄と、確からしさの物差しを持たせる。物差しは、型の行か上の「確からしさの物差し」に定める。
- 埋めた例: 型の欄を満たす小さな例を、その型を出す単位の `references/` に置いてよい。例は形の一例で、規範ではない。型の表の行から例へはリンクしない。例の書き方は、開発スキル群の規約の「埋めた例」の節にある。

## 成果物を書くとき

型の欄を埋める側の決まり。受け取る側が「この型として受け取れるか」を判定するのは冒頭の3段落目のとおり欄がそろっているかで、ここの決まりは、中身を読む人が取り違えないためのもの。受け取る側は、ここの決まりに合わない書き方を指摘にしてよいが、それを理由に型として受け取ることは止めない。

- 語を選ぶ: 型が語を閉じた欄は、その語から選ぶ。型が閉じていない、値を選んで答える欄（案件の入口に合わせて決める欄など）は、案件が語を決めて一覧にし、その一覧から選ぶ。理由、概要、経緯のような文で書く欄は、語を閉じない。
- 無いことの書き方: 「見たが無い（なし、0件）」と「見ていない（未確認）」を分けて書く。当てはまらない欄は、理由を添えて「当てはまらない」と書き、空欄で済ませない。型の行で条件を付けた欄（「あれば」「〜のとき」「決めたときだけ」など）は、条件に当たらないときは欄ごと書かなくてよく、「あれば」の欄を書いていなければ「見たが無い」と読む。見ていないときは「未確認」と書く。
- 正本は一か所: 読みやすさのために再掲や集計を置くときは、正本を指し、数え方を書いておく（「別の道具が作った成果物を受けるとき」の、写しとして突き合わせる扱いと同じ）。過去の版の事実を残す記録は、重複とみなさない。
- 事実と推定: 観察や調べの結果を持つ型では、事実と推定を欄で分け、その型の物差しと、基準の版か取得日を書く。物差しを、型をまたいで読み替えない。確認の水準（実行／静的／公開情報／未確認）を持つ型では、人の答え（証言）はどの段にも当たらないので、観察の水準を上げる根拠にせず、答えとして並べて残す。関係者の決定で業務規則の確かさを「確定」にするのは、これとは別の扱い（業務規則の一覧の確かさの欄で決める）。
- 機械で突き合わせたい所（識別子、語を閉じた欄の値）は、文の中に埋めず、行と欄に分けて書く。理由や経緯は文で書く。表にするか、どの形式にするかは案件に任せる。
- 分母: 一覧は、何の全件に対する一覧か（対象の集まりの出どころと版）を書き、外した行も理由と一緒に残す。件数だけで網羅を主張しない。
- 識別子: 接頭辞の付け方と変えない条件は「識別子の書き方」に従い、設計の判断の系列は「判断ごとの共通の欄」に従う。例の中の識別子は作り物で、写す原典は無い。
