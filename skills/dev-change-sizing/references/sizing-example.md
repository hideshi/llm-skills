# 規模の判定の例

型: 規模の判定
形の一例。正本は型の一覧の欄。形式・節名・置き場所は任意で、案件に既に形があればその形に従う。値はすべて作り物。

題材は、確定した請求書の明細を直せないようにする変更の、着手の時の判定。まだ設計も規則の整理もしていないので、見込みで書いた。終わる時には、実際の差分で判定し直す。

## 時点と道

| 欄 | 中身 |
|---|---|
| 判定の時点 | 着手 |
| 根拠 | 予測（依頼の文と、明細を変える処理の所在の探索から） |
| 道 | 通常の道（明細を変える処理の直しと、画面の直しの2つの作業に分かれる見込み） |
| 引き上げと抑制の根拠 | 引き上げ: 確定と明細の処理が並んで走ると、確定の後に明細が変わりうる。抑制: 誰が確定でき、誰が明細を直せるかは変えない |
| 影響する続けて使う文書の分類 | 業務の規則（新しい規則ができる見込み）、データ（並んで走る処理を守るために、保存の構造が変わる見込み）、見える振る舞い（請求書の詳細の画面） |
| 承認済みの完了条件への影響 | なし（新しい要件を書く） |
| 範囲外の疑い | 依頼の文に「確定した請求書を取り消して作り直す」ことが出てくる。原典の参照の範囲外の一覧の「請求書の取り消し」に当たりそうなので、人に確かめる |

## 観点

| 観点 | 要るか | 理由 |
|---|---|---|
| データ | 要る | 確定と明細の処理が同じ請求書を同時に更新しうる |
| エラー | 要る | 確定済みで拒む、新しい失敗と利用者に見せるエラーが増える |
| 認可 | 要らない | 誰が確定でき、誰が明細を直せるかは変えない |

この例では、表を3行にとどめ、ほかの3つの観点は文で書き、残りは省いた（末尾の行）。単位の本文は、観点ごとに要るか要らないかと理由を求めている。

- 責務の配置: 要る（確定済みで拒む、新しい分岐の置き場所を決める）。
- 呼ばれる契約: 要らない（明細を変える API は画面からだけ呼ばれ、失敗の返し方の形は、決まった共通の形に載る見込み）。
- モデルの検査: 候補（並んで走る処理がある。人の依頼の記録が無いので、人に確かめる）。
- そのほかの観点は、この例では省いた。実際の判定では、観点ごとに1行ずつ、要るか要らないかと理由を書く。

## 仕様化・運用・点検の作業

| 作業 | 当たるか | 理由 |
|---|---|---|
| ドメインモデル | 当たる | 確定した請求書の明細は変えられない、という新しい業務規則ができる見込み |
| 画面の設計 | 当たる | 請求書の詳細の画面の、明細の編集の操作が変わる |
| 本番の手順 | 当たる | 保存の構造が変わる見込みで、既存のデータの移行が要る見込み |

規則の抽出、一次情報、依存は、当たらない（業務規則は関係者に確かめられ、外の仕様と部品の版は変えないため）。点検の作業（アクセシビリティの点検）は、着手の時には書かず、終わる時の判定で実際の差分から書く。
