## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 「道」「要る設計の観点」「文書への影響」を互いに独立に決め、仕様化の契機は設計の観点と切り分ける | 作業が1つで済む小さな変更でも新しい状態や共有処理への波及があれば設計の観点が要るため。また仕様化の作業を設計の判断と混ぜないため | 軽い道でも設計見落としが起きた件数や仕様化混入による手戻りの件数を記録し、3軸と仕様化の分け方を見直す |
| 「要らない」観点の理由もすべて1行ずつ書き、正本を規模の判定に置く | 検討して不要と判断したのか、見落として抜けたのかを後から区別し、設計の判断側との二重記載を防ぐため | 「要らない」と書いた観点が後工程で必要と判明して差し戻された件数と理由記録の妥当性を比べ、省略不可の基準を見直す |
| モデルの検査は人が依頼したときだけ「要る」とし、記録が無ければ「候補」にとどめる | 形式モデルの検査は手間が大きく、エージェントの判断だけで重い作業を勝手に増やさないため | 候補止まりで見送り後に並行・状態不具合が出た件数と依頼外実施の工数負担を比較し、発議条件を見直す |
| 着手時・確定時・終了時の3時点で判定し直し、終了時は実際の差分だけを根拠にする | 着手時の見込みより変更が広がったまま、軽い道や設計不要の扱いで完了するのを防ぐため | 着手時から終了時への規模昇格率と、終了時見直しを省いてレビューで差戻しになった件数を記録し、再判定時点を見直す |
| 引き上げすぎの抑制（本番未使用機能や新規分岐を生まないキーワードで引き上げない） | キーワードの一致だけで過剰な手続きに膨らみ、実用性を損なうのを防ぐため | 抑制した変更で後の工程に設計漏れが出た件数と過剰手続きを省けた工数の比較を記録し、抑制条件を見直す |
| 運用の契機（本番の手順、依存）を設計の観点と分けて「当たる・当たらない」で書き、秘密・個人情報・ログの決まりは続けて使う文書への影響で判定する | 運用の作業は設計の判断を作らないので観点に混ぜず、文書で持つものを二か所で判定しないため | 契機の当て漏れ（本番の作業で手順が無かった件数）と、文書への影響と運用の契機で同じことを二重に書いた件数を記録し、表の分け方を見直す |
| ログと応答と入口の安全は、方式や決まりを新しく決める・変えるときだけ観点に当て、決まった方針への適合は当てない。標準の手順書のまま流せる反映は本番の手順に当てない | ログ1行や設定1行の足し忘れの直しまで設計と承認の道に入ると、小さな直しが重くなりすぎるため | 適合として当てなかった変更で、後に決まり自体の見直しが要ったと分かった件数を記録し、境目を見直す |
