# 変更の規模を判定する

変更がどれだけの手続きを要するかを判定する。判定するのは「道」（軽い道か通常の道か）と「要る設計の観点」と「文書への影響」の三つで、互いに独立に決める。小さく見える変更でも、新しい状態や、ほかの利用側を持つ処理に触れるなら、設計の観点が要る。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 改修の範囲 | 条件付き（既存のシステムを変えるとき必須） | 触る機能と経路、共有の処理と利用側 |
| 完了条件の一覧 | 任意 | 新しい約束（規則、契約、受入条件）が入るかを見る |
| 原典の参照 | 任意 | 範囲外の一覧、続けて使う文書（業務の規則、データ設計、公開する契約など）の所在 |
| 作業の一覧 | 任意 | 作業に分けた後に、道を決め直すとき。作業の一覧があれば通常の道 |
| 設計の判断 | 任意 | 設計が固まった後に、道と観点を見直すとき |
| 変更の事実 | 条件付き（終わる時の判定では必須） | 実際の差分から判定し直す |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

どれも無く、依頼文だけのときは、依頼文から読める範囲で判定し、「根拠は予測」と書く。終わる時の判定で変更の事実が無いときは、判定せずに止める。

## 出力

| 型 | 中身の補足 |
|---|---|
| 規模の判定 | 下の手順の結果。判定の時点と、根拠が予測か実際の差分かを必ず書く |

## 使わない場面

- 設計の中身を決める（設計の判断を作る、別の仕事）。
- 完了条件を作業に分ける。
- 差分の良し悪しをレビューする、完了を判定する。

## 手順

### 1. 集める

- 触るファイルの数（見込みか実績か）、触る責務（業務の判断、手順の調整、入出力、具体の仕組み）。
- 新しい状態や分岐先、新しい概念、新しい公開の契約があるか。
- 既にある状態やデータへの影響、複数の整合性の単位（一度に守る範囲）にまたがるか。
- 横断の関心事（権限、監査、通知、入力検証、利用者の分離）に新しい分岐が生まれるか。
- ログや入口の安全の決まりを新しく作る・変えるのか、決まりに合わせるだけか。
- 画面を足すか、画面の流れや見せる情報が変わるか。画面で使う部品やトークンを足す・変えるか、決まった部品を使うだけか。
- 本番への反映に、データの移行、設定か秘密の項目の追加・変更、利用者に見える停止、順序の制約があるか。部品か実行環境を足すか、版を変えるか。
- 対応する完了条件の識別子。件数やファイルは、推測でなく検索して数える。

### 2. 道を決める

| 道 | 選ぶとき |
|---|---|
| 軽い道 | 作業が1つで済む見込み。1か所の是正、既存の中に条件を足すだけの変更 |
| 通常の道 | 作業が2つ以上に分かれる見込み。または、別の担当や別の作業場所と並べて進める |

着手の時の判定は見込みでよい。作業に分けた結果で道が変わったら、判定し直す。

### 3. 要る設計の観点を決める

[型の一覧](../dev-shared/references/artifact-types.md)の「設計の観点と契機」の表で、契機に当たる観点だけを「要る」とし、それぞれ理由を1行書く。当たらない観点は「要らない: 理由」と書く（要らない理由の正本はこの判定。設計の判断には写さない）。

- モデルの検査は、人が依頼したときだけ「要る」とし、依頼の記録の所在（いつ、誰が、どの性質を）を書く。記録が無ければ「候補」と書き、人に確かめる。
- 設計の判断が入力にあれば、判断の中で新しく分かった契機（例: 非同期にすると決まった）も拾う。
- 同じ型の一覧の「仕様化の契機」の表で、仕様化の作業（モデル、規則の抽出、一次情報、画面の設計）ごとに「当たる・当たらない」と理由を書く。画面の設計に当たるかは、Web の画面を足すか、画面の流れ、見せる情報、操作が変わるかで決める（文言を決まりに合わせるだけの直しは当てない）。完了条件の一覧があれば、その「適用する画面」に、途中で書き足された画面（設計や回答で画面が要ると分かったもの）が無いかも見て拾う。これは設計の観点ではないので、設計の判断を求めない。
- 設計の判断が入力にあれば、デザインシステムの判断が足されていないか（画面への意見で、部品やトークンの共通の定義を扱ったもの）も見て、デザインシステムの観点に拾う。
- 同じ型の一覧の「運用の契機」の表で、運用の作業（本番の手順、依存）ごとに「当たる・当たらない」と理由を書く。これも設計の判断を求めない。依存に当たったら、告知が当たるかの点検を別の組み合わせとして起こすかを、人に確かめる。

### 4. 引き上げすぎを抑える

- 本番で使われていない機能、外部との連携が本番で動いていない機能は、移行や互換の観点を要らないとしてよい。そう判断した根拠を書く。
- キーワード（権限、通知など）に当たっても、新しい分岐を生まないなら引き上げない。
- ログと、応答と入口の安全は、決まっている方針に合わせるだけなら要らないとする（決まった欄でログを足す、決まった設定を入れ忘れた入口に足す）。合わせる先の決まりの所在を理由に書く。
- デザインシステムは、既にある部品とトークンを決まりどおりに使うだけなら要らないとする。使う部品の決まりの所在を理由に書く。
- 文面は、決まった雛形の言い回しを直すだけなら要らないとする。雛形の所在を理由に書く。
- 保守されている標準の手順書の今の版のまま流せる反映は、本番の手順に当てない。手順書の所在を理由に書く。

### 5. 続けて使う文書への影響

道や設計の観点とは別に、全部の変更で判定する。

| 分類 | 当たるとき |
|---|---|
| 業務の規則 | 規則や不変条件が変わる |
| データ | 保存の構造や意味が変わる |
| 見える振る舞い | 利用者の操作や見える結果が変わる |
| 長く続く契約 | 外部に公開した契約が変わる |
| 秘密の項目 | 秘密の項目（鍵、トークン、資格情報）を足す・変える・やめる、または使う場所が変わる |
| 個人情報の扱い | 個人の情報を取る・保存する・渡す先・保持の期間が変わる |
| ログの決まり | 記録する出来事、欄、書かないものの決まりが変わる |
| 操作マニュアル | 続けて使う操作マニュアルがあり、そこに書いた仕事の前提・操作・結果が変わる。または、依頼者が操作マニュアルを新しく求めた |
| 無し | コードとテストだけ。その理由を書く |

当たる分類の文書がまだ無いときは、そのことを書く（作るかどうかは組み合わせの側で決める）。

探すのは、変わる用語、契約、操作を直接参照している文書に限る。見つからなくなったら止める。

### 6. 承認済みの完了条件への影響

| 影響 | 扱い |
|---|---|
| 表現をそろえるだけ | その箇所だけ直してよい |
| 受入条件、公開する契約、必須の試験、新しい概念が変わる | 完了条件を承認し直すまで、実装を進めない。ただし、テストを先に書かない範囲の追記は、依頼者の確認の記録があれば承認し直しに当たらない |
| 閉じた変更に関わる | 閉じたものは変えず、新しく起こす |
| 無し | — |

### 7. 範囲外の疑い

原典の参照に範囲外の一覧があれば照合し、当たりそうなら人に確かめる。

### 8. 時点ごとの違い

- 着手の時: 見込みで判定する。
- 原因や設計が固まった時: 見込みを実績に近づけて、道と観点を見直す。
- 終わる時: 変更の事実（実際の差分）だけを根拠に、道、観点、運用の契機、5、6 を判定し直す。着手の時の判定を写さない。道が通常の道に変わったのに作業の一覧が無い、要るとなった観点に設計の判断が無い、のどちらかなら、そのことを判定の先頭に書く。運用の作業と続けて使う文書は、当たるかだけを書く（成果物と承認の有無は、後で作られることがあるので監査が確かめる）。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 規模の判定に、時点、根拠の種類、道、観点ごとの要る・要らないと理由、仕様化と運用の作業ごとの当たる・当たらない、文書への影響、完了条件への影響がそろっている。
- 終わる時の判定なら、根拠が実際の差分になっている。
- 承認し直しが要るなら、そのことが判定の先頭に書かれている。
