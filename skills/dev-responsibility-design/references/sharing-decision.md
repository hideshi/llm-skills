# 共通化の判断

似た処理を一つにまとめるかを決める表。三つの表は論理が違う。

## 1. 抽出の条件（全部を満たすとき、共通化してよい）

| 条件 | 確かめ方 |
|---|---|
| 同じ規則に従っている | 規則の出どころ（業務の規則、法令、契約）が同じか |
| 入力と出力の意味が同じ | 戻り値が表すものが、どの呼び出し元でも同じか |
| 変わる時期が同じ | 一方の規則が変わったとき、もう一方も必ず変わるか |
| 呼び出し元ごとの分岐が要らない | 共通化した後に、呼び出し元を見て分ける条件が入らないか |

## 2. 推奨のシグナル（複数当たれば、共通化を勧める）

- 同じ計算式や判定が、3か所以上に写されている。
- 写しの一方だけが直された不具合が、過去にあった。
- 規則の変更のたびに、同じ箇所を探して直している。

## 3. 統一しないシグナル（一つでも当たれば、統一しない）

| シグナル | 例 |
|---|---|
| 戻り値の意味が違う | 一方は請求額、もう一方は見積もりの目安 |
| 呼び出し元ごとの分岐が混ざる | 共通の関数に「呼び出し元が A なら」という条件が要る |
| 寿命が違う | 一方は近く廃止が決まっている |
| 規則の根拠が違う | 一方は法令、もう一方は社内の決まり |
| たまたま似ているだけ | 今は同じ式だが、決めた人も理由も別 |

統一しないと決めたときは、その理由を設計の判断に残す。後で同じ議論を繰り返さないため。

## 共通化した後の形

- 共通の核（純粋な計算）と、呼び出し元ごとの差を吸収する薄い部分に分ける。
- 核と使う側は別の作業にし、核を先に作る。
