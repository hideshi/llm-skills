# 責務の配置を設計する

ロジックの置き場所を、「このロジックは何を守るか」で決める。ディレクトリや型の名前に合わせて決めない。結果は設計の判断として残し、テストの境界と作業の分け方の材料にする。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 原典の参照 | 必須 | 業務の規則と不変条件、計算の規則、構成の方針 |
| 完了条件の一覧 | 任意 | 判断の根拠として項目の識別子を書く |
| 現状の振る舞いの記録 | 条件付き（既存のコードの配置を診断するとき、既にある重複の共通化を判断するとき必須） | 今の置き場所と、呼び出し元を検索した結果 |
| 業務規則の一覧 | 任意 | 規則ごとの所有と種類から、守る置き場所を決める。確かさが仮説・未確定の規則は根拠にせず、そのことを未確認の欄に書く |
| ドメインモデル | 任意 | 一緒に変わるまとまり、状態と遷移、計算の規則 |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

業務の規則が原典に無いときは、置き場所を推測で決めず、規則を人に確かめる。既存のコードは今の状態の証拠として読み、業務の正しさをそこから逆算しない。

## 出力

| 型 | 中身の補足 |
|---|---|
| 設計の判断 | 観点は「責務の配置」か「共通化と契約の変更」。責務ごとの置き場所、横断の関心事の置き場所、わざと二重に守る所、純粋な計算の定義、共通化の可否、旧の撤去の条件 |
| 方針外の課題の記録 | 見つけた配置の違反のうち、今は直さないもの |

## 使わない場面

- 公開する操作、エラーの種類、応答の形を決める。呼び出し元が自分の管理の外にある、または同じ変更で全部の呼び出し元を直せない共通の処理の契約の変更（版と移行の案内が要るもの）も、ここでは扱わない。
- 保存の構造、制約、移行を設計する。
- プロセスの外への作用（外部サービス、別のシステム）を設計する。
- 実装する、テストを書く。

## 手順

### 1. ロジックを4つの責務に振り分ける

| 責務 | 守るもの | 例 |
|---|---|---|
| 業務の判断 | 不変条件、状態遷移の可否、純粋な計算 | 上限を超えたら受け付けない、金額の計算 |
| 手順の調整 | 処理の順序、操作する人の認可 | 読み込み、判断を呼び、保存し、通知を頼む |
| 入出力 | 入力の解釈と形式の検証、応答の整形 | 型や必須の検査、表示用の形への変換 |
| 具体の仕組み | 保存、通信、時刻や乱数の取得 | データベース、外部の呼び出し |

- 「誰ができるか」（操作する人の権限）は手順の調整に、「いつできるか」（状態による可否）は業務の判断に置く。
- 一つの責務を一つのディレクトリや型と対応させなくてよい。委譲するだけの型を増やさない。
- DDD などの用語で層を呼ぶ案件では、[用語の対応](references/layer-vocabulary.md)を使う。

### 2. 依存の向きを決める

- 業務の判断は、具体の仕組みに依存しない。具体の仕組みが必要なら、手順の調整が値を渡す。
- 入出力の境界は薄くし、業務の判断を書かない。
- 例外として依存を許すときは、理由と範囲を設計の判断に書く。

### 3. 横断の関心事の置き場所を決める

- 権限、監査、通知、入力検証、利用者の分離など、関わる関心事ごとに担当の置き場所を1か所以上決める。
- 同じ確かめを複数の所でしていたら、意図した二重の守りか、ただの重複かを分け、意図なら明記する。
- その置き場所を通らない経路（別の入口、一括処理、管理用の操作）が無いかを確かめる。
- 結果を「横断の関心事の一覧」（関心事ごとの守る場所、迂回の有無、確かめる観点）として設計の判断の中に書く。人が採った後は、案件が続けて使う文書に反映する。関心事には識別子を振らない（ほかからは文書の所在と節で指す）。誰が何をできるかの決め方そのもの（認可の規則）は、ここでは決めない。

### 4. 純粋な計算を切り出す

- 副作用が無く、同じ入力から同じ出力が出て、外から注入するものが要らない計算を、業務の判断として切り出す。
- 定義は1か所にまとめ、署名、計算式、前提、端の場合（空、ゼロ、境界）、出力が守る条件、使う側の一覧と使い方の差を書く。
- 計算の中で問い合わせない。手順の調整に計算を埋め込まない。可否の判定を定義したら、同じ条件を呼び出し側で書き直さない。

### 5. 共通化するかを決める

[共通化の判断](references/sharing-decision.md)の三つの表で決める。抽出の条件は全部を満たすこと、統一しない理由は一つでも当たれば統一しない。似ているだけのものを共通化しない。

### 6. 共通の処理の契約を変える

- ここで扱うのは、呼び出し元を同じ変更で全部直せる共通の処理だけ。直せないなら、呼ばれる契約として互換と版を決める。
- 原則は署名を進化させ、呼び出し元とテストを同じ変更で直す。旧と新を並べたまま長く残さない。
- 段階的に移すと決めたら、旧を撤去することを完了条件と順序の制約に書く。
- 型や契約の変更が及ぶ箇所を検索して数え、波及として設計の判断に書く。

### 7. テストの境界への注意

- 代わりの実装を使った試験だけで、保存の制約、トランザクション、外部との接続が成り立つことを保証したとしない。そこは本物を通す試験の観点として、確かめる観点に書く。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 設計の判断に、判断ごとの共通の欄（識別子、観点、承認の状態、確かめる観点、未確認）がそろい、一覧の行に鍵がある（[型の一覧](../dev-shared/references/artifact-types.md)の「設計の判断の書き方」）。
- 変更に関わるロジックのすべてに、責務と置き場所が決まっている。
- 横断の関心事ごとに置き場所があり、迂回できる経路の有無を確かめた結果が書かれている。
- 共通化の判断と契約の変更には、選ばなかった案と理由、波及の件数、旧の撤去の条件がある。
- 人が決める事柄が、決定待ちとして分かる。
