# 応答と入口の安全を点検する

今動いているシステムの入口と応答を、項目ごとに「見るか（適用）」「問題か（判定）」「直すか受け入れるか（対応）」の三つに分けて記録する。項目の名前と、普通の応答だけで判定できるかの区分は、[型の一覧](../dev-shared/references/artifact-types.md)の「応答と入口の安全の項目」に従う。HTTP の上で何を観測するかの具体は [HTTP の場合](references/http.md) に分ける。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 改修の範囲 | 必須 | 点検する入口と応答（画面、データを返す窓口、ファイルの取得）、環境、対象の版 |
| 原典の参照 | 条件付き（要求を送るとき必須） | 要求を送ってよい相手の許可の記録（ホスト、環境、要求の種類と数の上限、期間、許した人）。案件の安全の方針（見る項目、対象外、受け入れた残り）、設定を付ける層の構成、走査の道具の結果 |
| 安全の点検の記録 | 任意 | 前回の点検（比べる元、閉じる行）。無ければ初回として扱う |
| 設計の判断 | 任意 | 応答と入口の安全の設計（項目ごとに決めた設定と、設定を付ける層） |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

点検する入口と環境が決まっていなければ、点検せずに止める。要求を送ってよい相手の許可の記録が無ければ、要求を作るところまで（送る要求の一覧と、観測する項目）で止め、送らずに返す。

## 出力

| 型 | 中身の補足 |
|---|---|
| 安全の点検の記録 | 点検の種類は「入口の点検」。許可の所在、範囲（見た入口と環境、見なかったもの）、項目ごとの適用・判定・根拠、前回との差 |
| 問題台帳 | 判定が「問題がある」の行と、人の判断が要る行。直す層、壊れうる画面、確認の水準、判断の区分（誰が決めるか。本番で確かめられない「環境による」の行は「本番の事実確認待ち」）。人の決定（直す、受け入れる、保留）の欄は書かずに渡す（人が決めたときに足す） |
| 検証の記録 | 送った要求の一覧（相手、種類、数、日時）、読んだコードと設定の所在、使った道具と版、送らなかった要求と理由 |

## 使わない場面

- これから作る入口と応答の安全を設計する（設計の判断を作る、別の仕事）。
- 変更の差分が安全かを点検する（差分の点検かレビューの仕事）。
- 値を変えて送る走査、認証を回る試し、攻撃に当たる要求を送る。必要と分かったら、その旨を問題台帳に書いて人に返す。
- 使っている部品の弱点の告知が当たるかを点検する。

## 手順

### 1. 送ってよい範囲を確かめる

- 許可の記録から、送ってよい相手（自分たちが管理するホスト）、環境、要求の種類、数の上限、期間を読み、点検の記録に許可の所在を書く。第三者のホストには送らない。
- 送るのは、状態を変えない要求（読むだけの要求）だけ。読むだけの形でも状態を変えうる所在（ログアウト、確定や配信停止の所在、一度きりの所在、作業を始める所在）は踏まない。
- ログインが要る画面は、許可の記録が点検用の利用者を許しているときだけ見る。担当はログインせず、人がログイン済みのセッションか、環境の変数に入れた点検用の資格情報を用意する。担当は値を読まず、記録に写さない。許した相手へ点検用のセッションを送ることだけは、下の「秘密を入れない」の例外とする。
- 移動先が許した範囲の外なら追わない。応答が読み込む外の資源は、所在を記録するだけで取りに行かない。
- 本番は、許可の記録が本番を含み、普通の利用者と同じ読むだけの要求のときだけ見る。それ以外は、手元か検証の環境で見る。
- 送る要求に、秘密や個人の情報を入れない。点検の記録にも、応答の中の秘密、個人の情報、Cookie の値を写さない（属性だけを書く）。
- 点検の記録と問題台帳は、未修正の弱点と内部の構成の一覧になる。置き場所、共有の範囲、外へ渡す前の確かめは、[型の一覧](../dev-shared/references/artifact-types.md)の「本番の事実と、記録の扱い」に従う。
- 外の診断のサービスに、対象のホストの名前を出さない。

### 2. 適用を決める

- 項目ごとに、適用（必須／触れたら／対象外／方針が無い）を、案件の安全の方針から決める。方針が無ければ「方針が無い」と書き、対象外と受け入れを担当が補わない。
- 製品にその面があるなら、方針が無くても、型の一覧のコードや設定を読む区分のうち、秘密の露出、1件ごとの確かめ、出力の変換、出どころの確かめ、問い合わせの組み立て、セッションの作り直し（認証を扱うとき）、ファイルの受け付け（受けるとき）は外さない。外すなら人の承認を取る。
- 「省いてよい」のは、その面が製品に無いときだけ。今ある面の点検を免除する理由にしない。

### 3. 応答から観測する

- 応答だけで判定できる区分の項目を、許した範囲の普通の要求の応答で観測する。画面の文書を返す層と、データやファイルを返す層の両方を見る。
- 走査の道具の結果があれば、指摘ごとに先に確かめる: 画面の文書の応答か、データの窓口だけか／実際に読み込んでいる資源の版か、古い版の文字列が残っているだけか／本文が本当にスタックか、エラーという単語があるだけか／開発用の環境だけの設定か。
- 手元の環境だけで出る差（暗号化しない通信での強制の見出しの欠け、開発用の環境の呼び出しの全許可）は、判定を「環境による」にし、本番で確かめたか、本番は確認不能かを書き分ける。本番だけの項目を、手元で出ていないから無いとしない。

### 4. コードと設定で確かめる

- コードや設定を読む区分の項目は、ルートの定義、中継の処理、設定、試験を読んで確かめる。応答を見ただけで、確かめたことにしない。
- 認証が成り立つ所と権限が上がる所を全部挙げ、それぞれでセッションを作り直しているかを見る（パスワードのほか、一度きりの番号の確かめ、別の認証の成功、外の認証の入口）。
- 多段の手順やゲストのセッションがある機能は、守るものと公開してよいものを対応付け、「入口を開いただけ」「認証に失敗した後」「手順の印だけ進んだ」の各状態で守るものが拒まれるかを、試験とコードで確かめる。
- 画面で入力させる認証の番号は、試せる回数の上限、有効期限、送り直したときの失効、送信の回数の制限を確かめる。
- 値を変えないと成り立つかが分からない項目は、ここでは要求を送らず、確かめ方（試験の観点、隔離した環境での確かめ）を問題台帳に書いて人に返す。

### 5. 判定し、問題台帳に載せる

- 判定は、合格／問題がある／誤検知／環境による、のどれか。判定できなければ「確認不能」と書き、足りない証拠を書く。
- 問題がある行には、直す層と、直すと壊れうる画面を書き、問題台帳に載せる。直した後に、手元で観測し直せる層を勧める。
- 誤検知と、本番で確かめて問題が無かった「環境による」ものは、対応は要らないとし、理由を残す。本番は確認不能の「環境による」ものは閉じず、問題台帳の事実確認（判断の区分は「本番の事実確認待ち」）に載せる。
- 直すか受け入れるかは、この単位では決めない。人が決め、問題台帳の人の決定に書く（受け入れは方針外の課題の記録が正本）。
- 前回の点検の記録があれば比べ、閉じた行、新しく出た行、判定が変わった行を先頭に置く。点検しなかった項目を閉じたとしない。

### 6. 書く

- 指摘ごとに、まず起きることを専門の語を使わずに書き（誰が、何を、どうできてしまうか、何が欠けているか）、その後に語を一言で添え、適用・判定・対応と直す層、人が決めることを書く。項目の名前や道具の警告の名前だけを見出しにしない。
- 攻撃の手順や、こう送れば取れる、という形は書かない。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 安全の点検の記録に、許可の所在、範囲（見た入口と環境、見なかったもの）、項目ごとの適用・判定・根拠、前回との差（または比較元なし）がある。
- 応答だけで観測した項目と、コードや設定で確かめた項目が分かれ、前者で後者を確かめたことにしていない。
- 問題がある行と人の判断が要る行が、問題台帳の識別子で結ばれている。
- 許した範囲の外へ要求を送っていない。送った要求と送らなかった要求が、検証の記録にある。
