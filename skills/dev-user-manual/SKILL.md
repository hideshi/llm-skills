# 操作マニュアルを書く

利用者が自分の仕事をシステムでこなせるようになるための手順書を書く。マニュアルは仕様を作らない。正本は画面の設計と実際の画面で、マニュアルはそれを読む人の仕事の順に並べ直したもの。

## 入力

| 型 | 必須 | 使い方 |
|---|---|---|
| 画面の設計 | 任意 | 画面の識別子、ラベル、流れ、状態。無ければ実際の画面から書き、そう記録する |
| 完了条件の一覧 | 任意 | 利用者の仕事と、できた状態の手がかり |
| テストケース表 | 任意 | 画面をまたぐ受入の試験のシナリオ。章立ての背骨にする |
| 設計の判断 | 任意 | エラーの一覧の利用者に見せる文と次の行動、認可（役割ごとにできること） |
| 操作マニュアル | 条件付き（今あるマニュアルを直すとき必須） | 今の台帳、章、確かめた記録 |
| 原典の参照 | 任意 | 製品の呼び名、読む人、案件のマニュアルの置き場と形式の決まり |

型の中身は [型の一覧](../dev-shared/references/artifact-types.md) を見る。

- 手順を辿れる隔離した環境が無いときは、章を「画面の設計から書いただけ」か「未確認」にして進め、確定させない。
- 読む人（役割）が決まっていないときは、書かずに止め、依頼者に一度だけ聞く。

## 出力

| 型 | 中身の補足 |
|---|---|
| 操作マニュアル | 型の中身に従う。台帳と確かめた記録は内部用で、配る形に含めない |
| 問題台帳 | 書く途中で見つけた、仕様と画面の食い違い、画面の不具合、画面の注記の矛盾。判断の区分を付けて返す |

## 使わない場面

- 画面の構成や流れ、文言の決まりそのものを決める（画面の設計の仕事）。
- 保守を引き継ぐ側のためのシステムの地図、本番で運用の担当が流す手順を書く。
- デモ動画や受入の証拠を撮る。研修の教材、試験問題を作る。規程や法令に沿った文書を書く。
- 画面の不具合を直す（見つけたら問題台帳で返す）。

## 手順

### 1. 台帳を作る

ありうる仕事を、利用者の言葉で1行ずつ挙げる。出どころは、メニュー、画面の設計の画面一覧、受入の試験のシナリオ、利用者からの聞き取り。行ごとに、根拠と、判断（載せる／後回し／対象外／未判断）と理由を書く。画面の一覧をそのまま章にしない。同じ名前のメニューがあっても、その仕事がそこで完了しないなら、その行は対象外にし、実際に完了する経路を別の行にする。「未判断」の行は依頼者に確かめるまで章にしない。

### 2. 章を書く

「載せる」の仕事だけを章にする。章の並びは、はじめる → 仕事ごと → うまくいかないとき。各章に、目的、始める前に要ること、番号の付いた手順（1つの手順に1つの操作。操作の場所を先に、操作を後に書く）、できた状態（画面で見える結果）を書く。

- 利用者の言葉と、実際の画面のラベルで書く。画面の設計と実際の画面のラベルが違えば、実際の画面のラベルを書き、食い違いを問題台帳に入れる。
- 内部の識別子（規則の番号、表や列の名前、試験用の印）、開発の URL や内部の経路を本文に書かない。台帳との対応は内部用の欄にだけ置く。
- その仕事のできた状態に要らない作業を、同じ章に混ぜない。別の仕事なら別の章にする。
- 画面の表示や注記が仕様と食い違う、または互いに矛盾するときは、マニュアルの側で正しい運用を決めない。実装を見るのは今の動きを知るためだけにし、食い違いを問題台帳に入れて返す。仕様か実装が直るか、決める権限のある人が決めるまで、その章を確定させない。

書き方の勧めは [書き方](references/writing.md) を見る。

### 3. 実際の画面で辿る

隔離した環境で、作り物のデータと作り物の利用者を使い、本番のデータと資格情報を使わない。メールなど外部への送信は捕まえる。読む人の役割で入り、章に書いた手順だけを頼りに、できた状態まで辿る。

- 辿れたら、章の辿った段を「実際の画面で辿った」にし、日、環境、版を書く。
- 書いた前提が無くても辿れたら、その前提を外す。
- 辿れない、または画面の不具合に当たったら、章を確定させず、問題台帳に入れて返す。今の不具合を正しい手順として書かない。
- 本番でしか確かめられない章は「未確認」にする。

### 4. 画面の写しを入れるとき

- 写しは作り物のデータで撮る。塗りつぶしは最後の手段にし、塗った後の画像にも元の値が残っていないか確かめる。
- 受入の証拠の写しを流用しない（証拠は実際の行が映っていることを求め、マニュアルの写しとは求めが逆）。
- ほかの会社の画面、ロゴ、公式の図を写して載せない。
- 手順で使う欄が写しの中で切れていないかを、切り出した後に見る。

### 5. 配る形にして確かめる

配る範囲（誰に、どの章を）を決め、型の欄に書く。正本の形式と置き場は案件の決まりに従い、無ければ一つのファイルを正本にする。配る形（PDF など）に変換するときは、変換した後の実物を開いて、目次、章、画像、内部用の台帳や記録が入っていないことを確かめる。管理者向けの章を、それを読まない人に配る形に入れない。

### 6. 画面が変わったら

記載した仕事の前提、操作、結果に影響した変更なら、その章だけを直し、手順3で辿り直して確かめた日を更新する。新しい仕事は台帳に「未判断」で足してから判断する。確かめた日が見直すきっかけ（案件が決める）を過ぎた章は、配る前に辿り直す。

手順の根拠と、先行の手法から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 終了条件

- 台帳の判断の欄が空でなく、「載せる」の行だけが章を持つ。
- 章ごとに、目的、前提、番号の付いた手順、できた状態があり、確からしさと確かめた日・環境・版がある。
- 確定でない章と、問題台帳に入れた食い違いの一覧がある。
- 配る形にしたなら、配る範囲と、変換した後の実物を開いて確かめた記録がある。
