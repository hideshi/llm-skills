## 先行の手法

## 独自の判断

| 決まり | 理由 | 確かめ方 |
|---|---|---|
| 先に仕事の台帳を作り、判断（載せる／後回し／対象外／未判断）の付いた行だけを章にする | 画面の一覧をそのまま章にすると、読む人の仕事ではなく画面の辞書になり、完了の経路でない画面まで章になるため | 配った後に「この手順でできなかった」と返った章の数と、台帳に無い仕事を聞かれた件数を数え、台帳の出どころを見直す |
| マニュアルは仕様を作らず、仕様と画面の食い違いや画面の不具合は問題台帳で返す | マニュアルの側で埋めると、仕様の穴が文書の中に隠れ、今の不具合が正しい手順として固まるため | 問題台帳に返した件数のうち、仕様か実装が直った件数を数え、返し方を見直す |
| 章ごとに、実際の画面で辿ったかを閉じた語で持ち、辿っていない章を確定させない | 画面の設計だけから書いた手順は、実際の画面と食い違うことがあるため | 辿った章と辿っていない章で、配った後の問い合わせの数を比べる |
| 辿るのは隔離した環境で、作り物のデータと利用者を使い、本番では辿らない | 手順を辿ると登録や送信が本当に起きるため | 辿った記録に本番の環境が書かれた件数を数え、0件であることを確かめる |
| 画面が変わったら、記載した仕事の前提・操作・結果に影響した章だけを直し、辿り直す | 全部を書き直すと手間が大きく、変わっていない章の確かめた日が意味を失うため | 画面の変更の後に、直さなかった章で食い違いが見つかった件数を数え、影響の見方を見直す |
| 配る形に変換した後の実物を開いて確かめる | 変換で目次、画像、内部用の記録の扱いが変わることがあり、元の文では分からないため | 配った後に、変換による欠けや内部用の記録の混入が見つかった件数を数える |
