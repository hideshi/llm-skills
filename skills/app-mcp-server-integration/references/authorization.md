# 認可

アプリのMCPサーバーを、OAuthのリソースサーバーとして動かすときの検証と管理。トークンの発行、PKCE、クライアントの登録（CIMD・DCR）の実装は扱わない。仕様の規定の強さは、[spec-tracking.md](spec-tracking.md) で確かめた版のもの。

## 1. 要求ごとの検証（INV-6）

すべての要求で、次の順に確かめる。どれかが確かめられない（ストアに届かない等）ときは、実行しない。

1. トークンがあり、形が正しく、期限内で、取り消されていない。無効・期限切れなら401（[仕様] MUST）。401には、保護リソースの情報（Protected Resource Metadata）の場所を `WWW-Authenticate` で示す（PRM の実装は [仕様] MUST。401での案内の強さは未確認）。
2. トークンの宛先が、このサーバーである。自分を宛先として発行されたトークンだけを受け付け、ほかに宛てたトークンは受け取らない（[仕様] MUST / MUST NOT）。宛先は、発行時の `resource` と、このサーバーの正規のURIとの一致で確かめる。
3. 受け取ったトークンを、上流のAPIやほかのサービスへ渡さない（[仕様] MUST NOT、トークンの中継の禁止）。上流が必要なら、上流用の資格情報を別に持つ。
4. 認可の世代（後述）が、今の世代と一致する。
5. 要求に必要なスコープがある。足りなければ403と `error="insufficient_scope"`、必要なスコープの一覧（[仕様] SHOULD）。
6. アカウントの今のロールで、そのツールが見える（INV-3）。見えなければ、存在しないツールと同じ応答。

```text
verify(request):
  token = bearer(request)            # 無ければ 401
  grant = store.lookup(hash(token))  # 届かなければ 実行しない
  if not grant or grant.expired or grant.revoked: return 401
  if grant.resource != CANONICAL_URI: return 401
  if grant.generations != current_generations(grant.account, grant.client): return 401
  if required_scope(tool) not in grant.scopes: return 403 insufficient_scope
  if tool not visible_to(role_of(grant.account)): return unknown_tool_error
```

### スコープ（[設計]）

仕様は具体的なスコープ名を定めていない（クライアントが最小権限でスコープを求めることは SHOULD、サーバーがスコープの階層を考慮することは MUST）。このスキルは、読み取りと書き込みでスコープを分けることを既定にする（例: `<app>:read`、`<app>:write`）。これは仕様の要求ではなく、このスキルの設計判断。分ける理由は、読み取りだけの接続を許せるようにすることと、書き込みのトークンが漏れた範囲を同意の画面で見せること。スコープは、ロールによる絞り込み（INV-3）と確認（INV-8）の代わりにはならない。

## 2. 接続の管理（INV-7）

- 接続（クライアント）の追加・許可・停止をする主体を決める（既定は管理者だけ）。利用者の同意は、許可された接続にだけ出す。
- **世代**: アカウント、クライアント、アカウント×クライアントの許可、のそれぞれに世代（増えていく番号）を持つ。トークンは発行時の世代を記録し、要求ごとに今の世代と比べる。停止・取り消し・権限の変更で世代を進めると、発行済みのトークンが次の要求から使えなくなる。
- 再開しても世代は戻さない。古いトークンは使えないまま。再開後は再認可させる。
- 確認（INV-9）にも認可の世代を結びつける。確認の途中で接続を止めたら、その確認も使えなくなる。
- 古い画面から同じ操作が二重に送られたときに、意図しない再開が起きないよう、画面の操作には対象の今の状態を添えて照合する。

## 3. トランスポートの守り

- HTTPの経路は、アプリのCookieの認証と分ける。Bearerだけで認可し、Cookieで通る経路を作らない。
- `Origin` があるときは、許した値と一致するかを確かめる。CLIのクライアントは `Origin` を送らないことがあるので、ブラウザ向けの同一オリジンの検査をそのまま使わない（アプリの既存の守りが、ブラウザ固有のヘッダーを必須にしていないか確かめる）。
- セッションのIDに認可を頼らない。仕様の版によってはセッションが無い（[spec-tracking.md](spec-tracking.md)）。状態を持っていることを、認証の代わりにしない。

## 4. stdio との違い

この資料は HTTP で公開するサーバーだけを扱う。stdio で動くサーバーは、仕様が HTTP の認可に従わないよう求め（SHOULD NOT）、資格情報を環境から取る。このスキルの対象外。

## 5. 成果物に書くこと

- 検証の順と、各段で返す応答の表。
- スコープの名前と、仕様の要求か設計判断かの別。
- 接続を管理する主体、世代を進める操作の一覧、再開の扱い。
- 確かめた仕様の版と日付。
