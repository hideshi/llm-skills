# 書き込みの安全

書き込みのツールを、利用者の確認なしに実行させないための設計。INV-8〜12 を扱う。確認の仕組みの名前（MRTR、`input_required`、`requestState`）は、[spec-tracking.md](spec-tracking.md) で確かめた版のもの。版が変わったら、仕組みの対応だけを直す。

## 1. 流れ

```text
クライアント → サーバー: 書き込みのツールの呼び出し
サーバー: 検証（認可・有効・ロール・引数）。検査だけをして、変更しない
サーバー: 対象の今の状態を読み、確認の文と、署名した確認の状態を作る
サーバー → クライアント: 追加の入力が要る、という結果（確認の要求と状態）
クライアント → 利用者: 確認の文を見せる
利用者 → クライアント: 承諾・却下・取り消し
クライアント → サーバー: 同じ呼び出しを、応答と状態を付けて送り直す
サーバー: 状態の完全性と期限を確かめ、使用済みに記録する
サーバー: accept のときだけ、もう一度すべて検証し、照合と保存を不可分に行う
```

サーバーに「承認待ち」の表は作らなくてよい。確認に必要な文脈は、署名した状態に入れてクライアントに持たせる。ただし、1回だけ使えることはサーバー側の記録で強制する（3節）。

## 2. 確認への対応の判定（INV-8）

- クライアントが確認に対応するかは、**要求ごとに**、その要求の `_meta` にある能力の宣言で判定する（[仕様] 能力は要求ごとに宣言する MUST）。前の要求の結果をキャッシュしない（[設計]）。
- 宣言していない種類の入力の要求を送らない（[仕様] MUST NOT。確認に対応すると宣言していないクライアントに、確認の要求を含めない）。
- 対応しないクライアントでは、書き込みを実行しない。ツールの実行エラーとして、確認に対応したクライアントが要ることを返す。読み取りは使える。
- 応答が `accept` 以外（`decline`、`cancel`、欠落、型の不正、未知の値）なら、何も変えない。
- サーバーが発行した確認の欄だけを読む。クライアントが足した欄は無視する。

## 3. 確認の状態（INV-9）

確認の状態（`requestState` など）は、攻撃者が操作できる入力として扱う（[仕様] MUST）。

| 結びつける項目 | 理由 |
|---|---|
| 用途の識別子と形式の版 | ほかの用途の署名を流用させない |
| 利用者（アカウント） | 別の利用者の確認を使わせない |
| クライアント | 別の接続の確認を使わせない |
| 認可の世代 | 確認の途中で接続を止めたら使えなくする（INV-7） |
| ツールの名前 | 別のツールへ流用させない |
| 引数のダイジェスト | 確認した内容と違う引数で実行させない |
| 対象の状態のダイジェスト | 確認の後の変更を検出する（INV-10） |
| そのツールの単位の設定の世代 | 確認の途中で、その単位を無効にしたら使えなくする（INV-2）。ほかの単位の設定の変更では無効にしない（[設計] の既定。全体で1つの世代を持つ実装も安全だが、無関係な単位の変更で確認中の書き込みまで使えなくなる） |
| 期限 | 短く固定する |
| 一意の番号 | 1回だけの使用を記録する |

- **完全性**: 状態が認可、資源へのアクセス、業務の判断に影響するなら完全性を守り、検証に失敗した状態を断る（[仕様] MUST。仕様は例として HMAC か AEAD を挙げる）。書き込みの確認は必ずこれに当たる。引数や対象を状態に入れて秘匿したいなら AEAD を選ぶ（[設計]）。鍵は用途ごとに分け、署名の比較は定数時間で行う。状態の長さに上限を付け、超えたものは開かずに断る。
- **1回だけ**: 署名は、何回使われたかを知らない（[仕様] 署名や期限だけでは1回だけの使用は保証されず、必要ならサーバーで強制する MUST）。番号を、結果を判定する**前に**、排他的に使用済みとして記録する。`decline` や `cancel` でも消費する。記録できなければ（上限に達した、ストアに届かない）実行しない。
- **状態は認証ではない**: 状態を持っていることを、認証や認可の代わりにしない（[設計]）。仕様は、認可を持つサーバーがすべての要求を検証すること（MUST）と、ツールの引数で渡す状態のハンドルを持つことを認証として扱わないこと（MUST NOT）を定める。このスキルは同じ考えを確認の状態にも当てはめる。送り直しの要求でも、トークンの検証、スコープ、ロール、有効・無効をすべてやり直す。
- **使用済みの記録の置き場**（[設計]、案件で選ぶ）:

| 形 | 向く構成 | 注意 |
|---|---|---|
| メモリに記録し、鍵を起動ごとに作る | 1プロセス | 再起動で鍵が変わり、古い確認は全部使えなくなる（安全側）。件数に上限を付け、期限切れを掃除する |
| 共有のストアに記録し、鍵を共有する | 複数プロセス | 番号の挿入を一意制約などで排他にする。鍵の入れ替えの手順を決める |

- 実行は最大1回。結果がクライアントに届かなかった場合も、同じ確認での再送は断り、確認からやり直させる。結果の到達は保証しない、と要件に書く。

## 4. 照合と保存（INV-10）

- 確認のときに、操作の意味に関わる保存内容（本文、公開状態、公開日時、URL、並び順、分類、所有者、共有の範囲など）のダイジェストを取り、状態に入れる。更新日時の列だけに頼らない（精度が粗いと、同じ時刻の別の変更を見落とす）。
- 保存のときに、今の内容のダイジェストが確認のときと同じかを照合し、同じときだけ保存する。照合と保存は不可分にする（読んだ値を `WHERE` 句に入れた1つの更新文、または1つのトランザクションの中での読み直しと更新）。照合した後に保存するまでの間に、別の変更が入り込めないようにする。
- 変わっていたら保存せず、確認からやり直すよう返す。

```text
apply(args, confirmed_state):
  in transaction:
    current = load_for_update(target)
    if digest(current) != confirmed_state.target_digest: abort "対象が変わった"
    save_via_existing_path(target, args)   # INV-12
```

## 5. 確認の文（INV-11）

- 文は**サーバーが作る**。エージェントが書いた要約や説明を入れない。
- 固定の枠と、入力に由来する内容を分ける。入力は引用として、枠の文と混ざらない形で出す（区切り、欄の名前）。
- 先頭の数行に、**何を・どこへ・どう変えるか**を具体的に置く（例:「記事『…』の本文を変更し、公開中のページに反映」）。クライアントによっては長い文を折りたたむので、要点を先頭に置く。公開中の内容が変わること、公開されること、URLが変わることは強調する。
- 変わる欄は、差分か新しい全文で見せる。上限を超えて省略が要るなら、確認を出さずに断る。
- どのモードでも、確認で秘密情報（パスワード、APIキー、トークン、支払いの情報）を求めない（[設計]）。仕様が禁じているのは form モードでの要求で（[仕様] MUST NOT）、そうした情報には url モードを使うよう求めている。このスキルは、書き込みの確認に秘密情報を入れる理由が無いので、どのモードでも求めない。
- 確認の欄は、承諾・却下だけで答えられる形にする（必須の入力欄を置くと、承諾だけで進めないクライアントがある）。

## 6. 既存の経路を通す（INV-12）

- 書き込みは、既存のUIと同じ検査、保存、保存後の処理（キャッシュの破棄、索引の更新、通知など）を通す。MCP用に別の保存の関数を書かない。
- 既存のハンドラが、HTTPの解析と業務の処理を混ぜている場合は、先に業務の処理を切り出す（挙動は変えない）。切り出しは別の変更として先に行い、既存の試験を通す。
- 省略・空・null・全置換の意味を、ツールごとに固定し、説明文に書く。

## 7. プロンプトインジェクションとの関係

確認は、LLMが読んだ内容に従って書き込もうとしたときに、利用者が止める機会を作る。LLMが従うこと自体は止められない。確認の文がエージェントの説明でなくサーバーの文であること（5節）と、確認の後に内容が変わらないこと（3節・4節）が、この機会を意味のあるものにする。
