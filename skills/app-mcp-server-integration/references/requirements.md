# 要件定義

アプリにMCPサーバーを足すときに、要件の段階で決めることの一覧。一般の要件定義の進め方は扱わない。ここで決めた答えは、案件の要件定義書に書く。

## 1. 公開する範囲

| 決めること | 既定（[設計]） | 関係する不変条件 |
|---|---|---|
| ツールにする機能と、有効・無効の単位 | 単位はふつう機能1つ。種類ごとに公開の可否が違うなら、機能より細かい単位に分ける。設定の世代も単位ごとに持ち、ある単位の変更でほかの単位の確認を無効にしない | INV-2, 9 |
| 各ツールの分類（読み取り・書き込み） | 分類を書かないものは書き込み | INV-1 |
| 書き込みの範囲 | 初版は作成・編集・状態の変更に絞り、削除や、取り消せない操作は入れない | INV-8 |
| 読み取りで返す欄と件数の上限 | 作業に要る欄だけ。下書き・非公開・個人の情報を返すかは欄ごとに決める | INV-4 |
| 有効・無効を変えられる人 | アプリの最上位の管理者だけ | INV-2 |

読み取りの結果は、エージェントを通じてLLMの提供元へ送られる。社外に出せない情報を持つ機能は、読み取りだけでも公開の対象にするかを、データの扱いの方針と照らして決める（INV-4）。

## 2. ロールとツールの表

アプリの既存のロールごとに、見えるツールを表にする。

| ツール | 分類 | 管理者 | 一般の利用者 | … |
|---|---|---|---|---|
| （例）記事の一覧 | 読み取り | 可 | 不可 | |
| （例）記事の編集 | 書き込み | 可（確認つき） | 不可 | |

- 表に無いロール、未知のロールは、すべて不可にする（[設計]）。
- 見えないツールの呼び出しへの応答は、存在しないツールと同じにする（INV-3）。ツールの有無からロールの範囲を推測させないため。
- ロールを下げたとき、発行済みのトークンで使えるツールが次の要求から狭まるかを決める（既定は「狭まる」。業務の権限は要求ごとに読み直す）。

## 3. 接続の管理

| 決めること | 既定（[設計]） |
|---|---|
| 接続（クライアント）を追加・許可・停止できる人 | 管理者だけ |
| 利用者が接続に同意できる条件 | 許可されたアカウントだけ |
| 停止・取り消しの効果 | 発行済みのトークンも止める。再開しても古いトークンは戻らない |
| クライアントの登録の方式 | 案件で選ぶ（事前登録、CIMD、DCR。方式の実装は持たない範囲） |

詳しくは [authorization.md](authorization.md)。

## 4. 書き込みの確認

| 決めること | 既定（[設計]） |
|---|---|
| 確認に対応しないクライアント | 書き込まない。読み取りだけ使える |
| 確認の期限 | 短く（数分から十数分）。案件の作業の長さで決める |
| 確認の文に出せる長さの上限 | 上限を超える変更は確認を出さずに断り、既存のUIを案内する。省略した文で確認を通さない |
| 確認の後に対象が変わった場合 | 保存しない。確認からやり直す |

詳しくは [write-safety.md](write-safety.md)。

## 5. 要件の段階で答える問い

不変条件ではないが、要件の段階で答えを決め、記録する。

- **MCP経由の変更を、既存のUIからの変更と区別して記録するか。** 記録するなら、どの利用者のどの接続による変更かに結びつける。記録の項目と保持の期間は、データの扱いの方針に合わせる。記録しない場合は、事後に「誰がエージェントに何をさせたか」を追えないことを、守らない範囲に書く。
- 確認を自動で承諾するよう設定されたクライアントからの書き込みを、利用者の責任とするか。サーバーでは人の操作かを証明できない（SKILL.md の「守れることと守れないこと」）。
- 長時間の処理（tasks 拡張）を持つか。持つなら、確認の守りが同じく効くかを [spec-tracking.md](spec-tracking.md) の未確認の点から確かめる。

## 6. 守らない範囲を書く

要件定義書に、サーバーが守らない範囲を明記する。少なくとも次を含める。

- エージェントが読んだ内容に従うこと（プロンプトインジェクション）の防止。サーバーは書き込みの確認で影響を止めるだけ。
- クライアントの表示（確認の文が全部見えるか）。クライアントによる。
- 人の操作の証明。
