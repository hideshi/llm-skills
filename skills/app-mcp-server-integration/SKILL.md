# App MCP Server Integration

既存のWebアプリ（サービス）にMCPサーバーを組み込み、HTTPで外部のエージェントに公開するときの、要件定義・設計・実装・試験の手順。言語やSDKに依存しない。例は擬似コードにとどめる。

## 使う場面・使わない場面

- 使う: アプリの機能（記事、商品、記録など）を、MCPのツールとして読み書きさせる。認可にOAuthのリソースサーバーとして加わる。書き込みの前に利用者の確認を求める。
- 使わない: MCPクライアントの実装。既存のMCPサーバーを設定して使うだけの作業。stdio で動くサーバーの認可（仕様は stdio に HTTP の認可を適用しないよう求め、資格情報は環境から取る）。

## 最初に読むもの

MCPの仕様は版ごとに大きく変わる。どの段階でも、作業を始める前に [仕様の追従](references/spec-tracking.md) の確認手順を行い、このスキルが確かめた版と、使う版が同じかを見る。違えば、差分を確かめてから下の不変条件を当てはめる。

## 書き分けの約束

本文では、次の2つを分けて書く。

- **[仕様]**: MCP仕様のMUST・SHOULDなど。強さの語をそのまま写す。
- **[設計]**: 仕様は求めていないが、このスキルが既定として採る判断。案件で外すときは、理由と代わりの守りを記録する。

## 不変条件

IDは変えない。追加は末尾に足し、削除したIDは欠番として残す。詳細と根拠は各段階の参照に書く。

| ID | 条件（1行） | 根拠 |
|---|---|---|
| INV-1 | ツールは読み取りと書き込みに分け、分類を省いたものは書き込みとして扱う。区別はサーバーが強制し、注釈には任せない | 設計（注釈が信頼できないことは仕様） |
| INV-2 | 機能・単位ごとに有効・無効を切り替えられ、既定は無効。無効のツールは一覧に出さず、実行もしない | 設計 |
| INV-3 | ロールで見せるツールを絞り、見えないツールには存在しないツールと同じ応答を返す | 設計（一覧の絞り込みが許されることは仕様） |
| INV-4 | 読み取りでも返す欄を最小にし、件数に上限を付ける。返したものはLLMの提供元へ出ていくものとして扱う | 設計 |
| INV-5 | ツールの名前と説明文は固定にし、利用者が書いた内容を入れない。返す利用者の内容は欄や引用で地の文と分ける | 設計 |
| INV-6 | 受け取る要求はすべて検証する。無効なトークンに401、スコープ不足に403。宛先の違うトークンは受け取らず、上流へも渡さない | 仕様（read/write のスコープ分離は設計） |
| INV-7 | 接続の追加・許可・停止の主体を決める。停止したら発行済みのトークンも止め、再開しても古いトークンは戻らない | 設計 |
| INV-8 | 書き込みは、確認の accept が無ければ実行しない。確認への対応は要求ごとに判定し、対応しないクライアントでは書き込まない | 設計（能力を要求ごとに宣言することは仕様） |
| INV-9 | 確認は利用者・クライアント・認可の世代・ツール・引数・対象の状態・そのツールの単位の設定の世代に結びつけ、期限を付け、完全性を守り、1回だけ使えるようサーバーで強制する | 仕様と設計 |
| INV-10 | 確認の後に対象が変わっていたら保存しない。照合と保存は不可分にする | 設計 |
| INV-11 | 確認の文はサーバーが作り、入力は引用として分け、何を・どこへ・どう変えるかを先頭に出す。どのモードでも秘密情報を求めない | 設計（form モードの禁止は仕様） |
| INV-12 | 書き込みは、既存のUIと同じ検査・保存の経路を通す | 設計 |
| INV-13 | 日時はRFC 3339の時差付きにし、変換は1か所でする | 設計 |
| INV-14 | 引数・本文・トークン・requestState をログに出さない | 設計 |
| INV-15 | アカウント×クライアントごとに回数を制限する | 仕様（ツール呼び出しの回数制限）と設計（単位） |

不変条件は、特定の仕組み（セッション、`elicitation/create` という名前の要求など）に依存しない言い方で書いてある。仕様の版が変わっても、仕組みの対応だけを [仕様の追従](references/spec-tracking.md) で直す。

### 守れることと守れないこと

INV-5 の区別は、プロンプトインジェクションの影響を軽くする手段であり、LLMが読んだ内容に従うことは防げない。サーバーが守れるのは「従った結果の書き込みが、利用者の確認なしに実行されないこと」で、それを INV-8〜11 で止める。確認を自動で承諾するようクライアントを設定した場合や、利用者が内容を読まずに承諾した場合は、サーバーでは区別できない。この限界を要件に書く。

## 段階ごとの索引

各段階で、表の参照を必ず読む。ほかの参照は必要なときに読む。

| 段階 | 必ず読む | 出すもの |

| 要件定義 | [requirements.md](references/requirements.md) | 公開する機能と単位、ロールとツールの表、書き込みの範囲、決めた問いの答え |

| 書き込みの設計 | [write-safety.md](references/write-safety.md) | 確認の流れ、結びつける項目、確認の文の型、照合と保存の方法 |
| 実装 | [implementation.md](references/implementation.md) | ツールの登録の形、要求の処理順、ログと回数制限 |

段階を飛ばして実装から始めた場合も、試験の段階で対応表を埋め、抜けた不変条件を要件まで戻って決める。

## 持たない範囲

次は、このスキルでは扱わない。汎用の手順に任せる。

- 一般の要件定義の進め方
- 試験の技法そのもの（このスキルは、何を試すかだけを決める）
- Webセキュリティの一般項目（CSRF、XSS、TLS、入力の一般的な検査など）
- OAuthの実装そのもの（トークンの発行、PKCE、CIMD・DCR によるクライアント登録）
- ログの一般設計

## 返すもの

段階ごとの成果物は、利用者が指定した場所（案件の要件定義書・設計書・試験計画）に置く。スキルの中に、個別の案件の設計や実測を保存しない。どの成果物にも、使った仕様の版と確かめた日を書く。
