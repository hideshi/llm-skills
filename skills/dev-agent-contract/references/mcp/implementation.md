# 実装の形

設計の判断として実装に渡す、言語やSDKに依存しない実装の形。例は擬似コード。SDKを使う場合も、ここに書いた守りがSDKのどこで行われ、どこで行われないかを確かめ、足りない所を自分で足す。

## 1. ツールの登録（INV-1, 2, 5）

ツールは、機能（アプリのモジュール）が宣言し、共通の部品が登録する。

```text
Tool {
  name, title, description       # 固定の文字列。利用者のデータを入れない（INV-5）
  input_schema
  effect: WRITE | READ           # 既定値は WRITE（INV-1）
  unit                           # 有効・無効の単位（INV-2）。設定と世代は単位ごとに持ち、確認には自分の単位の世代だけを結びつける
  roles                          # 見せるロール（INV-3）
  read(principal, args)          # READ だけが持つ
  prepare(principal, args)       # WRITE だけが持つ。検査と確認の文と対象のダイジェストを作る。変更しない
  apply(principal, args, state)  # WRITE だけが持つ。照合と保存を不可分に行う
}
```

起動時に検査し、問題があれば起動を止める。

- 分類の値が未知、または読み取りと書き込みの関数が混ざっている。
- 名前の重複、仕様の名前の規則に合わない名前。
- 単位の名前の重複、宣言の無い単位。

分類（`effect`）は、ツールの注釈（読み取り専用のヒントなど）とは別に持つ。注釈はクライアント向けの手がかりとして付けてよいが、サーバーの判断に使わない（INV-1）。

## 2. 要求の処理の順

```text
handle(request):
  check_transport(request)                     # 大きさ、深さ、ヘッダーと本文の一致、版
  principal = verify(request)                  # authorization.md の1節
  if not rate_limiter.allow(principal.account, principal.client): return 429   # INV-15
  switch method:
    tools/list: return tools visible to principal and enabled               # INV-2, 3
    tools/call:
      tool = lookup(name)
      if not tool or not enabled(tool.unit) or not visible(tool, principal):
        return unknown_tool_error                                             # 3つとも同じ応答
      args = parse_typed(tool.input_schema, request.args)                     # 未知の欄は断る
      # tool.read と write_flow は、既存の画面と同じ1件ごとの確かめと所属の絞り込みを通る（INV-16）
      if tool.effect == READ: return limit_fields_and_count(tool.read(principal, args))  # INV-4
      return write_flow(tool, principal, args, request)                      # write-safety.md
```

- 書き込みは、1つの共通の処理（`write_flow`）からだけ呼ぶ。確認の検証が失敗したら、ほかの経路で実行しない。検証の途中で例外が起きたら、実行へ進まず断る。
- 引数は型付きで解析する。重複したキー、末尾の余分なデータ、不正な文字コード、範囲外の数値、未知の欄を断る。ダイジェストを取る対象と、実行に渡す対象は、同じ解析の結果にする（解析を2回して食い違わせない）。
- 一覧の件数、応答の大きさ、ストアの処理時間に上限を付ける（INV-4）。

## 3. 返す内容（INV-4, 5）

- 返す欄は、ツールごとに許した欄だけ。内部のID、個人の情報、下書きを返すかは、公開の範囲の表で決めた通りにする。
- 利用者が書いた内容（本文、題名、コメント）は、構造化した欄に入れて返す。説明の文にはめ込まない。文で返す場合は、引用であることが分かる区切りを付ける。
- ツールの説明文や一覧に、データから作った文字列を入れない。

## 4. 日時（INV-13）

- 読み取りも書き込みも、RFC 3339 の時差付きにする。読み取りで返す形は1つに決め（例: UTC）、読んだ値をそのまま書き戻せるようにする。
- 時差の無い値は断る。範囲の外の値（アプリが扱えない年代）も断る。
- 書式の変換は共通の関数1か所だけで行い、ツールのコードに書式を直接書かない。試験で、全ツールがその関数を通ることを確かめる。
- 確認の文は人が読むので、アプリのタイムゾーンで地域名を付けて出してよい。
- 時刻を持たない日付は、日時とは別の型として扱う。

## 5. ログ（INV-14）

- 出してよいのは、登録済みのツール名、固定の分類（成功、拒否の理由の種類など）、所要時間。
- 出さないもの: 引数、本文、トークン、確認の状態、確認への応答、`Authorization` ヘッダー、OAuthのコードや値、未知のツール名（固定の分類に置き換える）、生のエラー文、panic などの内容。
- ライブラリやフレームワークが要求の本文やヘッダーを自動でログに出していないかを確かめる。

## 6. 回数の制限（INV-15）

- 認証の後に、アカウント×クライアントの組ごとに制限する（例: トークンバケット）。超えたら429。
- 認証の前にも、全体の回数と同時実行の数に上限を付ける。
- 制限の記録の件数に上限を付け、古い記録を捨てる条件を決める。上限に達したら、安全側（断る）に倒す。
- 複数プロセスで動かすなら、記録を共有するか、プロセスごとの上限を合計で割り振るかを決める。

## 7. 一覧の更新

ツールの有効・無効を変えたとき、接続中のクライアントが一覧を読み直すかは、仕様の版とクライアントによる（通知の仕組みや、一覧のキャッシュの期限）。読み直されなくても、呼び出しは要求ごとに有効・無効を確かめるので、無効のツールは実行されない（INV-2）。
