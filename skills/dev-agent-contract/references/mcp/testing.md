# 確かめる観点

不変条件ごとに、何を試すかを決める。試験の技法そのもの（試験の書き方、モックの作り方など）は扱わない。

## 1. 不変条件と試験の対応表

設計の判断の確かめる観点に、この表を写す。テストケースを導くときに、各行にテストケースの識別子を結ぶ。空の行が残っていたら、その不変条件は守られていないものとして扱う。

| ID | 少なくとも試すこと |
|---|---|
| INV-1 | 分類を省いたツールが書き込みとして扱われる（確認なしに実行されない）。未知の分類、関数の混在で起動が止まる。注釈を読み取り専用にしても、書き込みのツールは確認を求める |
| INV-2 | 有効にしていない単位のツールが一覧に出ず、呼び出しが存在しないツールと同じ応答になる。確認の途中でその単位を無効にすると、承諾しても実行されない。有効に戻しても古い確認は使えない。別の単位の設定を変えても、確認は使える |
| INV-3 | 見えないロールで、一覧に出ず、呼び出しの応答が存在しないツールと**同じ値・同じ文言**になる。確認の送り直しも同じ判定を通る。未知のロールはすべて拒否 |
| INV-4 | 許した欄以外が返らない。件数の上限を超える要求で、上限までしか返らない |
| INV-5 | 利用者のデータに指示の文を入れても、ツールの名前・説明文・一覧が変わらない。返す内容が欄か引用に入っている |
| INV-6 | トークンなし・不正・期限切れで401。別の宛先のトークンで401。スコープ不足で403と `insufficient_scope`。ストアに届かないとき実行しない。上流への要求にトークンが含まれない |
| INV-7 | 停止の後、発行済みのトークンが次の要求で使えない。再開しても古いトークンが使えない。停止の前に出した確認が使えない |
| INV-8 | 能力を宣言しない要求で書き込みが実行されない。同じクライアントでも、前の要求で宣言し、今の要求で宣言しなければ実行されない。`decline`・`cancel`・欠落・未知の値で何も変わらない |
| INV-9 | 状態を1バイト変えると断る。期限切れで断る。別の利用者・クライアント・ツール・引数での送り直しを断る。同じ状態を2回使うと2回目を断る（`decline` の後も）。使用済みの記録が満杯のとき実行しない |
| INV-10 | 確認の後に、既存のUIの経路で対象を変えると、承諾しても保存されない。照合と保存の間に別の更新を割り込ませる試験（並行の試験）で、片方だけが保存される |
| INV-11 | 確認の文の先頭に操作・対象・変わる欄がある。入力が引用の区切りの中にある。上限を超える変更は確認を出さずに断る。秘密情報を求める欄が無い |
| INV-12 | MCPからの書き込みと既存のUIからの書き込みで、検査の結果と保存後の処理が同じ |
| INV-13 | 時差の無い値を断る。読んだ値をそのまま書き戻せる。すべてのツールが共通の変換の関数を通る（新しいツールも検査の対象に入る形で） |
| INV-14 | カナリア試験（3節） |
| INV-15 | 上限を超えた要求が429。別のアカウント・クライアントの組は影響を受けない。記録の上限に達したら断る |
| INV-16 | 読み取り・書き込みの道具に、他人やほかの組織のものの識別子を渡すと拒まれる（拒み方は、認可の設計の判断の「存在を知らせるか」どおり）。引数の所属や参照先に、ほかの組織のものを入れても拒まれる。一覧と検索の道具が、既存の画面と同じ所属の範囲しか返さない。道具を見せる役割が、許可の表で許された主体より広くない |

## 2. 守りを外して試験が落ちることを確かめる（ミューテーション）

試験と往復の確かめ（この節と4節）は、隔離した環境で、本番のデータと本番の資格情報を使わずに行う。書き込みの後の処理が外へ送るなら（通知、外部の API）、送信を捕まえる設定にしてから動かす。

試験が通っても、守りを試していなければ意味が無い。不変条件ごとに、守っているコードを一時的に外し（条件を反転、検査を削除、照合を外す）、対応する試験が落ちることを確かめる。

- 少なくとも INV-1、2、3、6、8、9（改ざん、1回だけ）、10、16 で行う。
- 落ちなかった場合は、試験を直してから、もう一度行う。
- 結果（どの守りを外し、どの試験が落ちたか）を検証の記録に残す。道具を使ってもよいし、手で行ってもよい。

## 3. ログのカナリア試験（INV-14）

- 引数、本文、トークン、確認の状態、確認への応答、未知のツール名に、一意の目印の文字列（カナリア）を入れて、成功・拒否・エラー・panic の各経路を通す。
- 出たログのすべて（アプリのログ、フレームワークのアクセスログを含む）に、目印が現れないことを確かめる。
- 新しいツールを足したときも、自動でこの試験の対象に入る形にする。

## 4. 往復の試験

確認の送り直しを含む、要求から保存までの往復を試す。

1. 書き込みのツールを呼ぶ → 追加の入力が要るという結果と、確認の文、状態が返る。この時点で何も変わっていない。
2. 状態と `accept` を付けて同じ呼び出しを送り直す → 保存され、結果が返る。
3. 同じ状態で、もう一度送り直す → 断られ、2回保存されない。
4. 送り直しの要求の識別子が、最初と違っても同じに扱われる（2026-07-28 では、最初の要求と送り直しで JSON-RPC の `id` を変えることがクライアントの MUST）。
5. 仕様の版のヘッダーや能力の宣言が無い、または食い違う要求の扱い。

可能なら、実際のクライアント（少なくとも1つ）で同じ往復を通し、確認の文がどう表示されるか（折りたたまれる行など）を記録する。クライアントの版と日付を添える。
