# このスキルを修正・試用し、必要なら改善 PR を作る

利用者がこのスキル自体の修正・試用や PR を希望したときだけ読む。通常の振り返りとは別の作業で、振り返りメモや個人用スキルは配布元に保存しない。

流れは **修正用ブランチで変更 → 検証 → 指定された導入先で試す → 希望するときに PR**。手元の試用だけで終えてよい。最初から PR まで頼まれたら、長い試用を必須にしない。

## 依頼の範囲

| 利用者の依頼 | 含むこと | 含まないこと |
|---|---|---|
| 改善点を挙げた、差分を見たい | 差分の作成 | 導入、プッシュ、PR |
| 手元で直して使いたい | 修正用ブランチでの変更・検証・ローカルのコミット、指定された導入先への反映 | fork の作成、プッシュ、PR |
| PR にして | 上記に加え、公開前の確認、プッシュ、PR の作成 | マージ、リリース、ほかのアプリへの反映 |

「気になるね」などの反応を、修正や公開の承認に読み替えない。すでに示された意向は聞き直さない。

## 1. 問題と配布元を確かめる

期待、実際、起きる条件、原因となる本文の箇所を特定する。スキルの指示が原因か、エージェントの誤りや環境の制約かを分ける。再現できていない部分は未確認とする。

配布元は、このスキルを含む `llm-skills` のリポジトリ。URL は導入記録と配布元のチェックアウトの Git remote で確かめ、アプリの remote と取り違えない。名前から所有者や URL を推測しない。分からなければ利用者に聞く。配布元を確かめられたら、最新の本文と既存の Issue / PR を読み、解決済みや重複でないかを見る。手元の修正だけなら、URL が未確認でも、利用者が指定したチェックアウトや導入版を基点にして進めてよい（由来を記録する）。

## 2. 修正用ブランチで直す

配布元か利用者の fork の、別のチェックアウトと作業用ブランチを使う。導入先のアプリ、稼働中のスキルのコピー、個人リポジトリを編集の場所にしない。利用中のチェックアウトのブランチを勝手に切り替えない。リンク経由で稼働中のスキルが変わるなら、別のチェックアウトを使う。基点のコミットとブランチを記録する。

配布元の AGENTS.md、貢献の指針、検証方法に合わせる。今回の問題を直す最小の変更にし、一つの特殊な例を全利用者への義務にしない。関連する説明も直す。

## 3. 検証する

frontmatter、参照リンク、手順の整合を確かめる。元の問題が起きる例と、既存の正常な例の両方で、直した指示が意図どおりに働くかを見る。実機で動かしていないものは、その限界を書く。

## 4. 導入して試す（希望された場合）

差分、基点と修正後のコミット、導入先の全パス、方式、切り戻し方を示し、依頼された導入先にだけ反映する。コピー方式では `references/` と `LICENSE` を含むフォルダー全体を反映し、ほかの独自変更を上書きしない。導入記録には、配布元の版、修正版のブランチとコミット、導入先と方式、試用中であることを残す。

ブランチを作っただけでは利用版は変わらない。再読み込みか新しいセッションで、修正版の内容が実際に読まれることを確かめてから、導入済みと報告する。

次の通常の区切りで、元の問題が消えたか、正常な使い方に悪影響や負担がないかを確かめ、継続・再調整・利用停止を選ぶ。効果が確かめられなければ未確認とする。重大な欠陥が分かっている旧版へ自動で戻さない。試用の記録は利用者のメモに残し、配布元の変更には含めない。

## 5. 公開の前に確かめる

利用者が PR を希望したら、配布元の最新の版と既存の Issue / PR を改めて確かめる。

**書き直す。** 元の会話、振り返りメモ、個人用スキル、導入記録、ログをそのまま載せない。問題の条件を保った最小の架空例と、確かめた結果の一般化した要約を新しく書く。架空例で確かめたことと、実際の試用で確かめたことは分けて書く。人・組織・顧客・アプリ・個人リポジトリの名前、ローカルのパス、内部の URL やホスト名、メールアドレス、実データ、認証情報を使わない。業務内容、構成、日時、件数の組み合わせで特定されないかも見る。

**履歴を分ける。** 配布元の公開済みの版から新しい公開用ブランチを作り、確かめた最小の修正だけを適用する。試用ブランチのマージや、そのままの cherry-pick で履歴やメッセージを持ち込まない。公開用のブランチだけを送り、全ブランチやタグをまとめて送らない。利用者の手元の履歴を書き換えない。

**送る前に全部見る。** PR のタイトル・本文、ブランチ名、コミットのメッセージと著者情報、差分（削除行、ファイル名を含む）、送る履歴、添付やスクリーンショット、メタデータ。既存の Issue / PR の検索語にも利用者固有の情報を入れない。秘密の検出の道具は補助に留め、一致がないことだけで確認済みとしない。確認の報告に秘密の値を再掲しない。

**確かめられなければ送らない。** PR まで頼まれていても、秘匿情報を除けたと確かめられなければ、プッシュ、PR、Issue、コメント、添付を送らず、手元の修正版の利用に留める。確認の後に内容が変わったら、変わった部分を見直してから送る。

## 6. PR を作って結果を返す

使えるホスティングサービスの機能で、送信先とベースブランチを確かめ、公開用ブランチをプッシュして PR を作る。特定の CLI や MCP を必須にしない。書き込み権限がなければ、利用者が承認した fork を使う（fork の新規作成の希望が分からなければ、その点だけ聞く）。PR の本文は「問題と起きる条件」「直した後の挙動」「検証と未確認」を中心に短く書く。

認証や権限が足りなければ、未実施のことと、用意できた差分・PR の本文・残りの操作を返す。作れなかった PR を作成済みと報告しない。認証情報を会話に貼るよう求めない。作ったら URL、主な変更、検証の結果を返す。既存の PR があれば重複して作らない。
