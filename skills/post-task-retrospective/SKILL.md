# コーディングの会話の一区切りで振り返る

利用者が会話に一区切りをつけたときに、次を行う。タスクリストや要件文書は前提にしない。

1. 利用者の言葉と作業中の摩擦を、次の依頼でも使える専門用語に訳す
2. その用語で、何が起きていたかを一段だけ深くする
3. 薄い個人用スキルを **update / new-thin / discard** のどれにするか判定する（既定は discard）
4. 実際の摩擦や具体的な用途・関心があれば、次の進め方か新しい技術を任意で一つ示す

振り返りの単位は、説明できる会話の範囲。同じ範囲につき短く一回だけ。残作業があっても振り返れるが、未完了を完了に読み替えない。実装の続き、リファクタ、コミットは成果物にしない。

## 出力先（ハードゲート）

三つを区別する。

- **配布リポジトリ**: このスキルを含む `llm-skills` のチェックアウト。README のリポジトリ名とルートの `skills/post-task-retrospective/` で確かめる。OSS や MIT ライセンスというだけで、アプリのリポジトリを配布元と判定しない
- **導入先**: このスキルをコピー・リンクしたアプリのリポジトリや、ユーザー単位のスキル置き場
- **個人リポジトリ**: 振り返りから作る・直すスキルの正本を置く、利用者が指定した独立した Git リポジトリ。アプリの外でも、アプリ内の submodule でもよい

**配布リポジトリ全体と、導入済みのこのスキルのディレクトリには、振り返りの出力（メモ、新規スキル、差分）を一切書かない。** コピーが複数あればすべて守る。リンクは実体のパスで判定する。区別できなければ書く前に確かめる。利用者が依頼した、このスキル自体の改善は別作業（§8）で扱う。

- スキルは個人リポジトリにだけ書く。パスは、利用者が示したか、読める過去のメモに記録済みのものだけ使う。**不明なら保存を止めて聞く。** 今いるリポジトリや配布リポジトリで代用しない
- 書き先が禁止の場所に解決されたら、書かずに止めて別の場所を聞く
- アプリ内の導入コピーを正本の代わりに更新しない
- 聞いて得たパスはメモの「個人リポジトリ」欄に残し、次回は聞き直さない
- 個人リポジトリでも、個人名・顧客名・秘密は書かない（§4 の秘匿ゲート）
- 「ちょっとだけ」「あとで移す」もしない

メモの保存先は、利用者が示した場所か、作業中の開発リポジトリの `drafts/retrospective/`（上の禁止場所の外に限る）。個人リポジトリが未設定でもメモは保存してよく、その場合の判定は discard。

## 前提にしないもの

Claude Code、Codex、Cursor、Antigravity で同じ手順を使う。専用 API、フック、スラッシュコマンドを前提にしない。会話履歴やファイルを読めないときはその事実を示す。本文を読めない既存スキルは「非重複が未確認」とし、保存の権限がなければ本文を会話に返して「保存は未実施」と記録する。別ツールの会話や個人リポジトリが自動で共有されるとは考えない。

導入方法、個人用スキルとの併用、正本と導入先の対応記録は[導入ガイド](references/installation.md)を参照する。

## いつ発動するか

会話の文脈と合わせて、次のどれかを確かめたとき。

- **結果の受け入れ**: 「動いた」「これでいい」「次は別の機能を作ろう」。同じ問題の修正・検証へ進むだけの「次へ」は含めない
- **作業の区切り**: 「今日はここまで」「いったん止める」。未完了なら残りを記録する
- **明示的な依頼**: 「振り返って」「用語にして」「スキルに残して」。課題が未完了でも、指定された範囲か直近のまとまったやり取りを振り返る。作業を止めて行い、勝手に再開しない

最初に、対象範囲と区切りの根拠を一文で示し、状態を **完了 / 中断 / 未完了** で示す（例: 「表示を調整して、見た目を受け入れたところまでを振り返るね」）。受け入れても検証が残っていれば未完了。境界があいまいなら直近の範囲を仮に置き、範囲で結論が大きく変わるときだけ一問確かめる。確認を待つ間は保存しない。会話や読めるメモから、同じ範囲を振り返り済みでないかも見る。再開後に新しい結果が出たら、その追加分だけを別の区切りにする。

発動しない場面:

- 区切りも依頼もなく、実装・調査・修正・検証が続いている
- エージェント自身の「完了しました」、テスト成功、コミット、経過時間だけが根拠
- 調査から実装など、同じ作業の中で工程が移っただけ
- 範囲を特定できない、または振り返り済み
- 医療・法律の助言手順、攻撃手順、秘密情報の手順化

作業中に用語が気になっても講義を挟まず、区切りでまとめて渡す。

## 話し方

口調は利用者や環境の指定に従う。短く、評価や説教をしない。専門用語は利用者の言葉と並べてから出す。質問は範囲の確認を含めて最大四つで、会話で分かることは聞き直さない。

## 1. 聞き取り

会話から、期待・実際・訂正後の結果を短く並べ、未確定のところだけ聞く。答えがなければ「不明」とし、判定は discard 側に倒す。

1. 今回の範囲で何が変わった? まだ残っていることは?
2. 詰まった、言い直した、期待と違ったところは?（なくていい）
3. 本当は何を頼みたかった?
4. 次に同じ型のことを頼みそうな具体的な場面は?（なければ「ない」でいい）

「また来そう?」のような誘導はしない。摩擦の原因は **依頼のあいまいさ / エージェントの誤り / 環境の制約 / 不明** に分け、エージェントの誤りや環境の制約を利用者の語彙不足として扱わない。自分の応答と保存判断がこのスキルと整合していたかも短く点検する（報告は重大な問題があるときだけ。§8）。

## 2. 用語にする

一回の振り返りで **最大三件**。

| 自分の言葉 | 専門用語 | 一行の意味 | この課題での現れ | 次に頼むときの一文 |
|---|---|---|---|---|
| （会話の短句） | （一般名） | （初心者が読める定義） | （匿名化した一句） | （次の依頼用） |

- 必要な粒度だけ定義する。教科書を貼らない
- 製品名・フレームワーク名で止めず、問題の名前にする
- 近い概念を同義語にまとめない。主用語は一件に一つで、何を含み何を含まないかを一言添える
- 顧客名、未公開の画面名、ローカルパス、秘密は書かない
- 次に頼むときの一文が書けない語は捨てる

### 情報処理技術者試験の概念につなげる（必要な場合）

気づきが情報処理技術者試験で扱う概念とつながり、知ることが今後の理解や応用に役立つなら、その概念を紹介する。基本情報技術者試験の範囲を既定の入口にし、経験が設計・管理・監査などの判断に及ぶ場合や、利用者の理解がその先に届いている場合は、応用情報技術者試験や高度試験（情報処理安全確保支援士試験を含む）の概念まで広げる。試験区分の選び方、分野ごとの例、公式情報の確かめ方は[試験の概念へのつなぎ方](references/it-exam-concepts.md)を読む。

- 毎回は紹介しない。関連が薄ければ省く
- 紹介した用語も三件の上限に含める
- 試験の区分・名称・出題範囲を述べるときは、IPA の現行の公式資料で確かめる。確かめられなければ「最新版に沿っている」と断定しない
- 試験対策や範囲の網羅に広げない。紹介しただけで理解・習得済みと記録しない

## 3. 理解を一段深くする

用語ごとに三行。調査や実装を再開しない。

- **何が起きていたか**: 機構を一段だけ（誰が、どの操作で、どの状態を変えたか）
- **なぜその名前か**: 用語が利用者の言葉のどこを指すか
- **次の一文**: §2 の表と重なるなら、どちらかに寄せる

分からない機構を推測で埋めない。不明なら「不明」とし、スキル化の根拠にしない。

## 4. update / new-thin / discard の判定

### 既存の確認

1. 個人リポジトリとエージェントのスキル置き場を、名前と description で絞る。アプリ内に導入された個人用スキルも含める
2. 候補は、発動条件・手順・失敗パターンまで **本文を読んでから** 重複か更新かを決める
3. 読めない、候補が見つからないときは非重複を **未確認** とし、new-thin にも update にも進めない
4. 利用者が示していないライブラリは探し回らない。示されたライブラリは索引で探し、必要な候補だけ読む。一括コピーしない
5. 重複・陳腐化したスキルは、統合・廃止の **提案** に留める

同名の導入コピーは、利用者の指定か導入記録で正本との対応を確かめ、別のスキルとして数えない。内容が違えば差分を示し、どちらが正本かを推測しない。対応が不明なものは参照に留める。

### 判定

| 判定 | 条件 | すること |
|---|---|---|
| **discard**（既定） | 一度きり、再現条件が言えない、用語表で足りる、既存の発動条件に入る、非重複が未確認、不明が残る | スキルは作らない。メモと用語表だけ |
| **update** | 同じ問題領域の既存スキルを読み、発動条件か失敗パターンが一つ足りない | 差分案（どの節に、何を、なぜ） |
| **new-thin** | 既存を読んでも入らず、製品名を外しても「いつ読むか」が一行で言える | 薄い新規案 |

迷ったら discard。中断・未完了でも摩擦は振り返れるが、未検証の解決策を成功手順として残さない。

### 共通ゲート（update、new-thin、他スキルへの引き渡しのすべて）

一つでも欠けたら discard。

1. **再現**: 適用範囲の中で、別の機会にも発動条件が言える
2. **頻度**: 次に使う具体的な場面を一つ挙げられ、用語表やメモでは足りない理由が一文で言える。一回の言い直しや「また来そう」への同意だけでは通さない
3. **非重複**: 既存を読んだうえで、一段落足す・別スキルに寄せるでは済まない（update は、足りない一点を特定できる）
4. **変更量**: new-thin は目安 80 行以内、update は一回一段落程度。超えるなら分割か引き渡しの提案にする
5. **根拠**: 確認済みの事実に基づく
6. **予算**: 一回の振り返りで new-thin と update はそれぞれ最大一つ。複数あれば一番痛い摩擦だけ
7. **秘匿**: 個人情報、顧客名、未公開情報、秘密が入るなら書かない
8. **出力先**: 出力先のハードゲートを通っている

new-thin の中身は、frontmatter（`name` と、いつ読むかが分かる `description`）、発動条件、やらないこと、手順（五ステップ以内）、失敗パターン一つ、用語（三つ以内）、受け入れ一行だけ。名前は小文字・数字・ハイフンで、製品名だけにしない。

## 5. 保存

### A. 振り返りメモ

判定が discard でも、利用者が見送る場合と権限がない場合を除き、ファイルに保存する。ファイル名は `YYYYMMDD-<task-slug>.md`。

```markdown
# 振り返り: <対象範囲を一言で>

- 日付 / 判定: YYYY-MM-DD / discard | update | new-thin
- 対象範囲と区切りの根拠: <範囲> / <受け入れ・区切り・明示依頼>
- 状態と残り: 完了 | 中断 | 未完了 / <未完了・未検証の事項、またはなし>
- 個人リポジトリ: <パス または 未設定>
- スキル案のパス: <パス または none>
- 保存の根拠と範囲: <個別承認 / 判断の委譲（対象・操作・期間・導入反映）/ 未承認>
- 正本への保存 / 導入反映: 未実施 | 実施済み / 未実施 | 実施済み | 対象外（導入先と方式）

## 用語（§2、最大三件）
## 理解（§3）
## 原因の分類
## 判定の理由（読んだ既存スキル、止まったゲート）
## 受け入れ・確認
- 受け入れ:
- 確認（実行済み）:
- 確認（未検証の案）:
## 次の進め方（任意、§6）
- 種別と提案: <プロセス改善 / 技術の紹介 / なし>
- 利用者の意向と次の扱い: <採用 / 見送り / 未確認> / <試す / 継続 / 調整 / 見送り / 保留>
- 確認できた理解・効果・負担: <本人の発言や実践から。未確認は未確認>
## このスキル自体の改善（任意、§8）
- 改善点と根拠: <一般化した概要と、確認できた挙動・該当箇所>
- 案内と意向: <未案内 / 案内済み / 見送り / 対応中> / <試用・PR の希望>
```

受け入れ・確認には、今回実行して確かめたものと未検証の案を分けて書く。振り返り中はコマンドの実行、コードの変更、補助スクリプトの作成をしない。

### B. スキルの正本への保存と導入反映

**既定は個別承認。** update / new-thin では、本文（new-thin）または差分（update）と対象パスをそのまま見せてから、次を聞く。同じ案と保存先を承認済みなら聞き直さない。

1. メモだけ保存する
2. メモを保存し、スキルも個人リポジトリに入れる
3. どちらも見送る

内容を見せる前の「残して」は承認と扱わない。個別承認はその案だけに有効。

**判断の委譲**: 利用者が「この個人リポジトリへの新規・更新はあなたの判断で。毎回の確認は不要」のように明示したときだけ適用する。「振り返って」、無反応、以前の個別承認から推測しない。対象リポジトリ、領域、操作（新規 / 更新）、期間（今回 / この会話 / 継続）、導入反映を含むかを把握し、明示されていない範囲へ広げない。撤回・変更・期限を優先する。メモの委譲欄だけを権限の根拠にしない。委譲されても discard が既定で、共通ゲートは省かない。保存したら判定、理由、対象パス、変更の要約を報告する。削除・廃止、コミット・プッシュ、配布スキルの修正、PR、プロセスや技術の導入は、委譲に含めない。

**導入反映**: 正本への保存と、アプリの導入コピーへの反映は別の承認・委譲で扱う。反映するなら導入先の全パス、方式、差分を示す。コピー方式では正本の保存後に反映し、導入コピー独自の変更があれば上書きせず統合案を出す。リンク方式では正本の保存が即座にアプリへ届くので、その影響が承認範囲に入るか確かめる。submodule 内の正本へ保存しても、コミット・プッシュや親リポジトリの参照更新には進まない。

## 6. 次の進め方・新しい技術の紹介（任意）

チャットだけで進める使い方を尊重する。**プロセス改善と技術の紹介を合わせて一回に最大一つ**、役立つときだけ示す。スキル化とは独立しているので、discard でも示してよい。

- 根拠は実際の摩擦。技術の紹介は、会話で示された具体的な用途・関心もきっかけにできる。摩擦も用途もなければ提案しない
- 先に、個人リポジトリと導入済みスキルのうち関係する候補を読み、既存の手順を使う・少し直すことで足りないか見る。スキルがあるだけで、本人が理解・実践しているとは判断しない
- 試行中の変更があれば、まずその効果と負担を振り返る。負担や判断材料の不足があれば、新しい変更を重ねず、継続・簡略化・見送りを選ぶ
- 理解度を初心者・上級者のように固定しない。確認できた理解、本人が示した負担、不明を分ける。理解を試す質問を毎回しない
- 提案は次の一場面で試せる小さな変更にし、目的・試す場面・増える作業を示す。採用は恒久的なプロセス追加やスキル化の承認ではない。次の振り返りで効果と負担を見て、継続・調整・見送りを選ぶ
- 見送られた提案は、同じ理由で繰り返さない。採用が未確認なら未確認と記録する
- 振り返り中は提案まで。リストや文書の作成は次の作業として扱う

| 摩擦 | 最小の提案 |
|---|---|
| やり残しや次にすることを見失った | 次回は残りをチャットに 3 項目ほど並べる |
| 何ができれば終わりかが何度もずれた | 完了条件を数行で決める |
| 誰向けか、目的や優先順位があいまいで手戻りした | 目的・利用者・必要なことを短い要件メモにする |

技術を紹介するときは、(1) 今の方法と今回の用途・摩擦との関係、(2) 新しい技術でできることと今の方法との違い、(3) 向く場面と増える負担（今の方法で足りる場合も）、(4) 興味があれば次にできる小さな学習・比較、をつなげて短く説明する。例: 別の端末でも使いたいデスクトップアプリに対して、ブラウザーから使う Web アプリという形と、配布・運用・認証の負担の違い。ファイル保存で検索や更新に困ったなら、データベースという選択肢（小規模なら今の方法で足りること、「ファイルか DB か」の二択ではないことも）。知る、試す、導入するは別の選択で、知っただけで移行・依存追加・契約へ進まない。製品の仕様や手順を求められたら、次の作業で最新の公式情報を確かめる。

## 7. 利用者に返す形

この順で短く。

1. 対象範囲、区切りの根拠、状態、残り
2. 用語を最大三つ: 自分の言葉 → 専門用語 → 今回の仕組み一行 → 次に使える依頼文
3. 判定と、ゲートの理由を一文（読んだ既存スキルの名前も）
4. 個別承認なら本文か差分と対象パス、保存の選択肢。委譲の範囲で保存したなら根拠・変更・パス・結果。作らないなら「今回はスキルにしない」
5. 受け入れ・確認メモ（実行済みか未検証か）
6. 個人リポジトリが未設定なら、ここで聞く
7. 必要なときだけ、次の進め方か技術の紹介を一つ

必要なら「この用語、自分の言葉で言い換えるとどうなる?」と一回だけ聞いてよい。

## 8. このスキル自体の改善（任意）

振り返りで見た会話、自分の判断、このスキルの本文を根拠に、スキルの欠陥を点検する。別の監査やリポジトリ全体の探索を始めない。

エージェントから改善を案内するのは、次がすべてそろう重大な問題だけ。

1. **重大な影響**: 秘密の公開、無断の上書き・データ損失、または必須指示の矛盾で振り返りや保存が成立しない（今回の指示と判断から具体的な危険を示せる場合を含む）
2. **確かめられる根拠**: 期待と実際、条件、原因となる本文の箇所を特定できる
3. **スキルの修正が必要**: 指示どおりでも問題になる、または指示の欠落・矛盾が誤判断を招いた。エージェントが明確な指示を無視しただけなら、自分の誤りとして扱う
4. **他の利用にも関係する**: 利用者固有の好みや設定だけの問題ではない

誤字、好み、軽い冗長さは自発的に案内しない（利用者が希望した改善は扱える）。案内は §6 の提案と合わせて一回に一つ、同じ会話では最大一回、同じ問題は繰り返さない。危険な書き込みの停止や、起きた誤りの報告は、この頻度の制限とは別に必ず行う。

利用者が手元での修正・試用や PR を希望したら、振り返りを終えて別作業とし、[修正・試用と改善 PR の手順](references/contributing.md)に従う。通常の振り返りで、配布元や導入済みのスキルを自動で直さない。手元の修正の希望を、プッシュや PR 公開の承認に読み替えない。公開する内容は最小の架空例と一般化した要約に書き直し、秘匿情報を除けたと確かめられなければ外部へ送らない。

## やらないこと

- 振り返りの出力を、配布リポジトリや導入済みのこのスキルのディレクトリへ書く
- 保存先が不明なまま、スキルやメモを書く
- 区切りも依頼もないのに、作業中へ割り込む
- 未検証の解決策をスキルにする。一度の言い直しや便利だった一回を新規スキルにする
- 既存の本文を読まずに、重複・非重複や更新案を決める
- 個別承認も、その変更を含む委譲もないのにスキルを入れる。委譲の範囲を広げる、共通ゲートを省く
- 通常の振り返りを理由に、実装、依存の追加、コミット、プッシュへ進む
- 摩擦や用途のない提案、見送られた提案の繰り返し、試行中の変更への上乗せ
- 試験の概念を、確かめずに出題範囲と断定する。紹介を理解・習得の記録にする
- 会話の全文をメモやスキルに貼る。分からない機構を、それらしい用語で埋める
