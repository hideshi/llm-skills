# 答え責任カードを作る

AI と協働して作ったソフトウェアを、持ち主が一行ずつ理解するのは現実的でない。それでも、成果物について問われたときに、根拠を示し、誤りを見つけて直し、採否を引き受けられる状態は保ちたい。答え責任カードは、そのために押さえる点だけをリポジトリごとに1枚にまとめたもの。

このスキルは、カードの下書きを作り、持ち主（と役割を持つ人）に確認の問いを出すまでを受け持つ。カードを採るか、どう直すかは持ち主が決める。

## 考え方

- 地図の下書きは、エージェントに任せてよい。地図を自分のものにする（自分の運用で確かめ、説明できるようになる）ことは任せられない。だから、下書きは確認の問いとセットで渡し、答えられなかった所を隠さずに残す。
- 点検の実行（試験、静的検査、CI）は任せてよい。持ち主に残るのは、採否と、根拠を問われたときの応答。そのために、任せた点検が何を見ていないかを持ち主が知っている必要がある。
- 誤りは、見つけるだけでなく、止めて直せる必要がある。主な失敗には、気づく手段と直し方の所在を結ぶ。
- 被害が持ち主の外へ及ぶ失敗と、取り返しのつかない失敗ほど、事前に深く理解する。後で直せる所は、運用の中で直しながら理解を得てよいが、気づく手段と直し方があることが前提。
- 理解は一度で終わらない。運用と変更のたびに、カードと理解の両方を更新する。
- カードが示すのは、出した問いに答えられたことまで。項目5が空でも、理解が十分だという保証ではない。

## 使い分け

| 依頼 | 使うもの |
|---|---|
| 自分（たち）が作ったリポジトリで、答えられる状態かを1枚で確かめたい | このスキル |
| 保守を引き継いだシステムの、どこに何があるかを調べたい | 引き継いだシステムの地図を作る手順（開発スキル群の `dev-system-map` など） |
| 機能が今どう動いているかを調べたい | 今の動きを調べる手順（開発スキル群の `dev-current-behavior-survey` など） |
| 入口や応答の安全を点検したい、依存の脆弱性を調べたい | 点検の手順（開発スキル群の `dev-entry-safety-check`、`dev-advisory-check` など） |
| 1件の変更を採ってよいか確かめたい | レビューや完了前の監査の手順（開発スキル群の `dev-profile-review-cycle` など）。このスキルは、変更が触れる項目5の箇所を示し、その問いを出すまで（手順7） |
| コードの説明文書や学習の教材を作りたい | このスキルではない |
| 会話の区切りで、学んだことを振り返りたい | `post-task-retrospective` |

カードは点検の結果を写す場所ではない。点検の記録があれば所在で指し、点検の対象と対象外を短く書く。

## 入力

- 対象のリポジトリと、カードを作る時点の版（コミット）。
- 既にカードがあれば、その所在と版（更新のとき）。
- カードの置き場所の決まり（無ければ手順1で決める）。

## 出力

- 答え責任カードの下書き（形は [カードの雛形](templates/answerability-card.md)）。
- 確認の問いと答えの記録（カードの項目5と、付録の答えられた問い）。
- 更新のときは、前の版からの差分の要約。

カードも記録も、このスキルの配布元のリポジトリと、導入したスキルのコピーには書かない。

## 手順

### 1. 受付、役割、置き場所

- 対象の版を記録する。カードの中身は、この版について言えることに限る。
- 役割を先に決める（カードの項目0）。採否を決める人、根拠を問われて答える人、点検を実行するもの（道具や担当）、誤りを止めて直す人、影響を受ける人。1人が兼ねるなら、兼ねると書く。役割の名前で書き、個人名は書かない。
  - 複数の人が関わるなら、領域ごとに、確認の問いをだれに出すかを決める。
- リポジトリが公開扱いかを確かめる（公開されている、将来公開すると書かれている、持ち主が公開予定と言った、のどれか）。
- 置き場所を持ち主と決める。
  - 公開扱いのリポジトリでは、カードをリポジトリの外（持ち主の非公開の置き場）に置くのを既定にする。失敗空間、点検が見ていないもの、説明できない箇所は、弱点の一覧として読めるため。
  - 公開扱いでないリポジトリでは、リポジトリの中か外かを持ち主が決める。中に置くなら、後で公開すると履歴に残ることを伝える。
  - 決めた置き場所にエージェントが書けないときは、カードを会話で渡す。作業中のリポジトリに仮置きしない（追跡されないファイルも含む）。
  - どの置き場所でも、秘密の値、接続先・アカウント・契約の内容などの運用情報、個人の情報は書かない。所在で指すだけにする。
- 既にカードがあれば、手順7（更新）から入る。

### 2. 読む文書を集める

- 読む: README、AGENTS.md や CLAUDE.md などのエージェント向けの指示、設計文書、試験と品質の保証範囲の文書、CI と品質ゲートの設定、依存の宣言、公開の設定（ライセンス、配布、公開範囲）、運用や戻し方の手順の文書。
- 読んだ文書の一覧を、版つきで残す（カードの付録）。読んでいない文書（無かった、時間で絞った）も書く。
- コードは、文書の記述を確かめる所と、文書に無い外部通信や保存の所在を探す所に限って読む。コードの全体の説明はしない。

### 3. 下書きを作る

カードの各項目（雛形のとおり）を埋める。どの行にも根拠の種類を付ける。

まず、カードの項目0に流れ（入力・処理・出力）を1〜3行で書く。このリポジトリが何を受け取り、何をして、何を出すか・残すか（外へ送るもの、保存するものを含む）。細部ではなく全体の流れにとどめ、ほかの行と同じく根拠の種類と所在を付ける。失敗空間（項目3）と理解の深さ（項目6）は、この流れのどこで起きるか、どこに当たるかを手がかりに書く。

| 根拠の種類 | 意味 | カードの項目0〜4、6に置けるか |
|---|---|---|
| 文書 | 文書に書いてある（所在: ファイルと節か行） | 置ける |
| 設定 | 設定ファイルから読める（所在） | 置ける |
| コード | コードを読んで確かめた（所在） | 置ける |
| 導出 | 所在のある事実から、エージェントが導いた読み（元の事実の所在を書く） | 印を付けて置ける。持ち主が確かめるまで「導出・未確認」と書き、項目5にも問いを置く |
| 持ち主の答え | 役割を持つ人の答え（日）。文書・設定・コードと照らせなかったものは「未照合」と書く | 置ける |
| 推測 | 所在のある事実に結べない読み | 置かない。項目5の問いにだけする |

- 項目3（失敗空間）と項目4（点検が見ていないもの）は、文書にほとんど書かれないので、導出が中心になる。導出の行は、元の事実と読みを分けて書き、事実の顔で断定しない。
- 文書と、設定やコードが食い違えば、どちらも所在つきで書き、項目5の問いにする。
- 文書に無いことと、決まっていないことを分ける。決まっていない（例: 承認を挟む地点が定められていない）なら、「なし」ではなく「決まっていない（項目5の番号）」と書き、項目5に載せる。見たが無いなら「なし（見た範囲: …）」と書く。確かめていないなら「未確認（項目5の番号）」と書く。
- 失敗空間（項目3）は、被害が持ち主の外へ及ぶもの、取り返しがつかないものを先に並べる。5つ前後に絞り、絞った基準を書く。行ごとに、気づく手段（項目4のどれか）と、止め方・直し方の所在を書く。直し方の手順は写さず、所在で指す。
- 理解の深さ（項目6）は、領域ごとに3段のどれかに割り当てる。割り当てはエージェントの案で、決めるのは持ち主。
  - 深く理解する: 権限、個人情報、外部への通信、公開範囲、認証、取り返しのつかない操作など、他人に被害が及ぶ所、または取り返しがつかない所。
  - 地図だけ持つ: 内部の構成。どこに何があり、壊れたらどこに症状が出るか。地図に当たる文書の所在を書く。無ければ項目5へ。
  - 任せる: 点検の実行と、一行ずつは読まない実装の細部。条件は、後で直せること、項目4のどれかの点検が見ていること、被害が持ち主の外へ及ばないこと。条件を満たさない領域は「地図だけ持つ」以上にするか、項目5に載せる。

### 4. 確認の問いを作る

持ち主（と、領域ごとに決めた人）が自分の言葉で説明できるかを確かめる。試験ではなく、地図を自分のものにするための問い。

- 初回（カードを新しく作るとき）は、流れの問い「このリポジトリは何を受け取り、何をして、何を外へ出す・残す？」を、下の順によらず必ず最初に出す（5〜8個の枠に数える）。答えは項目0の流れの行と照らす。更新では、流れの行を直したときに出し直す。
- 項目5の行数に上限は無い。1回に出す問いは5〜8個に絞り、次の順に選ぶ。出さなかった問いは、状態を変えずに項目5に残す（一度も出していないものは「未出題」）。
  1. 変更を採る前に入ったとき（手順7）は、その変更が触れる箇所の問い。この回は、変更が触れる問いだけを出す。8個を超えたら回を分けて続け、全部を出し終えるまでを1つの機会とする。
  2. 深く理解する段の領域で、状態が未回答・答えられなかった・食い違った・下書きを見て答えた問い。
  3. 深く理解する段の領域で、状態が未出題の問い。この中では、取り返しのつかない失敗（項目3）、承認を挟む地点（項目2）、点検が見ていないもの（項目4）、それ以外、の順。
  4. それ以外の領域で、状態が未回答・答えられなかった・食い違った問い。
  5. それ以外の領域で、状態が未出題の問い（導出の確かめなど）。
  
  順位3の中は上の並びを先に当て、同じ位置の中と、ほかの順位の中では、被害が持ち主の外へ及ぶものを先に、次に項目5の番号の小さいもの（先に載ったもの）を先にする。複数の項目に関わる行は、並びのいちばん先の項目で扱う。「答えた（未照合）」の行は選ばず、枠にも数えない（照らす先ができたら、出し直さずに記録した答えを照らす）。
- 1問は1文で、答えが一言から数行で済む形にする。止め方・直し方の問いを、深く理解する段の領域では必ず含める。例:
  - 「このリポジトリが外へ送る通信は何で、何を送る？」
  - 「〜の試験が全部通っても防げない失敗は何？」
  - 「〜が壊れたら、最初にどこに症状が出る？ どう止める？」
  - 「依存を1つ足すとき、誰がどこで採否を決める？」
- 問いに答えを含めない。選択肢を出さない。問いは下書きを見せる前に出すのを既定にする。下書きを見ながら答えたときは、そう記録する。
- 答えを、文書・設定・コードと照らす。
  - 合っていれば、その行の根拠に「持ち主の答え」を足し、導出なら「導出＋持ち主の答え（日）」にする。問いは付録の「答えられた問い」に移す。ただし、深く理解する段の領域の問いは、下書きを見ずに答えられたときだけ移す。見ながら答えたときは、カードの項目0〜4、6の根拠は変えてよいが、問いは項目5に「下書きを見て答えた」として残し、次の機会に出し直す。
  - 照らす先が無ければ、「持ち主の答え（未照合）」として置き、項目5の状態を「答えた（未照合）」にする。この行は保留の促しの対象にしない（ただし深く理解する段で下書きを見て答えたときは、前の項を先に当てる）。照らす先ができたら照らし、合っていれば外し、食い違えば「食い違った」にする。持ち主がこのままでよいと決めたとき（日を記録する）も外す。
  - 答えられなかった、または食い違ったときは、項目5に残す。食い違いは、どちらが正しいかを決めつけず、両方を書く。
- 答えたくない、今は答えない、と言われたら、そのまま「未回答」として残す。

### 5. 項目5（説明できない箇所）と保留

- 項目5には、2つの種類を分けて置く。
  - 確かめが要る所: エージェントの導出と推測、決まっていない所、文書と食い違う所。
  - 説明できない所: 問いに答えられなかった所、未回答の所。
- 項目5の行は、推測で埋めない。確かめが要る所は、確かめた文書が出ても、それだけでは外さない。持ち主がその箇所を説明できたと記録されてから外す（文書が出たら、問いを出す）。
- 保留の促しは、取り返しのつかなさで強さを分ける。
  - 深く理解する段の領域（他人に被害が及ぶ、取り返しがつかない）に関わる変更: 項目5のその箇所の問いに、下書きを見ずに答えられるまで、採用を保留するよう促す。
  - それ以外の領域に関わる変更: 小さく、戻せる形で進めて、運用の中で理解を得る道を示す。項目3か項目4に、その領域で気づく手段があり、戻し方があることが前提。無ければ前の段と同じに扱う。
  - 持ち主が促しを受けずに採ると決めたら、それは持ち主の判断として尊重し、日と理由をカードの更新の記録に残す。
- カードの頭に、保留の促しの一文と項目5への案内を書く。
- 持ち主が望めば、リポジトリのエージェント向けの指示（AGENTS.md など）に、「答え責任カードの項目5に関わる変更は、採用の前に持ち主の理解を確かめる」の一文を足す案を出す。足すかは持ち主が決める。公開扱いのリポジトリでは、カードの所在と、説明できない箇所の中身は書かない（一文だけにする）。

### 6. 持ち主の添削と採否

- 下書きを持ち主に渡し、直してもらう。持ち主が直した所は、根拠を「持ち主の答え」にする。
- カードの状態は、下書き、持ち主が採った（版と日）、のどちらかにする。エージェントは「採った」にしない。
- 採らなかった行と理由は、付録に残す（後の更新で同じ行を出し直さないため）。

### 7. 更新

次のときにカードを見直す。

- 承認を挟む地点、権限の境界、外部通信、保存するデータ、公開範囲に関わる変更をしたとき。
- 大きな機能を足したとき、構成を大きく変えたとき。
- 項目5の箇所に関わる変更を採ろうとするとき（手順5。下の「変更を採る前に入ったとき」）。採ったら、採った後の版で更新の流れを行う。
- 前の見直しから一定の期間がたったとき。期間は持ち主に問い、カードに書く。

変更を採る前に入ったとき（項目5の箇所に関わる変更を採ろうとするとき）は、カードの版は動かさない。その変更が触れる項目5の行を示し、その箇所の問いを手順4のとおりに出して、結果を項目5と付録に記録する。この回では、カードの項目0〜4、6は書き換えない。この回のすべての答えの要旨（項目5に残る行の答えも含む）を、付録の「変更を採る前の回の答え」に控える。答えで変わる所は、次に更新の流れを行うとき（変更を採ったなら、採った後の版で行う）に反映する。

更新の流れ（変更を採る前の回では行わない。変更を採った後の版か、見直しの時点の版で行う）:

1. 前のカードの版から今の版までの変更を読み、影響する項目と、新しくできた箇所を挙げる。
2. 影響する所だけを、手順3のとおりに直す。全体を書き直さない。付録の「変更を採る前の回の答え」で変わる根拠も、ここで反映し、反映した日を書く。変わる根拠が無い行（答えられなかった、食い違った）と、採った変更で行の中身が変わった行は、根拠に足さず「反映なし」と日と理由を書く（後者は、手順3で直した所の問いとして次の手順で出す）。
3. 項目5に残っている問い（状態を問わない）と、直した所・新しい箇所の問いを、手順4のとおりに出す。期間による見直しでは、変更が無くても、項目5の問いを出し直す。「答えた（未照合）」の行は、問いを出し直す代わりに、照らす先ができたかを確かめる。
4. 状態を「下書き」に戻し、手順6で持ち主に採り直してもらう。前の版の「採った」を新しい版に持ち越さない。
5. 直した所、消した行、項目5から外れた行（説明できるようになった、と記録された行）を、差分の要約として更新の記録に残す。

## 根拠

手順の根拠と、典拠の考え方から変えたところは [根拠と変えたところ](references/grounding.md) を見る。

## 書くときの決まり

- 1枚とは、項目0〜6を指す。目安は、項目ごとに表1つか箇条書き数行。詳しい説明は書かず、所在で指す。読んだ文書、答えられた問い、採らなかった行、更新の記録は付録に置く。
- 項目5が長くなるときは、深く理解する段の行と、答えられなかった・食い違った行を先に置き、残りは付録に続ける（項目5の一部として扱う）。
- 断定してよいのは、根拠の種類が文書・設定・コード・持ち主の答えの行だけ。持ち主が確かめていない導出は「導出・未確認」の印を付ける。
- 公開扱いのリポジトリの中にカードを置くと持ち主が決めたときは、項目3〜5を、悪用の手がかりにならない粒度（「〜の権限の確かめ」まで。手順や値は書かない）にとどめる。
- 秘密の値、運用情報、個人の情報は、どの置き場所でも書かない。役割は役割の名前で書く。

## 終了条件

- カードの頭に、対象の版、作った日、状態（下書き）、置き場所の決定がある。付録に読んだ文書の一覧がある。
- 項目0に、流れ（入力・処理・出力）と役割がある（兼ねるなら、兼ねると書いてある）。
- 初回は、流れの問いを出し、答えが付録か項目5に記録されている。
- 項目0〜4、6のどの行にも、根拠の種類と所在がある。「決まっていない」「未確認」の行は、項目5の番号を指している。推測の行は項目5にだけある。持ち主が確かめていない導出の行には「導出・未確認」の印があり、項目5にも問いがある。
- 確認の問いを出し、付録の答えられた問いには、手順4の条件を満たした問いだけがある。それ以外の問いは、雛形の状態の語のどれかで項目5に残っている。
- 置き場所が決まり、公開扱いのときの扱い（既定は外に置く）を持ち主に確かめている。
- 更新の流れを行ったとき（変更を採った後の版、見直しの時点の版）は、状態が下書きに戻り、差分の要約があり、付録の「変更を採る前の回の答え」に「未反映」の行が残っていない。
- 変更を採る前に入ったときは、変更が触れる項目5の行が示され、問いの結果が項目5と付録に記録され、この回のすべての答えが付録の「変更を採る前の回の答え」に控えられている（版と状態は動かさない）。
