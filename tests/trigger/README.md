# 起動の試験

一言の依頼から、期待するスキルが選ばれるかを確かめる試験。試験の定義の正本は [cases.json](cases.json)。`docs/` の表は、ID を合わせた人向けの説明で、依頼文と合格とするスキルの正確な定義は cases.json にある（ID が一致することは試験で確かめる）。

対応する OS は Linux と macOS（プロセスの組の扱いに unix の仕組みを使う）。

## 普段の試験（モデルを呼ばない）

```sh
cd tests/trigger
go test ./...
```

確かめること:

- 定義の書き方（ID の重なり、実在するスキルの名前、禁じた頭との矛盾、overlay の有無など）と、流す試験の選び方
- 定義と `docs/` の表の ID の一致
- ログの読み取り、判定、外の参照の検出、集計、合否の判定（`testdata/` の作り物のログで）
- 隔離の確認（フック、MCP、道具、読み込まれたスキル、誤りで終わった回を除外すること）
- 試験用リポジトリの作り方と、各回の前の戻し方。利用者の git の環境を持ち込まないこと
- CLI の起動（偽の CLI で、引数、渡す環境変数、時間切れのときに子のプロセスまで止めること）

## 本物のモデルを呼ぶ試験

Claude Code の CLI（`claude`）と、その認証が要る。費用と時間がかかるので、スキルの description や振り分けの表を変えたとき、スキルを足したときに、手元で流す。

```sh
cd tests/trigger
TRIGGER_LIVE=1 go test -run TestTriggerLive -timeout 0 -v
```

一部だけを流す例:

```sh
TRIGGER_LIVE=1 TRIGGER_MODELS=sonnet TRIGGER_RUNS=1 TRIGGER_CASES=H,T2 \
  go test -run TestTriggerLive -timeout 0 -v
```

- 環境変数は [live_test.go](live_test.go) の冒頭に並べてある。既定では Sonnet と Haiku を各3回流し、Sonnet について、1件ごとの合格率が 0.66 を下回った試験と、全部の試験を合わせた合格率が 0.95 を下回ったことを失敗にする（2026-11-14 利用者が決めた基準）。Haiku は記録だけ。
- 合格率で判定するモデル（`TRIGGER_REQUIRED`）は、流すモデル（`TRIGGER_MODELS`）に含める。含まれないと、始める前に止める。
- 定義に無い ID やまとまりを指定すると、始める前に止める。
- `-timeout 0` を付ける。付け忘れても、go test の時間の上限の30秒前に残りを流さずに打ち切り、試験用リポジトリを消す。
- 結果は `TRIGGER_OUT`（既定は一時フォルダ）の下に、流した日時のフォルダを作って書く（`results.md`、`results.json`、各回のログ）。自動では消さない。

### 隔離

試験されるセッションに、試験の仕組みと、流す人の環境が入らないようにする。

1. 一時フォルダに試験用リポジトリを作る。リポジトリの全スキルを、リンクを辿った実体で `.claude/skills` だけに置き、`fixtures/base` を根に置いてコミットする。親フォルダには、ほかに何も置かない。git は、利用者の設定と `GIT_*` の変数を使わずに動かす。
2. 各回の前に最初の状態へ戻し（無視されるファイルも消す）、まとまりに `overlay` があれば上書きする（未コミットの「この変更」を作るため）。
3. 1回ずつ新しいセッションで `claude -p` を起動する。
   - 読み込む設定は、試験用リポジトリのものだけにする（`--setting-sources project`）。利用者の言語の指定、フック、利用者単位のスキルとプラグインは入らない。
   - MCP のサーバーは読み込まない（`--strict-mcp-config`）。セッションの記録は残さない（`--no-session-persistence`）。
   - 使える道具は `Glob`、`Grep`、`Read`、`Skill` だけ。手番は3回まで。
   - 環境変数は、認証、プロキシ、言語と端末に要るものだけを渡す。
4. ログの始まり（init の行）で、上の条件が守られたかを確かめる。フックが走った、MCP がある、道具が違う、置いたスキルが読み込まれていない、のどれかなら、その回を集計から外して失敗として報告する。認証切れや利用の上限などで誤りとして終わった回も同じ。

### 判定

- 最初に使ったスキルが `accept` にあれば合格（経路は「直接」）。
- 先頭に続く `profiles` のスキル（振り分け役）を読み飛ばし、その次が `accept` にあれば合格（「経由」）。
- 振り分け役だけを使い、ほかのスキルを使わずに終われば合格（「振り分けまで」）。手番が3回なので、振り分けの後で手番が尽きることがある。振り分けまでで止まった回が多いときは、表の内訳で分かる。
- `forbidPrefixes` の頭のスキルを一度でも使えば不合格。`accept` が無い試験は、禁じたスキルを使わなければ合格（「不使用」）。
- 存在しない名前などで誤りになった Skill の呼び出しは、使ったと数えない。
- Skill の道具を使わずに、置き場の SKILL.md を読んだり探したりしただけの回は、使ったと数えない。その名前は `results.json` の `readSkills` に記録する。
- リポジトリの外を指した呼び出しは拾い、拒否されずに中身を読んだ回は集計から外して失敗として報告する。拒否された回は集計に残す。

### 試験を足すとき

- 依頼の前置きは、`fixtures` に置いた材料と食い違わないように書く（ないはずの枝、ないはずの節、実装済みの要件を「実装して」と頼む、など）。食い違うと、モデルが先に現実を確かめて、スキルを使わずに止まる。
- 前置きが指す文書が要るなら、`fixtures/base` に置く。
- まとまりの `overlay` は、そのまとまりの全件の前に上書きされる。
- `docOnly` は、`docs/` の表にはあるが、この試験では流さない ID（別の手順で試すもの）。
- `cases.json` と `docs/` の表の両方に足す。

## 限界

- 見ているのは最初の選び方だけで、スキルの中身どおりに最後まで動くかは確かめない。
- モデルの答えはぶれるので、合格率で見る。少ない回数で落ちたときは、ログを読んで、試験の作りのミスでないかを確かめる。
- CLI に組み込みのスキル（`code-review`、`security-review` など）と、ログインしたアカウントの情報（メールアドレスなど）は、設定を絞っても読み込まれる。組み込みのスキルは誰の環境にもあるので、取り合いを見る相手として残す。読み込まれた組み込みのスキルは `results.json` の `otherSkills` に記録する。
- CLI は、セッションの記録を残さない設定でも、試験用リポジトリごとに空の記憶の置き場（`~/.claude/projects/` の下）を作る。試験用リポジトリは毎回新しいパスなので、前の回の記憶は読まれない。空のフォルダが溜まるので、ときどき消す。
- 設定や指示のファイルのように、道具を通らない読み込みは、外の参照の検出では拾えない。上の隔離の仕組みで入口を塞ぎ、init の行で確かめる。
- 今は Claude Code だけ。Cursor と Antigravity の CLI は、ログの形と隔離の仕組みが違うので、道具ごとに足す必要がある。
