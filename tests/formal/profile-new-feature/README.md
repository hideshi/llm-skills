# 新規開発のプロファイルのモデル

`skills/dev-profile-new-feature` の工程の順序、条件、戻る流れ、人の決定を TLA+ で表し、TLC で検査する。共通の注意は [../README.md](../README.md)。

## 確かめる性質

| 性質 | プロファイルの決まり |
|---|---|
| `ReqBeforeDesign` | 要件（完了条件の一覧）を書き終えてから、画面（`screen`・`wireframe`・`screen-ok`）・受入条件の確かめ・設計・テストケースへ進む（画面の工程は要件を書き終えた後にだけ入る、を含む） |
| `NoHypothesisIntoDesign` | 仮説・未確定の業務規則を残したまま、画面、設計、テストケースへ進まない |
| `ScreenBeforeDownstream` | 画面の契機があれば、受入条件の確かめ・設計・テストケースの前に、今の要件に追随して `screen-ok` で採られた画面の設計がある |
| `FeedbackRoutedFirst` | 振り分けの済んでいない画面への意見があるうちは、`req` の外へ出ない（画面・モデル・設計へ直接戻らない） |
| `ScreenRevisitedAfterDesignChange` | 設計で画面が古くなったら（設計の判断、`design-ok` の決定、設計で初めて画面が要ると分かった）、`design-ok` の前に、画面を直して `screen-ok` で採り直す |
| `ModelBeforeDesign` | 新しい概念や規則があるなら、モデルを作ってから（`domain-model`）設計やテストケースへ進む |
| `ReqQuestionsAnswered` | 要件の確認事項に今回の範囲の未回答があれば、人に確かめてから（`req-ask`）設計やテストケースへ進む |
| `ExtBeforeUse` | 一次情報が要るなら、調べてから（`primary-source`）テストケースや設計の承認へ進む（設計の途中で要ると分かった場合を含む） |
| `NoImplementWithPending` | 設計の判断に人の決定待ちが残っている作業は、始めない |
| `DesignBeforeImplement` | 要る観点の設計をしてから実装する |
| `TestsBeforeImplement` | テストケースを導いてから実装する |
| `SizingBeforeReview` | 最後の変更の後で規模を判定し直してから、レビューに回す |
| `EvidenceBeforeReview` | 受入の証拠は、確定してからレビューに回す |
| `TasksBeforeAudit` | 通常の道なら、監査の前に作業の一覧がある（実装の後の判定で通常の道に変わったときも） |
| `LateDesignBeforeReview` | 実装の後の判定で、要る観点に設計の判断が無いと分かったら、設計し直してから証拠・レビュー・監査へ進む |
| `OpsApprovedBeforeReview` | 運用の成果物（`ops-artifacts`・`ops-ok`）が要るなら、最後の変更の後で承認してから、証拠の確定（`evidence`）とレビュー（`review-round`）へ進む（`ops` は、モデルの検査なしで手戻りなしか変更要求の依頼にだけ掛ける） |
| `ApprovedChangeNeedsHuman` | 中断して再開したとき、中断の間に人が承認した成果物が変わっていたら、人に確かめてから工程に戻る（中断は工程 `implement` で1回までの割り込み。"R"・"HR" は工程ではなく、遷移の突き合わせの書き出しから外す。人が認めた後の戻り先（承認し直しなど）は表さずに元の工程へ戻す） |
| `ResumeReturnsToSaved` | 再開したら、中断した工程に戻る（動作の性質。戻り先は突き合わせでは見ていないので、これで見る） |
| `Terminates` | どの依頼でも、いつか終わる（公平性の下で） |

行き止まりが無いこと（デッドロックの検査）と、どの工程にもたどり着けること（`-coverage`）も見る。

## 仮定と範囲

- 依頼ごとの違い（受入条件の確かめが要るか、設計が要るか、モデルの検査の依頼と反例、決定待ち、着手の時の道、設計の後に通常の道になるか、軽い道の実装中に作業が増えるか、証拠が要るか、一次情報の確かめが要るか・推定の規則が出るか・設計の途中で要ると分かるか、モデルを作るか・仮説が残るか・回答で規則が変わるか・要件の確認事項に未回答があるか、手戻りの種類（受入条件の書き直しの案を採るを含む））は、初期状態で非決定に選ぶ。関係する違いは一つの値にまとめた（`formal`、`external`、`spec`、`rework`、`ops`、`screen`）。全部の通りの数は、TLC の初期状態の数として検査の記録に書く。
- 画面の違いは `screen` の一つの値にまとめた（画面なし／画面だけ／ワイヤーで意見なし／意見が要件／意見がモデル／意見が画面／意見が部品やトークンの共通の定義）。画面の手戻り（画面から受入条件の案を返す、設計で画面が変わる、ワイヤーから画面の設計を変える案を返す）は `rework` に入れた。`screen` の "late" は、初めは画面の契機が無く、設計で画面が要ると分かる依頼（`design` → `req` で契機を立てて `screen` を通る）。`rework` の "decisionScreen" は、`design-ok` の決定（反例でない）で画面に及ぶ直しが要る手戻り（`design-ok` → `design` → `screen`）。状態の数を抑えるため、画面はモデルの検査なし、運用は無しか業務の決定だけ、一次情報は推定の規則が出ない依頼にだけ掛ける。意見がモデルのときは、規則が仮説に戻って `domain-model`・`req-ask` を通る形で表す。要件に戻る道（受入条件の書き直し、設計の途中の一次情報、承認し直し、運用の業務の決定、設計で画面が要ると分かる）は、安全側に倒して、必ず画面の採用を外して `screen` を通り直させる（プロファイルでは、変えた項目に結ばれた画面だけが無効になる）。
- 表していない画面の道: 画面とモデルの検査の組み合わせ、画面と運用の成果物のうち業務の決定以外（台帳の確認事項、手元で流した不具合、承認しない）、画面と推定の規則の組み合わせ、設計から戻った画面への意見（意見は1回目の `screen-ok` で使い切る）。
- `FeedbackRoutedFirst` と `ScreenRevisitedAfterDesignChange` は、旗を立てて決まった工程で下ろす形の性質で、旗を立てた次の一歩しか縛らない。迂回を作ると破れることは崩した写しで確かめたが、旗の立て忘れはこの性質では見つからない。`req` へ戻るときの画面の採用の外し忘れも、外すこと自体が仕組みなので、どの性質でも見つからない。
- 業務規則の回答の中身（確定、変更、却下など）は区別せず、「業務規則の回答は `domain-model` に戻る」という順序だけを表す。
- 手戻りは、それぞれ1回まで起きうるとする。レビュー・承認し直し・監査の手戻りは、一つの依頼で一種類まで。
- 寄り道（`primary-source`・`domain-model`・`req-ask`）は、工程 `req` が「済んでいない寄り道があれば先にする」順で表す。どの順でも戻る先は `req` なので、確かめる性質には影響しない。
- 表していないもの: テストを先に書くのを外す場合、一言の依頼で途中の工程から入る場合（入口は工程 `sizing` だけ）。監査が「止める」ときの戻り先は `implement` だけを表す。
- 工程 `sizing-after-implement` で「通常の道なのに作業の一覧が無い」「要る観点に設計の判断が無い」と出て戻る流れは、プロファイルの決まりにあるが、工程 `sizing` から順に進むかぎり起きない（安全のための決まり）。モデルでもたどり着かないので、遷移の表には載せていない。
