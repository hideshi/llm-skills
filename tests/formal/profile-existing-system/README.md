# 既存システムの改修のプロファイルのモデル

`skills/dev-profile-existing-system` の工程の順序、条件、戻る流れ、人の決定を TLA+ で表し、TLC で検査する。単位の中身（何をどう調べるか、設計するか）は表さない。共通の注意は [../README.md](../README.md)。

## 確かめる性質

| 性質 | プロファイルの決まり |
|---|---|
| `BaselineBeforeCode` | 回帰の基準は、コードを変える工程（`fix`・`implement`）より前に通す（A に当たるとき） |
| `TestCasesBeforeTasks` | 作業に分ける（`tasks`）のは、テストケース表を作った（`test-design`）後。是正から分けるときも同じ（中断からの再開は除く）。動作の性質 |
| `NoImplementWithPending` | 設計の判断に人の決定待ちが残っている作業は、始めない |
| `NoHypothesisIntoDesign` | 仮説・未確定の業務規則（工程 `survey` で抜き出した候補、一次情報から推定したものを含む）を残したまま、設計（`design`）や試験の設計（`test-design`）へ進まない。是正を作業に分けるための `test-design` は要件を通らないので除く（そこで仮説の規則を根拠にしないのは本文の決まりで、モデルでは表さない） |
| `ModelBeforeDesign` | 業務規則が変わるなら、モデルを直してから（`domain-model`）設計や試験の設計へ進む |
| `ReqQuestionsAnswered` | 要件の確認事項に今回の範囲の未回答があれば、人に確かめてから（`req-ask`）設計や試験の設計へ進む |
| `ExtBeforeUse` | 一次情報が要るなら、調べてから（`primary-source`）試験の設計や設計の承認へ進む（設計の途中で要ると分かった場合を含む） |
| `EvidenceBeforeReview` | 受入の証拠は、確定してからレビューに回す |
| `SizingBeforeAudit` | 監査の前に、最後の変更の後で規模を判定し直している |
| `TasksBeforeAudit` | 作業に分ける条件に当たるなら、監査の前に作業の一覧がある |
| `LateDesignBeforeReview` | 実装の後の判定で、要る観点に設計の判断が無いと分かったら、設計し直してから証拠・レビュー・監査へ進む |
| `EvidenceNotWasted` | 確定した受入の証拠を、要件の書き直し（工程 `req`）で無駄にしない |
| `OpsApprovedBeforeReview` | 運用の成果物（`ops-artifacts`・`ops-ok`）が要るなら、最後の変更の後で承認してから、証拠の確定（`evidence`）とレビュー（`review-round`）へ進む（運用の成果物の違い `ops` は、状態の数を抑えるため、モデルの検査なしで手戻りなしか変更要求の依頼にだけ掛ける） |
| `ApprovedChangeNeedsHuman` | 中断して再開したとき、中断の間に人が承認した成果物が変わっていたら、人に確かめてから工程に戻る（中断は工程 `implement` で1回までの割り込み。"R"・"HR" は工程ではなく、遷移の突き合わせの書き出しから外す。人が認めた後の戻り先（承認し直しなど）は表さずに元の工程へ戻す） |
| `ResumeReturnsToSaved` | 再開したら、中断した工程に戻る（動作の性質。戻り先は突き合わせでは見ていないので、これで見る） |
| `ScreenAfterRequirements` | 画面の工程（`screen`・`wireframe`・`screen-ok`）は、要件を書き終えた後にだけ入る |
| `ScreenBeforeDownstream` | 画面の契機があれば、設計と試験の設計の前に、今の要件に追随して `screen-ok` で採られた画面の設計がある |
| `FeedbackRoutedFirst` | 振り分けの済んでいない画面への意見があるうちは、`req` の外へ出ない（画面・モデル・設計へ直接戻らない） |
| `ScreenRevisitedAfterDesignChange` | 設計で画面が古くなったら（設計の判断、`design-ok` の決定、設計で初めて画面が要ると分かった）、`design-ok` の前に、画面を直して `screen-ok` で採り直す |
| `Terminates` | どの依頼でも、いつか終わる（公平性の下で） |
| 行き止まりが無い | TLC のデッドロックの検査（既定で有効） |
| どの工程にもたどり着ける | `-coverage` で、全部の動作が1回以上起きることを見る |

## 仮定と範囲

- 依頼ごとの違い（`Requests`）は、初期状態で非決定に選ぶ。意味の無い組み合わせを作らないよう、関係する違いは一つの値にまとめた（判定 A・C と調べる段の寄り道をまとめた `survey`。機能の変更か不具合か・設計が要るか・是正の途中で設計が要ると分かるか、をまとめた `kind`。モデルの検査の対象と反例の有無をまとめた `formal`。モデルを直すか・仮説が残るか・回答で規則が変わるか・抜き出した候補を根拠にするか・要件の確認事項に未回答があるか、をまとめた `spec`。一次情報の確かめの要否・推定の規則が出るか・設計の途中で要ると分かるか、をまとめた `external`。手戻りの種類の `rework`。運用の成果物の `ops`。画面の違いの `screen`）。全部の通りの数は、TLC の初期状態の数として検査の記録に書く。
- 画面の違いは `screen` の一つの値にまとめた（画面なし／画面だけ／ワイヤーで意見なし／意見が要件／意見がモデル／意見が画面／意見が部品やトークンの共通の定義）。画面の手戻り（画面から受入条件の案を返す、設計で画面が変わる、ワイヤーから画面の設計を変える案を返す）は `rework` に入れた。状態の数を抑えるため、画面は、調べと監査の寄り道なし、モデルの検査なし、運用なし、一次情報が確定だけまで、機能の変更で、規則の仮説が残らない依頼にだけ掛ける。既存の画面の踏襲（範囲の合意）は `screen` の中に含め、分けて表さない。`screen` の "late"（設計で初めて画面が要ると分かる）と、`rework` の "decisionScreen"（`design-ok` の決定で画面に及ぶ直し）も表す。要件に戻る道は、安全側に倒して、必ず画面の採用を外す（プロファイルでは、変えた項目に結ばれた画面だけが無効になる）。
- 表していない画面の道: 画面と、運用の成果物・モデルの検査・推定の規則・設計の途中の一次情報・調べの寄り道・不具合の是正（是正から機能の変更への切り替えを含む）の組み合わせ、設計から戻った画面への意見。新規開発のモデルは、運用の業務の決定と設計の途中の一次情報の組み合わせを表している。状態が上限に近いので、これらを足すときは画面の経路だけの別のモデルに分ける。運用の業務の決定と、是正から機能の変更への切り替えで `req` へ戻るときに画面の採用を外す式は、画面と組み合わせていないので、この道ではたどり着かない（式を足しただけで、検査では働いていない）。
- `FeedbackRoutedFirst` と `ScreenRevisitedAfterDesignChange` は、旗を立てて決まった工程で下ろす形の性質で、旗を立てた次の一歩しか縛らない。迂回を作ると破れることは崩した写しで確かめたが、旗の立て忘れはこの性質では見つからない。`req` へ戻るときの画面の採用の外し忘れも、外すこと自体が仕組みなので、どの性質でも見つからない。
- 業務規則の回答の中身（確定、変更、却下など）は区別せず、「業務規則の回答は `domain-model` に戻る」という順序だけを表す。一覧の書き換えそのものは表さない。
- 手戻り（レビューの変更要求、完了条件の承認し直し、反例による設計の直し、是正から設計への切り替え、監査の「条件付き」「止める」、回答による規則の変更）は、それぞれ1回まで起きうるとする。レビューと監査と承認し直しの手戻りは、一つの依頼で一種類まで。
- 寄り道（`formal-check`・`data-audit`・`survey-ask`、`primary-source`・`domain-model`・`req-ask`）は、工程 `survey`・`req` が「済んでいない寄り道があれば先にする」順で表す。プロファイルでは順序を決めていないが、どの順でも、戻る先は同じ工程なので、確かめる性質には影響しない。
- 表していないもの: B が「両方」の場合、急ぎの不具合で是正を基準より先に進める例外、テストを先に書くのを外す場合、監査の依頼の前提（隔離した複製のデータを使えるか）。監査が「止める」ときの戻り先は、原因の工程のうち `fix`・`implement` だけを表す。
- 定数 `Old` を `TRUE` にすると、2026-11-13 の設計の群のレビュー（別のモデルによる）の前の流れ（是正から設計（今の `design`）へ直接進む、受入の証拠の後に規模を判定し直す）と、`fix` から作業に分ける道（今は `fix` → `test-design` → `tasks`）が無い流れになる。

## プロファイルとの対応

モデルの工程（`pc`）は、プロファイルの工程の識別子と同じ。`"B"`（判定 B）と `"Done"`（終わり）は工程ではない。遷移は、プロファイルの「### 遷移」の表と、`scripts/check_dev_flows.py` で突き合わせる。

## 限界

- モデルは手で書いた写し。工程と遷移のずれは `scripts/check_dev_flows.py` で見つけられるが、条件の中身（表の「条件」の列と、モデルの式）の対応は人が確かめる。
- 確かめているのは、決まりどおりに工程を進めたときの順序だけ。担当（モデル）が決まりに従うか、各工程の中身が正しいかは確かめない。
- 「違反なし」は、上の仮定（手戻りは各1回まで、表していない場合を除く）の範囲での結果。
