# 依存の更新のプロファイルのモデル

`skills/dev-profile-dependency-upkeep` の工程の順序、条件、戻る流れ、人の決定を TLA+ で表し、TLC で検査する。共通の注意は [../README.md](../README.md)。

## 確かめる性質

| 性質 | プロファイルの決まり |
|---|---|
| `DecideBeforeBump` | 告知を点検したなら、人が当たるかを決める（`triage-ask`）前に版を上げない |
| `NoBumpWithoutFix` | `triage-ask` で全件を直さないと決めたら、版を上げない |
| `BaselineBeforeBump` | 基準を固める条件に当たるなら、版を上げる前に固める（急ぐときに並べて固める例外は表していない） |
| `ProcedureBeforeReview` | 本番の手順が要るなら、レビューの前に承認する。レビューや監査から版上げに戻ったら、承認をやり直す |
| `ReviewBeforeAudit` | 監査は、直近の版上げの後のレビューの承認を受けてから |
| `AuditBeforeFinal` | 版上げを終えて最終確認に来るのは、監査が「進めてよい」の後（全件を直さない、設計が要って外へ出るときを除く） |
| `Terminates` | どの依頼でも、いつか終わる（公平性の下で） |

## 仮定と範囲

- 入口は二つ（告知への対応、定期の更新）。定期の更新で告知を先に照らすかは `precheck` で選ぶ。初期状態で非決定に選ぶ。
- 差分の点検の高の指摘、レビューの変更要求、監査の「止める」と「条件付き」は、それぞれ1回まで起きうるとする。
- 追随に設計が要る（`design`）は、最初の版上げで分かるものとして表す。
- 表していないもの: 単位の中身（候補の比べ、行き先の版を人が決めること、ロックの差）、急ぐときに基準を版上げと並べて固める例外、中断と再開、本番に出した後の確かめ（この組み合わせの外）。
